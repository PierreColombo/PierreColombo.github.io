0. En une phrase

TL;DR — Scale AI formalise le « corpus-level trace diagnostics » (produire des insights en langage naturel, chiffrés et sourcés sur trace IDs, à partir d'un corpus entier de trajectoires d'agent) et propose Insights Generator (IG), un système multi-agents orchestrator / scout (hypothèses, breadth) / investigator (validation à l'échelle du corpus, depth) dont tous les accès aux traces passent par une couche Python stateful (Polars + primitives d'extraction LLM), évalué dans 4 réglages : LLM-as-a-judge, human-expert-as-a-judge, intervention humaine sur scaffold, patcher loop autonome.

Claim principal : des ingénieurs humains munis d'un rapport IG améliorent le pass rate d'un scaffold SpreadsheetBench de +30,4 pp sur le scaffold non modifié (57,4 % vs 27,0 %), contre +16,2 pp avec le rapport de la meilleure alternative (CC Subagents), écart de 14,2 pp, p ≈ 0,016 (Welch bilatéral), n = 6 participants par bras [§4.2, Tab. 2, App. A.9].

Claim secondaire (celui qui m'intéresse) : les auteurs affirment que « les classements sont cohérents entre les quatre réglages » [§1, contribution 2]. ⚠️ C'est faux telle quelle : le réglage human-expert-as-a-judge ne reproduit pas le classement du juge LLM, et le patcher loop non plus (voir §7.0).

1. Tâches & data

Objet analysé ≠ tâches d'entraînement. Il n'y a ici ni entraînement, ni RL, ni reward optimisé. Les « données » sont des corpus de traces d'exécution d'agents, et les « tâches » sont des questions de diagnostic posées sur ces corpus.

  • Origine des traces : générées en exécutant un scaffold ReAct fixe sur les task sets de deux benchmarks publics [App. A.4]. Pas de trace de production, pas d'annotation humaine des traces.
  • Pipeline : (1) exécuter le scaffold ReAct sur le benchmark → corpus figé ; (2) tous les systèmes comparés (IG + 4 baselines) réutilisent le même corpus figé plutôt que de recollecter — sauf le patcher loop qui régénère un corpus frais à chaque round depuis le scaffold patché $\mathcal{A}_r$ [App. A.4, App. A.10.1] ; (3) prétraitement IG : construction d'un trace store Polars, d'un schema cache (types par colonne, taux de null, distributions, corrélations notables) injecté dans le contexte de chaque subagent au dispatch, et d'un index vectoriel hybride sémantique-keyword [§3.4].
  • Identifiants : trace ID = chaîne courte, choisie explicitement pour « réduire l'usage de tokens et empêcher les références hallucinées, fréquentes avec des UUID » [§3.4]. ⚠️ Détail d'ingénierie sous-estimé mais réel : le format de l'identifiant conditionne la vérifiabilité des citations.

Volumes [Tab. 5] :

Distribution de difficulté : sur SSB, les tâches se répartissent en Cell-Level vs Sheet-Level avec des profils très différents — « approximativement 27 % vs 76 % de pass rate dans notre corpus » [App. A.4]. Sur HLE, 207/250 traces utilisent au moins un outil ; les 43 traces zéro-outil atteignent 9,3 % d'accuracy contre 26,6 % pour les traces avec outil [App. A.4] — sous-population que « tous les systèmes font remonter de façon consistante ».

Filtrage : aucun filtrage par pass@k, aucune sélection de difficulté. Les corpus sont pris tels quels. Curriculum : aucun, sauf dans le patcher loop où le corpus se déplace mécaniquement round après round (le scaffold s'améliore → les modes de défaillance restants se raffinent, cf. §7 ci-dessous).

Contamination / séparation train-test : traitée sérieusement pour l'étude d'intervention [App. A.11.2] — les 250 traces d'entraînement (générées avec GPT-5.2) et le set d'éval de 50 tâches (exécuté avec Claude Opus 4.6) sont disjoints ; le scoring final se fait sur un split test held-out, disjoint du dev set de 50 tâches ; l'accès au code d'éval, aux ground truths et aux définitions de tâches est interdit et vérifié post-hoc via les transcripts d'assistant de code exportés par les participants (« aucun participant exclu pour violation de protocole »). ✅ Ce protocole anti-fuite est le point le plus propre du papier.

Données SFT/IFT avant RL : sans objet (aucun entraînement).

Coût humain : Expérience 1 ≈ 2 h de travail expert par session de notation, 12 évaluateurs [App. A.11]. Expérience 2 ≤ 1,5 h par session d'intervention, 12 participants (6 par bras), budget API de 50 $ par participant [App. A.11.2]. Recrutement : ingénieurs logiciels professionnels ayant de l'expérience en développement d'agents LLM, via réseaux professionnels, avec un baseline-competency screen (calculer la distribution d'appels d'outils par trace) passé avant la révélation de l'assignation [App. A.11.2]. Rémunération « conforme ou supérieure aux exigences salariales locales », aucun travail bénévole ou crowdsourcé [App. A.11].

2. Environnement / harness

Deux harnesses distincts à ne pas confondre.

2.a Le harness analysé (le scaffold agent)

Agent ReAct générique dans les deux cas [Tab. 5] : - SpreadsheetBench : lire un classeur Excel, appliquer une manipulation décrite en langage naturel, persister le résultat. Outils : un outil unique d'exécution de code Python exposant openpyxl et pandas. Pas d'accès web. Budget 5 tours. Éval : exact cell-value match [App. A.4]. - HLE : QA expert closed-book, l'agent renvoie une réponse courte + une confidence auto-déclarée dans $[0, 100]$. Outils : web search, web fetch, exécution de code Python. Budget 20 tours [Tab. 5]. - Dans l'étude d'intervention, 4 paramètres sont verrouillés et le runner d'éval fait respecter le lock : modèle (Claude Opus 4.6), nombre max de tours (5), nombre de lignes de preview montrées à l'agent (5), timeout d'exécution par cellule (60 s). Les participants ne modifient que prompts, boucle d'agent et champs de config non verrouillés ; modifier le runner d'éval, la liste de task IDs ou le répertoire de données invalide la soumission [App. A.11.2].

2.b Le harness d'analyse (IG lui-même)

  • Observation : chaque subagent voit le schema cache (métadonnées par colonne) injecté au dispatch, plus ce que son propre code Python renvoie. Le contenu brut des traces ne transite jamais par le contexte du modèle sauf appel explicite à get_trace [§3.4, §3.5].
  • Espace d'actions : du point de vue de l'agent, un seul outil — un REPL Python stateful dans lequel 14 primitives sont pré-injectées comme fonctions appelables [§3.5, Tab. 4]. Disponibilité par rôle (Orch. / Scout / Inv.) :
Fonction Rôle Orch. Scout Inv.
load_traces corpus + extractions en DataFrame Polars ✓ ✓ ✓
get_trace contenu complet d'une trace ; outline de chunks si trop longue ✓ ✓ ✓
get_trace_chunk un chunk d'une trace longue ✓ ✓ ✓
get_schema types, taux de null, distributions, corrélations ✓ ✓ ✓
search_traces retrieval hybride sémantique-keyword ✓ ✓ ✓
get_extractions lister les colonnes d'extraction déjà persistées ✓ ✓ ✓
extract extraction de features structurées (chunking, batching, checkpointing) ✗ ✓ ✓
summarize_trace résumé LLM par trace, avec cache et résumé progressif ✓ ✓ ✓
summarize_group résumé LLM unique caractérisant un groupe ✓ ✓ ✓
compare_segments comparaison A/B profonde entre deux cohortes, avec budget de tokens ✗ ✗ ✓
save_column persister une colonne Polars calculée en parquet ✓ ✓ ✓
save_affected_traces persister la liste de trace IDs supportant un finding ✗ ✗ ✓
reload_data rafraîchir le DataFrame en cache ✓ ✓ ✓
consolidate fusionner les parquets d'extraction et rafraîchir le schema cache ✓ ✓ ✓
  • Multi-turn : boucle orchestrator-driven [Algo. 1]. À chaque tour l'orchestrator choisit : dispatcher un batch parallèle de Scouts, dispatcher un batch parallèle d'Investigators, ou soumettre le rapport. Les dispatches peuvent s'entrelacer dans n'importe quel ordre et nombre de rounds. Horizon : 500 tours max pour l'orchestrator, 500 max par subagent, avec auto-terminaison par soumission [Tab. 3].
  • Contexte long : seuil de chunking d'une trace longue à 50 000 tokens ; retrieval top-$k$ = 20 par défaut [Tab. 3]. Les auteurs précisent qu'« en pratique aucune trace individuelle ne dépasse la fenêtre de contexte de l'agent, mais le corpus complet de 296 traces SSB et celui de 250 traces HLE dépassent chacun toute fenêtre de contexte unique » [App. A.4] — ⚠️ la justification du système repose donc sur le volume du corpus, pas sur la longueur unitaire, contrairement à ce que suggère l'abstract (« individual traces span tens of thousands of tokens »). La longueur moyenne des traces n'est pas rapportée (« non directement rapportée ici », App. A.4).
  • Exécution : conteneur sandboxé partagé, 16 cœurs CPU, 65 536 MB (64 GB) de RAM, timeout 14 400 s (4 h) [Tab. 3]. L'orchestrator et chaque subagent ont leur propre session REPL. Extraction : 50 appels parallèles, checkpoint tous les 5 000 traces, auto-save à 250 traces, timeout 300 s par appel. Tous les appels LLM passent par un proxy LLM centralisé [App. A.2].
  • Déterminisme / reset / gestion des erreurs d'outils / sorties mal formées : non précisé. Aucune section sur les retries, les erreurs de parsing des sorties de subagent, ou la reproductibilité d'un run IG. ⚠️ Étant donné la variance de coût observée (20,82 $ à 139,54 $ sur 6 runs, Tab. 14), l'absence de discussion sur le déterminisme est une lacune.
  • Garde-fous encodés dans les prompts [App. A.1] — c'est la partie la plus réutilisable du papier :
  • Orchestrator, anti-overfitting : « Ne généralisez pas à partir de l'échantillon d'un seul scout. Chaque finding doit être validé par un investigator agent avec des preuves statistiques. Les findings à petite cohorte sont souvent de grande valeur ; n'abandonnez pas une hypothèse parce que sa cohorte est petite. »
  • Investigator, anti-overfitting : « Ne généralisez pas à partir de moins de 20 traces dans une comparaison. Quantifiez tout. Signalez le niveau de confiance : élevé (> 100 traces), moyen (20–100), faible (< 20). »
  • Investigator, validation hiérarchique : Level A stats larges par group-by Polars sur toutes les traces ; Level B extraction de features sur 50–100 traces ; Level C comparaisons de cohortes répétées 2–3 fois avec des échantillons différents pour la robustesse.
  • Investigator, contrainte dure : « Enregistrez la cohorte défendable — le sous-ensemble dont vous êtes confiant qu'il exhibe le pattern, PAS le pool plus large que vous avez analysé. La soumission est rejetée si ceci n'a pas été appelé. » (save_affected_traces)
  • Scout, recherche d'omissions : « La recherche ne peut pas matcher l'absence directement. Imaginez le texte qu'un agent qui AURAIT effectué l'action attendue produirait, cherchez CELA, puis contrastez les cohortes. » ⚠️ Astuce non triviale et directement transposable.
  • Scout, échantillonnage : 50–200 traces pour former des hypothèses ; quantification sur 10–30 traces.

  • Investigator, format de sortie : statut (confirmed / refuted / inconclusive), résumé 1–2 phrases, prévalence quantifiée, 8–10+ items de preuve, chacun avec trace ID + citation verbatim + explication de 2–3 phrases nommant le mécanisme visible dans CETTE trace. Les tests d'hypothèses (p-values, V de Cramér, odds ratios) vont dans les observations additionnelles, pas dans le résumé principal.

  • Exemple de trajectoire : le papier n'en donne aucune, ni pour l'agent analysé ni pour IG. Il donne en revanche un exemple d'insight [§1], présenté au conditionnel (« un insight IG représentatif pourrait se lire ») : « 84 % des traces incorrectes utilisant Python exhibent des "silent computation failures" : le code s'exécute sans erreur mais implémente le mauvais modèle mathématique. Le cross-checking ne les attrape pas parce qu'il vérifie la cohérence interne à l'intérieur du mauvais cadre plutôt que de remettre en cause le cadre lui-même. Observé dans 94/112 traces incorrectes utilisant Python (37,6 % de toutes les traces) ; 0/19 traces avec cross-checking n'ont détecté l'erreur de modélisation. »

3. Reward / vérifieur

Il n'y a pas de reward d'entraînement. Il y a quatre couches de vérification empilées, et c'est leur articulation qui est instructive.

3.1 Couche 1 — graders de benchmark (vérité terrain)

  • SSB : exact cell-value match contre ground truth, « déterministiquement scorable » [App. A.4]. L'éval est déterministe par run ; la variance run-à-run ne reflète que le non-déterminisme de l'agent (Claude Opus 4.6), d'où le protocole de 3 re-runs moyennés par soumission [App. A.11.2].
  • HLE : correctness jugée par un LLM judge appliqué aux réponses de référence du benchmark, « plutôt que par matching déterministe », de sorte que « HLE sert de stresseur complémentaire au grader déterministe de SSB » [App. A.4]. Modèle du juge HLE, prompt, accord avec des humains : non précisé.
  • C'est la seule couche ancrée sur une vérité extérieure, et c'est celle qui porte le résultat principal (+30,4 pp) et le patcher loop.

3.2 Couche 2 — LLM-as-a-judge sur la qualité des rapports (Claude Opus 4.6)

Trois étages, tous avec le même modèle juge [App. A.7] :

Étage 1 — clustering « union-gold » : un seul appel juge ingère tous les findings de tous les systèmes et les regroupe par phénomène sous-jacent, produisant un set de référence canonique. Règles recopiées : « Deux findings appartiennent au même cluster ssi ils décrivent le même phénomène sous-jacent dans le corpus (même comportement, mode de défaillance, ou pattern), même si leur cadrage, leurs chiffres de prévalence ou leurs prescriptions diffèrent. Utilisez les listes de trace IDs affectées comme preuve forte de mêmeté. (2) Un cluster peut contenir un finding unique (les observations uniques sont précieuses). (3) Donnez à chaque cluster un nom canonique concis (80 caractères max) et une description de 1–3 phrases. (4) Incluez jusqu'à 5 trace IDs représentatifs (préférez les IDs cités par plusieurs systèmes). (5) Produisez du JSON VALIDE. » Le clustering converge à 50 observations canoniques par benchmark [App. A.4].

⚠️ Faille méthodologique majeure. Le gold est construit en poolant les findings des systèmes évalués, IG compris, et la règle (2) fait qu'un finding unique devient son propre cluster. Un système est donc mécaniquement couvert sur ses propres findings uniques, et un finding faux ou halluciné devient un cluster gold — la métrique de coverage ne peut structurellement pas détecter une hallucination. « Coverage » mesure la diversité de la production, pas la vérité. Le papier ne discute pas ce point.

Étage 2 — rubrique par cluster, 5 dimensions, 0–3, avec ancres explicites [App. A.7] :

Dimension 0 1 2 3
detection absent mention en passant finding explicite finding explicite mis en évidence
mechanism aucun vague plausible net et testable
evidence aucune unique multiple quantifiée sur le corpus
specificity générique légèrement spécifique spécifique précise avec portée quantifiée
actionability aucune vague concrète concrète et testable

Discipline de notation imposée au juge : mettre 0 quand une dimension n'est pas attestée dans le rapport (« ne pas créditer ce qu'un lecteur bien intentionné pourrait inférer ») ; plafonner detection à 1 si le rapport fait une affirmation factuellement fausse sur l'observation ; utiliser les findings du rapport verbatim plutôt que de récompenser la paraphrase. Le corps ne rapporte que mechanism, specificity, actionability + composite ; detection est consommée par la coverage ; evidence est omise du corps au motif qu'elle « est fortement corrélée à mechanism dans nos runs » [App. A.7]. ⚠️ Omettre une dimension parce qu'elle corrèle avec une autre, alors que l'abstract revendique la supériorité sur « evidence quality », est discutable.

Étage 3 — tournoi pairwise : pour chaque paire non ordonnée, le juge voit les deux rapports deux fois en positions inversées pour contrôler le biais de position ; chaque round est noté indépendamment ; win rate = $(\text{wins} + 0{,}5 \times \text{ties}) / n_{\text{rounds}}$. Prompt recopié : « Votre travail : choisissez le rapport qu'un ingénieur d'amélioration de scaffold trouverait plus utile pour réellement réparer l'agent. Pesez la spécificité, l'ancrage probatoire (trace IDs cités et prévalence quantitative), la nouveauté (faire émerger des patterns non évidents), et l'actionabilité (changements de scaffold concrets). Pénalisez les platitudes génériques, les affirmations non étayées, et les rapports qui confondent l'ampleur avec la profondeur. Répondez en JSON strict : winner (A, B ou tie) ; confidence (low, med, high) ; rationale (1–3 phrases). »

⚠️⚠️ Le point central pour moi : aucune dimension du juge LLM ne mesure la véracité. detection / mechanism / evidence / specificity / actionability évaluent toutes la forme de l'argumentation. Seul le plafonnement de detection à 1 touche à la correction factuelle, et il est conditionné à ce que le juge détecte lui-même l'erreur. Or la rubrique humaine, elle, comporte une dimension correctness — et c'est précisément celle sur laquelle IG perd (§3.3).

⚠️ Couplage juge ↔ prompts du système évalué. Le prompt de l'Investigator IG impose structurellement : statut confirmed/refuted/inconclusive, prévalence quantifiée, 8–10+ items de preuve avec trace ID + quote verbatim + mécanisme, et rejet de la soumission si la cohorte n'est pas enregistrée [App. A.1]. La rubrique du juge récompense exactement ces propriétés (evidence 3 = « quantifiée sur le corpus », specificity 3 = « précise avec portée quantifiée », mechanism 3 = « net et testable »). La question canonique demande certes la même chose à tous les systèmes, mais IG est le seul dont l'architecture force la conformité. Une part du gain mesuré est donc de la conformité de format, pas de la qualité diagnostique.

⚠️ Le juge est Claude Opus 4.6, c'est-à-dire le même backbone que les cinq systèmes comparés [App. A.6]. Le risque de self-preference est uniforme entre systèmes (donc peu confondant pour le classement) mais non discuté.

⚠️ Le juge est qualifié de « calibré » deux fois (§1, §4.1). Aucune procédure de calibration n'est décrite nulle part, et §5.3 place explicitement la calibration en travaux futurs : « conduire une calibration supplémentaire du grader LLM-as-judge sur un échantillon d'experts plus large aidera à quantifier le degré auquel les intuitions des experts s'alignent sur les critères du juge ». Le qualificatif est donc infondé dans cette version.

3.3 Couche 3 — human-expert-as-a-judge

12 évaluateurs experts, 23 insights (11 IG, 12 CC), rubrique 1–5 sur 4 dimensions : correctness (le claim est-il réellement vrai au regard des traces), depth (explique-t-il le mécanisme ou décrit-il le symptôme), evidence quality (citations de traces spécifiques et vérifiables), actionability (amélioration concrète, proportionnée aux preuves, sans risque d'overfitting) [§4.3, App. A.11.1]. Présentation identique entre systèmes (statut, prévalence, description, bloc de preuves avec trace IDs et quotes, liste complète des traces affectées, action suggérée) pour neutraliser les confounds de style ; source non divulguée. Confounds explicitement signalés dans les consignes : correctness et evidence quality sont indépendantes ; un finding revendiquant une prévalence populationnelle en ne citant que 1–2 traces est plafonné à evidence-quality ≤ 3 ; un finding recommandant un changement radical sur la base d'un pattern étroit reçoit une actionability plus basse quelle que soit sa correction. Budget ≈ 120 min par participant, 5–10 min visés par insight.

Résultats [Tab. 6] :

Rapport N insights Correctness Actionability Depth Evid. Quality Moyenne
CC 12 4,278 (±0,08) 4,174 (±0,12) 4,139 (±0,09) 4,285 (±0,08) 4,219 (±0,07)
IG 11 4,136 (±0,12) 4,220 (±0,11) 4,311 (±0,10) 4,341 (±0,12) 4,252 (±0,10)

IG perd sur correctness (−0,14) et gagne sur depth (+0,17) et evidence quality (+0,06), toutes différences avec SEM qui se recouvrent, et les auteurs écrivent eux-mêmes « sans significativité statistique » [§4.3]. Les auteurs interprètent la divergence juge-LLM / juge-humain ainsi : « Nous soupçonnons que cela reflète l'incapacité d'un humain à évaluer efficacement des insights sur de grands ensembles de traces, de claims et de patterns de preuves dans des budgets de temps fixes. » ⚠️ C'est une hypothèse auto-favorable non testée : la lecture symétrique — le juge LLM récompense une forme argumentative qu'il produit lui-même, et les humains, qui sont les seuls à noter correctness, ne voient pas de différence — est au moins aussi compatible avec les données et n'est pas envisagée.

⚠️ Aucune mesure d'accord inter-annotateurs (kappa, ICC entre les 12 évaluateurs) n'est rapportée : la caption de Tab. 6 précise que les scores par insight sont d'abord moyennés sur les 12 évaluateurs et que le SEM est calculé entre insights. La fiabilité de la couche humaine elle-même est donc non mesurée.

3.4 Couche 4 — vérification par impact aval (la plus solide)

Pass rate sur split held-out après modification du scaffold — par un humain (§4.2) ou par un patcher autonome (§4.4). C'est la seule couche insensible au style du rapport. ✅ Le choix d'en faire la mesure primaire (« nous traitons la performance d'intervention humaine comme la mesure primaire d'utilité aval », §4) est méthodologiquement le bon.

3.5 Robustesse / attaque du vérifieur

Le vérifieur n'a pas été attaqué délibérément. Mais le papier documente involontairement une violation de contrat de vérifieur dans le patcher loop (App. A.10.4, détaillée en §7) : un edit de prompt qui contredit le contrat exact-match du grader SSB et fait chuter le pass rate de 0,80 à 0,58. C'est l'observation la plus transférable du papier pour qui conçoit un reward.

Verdict : plausible mais fragile. Le résultat aval (+30,4 pp, intervention humaine sur SSB) est le mieux protégé du papier — randomisation, blinding, config verrouillée, split disjoint, audit des transcripts, batterie de robustesse — et je le crois, dans son périmètre : un benchmark, n = 6, un backbone. Tout l'appareil d'évaluation automatique qui l'entoure (coverage union-gold, rubrique 0–3, tournoi pairwise) est en revanche à traiter avec méfiance : il mesure la conformité à un format que l'architecture d'IG impose par construction, il ne mesure jamais la véracité, et le seul réglage qui mesure la véracité (juge humain, dimension correctness) donne IG derrière la baseline. La contribution « framework d'évaluation » est donc le maillon faible, pas le système.

Meilleur ingrédient à transposer

La dissociation entre correctness et le reste de la rubrique — et le constat que le juge LLM n'a pas de dimension de véracité, ce qui le rend incapable de départager ce que les experts départagent.

Ce n'est pas le système IG lui-même (que je réimplémenterais volontiers, mais qui est de l'outillage, pas de la science) : c'est le résultat négatif que le papier produit sans le revendiquer. Un juge LLM entraîné sur detection / mechanism / evidence / specificity / actionability classe IG loin devant CC Subagents (77,9 % vs 62,4 % de win rate) ; un panel de 12 experts, sur une rubrique qui isole explicitement correctness, les trouve indistinguables et met CC devant sur la justesse (4,278 vs 4,136). Pour Gemini Law, c'est exactement le risque : une rubrique juridique qui note « structure de l'argument, densité de citations, actionabilité du conseil » est mécaniquement optimisable par un modèle qui produit des citations abondantes et bien formées, et ne pénalise pas la citation fausse. La correctness doit être une dimension séparée, vérifiée par un canal distinct (résolution de citation contre une base de données réelle), et jamais agrégée dans un score composite avec les dimensions de forme — sinon le reward récompense la forme.

Corollaire : le gold « union » auto-référentiel du papier (§3.2) est un anti-patron dont il faut se souvenir. Construire l'ensemble de référence en poolant les sorties des systèmes évalués garantit qu'un finding halluciné devienne sa propre entrée gold. Toute métrique de « couverture » d'un agent juridique doit être ancrée sur un référentiel construit indépendamment des sorties de modèle.

Expérience minimale

Sur un corpus de 200–300 rollouts d'un agent juridique sur Harvey LAB (échec et succès mélangés), faire noter 20–25 insights produits par deux systèmes d'analyse par (a) un juge LLM avec la rubrique de forme du papier [App. A.7, 5 dims 0–3] et (b) 8–12 juristes avec une rubrique 1–5 où correctness est isolée et où toute citation est vérifiée par résolution effective contre la base documentaire. Rapporter le kappa/ICC inter-juristes — que le papier omet — et la corrélation de rang entre les deux juges.

Résultat attendu : corrélation de rang forte sur depth / actionability, faible ou nulle sur correctness, et un taux de citations non résolvables non nul dans les insights les mieux notés par le juge LLM. Si c'est le cas, cela interdit d'utiliser une rubrique LLM agrégée comme reward sur du juridique long-forme, et impose un vérifieur de citations en canal séparé, avec veto plutôt que pondération.

Second test, bon marché : rejouer le Pure-Patcher juridiquement. Faire proposer à un agent des modifications de prompt système à partir du seul code du scaffold, sans rapport de diagnostic, puis mesurer Vals sur 3 rounds. Le papier prédit une amélioration franche au round 1 (0,41 → 0,80) puis un effondrement (0,58) causé par une seule instruction qui contredit le contrat du grader [App. A.10.4]. Si le même effondrement apparaît, c'est la démonstration la moins chère que j'aie vue qu'un agent d'amélioration non ancré sur des traces dérive vers la violation du contrat de reward — et donc que le diagnostic régénéré à chaque checkpoint est une défense, pas un luxe.

Question à poser en interne chez GDM

Pour les rubriques de juge utilisées sur Gemini Law : est-ce que correctness factuelle est notée sur un canal séparé avec droit de veto, ou est-elle agrégée dans un composite avec les dimensions de forme (structure, sourcing, actionabilité) ? Et quel accord inter-annotateurs a été mesuré entre juristes sur chaque dimension avant que le juge LLM ne soit calibré dessus ? Ce papier montre le mode de défaillance exact quand ces deux points ne sont pas traités — un juge LLM confiant, un classement net, et des experts qui ne le reproduisent pas.
