0. En une phrase

TL;DR. Un modèle gelé lit les traces d'échec de ses propres runs, propose des patchs bornés au fichier de config de son harness (prompts, sous-agents, politique runtime), et un gate automatique non-régressif ne retient que ceux qui n'abaissent ni le split held-in ni le split held-out ; 9 combinaisons modèle×benchmark, toutes en progrès.

Claim principal. Sans ingénieur humain ni agent externe plus fort, la boucle Weakness Mining → Harness Proposal → Proposal Validation fait passer le Pass (%) d'un harness minimal à un harness spécifique au modèle, avec un gain relatif overall allant jusqu'à +132 % (Qwen3.5-35B-A3B sur AppWorld, 22,5 → 52,2) et un gain absolu jusqu'à +40,6 pts (GLM-5 sur AppWorld, 44,4 → 85,0) [abstract ; §1 ; Tab. 1].

⚠️ Le claim « every final harness improves both splits » est imposé par construction : la règle d'acceptation §3.4 exige Δ_in ≥ 0 ET Δ_ho ≥ 0. Il n'y a donc aucun split réellement hors de la boucle d'optimisation — le point central pour juger la généralisation (voir §3 et §7).

1. Tâches & data

Deux niveaux de « data » à distinguer : (a) les tâches des benchmarks, non produites par les auteurs ; (b) les traces d'exécution, qui sont la vraie data de la boucle.

Origine des tâches : entièrement empruntée à trois benchmarks publics existants [§4.1] — aucune tâche créée, aucun coût d'annotation.

Pipeline / sous-échantillonnage (c'est là qu'il y a des choix des auteurs) : - Terminal-Bench-2.0 : 89 tâches en conteneur au total ; sous-ensemble fixe de 64 cas, après exclusion des tâches dépendant de ressources web instables et des tâches multimodales (non supportées par le harness initial) [§4.1 ; App. A]. Mirroring local d'une partie des ressources externes ; cap de bande passante sortante à 2 MB/s [App. A]. Taille des splits held-in/held-out : non précisé (⚠️ mon calcul : 43/21 reproduit exactement les colonnes Overall de Tab. 1 pour les 6 lignes TB2). - SWE-bench Verified : sous-ensemble fixe de 100 cas, partitionné 67 held-in / 33 held-out, échantillonné proportionnellement par repository, split gelé pour toutes les variantes de harness [§4.1 ; App. A]. - AppWorld : 180 exemples, 90 held-in / 90 held-out ; held-in = partition officielle train ; held-out = échantillonnage proportionnel de test_normal + test_challenge, puis gelé [§4.1 ; App. A].

Volume de la data de la boucle : le nombre de rounds T, la largeur de proposition K et le nombre total de candidats évalués sont non précisés dans le texte (seules les figures d'évolution, non chiffrées dans le corps, montrent les candidats acceptés/rejetés) [Alg. 1 ; Fig. 2].

Distribution de difficulté : non caractérisée. Pour AppWorld, le held-out mélange test_normal et test_challenge, donc le held-out est a priori plus dur que le held-in (train) — ce qui se voit dans Tab. 1 (held-out < held-in partout sur AppWorld).

Filtrage par pass@k du modèle de base : aucun. Le filtrage est fait sur la faisabilité d'exécution (ressources web, multimodalité), pas sur la difficulté [§4.1].

Curriculum : aucun au sens RL. Le seul « curriculum » est l'ordonnancement des clusters d'échec présentés au proposer, triés par support (taille du cluster) et actionability estimée [§3.2].

Contamination / séparation train-test : les benchmarks sont publics et antérieurs aux modèles évalués ; la contamination pré-entraînement n'est pas discutée. Surtout : le split « held-out » n'est caché qu'au proposer, pas au gate — il est explicitement lu par la règle de promotion [§3.4 ; §4.1 « Splits and protocol »]. Il n'existe aucun troisième split vierge.

Données SFT/IFT avant RL : sans objet — aucun entraînement, les poids sont gelés [§3.1].

Coût humain : le harness initial et, surtout, la liste des surfaces éditables sont écrits à la main [Fig. 3]. Les auteurs revendiquent « sans ingénieur humain » ; ⚠️ c'est vrai pour les éditions, pas pour l'espace de recherche qui les contient.

2. Environnement / harness

C'est la section la plus utile du papier : le harness y est un objet de première classe, déclaré, versionné et diffable.

Harness initial [Fig. 3, code recopié du source] — construit sur le SDK DeepAgent, volontairement minimal. Surfaces déclarées éditables :

Observation : messages, résultats d'appels d'outils, sorties du verifier — la trace τ enregistre « the messages, tool calls, and verifier outcomes » [§3.1]. Pas de description plus fine du format d'observation.

Espace d'actions / outils : les outils DeepAgent par défaut — lecture de fichier, écriture de fichier, édition de fichier, exécution shell [Fig. 3, légende]. Signatures exactes : non précisées. Self-Harness ne peut pas ajouter d'outil arbitraire : il modifie « the harness definition file that configures how DeepAgent is instantiated and controlled » [§4.1] — en pratique les retenues observées sont des prompts, des sous-agents, et l'activation de la politique runtime.

Multi-turn / horizon : - AppWorld : au plus 50 tours d'agent par tâche [App. A]. - SWE-bench Verified : timeout de 3 600 s par cas, 120 s par appel d'outil [App. A]. - Terminal-Bench-2.0 : budget de tours/temps non précisé (seul le cap réseau 2 MB/s est donné) ; la politique runtime éditable expose max_total_tool_messages, ce qui suggère que le cap est un paramètre du harness, pas de l'env [Fig. 3]. - Gestion du contexte long (troncature, résumé, mémoire) : non précisé au-delà de build_memory_sources() = /AGENTS.md.

Exécution : TB2 via Harbor ; SWE-bench dans un sandbox Docker par instance, patch scoré dans l'image officielle prébuild swebench/sweb.eval.x86_64.<instance-id> ; AppWorld dans un contexte frais avec état isolé [App. A]. Chaque tâche repart d'un environnement vierge [§4.1]. Modèles servis : MiniMax M2.5 via API hébergée, GLM-5 via OpenRouter, Qwen3.5-35B-A3B localement sur 4×H200 avec SGLang v0.5.12-cu129 [App. A].

Déterminisme : explicitement non supposé — « When evaluation is stochastic, we repeat candidate evaluation » [§3.4] ; métrique calculée sur 2 tentatives répétées par candidat [§4.1 ; App. A]. Température et config de décodage : « kept unchanged » mais valeurs non précisées.

Gestion des erreurs d'outils / sorties mal formées : traitée comme un objet d'optimisation, pas comme une fonctionnalité du harness initial. Le harness initial ne contient qu'une instruction en langue naturelle (« do not blindly retry »). Les éditions retenues ajoutent des mécanismes concrets : middleware déclenché par erreur d'outil (Qwen/TB2), plafond sur le nombre total de messages d'outil (M2.5/TB2) [§4.3]. Côté validation, un candidat qui « fail[s] execution before a valid evaluation result is obtained » ou qui ne modifie aucune surface éditable est rejeté [§3.4].

Exemple de trajectoire : le papier ne recopie aucune trace en texte ; il donne des comparaisons avant/après en figures. La plus explicite, en prose [§4.3 + App. B.1, tâche TB2 extract-elf, Qwen3.5] : harness initial → l'agent crée le script extracteur requis, rencontre des échecs d'écrasement et d'édition, retente de modifier le même artefact en boucle, supprime finalement /app/extract.js et s'arrête → le verifier échoue car le fichier requis est absent. Harness édité → un system prompt déclenché par erreur d'outil le redirige vers l'artefact manquant : il recrée l'extracteur, corrige le parsing, écrit le fichier de sortie, valide le JSON, et laisse l'artefact en place.

Mécanismes retenus, par benchmark [§4.3 ; App. B.2-B.3] — utile comme catalogue de « ce qui manque à un harness naïf » : - TB2 : création précoce de l'artefact de sortie ; manipulation prudente des sorties d'outil structurées ; plafond de messages d'outil contre les boucles stériles (M2.5) · precheck de dépendances, break de boucle, discipline de retry, récupération orientée artefact (Qwen) · persistance des changements d'environnement entre commandes shell, passage accéléré de l'exploration à l'implémentation (GLM-5). - SWE-bench : sous-agent d'inspection du diff (détection de diff vide) + sous-agent test-verifier (M2.5) · sous-agent patch-verifier + instruction pré-soumission « inspecte le diff, lance les tests ciblés » (Qwen) · cycle de vérification FAIL-TO-PASS avec récupération de dépendances : parse l'erreur d'import, installe le paquet manquant, relance le test exact (GLM-5). - AppWorld : sous-agent state-auditor + pagination + bornes temporelles (M2.5) · garde de « contrat de complétion » (tâche d'action vs demande d'information) + garde de pagination (Qwen) · règle action-vs-information + pagination exhaustive avant mutation d'état (GLM-5).

⚠️ Convergence notable : sur SWE-bench les trois modèles convergent vers du sous-agent de vérification, sur AppWorld vers la récupération d'état complète. L'implémentation diffère, le mécanisme non — ce qui affaiblit un peu la thèse « le harness doit être spécifique au modèle » et suggère plutôt « le harness doit être spécifique au benchmark ».

3. Reward / vérifieur

Il faut distinguer deux niveaux, le papier ne le fait pas explicitement.

(a) Vérifieur de tâche — verifiers officiels des benchmarks, non modifiés, gelés [§3.1 : « the model M and evaluator E are held fixed »] : - TB2 : verifier officiel via Harbor [App. A]. - SWE-bench Verified : évaluateur officiel dans l'image Docker par instance ; granularité FAIL-TO-PASS / PASS-TO-PASS visible dans les cas d'App. B.2 [App. B.2]. - AppWorld : tests unitaires state-based officiels [§4.1]. → Type : exécution de tests / état, binaire (pass/fail), outcome-level. Aucun LLM-as-judge dans le scoring. C'est le point fort méthodologique du papier : le signal d'optimisation est exogène et non-hackable par le proposer. - Métrique : Pass (%) = pourcentage de tentatives réussies, sur 2 tentatives répétées par candidat [§4.1]. - Fiabilité du vérifieur mesurée : non — héritée des benchmarks, aucun accord humain rapporté (cohérent : vérifieurs exécutables).

(b) « Reward » de la boucle externe — la règle d'acceptation, c'est le vrai objet à retenir [§3.4 ; Alg. 1 l.11] :

accepter Δ_j ssi Δ_in ≥ 0 ET Δ_ho ≥ 0 ET max(Δ_in, Δ_ho) > 0

avec Δ_in = P_in(h_t^(j)) − P_in(h_t) et Δ_ho = P_ho(h_t^(j)) − P_ho(h_t), en nombre de tâches passées (pas en %). Propriétés : - Conservatrice : une proposition qui échange un split contre l'autre est rejetée même si le total de passes augmente [§3.4]. C'est un gate de non-régression, pas un gate d'amélioration moyenne. - Stochasticité : agrégation des pass counts sur les répétitions avant d'appliquer la règle, « pour réduire la chance qu'une édition soit promue à cause d'un seul run favorable » [§3.4]. ⚠️ 2 répétitions seulement — protection très faible contre le bruit d'échantillonnage (cf. §7). - Gardes structurelles : rejet si le candidat ne modifie aucune surface éditable, ou s'il plante avant de produire un résultat d'éval valide [§3.4]. - Merge : si plusieurs candidats passent dans le même round, leurs éditions sont fusionnées en h_{t+1} [§3.4 ; Alg. 1 l.20] — ⚠️ la fusion n'est pas re-validée : rien dans le texte n'indique que h_{t+1} fusionné est re-testé avant de devenir le parent du round suivant. Interaction entre éditions non contrôlée. - Auditabilité : pour chaque candidat sont enregistrés les surfaces changées, les résultats par split, le nombre de répétitions, le résumé de la proposition et la décision accept/reject [§3.4].

(c) Signal intermédiaire : la signature d'échec — le vrai « process reward » du papier [§3.2]. Chaque trace échouée r_i reçoit φ(r_i) = (c_i, q_i, m_i) où c_i = cause terminale au niveau du verifier, q_i = statut causal du comportement agent concerné, m_i = mécanisme agent abstrait exposé par la trace. Clustering par égalité exacte de la signature — donc déterministe et ancré sur le verifier, pas sur une similarité sémantique latente. Chaque cluster porte sa taille, des instances représentatives, les symptômes partagés, l'évidence verifier et le mécanisme inféré ; les clusters sont ordonnés par support et actionability [§3.2]. Le bundle B_t ne prescrit pas d'édition — séparation explicite évaluateur / optimiseur.

Si juge LLM : le scoring n'en utilise pas, mais l'attribution de (c_i, q_i, m_i) et l'ordonnancement par « actionability » sont manifestement faits par un modèle. Le papier ne dit pas quel modèle fait cette attribution, ni avec quel prompt. ⚠️ Aucun prompt (miner, proposer) n'est reproduit, ni dans le corps ni en annexe — lacune majeure pour un papier dont c'est le cœur. Aucune mesure d'accord inter-annotateur ou humain sur les signatures.

Robustesse / anti-hacking : le verifier de tâche n'est pas modifiable par le proposer, donc le hacking classique du reward est structurellement exclu. En revanche le papier ne teste pas le hacking du gate — c'est-à-dire les éditions qui font monter le pass count sur ces 64 / 100 / 180 cas figés sans généraliser (voir §7). Les auteurs le reconnaissent en creux : « Higher-stakes harness changes would require stronger acceptance gates than pass-rate non-regression alone » [§5].

Régularité non commentée par les auteurs (⚠️ mon analyse) : le gain relatif est anticorrélé à la performance initiale. Le modèle le plus faible (Qwen3.5-35B-A3B, 18,0–22,5 % de base) gagne +104 à +132 % ; le plus fort sur SWE-bench (GLM-5, 52,0 %) gagne +7 %. Lecture : Self-Harness comble surtout l'écart entre un harness délibérément minimal et un harness raisonnable, écart d'autant plus grand que le modèle exploite mal un scaffold pauvre. Ce n'est pas la même chose que faire progresser l'état de l'art.

In-distribution vs OOD. C'est le point faible central et il touche directement la question « comment mesure-t-on la généralisation hors du jeu servant à optimiser ? ». - Le held-out est caché au proposer (il ne voit ni ses traces ni ses échecs) mais lu par le gate à chaque candidat [§3.4 ; §4.1]. C'est donc de la sélection sur le held-out, pas une évaluation hors échantillon. Le protocole ressemble à un validation set utilisé pour l'early stopping, rapporté comme un test set. - ⚠️ Conséquence : les gains held-out de Tab. 1 sont optimistement biaisés d'une quantité non mesurée, d'autant plus que K candidats × T rounds multiplient les comparaisons sur le même held-out (21 à 90 tâches selon le benchmark). Avec 2 répétitions et des splits de cette taille, une amélioration d'1 à 2 tâches est dans le bruit. - Il n'y a aucun troisième split vierge, aucun test du harness final sur les tâches TB2 exclues, sur le reste de SWE-bench Verified (400 cas non utilisés), ni sur un benchmark tiers. - Transfert entre modèles (un harness optimisé pour M2.5 appliqué à Qwen) : non mesuré. C'est pourtant l'ablation qui trancherait la thèse « le harness doit être model-specific » ; elle est absente. - Transfert entre benchmarks : non mesuré.

Ablations. Aucune. Ni sur le clustering par signature vs. traces brutes, ni sur la largeur K, ni sur le nombre de rounds T, ni sur le gate (avec/sans contrainte held-out), ni sur un contrôle trivial (allonger le prompt, ajouter des instructions génériques, prendre un harness public type SWE-agent). Les mécanismes retenus ne sont décrits que qualitativement [§4.3 ; App. B].

Scaling. Trois modèles de familles différentes, une seule taille testée par famille ; Qwen3.5-35B-A3B est le seul dont le nombre de paramètres est connu du titre. Effet du compute de la boucle : non rapporté (ni nombre total de rollouts, ni coût, ni durée — alors que la boucle coûte ~K×T×(|D_in|+|D_ho|)×2 exécutions complètes de benchmark).

Solidité. - ❌ Baselines : l'unique comparateur est un harness minimal conçu par les auteurs pour être pauvre [Fig. 3] ; aucune comparaison à un harness d'expert (Claude Code, SWE-agent, OpenHands) ni à Meta-Harness, pourtant cité comme l'alternative directe [§2]. Le compute n'est pas apparié : le harness final consomme des centaines d'évaluations de plus que le baseline. - ❌ Ablations : aucune isolant la contribution (mining, clustering, gate, diversité K). - ❌ Variance : 2 tentatives répétées, aucun écart-type, aucun intervalle de confiance, aucune seed multiple pour la boucle elle-même (une seule trajectoire d'évolution par cellule). - ❌ Fiabilité de l'éval : vérifieurs officiels exécutables (bon point), mais held-out utilisé comme critère de sélection → mesure de généralisation compromise ; contamination pré-entraînement non discutée ; sous-ensembles choisis par les auteurs. - ⚠️ Échelle : 64 / 100 / 180 tâches, soit des splits held-out de 21 / 33 / 90 tâches — une tâche vaut 1,1 à 4,8 points de pass rate selon le split. - ❌ Reproductibilité : dépôt public réel et non vide (vérif. externe 2026-09-30), mais il ne contient qu'un seul des neuf harness finaux (harnesses/qwen_tb2_final) et qu'un chemin d'éval Harbor ; ni les listes de splits, ni les prompts du miner/proposer, ni les configs SWE-bench/AppWorld ne sont dans le papier ni visiblement dans le dépôt. - ✅ Cohérence texte ↔ tableaux : excellente — tous les chiffres de l'abstract et de l'intro se retrouvent dans Tab. 1, et les Overall sont arithmétiquement cohérents avec les tailles de splits.

Verdict : plausible mais fragile — à répliquer. Le mécanisme est crédible et les cas qualitatifs sont convaincants (ajouter de la vérification exécutable et de la récupération d'artefact à un harness qui n'en a pas doit aider). Mais l'amplitude annoncée est ininterprétable : baseline volontairement faible, compte non apparié en compute, held-out sélectionné, aucune ablation, aucune variance. Le résultat honnête du papier est « une boucle propose-valider-accepter, pilotée par des vérifieurs exécutables, peut automatiser le travail de scaffolding qu'un ingénieur ferait à la main » — pas « +132 % ».

Evidence = 1/6. 1. baselines ❌ — comparateur unique = harness minimal maison, pas de harness expert ni Meta-Harness, compute non apparié. 2. ablation ❌ — aucune ablation ne sépare mining / clustering / gate / diversité. 3. variance ❌ — 2 répétitions, aucun écart-type ni IC, une seule trajectoire de boucle par cellule. 4. coherence ✅ — tous les chiffres de l'abstract et de l'intro retrouvés dans Tab. 1, Overall arithmétiquement cohérents (§7.0). 5. eval ❌ — le split « held-out » est le critère de promotion : sélection sur le jeu servant à mesurer la généralisation, sans split vierge. 6. repro ❌ — dépôt public mais partiel (1 harness final sur 9, pas de splits, pas de prompts miner/proposer).

Il faut un troisième split, jamais lu par le gate

Meilleur ingrédient à transposer. Le couple « signature d'échec ancrée sur le vérifieur + gate de promotion non-régressif », pas l'auto-amélioration en soi. Deux raisons : (1) il force à écrire la taxonomie d'échecs avant de toucher au scaffold, ce qui est exactement l'exercice utile en droit où les échecs sont hétérogènes ; (2) il transforme l'ingénierie de harness en transitions d'état enregistrées, testables et réversibles [§5], donc auditables — propriété précieuse dans un domaine où il faudra justifier chaque choix de scaffold devant des juristes. ⚠️ Et il faut corriger le défaut du papier : trois splits, pas deux — un pour le mining, un pour le gate, un vierge pour le rapport.

Expérience minimale. Prendre le harness Gemini juridique actuel, geler le modèle. Découper les tâches disponibles en trois : mining / gate / rapport (jamais lu). Définir 5 à 8 surfaces éditables explicites (prompt système, instruction de vérification, sous-agent vérificateur de citations, plafond de tours, instruction de récupération). Vérifieur composite : exactitude sur les items à réponse courte + taux de citations inexistantes ou non pertinentes (vérifiable mécaniquement contre la base documentaire). Lancer 3 rounds × K = 4 propositions, gate = non-régression sur les deux premiers splits, puis rapporter uniquement sur le troisième. Résultat attendu : gain net sur le taux d'hallucination de citations (le mode d'échec le plus « scaffold-adressable », analogue direct du « missing required artifact » du papier), gain faible ou nul sur la qualité argumentative. Un écart marqué entre le gain sur le split du gate et le gain sur le split vierge mesurerait directement le biais de sélection que le papier ne mesure pas — information utile en soi.

Question à poser en interne chez GDM. Quelle part des gains rapportés sur Harvey LAB / Vals est attribuable au harness plutôt qu'au post-training ? Existe-t-il un protocole imposant de geler le harness entre deux mesures de RL — et, symétriquement, une passe de tuning automatisé du harness sur le modèle baseline avant de mesurer le gain RL ? Sans cela, un gain RL peut être égalé par un scaffold mieux réglé, ce que ce papier suggère fortement (jusqu'à +22 pts sur SWE-bench Verified à poids gelés).
