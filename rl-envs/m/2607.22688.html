0. En une phrase

TL;DR. Co-Harness alterne, par rounds, (i) une boucle qui répare le harness (prompt, tools, skills, middleware, memory) à partir des trajectoires échouées via un LLM « HarnessCritic » à modèle gelé, et (ii) une boucle SFT sur les trajectoires réussies collectées sous le harness évolué, à harness gelé.

Claim principal. Deux rounds de co-évolution améliorent la pass@1 moyenne de +20.4 pp (58.5 % → 78.9 %) sur AIME24 / AIME25 / HMMT25, moyenné sur Qwen3-8B et Qwen3-32B, avec un max de +27.2 pp (HMMT25, 32B) ; et +24.7 pp en moyenne sur un harness statique conçu à la main [§1, Tab. 1]. Les auteurs affirment que ce couplage produit un « compounding self-improvement » que ni la boucle harness seule ni la boucle modèle seule n'atteignent, et que Co-Harness est « the first framework to co-evolve both » [§6].

⚠️ Le claim tel qu'il est formulé n'est pas testé. Aucun bras d'expérience ne fait varier une seule des deux boucles. Détail en §7 ci-dessous. Le papier est une proposition de design accompagnée d'une démonstration, pas une démonstration causale.

1. Tâches & data

  • Origine des tâches. Benchmarks publics existants uniquement : AIME 2024 (30 problèmes), AIME 2025 (30), HMMT February 2025 (30, individual round) [§4.1]. Aucune tâche construite, minée ou générée pour ce papier.
  • Pipeline de construction. Aucun. Le papier ne construit pas de jeu de tâches.
  • ⚠️ Jeu d'entraînement : non précisé — et c'est le trou central du papier. §3.4 dit seulement « we re-run the current model under that configuration and collect the resulting trajectory set $\mathcal{D}_t$ ». §2 (intro) dit « The agent first collects rollouts on a task set ». Sur quel task set, jamais dit. Aucune occurrence de « training set », « train split », « dataset » (hors légende de figure) dans tout le fichier source, annexes comprises. La lecture littérale — le modèle est rejoué sous $\phi_t^\star$ et les trajectoires servent au SFT — pointe vers les problèmes des benchmarks eux-mêmes.
  • Volume. Taille de $\mathcal{D}_t$ : non précisé. Nombre de trajectoires échouées par round alimentant HarnessCritic : non précisé (seul chiffre voisin : les 200 trajectoires annotées à la main de l'App. D, qui servent à un protocole d'annotation, pas à l'entraînement).
  • Distribution de difficulté. Traitée au niveau benchmark seulement : AIME24 « moderately challenging » → HMMT25 « extremely difficult » [§4.1]. Pas de distribution intra-benchmark.
  • Filtrage. « We keep trajectories that satisfy the task verifier or otherwise meet the quality filters associated with the benchmark » [§3.4]. Les « quality filters » ne sont jamais énumérés. Pas de filtrage par pass@k du modèle de base, pas de seuil chiffré. C'est du rejection sampling implicite : seules les trajectoires vérifiées correctes entrent dans le SFT.
  • Curriculum. Aucun au sens tâches. Le seul « ordre » est le schedule des rounds ($T=2$, $K=5$ itérations internes de HarnessCritic par round) [§4.1]. Pas de rééchantillonnage, pas de mélange, pas de pondération par difficulté.
  • Contamination et séparation train/test. Aucune mention. Zéro occurrence de « contamination » dans le source. ⚠️ Trois signaux convergents de fitting sur le test : 1. le jeu SFT n'est pas spécifié et la lecture littérale de §3.4 le fait coïncider avec les benchmarks d'éval ; 2. la validation des patches ($\mathcal{V}{\mathrm{in}}$, $\mathcal{V}}$, App. E) utilise des rollouts dont la provenance n'est pas dite non plus ; 3. l'étude de cas est explicitement une optimisation de harness sur AIME24 : 22 versions sélectionnées sur l'accuracy AIME24 [§4.3, App. F]. Le harness de départ du tableau principal est donc plausiblement fitté sur un benchmark d'éval. ⚠️ Indice fort : le score final de l'étude de cas (63.3 % AIME24, Qwen3-8B) est exactement le R0 du Tab. 1 pour Qwen3-8B/AIME24 (63.3). Le papier ne dit jamais si c'est la même run — non précisé — mais si oui, le « Baseline » du tableau principal encapsule 200 h de recherche de harness sur le test set.
  • Données SFT/IFT avant RL. Sans objet : il n'y a pas de RL. Le seul update de poids est un SFT par maximum de vraisemblance sur trajectoires vérifiées, $\theta_{t+1} = \arg\max_\theta \sum_{(x,\tau)\in\mathcal{D}t} \log p\theta(\tau \mid x)$ [§3.4]. Pas de cold start, pas de phase format.
  • Coût humain. Deux annotateurs experts (> 2 ans d'expérience en agent engineering), 200 trajectoires d'échec labellisées indépendamment selon la taxonomie du Tab. 2, désaccords tranchés par un troisième expert, 90 minutes pour les 200 trajectoires, sans voir les attributions du LLM ; $\kappa = 0.77$ inter-annotateurs ; toutes les expériences d'attribution utilisent $\theta_0$ (Round 0) [App. D]. ⚠️ 90 min pour 200 trajectoires d'agent = 27 s par trajectoire avec accès aux logs complets et à la config du harness. Pour des trajectoires TIR multi-turn, ce budget est difficilement compatible avec une lecture sérieuse des traces.

2. Environnement / harness

Le harness est l'objet du papier. Formalisé comme un 5-uplet $\phi = (\texttt{P}, \texttt{T}, \texttt{S}, \texttt{Mid}, \texttt{M})$ : prompt/instruction templates, tool definitions & interface schemas, reusable skills/modules, middleware, long-term memory policy. Le middleware « bundles the agent's runtime control surface » : orchestrateur (main loop + protocole), hooks d'interception yes/no et de vérification, et gestion de contexte (compression, troncature, routage de retrieval) [Déf. 3.1].

Configuration initiale $\phi_0$ (recopiée de App. C, Tab. 4)

Dim. Réglage
P (Prompt) System prompt : instruction de 512 tokens avec guidelines de raisonnement mathématique et instructions d'usage TIR (« use Python code to assist your reasoning ») ; pas de retrieval few-shot
T (Tool) Interpréteur de code Python (sandboxed subprocess) ; schéma de tool-call JSON spécifiant name: python, arguments.code: str ; timeout par défaut 30 s
S (Skill) None (skill set vide au Round 0)
Mid (Middleware) Orchestrateur : max turns ; terminaison sur <DONE> ou token de réponse finale. Hooks : retry sur ToolCallException (max 3, linear backoff). Gestion de contexte : compression par sliding-window gardant les 4k derniers tokens ; sorties de l'interpréteur tronquées à 2k tokens
M (Memory) Pas de mémoire long-terme ni de store de retrieval externe au Round 0

Observation et espace d'actions

  • Observation. Au premier tour : l'énoncé du problème inséré dans le system prompt. Ensuite : le contexte de conversation accumulé, où chaque tool call est suivi d'un tool_result injecté par le middleware [App. A].
  • Espace d'actions. Un seul outil. Format exact recopié de App. A :
<tool_call>
{"name": "python", "arguments": {"code": "..."}}
</tool_call>

Le middleware intercepte chaque tool call, dispatche le bloc de code vers le subprocess interpréteur Python, et réinjecte stdout, stderr et valeur de retour dans le contexte comme tool_result :

<tool_result>
{"stdout": "42\n", "stderr": "", "exit_code": 0}
</tool_result>

Le modèle continue ensuite de générer, émettant éventuellement d'autres tool calls ou produisant sa réponse finale.

  • Multi-turn. Oui. Horizon : max_turns initialement 15, porté à 30 après la Phase 2 de l'étude de cas [App. A, App. F]. Horizon typique observé : non précisé.
  • Gestion du contexte long. Sliding-window 4k tokens + troncature des sorties interpréteur à 2k [App. C]. Le papier identifie lui-même la défaillance associée : « A poorly configured compression policy discards critical intermediate results, causing the model to repeat calculations or lose track of partial progress » [App. A].
  • Exécution. Subprocess sandboxé, timeout 30 s. Backend d'inférence vllm (révélé incidemment par le crash gpu_util de l'étude de cas, App. F). Déterminisme : non discuté ; l'étude de cas manipule explicitement seed=42 comme levier de diversité pour l'ensembling, ce qui implique un sampling stochastique (température non précisée ; « temperature schedules » explorés en v4–v7 sans valeurs). Reset : non précisé.
  • Gestion des erreurs. C'est le cœur de la taxonomie. Quatre modes d'échec propres au TIR [App. A] :
  • T tool-schema failures : JSON malformé ou nom d'argument non supporté → l'interpréteur rejette l'appel avec une erreur de validation de schéma au lieu d'exécuter, ce qui produit « an unhelpful error token in the context and often stalls the episode » ;
  • Mid middleware failures : hook de retry absent ou mal configuré → un crash transitoire de l'interpréteur (ex. OOM du subprocess) termine l'épisode silencieusement au lieu de déclencher un retry ; « The model receives no feedback signal » ;
  • Mid context management failures : débordement de fenêtre sur les épisodes longs, politique de compression qui jette les résultats intermédiaires critiques ;
  • P prompt failures : le system prompt n'indique pas clairement d'utiliser le code comme outil de raisonnement primaire, le modèle diffère ses appels jusqu'à la dernière étape et rate l'exploration itérative.
  • Argument de design des auteurs. En TIR l'échec est binaire — « either the code executes and returns useful feedback, or it does not » — ce qui « creates a sharper gradient for HarnessCritic to act on » et explique selon eux pourquoi la co-évolution de harness rend particulièrement en TIR, alors qu'en pur texte un prompt sous-optimal ne dégrade que graduellement [App. A, App. E]. ⚠️ Argument plausible mais non testé : aucune expérience pur-texte n'est faite pour la comparaison.
  • Exemple de trajectoire. Le papier n'en donne aucun (ni complet ni tronqué). Seuls les deux fragments de format ci-dessus.

Registry et rollback (App. E)

Toutes les configurations sont versionnées dans un harness_registry/ : v0/harness.yaml ($\phi_0$), v1/harness.yaml ($\phi_0^\star$) + diffs/ contenant des patches YAML autonomes nommés (001_hook_retry.yaml, 002_tool_timeout.yaml, 003_prompt_scope.yaml, 004_strategy_maxrounds.yaml), etc. Chaque diff porte des métadonnées (round, source d'attribution, delta de validation) permettant rollback complet et audit. ⚠️ Le registry n'est pas publié ; les 4 noms de diffs ci-dessus sont les seuls contenus de patch concrets donnés dans tout le papier.

3. Reward / vérifieur

Il y a trois vérifieurs distincts dans ce papier, et le papier n'en mesure la fiabilité d'aucun.

3.1 Vérifieur de tâche (reward de la tâche)

  • Type. $R(x; \theta, \phi)$ « instantiated in our experiments as pass@1 or resolve rate depending on the benchmark » [§3.1]. En pratique : pass@1 sur AIME/HMMT, « averaging over multiple rollouts per problem » [§4.1]. ⚠️ Aucun benchmark à resolve rate n'existe dans le papier — texte résiduel (voir 7.0).
  • Granularité. Outcome, binaire par problème, moyenné sur rollouts. Pas de crédit partiel, pas de process reward.
  • Mécanique exacte. Non précisé. Le papier ne dit jamais comment la réponse finale est extraite ni comparée à la vérité terrain. AIME/HMMT ont des réponses entières, donc un exact match est implicite et trivialement fiable — mais ce n'est écrit nulle part.
  • Nombre de rollouts par problème. Non précisé (« multiple »). Point non trivial : avec 30 problèmes par benchmark, c'est la variable qui fixe le bruit de toutes les mesures du Tab. 1.
  • Termes additionnels. Aucun (pas de pénalité de format, de longueur, de bonus). Le seul terme non-accuracy du papier est la contrainte de budget wall-clock (3.33 h) de l'étude de cas, traitée « as an explicit constraint, not just a metric » [App. F].
  • Fiabilité mesurée. Non — et sur AIME, peu problématique.

3.2 Vérifieur de patch (le vrai vérifieur de la boucle harness)

C'est lui qui décide ce qui entre dans l'environnement. Protocole recopié de App. E :

Un patch $\tilde\phi_t$ est validé contre $\phi_t$ sur deux splits : un held-in $\mathcal{V}{\mathrm{in}}$ contenant des exemples qui exhibent le mode d'échec ciblé, et un held-out $\mathcal{V}}$ contenant des comportements précédemment réussis ou orthogonaux.

$$\delta_{\mathrm{in}} = R(\mathcal{V}{\mathrm{in}}; \theta_t, \tilde\phi_t) - R(\mathcal{V}}; \theta_t, \phi_t), \qquad \delta_{\mathrm{out}} = R(\mathcal{V}{\mathrm{out}}; \theta_t, \tilde\phi_t) - R(\mathcal{V}}; \theta_t, \phi_t)$$

Règle d'acceptation : $\delta_{\mathrm{in}} > 0$ ET $\delta_{\mathrm{out}} \geq 0$. Les auteurs affirment que cette règle « prevents the system from overfitting to isolated failures or trading away previously reliable behavior ». Les patches rejetés sont rollback immédiatement ; le registry enregistre acceptés et rejetés.

⚠️ Évaluation critique. C'est le point faible structurel. - Taille de $\mathcal{V}{\mathrm{in}}$ et $\mathcal{V}}$ : non précisé. Provenance : non précisé. - Le seuil est un strict > 0 sans plancher de bruit et sans test de significativité. Sur une métrique pass@1 estimée par quelques rollouts, $\delta_{\mathrm{in}} > 0$ est franchi par pur bruit avec une probabilité élevée. Avec $K=5$ itérations internes × 2 rounds × plusieurs candidats par itération, on fait beaucoup de tirages : c'est un protocole de sélection sur le bruit, et rien dans le papier ne le contrôle. - $\delta_{\mathrm{out}} \geq 0$ (inégalité large) accepte les régressions nulles mesurées, donc les petites régressions réelles noyées dans le bruit. - Taux de faux positifs de l'acceptation : non mesuré. Nombre de patches proposés / acceptés / rejetés : non rapporté, alors que le registry le contient par construction.

3.3 HarnessCritic comme attributeur (vérifieur de diagnostic)

  • Type. LLM-as-judge structuré, sortie JSON, CoT préalable.
  • Modèle du critic. ⚠️ Non précisé. Nulle part dans le papier. Les limitations disent seulement « Co-Harness requires a capable critic LLM » [§6]. C'est un trou de reproductibilité majeur : le composant central du papier n'a pas d'identité.
  • Taxonomie d'attribution [Tab. 2]. Cinq catégories harness actionnables + une abstention :
Root cause Locus Symptôme typique
prompt_ambiguity P instruction underspecification or conflicting goals
tool_schema_error T invalid tool call, bad argument schema, backend mismatch
skill_missing S missing reusable routine or decomposition primitive
middleware_mismatch Mid flawed loop protocol, hook behavior, or context management
memory_overflow M persistent state overflow, stale memory, or retrieval failure
agent_error — failure remains model-side after Harness inspection

agent_error est une abstention : ces cas sont exclus de la génération de patch [§3.3]. C'est le bon réflexe de design — le critic doit pouvoir dire « ce n'est pas le harness, c'est le modèle ».

  • Prompt recopié intégralement (App. B).
System: You are an expert agent scaffolding engineer.
Given a failed agent trajectory and the current Harness
configuration, identify the root cause of failure.

Output your reasoning in <think>...</think>, then output
a JSON object matching this schema:
{
  "root_cause": one of [
    "prompt_ambiguity", "tool_schema_error", "skill_missing",
    "middleware_mismatch", "memory_overflow", "agent_error"
  ],
  "harness_dim": one of ["P", "T", "S", "Mid", "M"],
  "severity": one of ["critical", "major", "minor"],
  "evidence": "< 1 sentence citing specific trajectory event >",
  "diff_suggestion": {
    "field_path": "middleware.hooks.post_tool_call[0].type",
    "old_value": null,
    "new_value": "retry_on_rate_limit"
  }
}

== CURRENT HARNESS CONFIGURATION ==
{harness_config_yaml}

== FAILED TRAJECTORY ==
{trajectory_text}
  • Agrégation. Une attribution isolée étant bruitée, les attributions sont agrégées sur un batch : classement des edits candidats par récurrence, sévérité et cohérence du field_path proposé, puis fusion des suggestions compatibles en un unique Harness Diff $\Delta\Phi_t$. Le diff est volontairement local : il n'enregistre que les champs qui changent, avec ancienne et nouvelle valeur — pour l'interprétabilité et le rollback [§3.3]. Aucune pondération chiffrée n'est donnée pour ce ranking.
  • Fiabilité mesurée. ⚠️ NON — et c'est le manquement le plus net du papier. L'App. D met en place un protocole d'annotation humaine complet (200 trajectoires, 2 experts + arbitre, $\kappa = 0.77$) qui n'a de sens que pour mesurer l'accord LLM ↔ humain sur la taxonomie… et ce chiffre n'est jamais rapporté. Aucune table, aucune figure, aucune phrase. Le $\kappa=0.77$ publié est l'accord entre les deux humains, pas entre le critic et les humains. Les limitations concèdent qualitativement « Attribution accuracy degrades for failure modes requiring counterfactual control-flow reasoning » [§6], sans le moindre chiffre. Conséquence : la précision d'attribution de HarnessCritic est inconnue.
  • Robustesse / attaque. Le vérifieur de patch n'a jamais été attaqué ni testé contre le hacking. Aucune section reward hacking. ⚠️ Crédibilité : le risque principal ici n'est pas un hacking par le modèle (le modèle ne contrôle pas le harness) mais un hacking par le critic — le critic propose des patches, mesure lui-même le gain sur $\mathcal{V}_{\mathrm{in}}$, et la règle d'acceptation est un seuil bruité. Les auteurs nomment d'ailleurs deux mécanismes de cette famille en §5 (« Harness over-patching », « Attribution cascade ») mais sans aucune mesure.

Le schéma de co-évolution : ordre, fréquence, ce qui est gelé quand

Réponse précise à la question posée, d'après §3.2 et l'Alg. 1 :

  • Alternance stricte par blocs, jamais simultanée. À chaque round $t$ : 1. Co-Harness Loop — $\theta_t$ GELÉ, $\phi$ bouge. Collecte des trajectoires échouées $\mathcal{F}t^-$ sous $(\theta_t, \phi_t)$, puis $K=5$ itérations internes : $\mathcal{A}_t \leftarrow \mathcal{C}(\mathcal{F}_t^-, \phi_t)$ → AggregateDiffs → Apply → Validate → commit au registry si non-régressif, sinon rejet → refresh de $\mathcal{F}_t^-$ sous le harness courant à chaque itération. Sortie : $\phi_t^\star$. 2. Model Alignment Loop — $\phi_t^\star$ GELÉ, $\theta$ bouge. Collecte de $\mathcal{D}_t$ sous $(\theta_t, \phi_t^\star)$, puis SFT : $\theta = \arg\max_\theta \sum \log p_\theta(\tau \mid x)$. 3. Report d'état : $\phi_{t+1} \leftarrow \phi_t^\star$. Le harness n'est jamais réinitialisé entre rounds ; il s'accumule.
  • Fréquence. $T = 2$ rounds complets [§4.1]. Round 0 = une passe HarnessCritic seule, sans SFT, qui sert de point de départ.
  • Critère d'arrêt (formulé mais non utilisé). Arrêt quand (i) aucun patch candidat ne passe la validation, ou (ii) le gain marginal de reward passe sous un petit seuil sur des rounds consécutifs [§3.2]. ⚠️ Le seuil n'est pas chiffré et les expériences utilisent « a fixed small number of rounds » — donc le critère d'arrêt n'est de fait jamais exercé.
  • Comparaison à un harness figé ? Partiellement, et pas sur la bonne cellule. Le papier compare bien à deux configurations à harness figé — Human (harness manuel, 0 SFT) et R0 (harness critic×1, 0 SFT) — mais les deux ont zéro SFT. La cellule manquante est « harness figé + 2 rounds de SFT ». Sans elle, « alterner > geler » n'est pas testé : ce qui est testé est « alterner > ne rien faire ».

Le design expérimental confond parfaitement les deux axes. Passes de HarnessCritic et rounds de SFT avancent toujours ensemble :

  • Aucune ablation. Zéro occurrence de « ablation » dans tout le source. Il n'existe ni bras harness-only poussé au-delà de R0 (3 passes critic, 0 SFT), ni bras SFT-only (harness gelé à $\phi_0^\star$, 2 rounds de SFT). Les deux contributions revendiquées — HarnessCritic et le couplage — ne sont donc jamais isolées.
  • Le harness d'évaluation bouge avec le modèle. Chaque ligne est mesurée sous son propre harness. Les +20.4 pp mélangent donc (a) du gain de poids et (b) du gain de scaffolding pur à l'inférence, sans aucune décomposition. Une partie du « compounding self-improvement » peut n'être que du prompt/middleware engineering mesuré à l'inférence.
  • La réponse des auteurs — « Harness Debt analysis » [§5] — ne teste pas ce qu'elle prétend tester. Ils posent exactement la bonne question : si les trajectoires sont collectées sous un scaffolding qui compense les faiblesses du modèle, le modèle entraîné pourrait sur-dépendre de ce scaffolding et sous-performer au test sans harness. Puis ils concluent que Co-Harness réduit la Harness Debt au motif que « the model trained on HarnessCritic-evolved trajectories achieves higher absolute accuracy at test time each round », en citant le 8B sur AIME25 (56.9 → 78.3, +21.4 pp) comme « genuine skill acquisition rather than mere Harness memorization ». ⚠️ Non-sequitur. Toutes ces mesures sont prises avec le harness évolué. Aucune évaluation sans harness, ni sous harness gelé, n'est jamais effectuée. Une accuracy qui monte sous un harness qui s'améliore en même temps est exactement ce qu'on observerait aussi dans le pire cas de Harness Debt. La seule expérience qui trancherait — évaluer $\theta_2$ sous $\phi_0$ (ou sans harness) — n'est pas faite, alors qu'elle est quasi gratuite : une passe d'éval, aucun entraînement.
  • Les auteurs nomment eux-mêmes les instabilités du couplage [§5, « When does co-evolution fail to compound? »], sans les mesurer : (1) SFT plateau (saturation du modèle, le round suivant retombe dans la même distribution d'échecs — « hints of this for 8B on AIME24 », cohérent avec R1 84.0 → R2 84.7) ; (2) Harness over-patching (accepter trop de diffs tôt introduit une complexité qui submerge un modèle faible) ; (3) Attribution cascade (un diff qui répare un défaut en introduisant un autre complexifie la distribution d'échecs du round suivant ; le registry versionné permet le rollback). Ce sont exactement les bons modes d'échec du couplage. ⚠️ Aucun n'est instrumenté, aucun n'a de métrique, aucun n'a de fréquence rapportée.

In-distribution vs OOD

  • Aucune mesure OOD. Les trois benchmarks sont la même distribution : math de compétition américaine, réponse entière, sous le même harness TIR. AIME24 / AIME25 / HMMT25 varient en difficulté, pas en domaine. Le papier ne présente d'ailleurs jamais ces benchmarks comme un test de généralisation.
  • Aucun transfert mesuré vers un autre environnement, un autre type de tâche, ou un autre harness. Pas de SWE-bench, pas de web, pas de tool-use général — alors que §3.1 mentionne « resolve rate » et que §6 cite SWE-smith et AgentTuning comme les paradigmes à harness figé que Co-Harness dépasserait.
  • Aucune évaluation du harness évolué sur un autre modèle (transférabilité de $\phi^\star$ entre Qwen3-8B et Qwen3-32B) — expérience naturelle, quasi gratuite, non faite. Elle aurait directement répondu à « le harness encode-t-il quelque chose de général ou compense-t-il ce modèle précis ? ».
  • Aucune évaluation sans harness / sous harness gelé (voir ci-dessus). ⚠️ C'est la mesure de transfert la plus importante pour un papier dont la thèse est la co-évolution, et elle est absente.

Ablations

Aucune. Rien n'isole : ni HarnessCritic vs mutation aléatoire du harness, ni la valeur de la taxonomie structurée vs attribution en langage libre, ni l'effet de $K$, ni l'effet de la règle d'acceptation $\delta_{\mathrm{in}}>0 \wedge \delta_{\mathrm{out}}\geq 0$ vs acceptation inconditionnelle, ni la contribution respective des 5 dimensions $(\texttt{P},\texttt{T},\texttt{S},\texttt{Mid},\texttt{M})$. Ce que l'étude de cas vaut quand même (§4.3, App. F). Qualitativement, c'est la partie la plus informative, et honnête dans sa narration : 22 versions, rollback de régression détecté, arbitrage accuracy/latence sous contrainte explicite de budget. Trois observations réutilisables : 1. Le critic passe l'essentiel de son temps sur de l'infra, pas sur de l'agent design : mismatch gpu_util vllm (crash en 32 s), zombie threads → passage ThreadPool → ProcessPool avec cleanup SIGKILL, batching global. Ce sont des tâches de SRE. ⚠️ Le fait que la config initiale d'un papier plante en 32 s en dit plus sur la fragilité du harness de départ que sur la puissance du critic. 2. Une régression de prompt coûte cher et n'est détectable que par re-rollout : v20–v22, un system prompt domain-specific « conflicted with Qwen3's internal reasoning format » et a coûté ~16.5 pp ; seule la validation par re-rollout l'a rattrapé, classée prompt_ambiguity et rollback [App. F]. C'est le datum le plus transférable du papier : des edits de harness qui paraissent sensés sont fortement négatifs, et rien d'autre qu'une mesure empirique ne les distingue. 3. Le gain d'accuracy net des Phases 2–3 est nul : v5 (Phase 1) atteignait déjà 63.3 %, le résultat final est 63.3 % — 200 h ont acheté de la latence (sous budget), pas de la qualité. Non relevé par les auteurs.

« Geler ou alterner » : ce que ce papier conclut, et si c'est étayé

  • Ce qu'il conclut. Alterner. « Current paradigms either freeze the Harness (SWE-smith, AgentTuning) or freeze the model (ADAS, OPRO); Co-Harness is the first framework to co-evolve both, realizing the compounding self-improvement that neither alone can achieve » [§6]. Le mécanisme revendiqué : un meilleur harness produit de meilleures trajectoires → un modèle plus fort → qui débloque de nouvelles opportunités de harness [§1, §3.6].
  • Précision utile : « alterner » ici veut dire gel strict par blocs, pas simultanéité. Dans chaque phase, un côté est totalement gelé. Le papier ne teste jamais une optimisation conjointe réelle. La bonne lecture n'est donc pas « geler vs alterner » mais « geler définitivement vs geler à tour de rôle ».
  • Est-ce étayé ? Non. Trois raisons, par ordre de gravité : 1. La cellule décisive manque. Le papier compare la co-évolution à Human et R0, tous deux sans aucun SFT. Il n'existe aucun bras « harness gelé à $\phi_0^\star$ + 2 rounds de SFT ». La conclusion soutenue par les données est « faire quelque chose bat ne rien faire », pas « alterner bat geler ». 2. L'éval bouge avec le traitement. Chaque round est évalué sous son propre harness, donc les +20.4 pp mélangent gain de poids et gain de scaffolding à l'inférence, sans décomposition. On ne sait même pas quelle fraction du résultat vient du modèle. 3. Le seul argument contre la Harness Debt est circulaire. §5 affirme que Co-Harness réduit la Harness Debt parce que l'accuracy monte — mesurée sous le harness évolué. L'expérience qui trancherait (évaluer $\theta_2$ sous $\phi_0$, ou sans harness) n'est pas faite, alors qu'elle coûte une passe d'éval.
  • Ce que le papier étaye réellement, et c'est non trivial : (a) un harness auto-évolué peut dépasser un harness humain statique à modèle gelé (Human 54.2 → R0 58.5, +4.3 pp moyens, le seul comparatif propre du papier) ; (b) des edits de harness apparemment sensés peuvent coûter ~16.5 pp, et seule une validation par re-rollout les rattrape [App. F] ; (c) les gains de rounds successifs décroissent vite (+15.0 puis +5.4 pp).
  • ⚠️ Ma position pour Gemini Law. Ce papier ne justifie pas d'alterner. Il justifie de figer le harness pendant le post-training, et de faire l'évolution de harness comme une phase séparée, explicitement datée et versionnée, à poids gelés. Raisons propres au juridique : (i) notre vérifieur sera un juge LLM/rubrique, beaucoup plus bruité que pass@1 sur AIME — la règle d'acceptation δ>0 y sélectionnerait massivement du bruit ; (ii) avec du RLVR (et non du SFT hors ligne), un harness mouvant déplace la distribution des rollouts en cours d'entraînement, ce que ce papier ne teste pas ; (iii) Harvey LAB et Vals sont des évals fixes : co-évoluer le harness contre elles, c'est fitter le scaffolding sur le benchmark — exactement ce que ce papier fait sur AIME24 (200 h, 22 versions) sans le reconnaître. Le seul cas où alterner devient intéressant est celui que le papier ne teste pas : quand le modèle post-trained révèle des goulots de harness qui n'existaient pas avant. Cela se vérifie à moindre coût par une passe d'attribution après entraînement, sans boucle.

Meilleur ingrédient à transposer

La taxonomie d'attribution structurée avec abstention explicite + le gate de non-régression $\delta_{\mathrm{out}} \geq 0$ sur une suite de régression figée [Tab. 2, §3.3, App. E]. Pourquoi : c'est le seul élément qui répond à une question qu'on se posera de toute façon dès les premières semaines — cet échec vient-il du modèle ou du scaffolding ? — et qui empêche d'entraîner le modèle sur des échecs que du prompt/tool engineering réglerait en une heure. La catégorie agent_error, qui exclut le cas de la génération de patch, est le bon garde-fou : elle interdit au critic de patcher le harness pour masquer une faiblesse du modèle. En juridique ce partage est plus dur (un échec de retrieval et un échec de raisonnement se ressemblent dans une trace) et donc plus utile. Le registry versionné vient gratuitement avec, et est une exigence d'audit en droit.

Expérience minimale

Deux passes d'éval, zéro entraînement — l'expérience que Co-Harness aurait dû faire. 1. Annoter 150–200 trajectoires d'échec de notre agent juridique courant (sur un dev set interne, pas LAB/Vals) avec une taxonomie à 6 catégories : retrieval_miss, citation_unverified, jurisdiction_mismatch, prompt_scope, context_overflow, model_error. Double annotation par 2 juristes + arbitre, mesure de $\kappa$ — puis, contrairement à l'App. D du papier, publier en interne l'accord juge-LLM ↔ humain. 2. Lire la part de model_error. Résultat attendu : si model_error < 50 %, le post-training n'est pas encore le goulot et une passe de harness engineering est plus rentable — c'est la thèse de Co-Harness, et elle vaut d'être vérifiée avant d'engager du compute RL. Si model_error > 70 %, la boucle harness ne vaut pas son coût et on gèle le harness. 3. Test décisif « geler ou alterner », que le papier n'a pas fait : après un premier round de post-training, réévaluer $\theta_1$ sous le harness $\phi_0$ d'origine. Coût : une passe d'éval. Si $\theta_1$ sous $\phi_0$ conserve l'essentiel du gain → le gain est dans les poids, on peut geler le harness sans rien perdre. Si le gain s'effondre → Harness Debt réelle, et il faut soit alterner, soit entraîner sous randomisation de harness. C'est l'expérience la moins chère de tout ce mémo et elle tranche directement le débat.

Question à poser en interne chez GDM

Deux : 1. Le harness d'éval de Harvey LAB / Vals est-il contractuellement figé de notre côté ? Si nous pouvons modifier prompts, outils et politique de retrieval entre deux soumissions, une partie de nos gains rapportés sera du harness engineering et non du post-training. Il faut un harness d'éval gelé et versionné (le registry de l'App. E est le bon format), sous peine de ne plus pouvoir attribuer nos propres progrès — c'est exactement l'ambiguïté qui rend le +20.4 pp de ce papier ininterprétable. 2. Qui possède le harness ? Si l'équipe produit itère sur le scaffolding pendant que nous itérons sur les poids, nous sommes dans la situation de ce papier sans l'avoir choisie : deux choses bougent, aucune attribution possible. Il faut au minimum un protocole de gel pendant les fenêtres de post-training et une suite de régression partagée.
