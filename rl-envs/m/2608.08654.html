0. En une phrase

TL;DR — étude contrôlée : sur une tâche logicielle fixe (6 opérations contre un dépôt GitHub privé), le scaffolding qui pilote l'agent explique un facteur ~20 sur le coût en tokens d'input, alors que la comparaison MCP vs CLI qui motivait l'étude sort inconclusive (13 ratios appariés de 0,43× à 29,06×, médiane 0,93) [Tab. 1, §4.1].

Claim principal, formulé précisément : 1. Claim fort — deux scaffoldings sans client MCP (pi, Tau) complètent 4/4 runs avec git/gh/shell : un catalogue MCP n'est pas nécessaire pour cette classe de travail [§9.1, Tab. 1]. 2. Claim quantitatif — à interface tenue constante (arm CLI seul, aucun serveur MCP attaché nulle part), ces deux scaffoldings coûtent 5,0× à 28× moins cher que les cinq scaffoldings MCP-capables [Tab. 2, §9.1]. Les auteurs précisent eux-mêmes que c'est une comparaison entre deux populations de scaffoldings, pas l'isolation d'une feature [§3.2, §8]. 3. Claim méthodologique — les deux arms se séparent sur le coût de l'échec (12,9 % de l'argent MCP dépensé pour rien contre 2,2 % côté CLI) et non sur sa fréquence (3/19 dans chaque arm) [Tab. 6]. 4. Claim d'instrumentation — les agents ignorent fréquemment l'interface qui leur est assignée ; toute comparaison qui ne vérifie pas le comportement réel mesure un mélange inconnu [§7, §9.5].

⚠️ Aucun RL, aucun reward, aucun entraînement. L'intérêt pour nous est harness + vérification + coût de rollout, pas l'optimisation.

1. Tâches & data

Origine des tâches — une tâche unique, écrite à la main par les auteurs, après trois itérations de design : la première (4 tool calls) « proved far too easy », la deuxième « impossible for most of the agents », la troisième retenue [§2].

La tâche — six opérations contre un dépôt git privé hébergé sur GitHub [§2.1] : 1. localiser une issue ouverte donnée ; 2. créer une branche ; 3. appliquer un patch fourni à un fichier ; 4. committer le changement ; 5. ouvrir une pull request depuis cette branche ; 6. rapporter le nombre de fichiers que contient un répertoire nommé.

Critère de choix explicite : faisable en une seule session par un modèle capable, exige à la fois du travail fichier local et des appels de service distant, et chaque étape laisse une trace durable vérifiable après coup [§2.1].

Volume — matrice principale de 54 cellules (7 scaffoldings × 5 modèles × 2 arms, couverture partielle), dont 8 cellules marquées void (pi et Tau n'ont pas de client MCP, leur arm MCP ne peut pas exister) → 46 runs exécutés, 40 complétés [§3 p. 10, Tab. 1, App. A]. Couverture non uniforme : tous les modèles n'ont pas été passés sur tous les scaffoldings [§2.5, Tab. 1] ; Claude Code n'apporte que 6 runs contre 8 pour la plupart [§8 p. 21].

Réplication — chaque configuration à modèle servi localement rejouée 3 fois, rien changé entre répétitions → second jeu de 90 runs, 70 exécutés, 61 complétés [§2.9, §8.1]. Les configurations hostées n'ont pas été répétées (budget), sauf deux cellules rejouées incidemment [§8 p. 21].

Expérience compagnon d'adhérence — même famille de tâche contre un dépôt public, 21 runs avec serveur MCP attaché et connexion confirmée ; inutilisable pour le coût (plusieurs routes vers le dépôt) mais informative sur le comportement [§7].

Distribution de difficulté — inexistante : une seule tâche, un seul domaine, limite reconnue par les auteurs [§8 « One task, in one domain »]. Les auteurs notent que GitHub est un cas favorable au CLI puisqu'il a un client en ligne de commande mature ; un domaine où MCP exposerait une opération sans équivalent CLI favoriserait MCP davantage [§8].

Filtrage / curriculum / contamination / données SFT — non applicable : aucun entraînement, aucun échantillonnage de tâches. Contamination : hors sujet ici, mais ⚠️ une tâche GitHub standard est massivement représentée dans les corpus de pré-entraînement — les auteurs en font d'ailleurs un argument (§1.2, asymétrie de familiarité shell vs schémas d'outils, citant Steinberger 2026 « as a hypothesis, not as evidence »).

Séparation train/test — n.a.

Coût humain — heures d'annotation : non précisé. En revanche le coût de production de l'étude est publié [§2.10] : 8 jours en août 2026, deux sessions Claude Code (2 222 puis 1 388 tours assistant), 1 660 933 432 tokens d'input agrégés, 3 798 219 d'output, cache = 97,1 % de l'input, input non caché = 6 805 tokens sur 8 jours, ratio input/output 437:1. ⚠️ Ces totaux excluent les runs de benchmark eux-mêmes, et la session était encore en cours lors du relevé [§2.10].

2. Environnement / harness

Observation — le papier ne reproduit aucun prompt ni aucune trace : le contenu exact de ce que voit le modèle à chaque tour est non précisé. Seuls sont mesurés, au proxy, les agrégats par requête [§2.5].

Espace d'actions et outils — deux arms au sens essai clinique [§2.4] : - MCP arm : le serveur GitHub MCP officiel est attaché ; il publie 44 outils couvrant issues, branches, commits et pull requests [§2.4]. La liste et les signatures ne sont pas recopiées dans le papier — non précisé au-delà du nombre. - command-line arm : aucun serveur MCP attaché ; l'agent dispose de son shell et du client gh [§2.4]. Écrire gh pr create --title ... --body ... et l'exécuter est l'action canonique [§1.1].

Nombre de schémas transmis par requête — c'est la variable la plus utile pour nous, et elle varie d'un facteur 6 à protocole identique [§4.3, Tab. 5, App. A] :

Scaffolding Schémas, arm MCP Schémas, arm CLI
Claude Code 74 (27 built-in + 3 lecture de ressources MCP + 44 du serveur) 27 (~22 k tokens avant que la tâche ait commencé)
opencode 57 10
Hermes 7 (gateway pair : un outil qui liste et décrit, un qui invoque par nom ; les 42 descriptions restantes fetchées à la demande) 6
Codex, qwen-code non rapportés (« — » dans App. A) non rapportés

Single/multi-turn — multi-turn, un seul run par session, pas de reprise. Nombre de tool calls observés : de 3 (Claude Code / qwen27b / cli) à 108 (Codex / qwen27b / mcp) [App. A]. Horizon maximal, budget de tours, politique de troncature ou de résumé du contexte : non précisé.

Exécution — un unique script shell d'orchestration : reset du fixture → sélection d'une cellule (scaffolding, modèle, arm) → invocation de l'agent en sous-processus → collecte de la sortie → appel du vérifieur [§2.7, Fig. 1 p. 7]. Chaque scaffolding est atteint identiquement par une ligne de commande ; critère de sélection : mode non interactif, endpoint modèle arbitraire pour tenir le modèle fixe [§8 p. 21].

Instrumentation — toutes les requêtes de tous les scaffoldings sont routées par un proxy LiteLLM local unique, qui enregistre par requête : input tokens, cached tokens, noms des tool calls, schémas par requête [§2.5, Fig. 1 p. 7]. Raison explicite : certains scaffoldings délèguent à des sous-agents, dont la consommation échapperait au comptage et ferait paraître bon marché un scaffolding coûteux [§2.5]. Exception : deux cellules Claude Code tournent sur un compte à abonnement qui s'authentifie chez son seul fournisseur et auto-rapportent ; validation : sur les douze runs Claude Code proxyfiés, l'auto-comptage du scaffolding et le proxy coïncident au token près, dans les deux sens, sur des runs d'un quart de million de tokens [§2.5].

Déterminisme / reset — le dépôt est restauré à son état initial avant chaque run, pour qu'un travail laissé par un run ne soit pas crédité au suivant [§2.2]. Déterminisme des modèles (température, seed) : non précisé.

Isolation des arms (le point le plus transférable) — en arm CLI, aucun serveur MCP n'est configuré ; en arm MCP, le serveur porte son propre credential tandis que le shell de l'agent pointe vers un répertoire de configuration vide, sans credentials, si bien qu'un repli sur gh échoue visiblement plutôt que de réussir en silence [§2.4]. Effet mesuré : après isolation, les 25 runs CLI de la matrice principale dont les tool calls ont été enregistrés n'ont utilisé que la ligne de commande [§7].

Gestion des erreurs — deux corrections de mesure documentées [§2.6] : 1. La vérification comptait initialement cinq conditions ; la cinquième comparait la PR à un numéro d'issue donné, mais la routine de reset réassignait un nouveau numéro d'issue à chaque run — condition insatisfaisable par construction. Toutes les complétions du papier sont recalculées sur les 4 conditions réellement satisfiables. 2. Dans un fichier de configuration, le credential du serveur MCP était écrit sous une forme de variable que le scaffolding n'expand que entre crochets : le serveur a démarré avec le nom du credential à la place de sa valeur et a été refusé par l'API à chaque appel. ⚠️ Vu de l'extérieur, le run était indistinguable d'un run normal : serveur attaché, catalogue transmis en entier, outils MCP appelés, complétion partielle, coût d'apparence ordinaire, aucune erreur dans l'enregistrement. Seul le message de clôture de l'agent, nommant la variable non expansée, trahissait la panne.

Règle qui en découle — « When a run failed because of an error in our setup or configuration, we fixed the error and repeated the run » [§2.6]. Impact chiffré : cette seule cellule, comptée comme échec, portait la part de coût gaspillé de l'arm MCP au-dessus de 40 % ; corrigée et rejouée 3 fois, elle complète à chaque fois et la part tombe à 12,9 % [§2.6, Tab. 6]. Les auteurs en font une recommandation générale : séparer les échecs de l'appareil de mesure des échecs de l'objet mesuré, et rejouer les premiers [§9.5].

Exemple de trajectoire — non fourni (aucune trace recopiée). Le plus proche : la description du failure mode de Tau en §8.1 (voir §3).

3. Reward / vérifieur

⚠️ Il n'y a pas de reward : c'est un vérifieur d'évaluation. Mais sa conception est exactement ce qu'on voudrait dans un env RL.

Type — vérification programmatique de l'état externe, par interrogation du dépôt via l'API GitHub après chaque run [§2.2]. Aucun juge LLM, aucun reward model, aucun exact match sur la sortie textuelle.

Quatre conditions indépendantes [§2.2] : 1. la branche existe ; 2. le fichier contient le contenu patché ; 3. une pull request a été ouverte ; 4. le nombre de fichiers rapporté est correct.

Granularité — crédit partiel : Completion = pourcentage des quatre conditions satisfaites [§2.2] ; App. A rapporte effectivement 25 % / 50 % / 75 % / 100 % par run. Mais la colonne « Completed » de Tab. 1 et les analyses de coût utilisent le seuil binaire strict « les quatre conditions satisfaites » [Tab. 1, légende Fig. 2]. Bon découplage : deux granularités, explicitement séparées.

Principe directeur, énoncé deux fois — « We did not ask the agent whether it had succeeded » [§2.2] ; justification : « an agent that believes it succeeded and an agent that did succeed produce identical prose » [§1.3]. Corollaire opérationnel : « A run that reports success but leaves no branch behind scores nothing for that condition » [§2.2].

Fiabilité du vérifieur — pas d'accord inter-annotateur mesuré (il n'y a pas d'humain dans la boucle) ; le vérifieur est déterministe et son code est publié [§9.5]. Le papier fournit en revanche un cas réel qui valide le choix de design [§8.1 p. 21] : Tau, sur le modèle 27B, a ouvert une pull request et rapporté correctement le nombre de fichiers sans jamais créer la branche ni appliquer le patch — 2/4 conditions, aucune erreur levée, sortie propre. Les auteurs : « it is precisely the failure mode that verification by repository inspection exists to catch — an agent that reports success and leaves no trace would pass any check that read only its own account of itself ». ⚠️ C'est le seul faux positif documenté, et il n'est visible que parce que la vérification est externe.

Termes additionnels — aucun (pas de format reward, pas de pénalité de longueur). Règle de comptabilité explicite, et importante [§2.8] : - le coût est calculé uniquement sur les runs ayant complété (« the question "what did this job cost" has no answer where the job was not done ») ; - la complétion est rapportée séparément, jamais repliée dans un coût ; - une condition sans run complété est marquée indéfinie, jamais imputée ; - le coût de l'échec est traité à part, sur tous les runs, rien exclu [§4.4, Tab. 6].

Si juge LLM — n.a., aucun juge.

Robustesse / anti-hacking — le vérifieur n'a pas été attaqué délibérément. Mais deux mécanismes anti-contournement existent de fait : - isolation par configuration plutôt que par prompt : ajouter au prompt une instruction nommant l'interface disponible et enjoignant de l'utiliser « did not change this behaviour materially » ; retirer les credentials de l'alternative, si [§7]. Formule des auteurs : « Configuration proved more effective than instruction » [§7]. - vérification par état externe : rend inopérant le contournement le plus naturel (déclarer le succès).

⚠️ Reste hackable en principe : rien n'empêche un agent de satisfaire les 4 conditions par un chemin illégitime (ex. §7 : quatre runs ont contourné les deux interfaces et interrogé l'API web GitHub directement en HTTP) — le vérifieur note l'état final, pas le chemin. En éval c'est correct ; en RL ce serait une porte de reward hacking.

In-distribution vs OOD, transfert

Aucun transfert mesuré : une tâche, un domaine, un service (GitHub) [§8]. Les auteurs identifient eux-mêmes la limite de portée : le claim « MCP n'est pas nécessaire » ne s'étend pas aux services sans client CLI mature [§9.1]. Généralisation la plus large qu'ils s'autorisent : playwright et le serveur MCP Playwright exposent substantiellement les mêmes opérations [§3.2] — argument d'existence, pas une mesure.

Ablations

  • Scaffolding isolé (interface fixée à CLI, aucun MCP nulle part) : Tab. 2 → facteur 28. C'est l'ablation qui porte le claim central.
  • Interface isolée (scaffolding fixé, arms variés) : Tab. 3 + 13 paires strictes → 0,43–29,06, inconclusive.
  • Méthode de livraison du catalogue : Tab. 5 → ×3,1, mais confondue (n=1 scaffolding).
  • Caching : Tab. 4, deux hypothèses de facturation (list price / −90 % sur le cache) → les deux arms restent proches sous l'une comme sous l'autre.
  • ⚠️ Ablation manquante : les deux contrôles (pi, Tau) diffèrent des quatre autres « in ways we did not measure » [§8 p. 22] — l'avantage de Tab. 1 ne peut pas être attribué à l'absence de MCP seule. Les auteurs le disent explicitement.
  • Contrôle de réimplémentation : Tau est une réimplémentation indépendante, en Python, par d'autres auteurs, de la philosophie de pi ; leur accord à 12 % près (14 660 vs 16 459) est traité comme preuve que le résultat tient au design et non à une implémentation [§2.3, §3].

Scaling

Effet de la taille du modèle : l'écart entre scaffoldings est maximal sur le plus petit modèle (27B, ×139) [§6, §9.3], ce qui va à l'encontre de l'attente « les petits modèles ont besoin de plus de support ». Lecture des auteurs : la généralité a un coût de fonctionnement payé par tâche qu'elle serve ou non, et les petits modèles le paient au taux le plus fort [§9.3]. Pas de scaling en nombre de tâches (n=1) ni en compute.

Solidité

  • ✅ Baselines appariées : tâche, dépôt, vérification, proxy et grille de prix identiques dans toutes les cellules ; versions de scaffolding listées [§1.3, §2.3, §2.5].
  • ✅ Ablations qui isolent : Tab. 2 isole le scaffolding à interface fixe, Tab. 3 isole l'interface à scaffolding fixe. Les deux isolations existent et pointent en sens opposés — ce qui est précisément le résultat.
  • ✅ Variance : réplication ×3 sur toutes les configurations locales, spread publié (médiane 1,51×, pire 5,41×), et la résolution de l'étude est énoncée comme règle de lecture : « a difference smaller than roughly twofold cannot be distinguished from run-to-run variation » [§8.1]. ⚠️ Les configurations hostées restent à un run.
  • ❌ Cohérence texte↔tableaux : §2.8 contredit §4.4 sur la médiane des runs échoués et complétés ; §4.2 contredit Tab. 4 (« twice the tokens » = 1,57×, « half as much again » = +20 %) ; les catégories de §7 somment à 25 sur 21 runs ; App. A p. 26 a six lignes superposées et illisibles. Les chiffres de l'abstract, eux, tiennent tous.
  • ✅ Fiabilité de l'éval : vérification déterministe par état externe, jamais par self-report ; fixture reset avant chaque run ; pas de juge LLM donc rien à valider contre des humains ; double comptabilisation (proxy vs auto-report) concordante au token près sur 12 runs [§2.2, §2.5].
  • ⚠️ Échelle : 46 runs live, 40 complétés, une tâche. Plusieurs conclusions reposent sur 2 à 4 runs (Claude Code : 2 runs complétés en arm CLI) ; 6 échecs au total portent toute l'analyse de §4.4 — « whether it is a property of the interface or an accident of which six runs failed, six runs cannot say » [§4.4].
  • ✅ Reproductibilité : harness, tâche, code de vérification et dataset run-par-run publiés, GPL-3.0, Zenodo DOI ; les tableaux d'App. A sont générés par bench/appendix_v9.py depuis le dataset plutôt que maintenus à la main [§1.3, App. A].

Verdict

Solide sur son claim étroit, honnête sur ses limites, trop petit pour le claim large. La discipline méthodologique est au-dessus de la moyenne du domaine : arms isolés par configuration et non par prompt, vérification externe, échecs d'appareil séparés des échecs d'objet, résolution de l'étude publiée avant les conclusions, refus explicite d'attribuer l'effet de Tab. 5, et publication intégrale du dataset. Les défauts sont l'échelle (n=1 tâche, 40 runs complétés) et un relâchement de rédaction sur plusieurs chiffres secondaires (voir 7.0), qui n'atteint pas l'abstract mais entame la confiance.

Grille evidence — 5/6 1. baselines ✅ — tâche/vérification/prix/proxy identiques partout, versions listées [§1.3, §2.3]. 2. ablation ✅ — Tab. 2 isole le scaffolding, Tab. 3 l'interface. 3. variance ✅ — 3 répétitions sur toutes les configs locales, spread 1,51×/5,41× publié [§8.1]. 4. coherence ❌ — §2.8 vs §4.4, §4.2 vs Tab. 4, comptages de §7 non additifs, App. A p. 26 illisible. 5. eval ✅ — vérifieur déterministe sur état externe, reset systématique, double comptabilisation concordante. 6. repro ✅ — code + harness + dataset + DOI Zenodo, tableaux régénérables.

Meilleur ingrédient à transposer — le vérifieur par inspection de l'état externe, décomposé en conditions booléennes indépendantes, avec crédit partiel et seuil strict tenus séparés. Le droit n'a pas de vérifieur exact sur la réponse finale, mais il a beaucoup d'état vérifiable autour d'elle : la citation existe-t-elle dans la base ? pointe-t-elle le passage invoqué ? la juridiction et la date de version sont-elles les bonnes ? le format procédural est-il respecté ? Ces conditions se vérifient par API contre un corpus, de façon déterministe et reproductible, exactement comme les 4 conditions GitHub. Le cas Tau [§8.1] est l'argument décisif : un agent peut produire une sortie parfaitement plausible (PR ouverte, chiffre correct, sortie propre, aucune erreur) sans avoir fait le travail — c'est le mode d'échec dominant attendu d'un agent juridique, et seul un vérifieur externe l'attrape.

Second ingrédient, plus immédiatement monnayable en RL : le catalogue d'outils à la demande. En RLVR multi-turn, les schémas d'outils sont retransmis à chaque tour et leur coût est multiplié par le nombre de tours [§4.5]. Un gateway pair (lister/décrire + invoquer par nom) à 7 schémas contre 44 divise l'input par ~3 [Tab. 5] — c'est du budget de rollout récupéré à politique inchangée.

Expérience minimale — sur notre harness juridique, tenir tout constant (tâches, modèle, vérifieur, budget de tours) et ne faire varier que la livraison du catalogue : (a) N outils de recherche juridique exposés intégralement à chaque tour, (b) 2 outils de gateway + fetch à la demande. Mesurer input tokens par rollout, tours jusqu'à complétion, et taux de succès du vérifieur. Résultat attendu, en transposant [Tab. 5] : facteur 2–3 sur l'input par rollout à taux de succès inchangé, donc 2–3× plus de rollouts à budget constant. Prérequis imposé par [§8.1] : répéter chaque configuration au moins 3 fois et publier le spread avant de conclure — sous 2× d'écart, rien n'est distinguable du bruit. Coût : faible, aucune modification de l'algorithme.

Expérience de contrôle, encore moins chère — rejouer le test de §7 chez nous : vérifier, sur les traces, quels outils l'agent a réellement appelés plutôt que ceux qu'on lui a donnés. Si le taux de contournement est non nul (le papier trouve 6/21 runs utilisant exclusivement l'interface assignée), toutes nos ablations d'outillage mesurent un mélange inconnu.

Question à poser en interne chez GDM — deux : 1. Sur le harness Gemini Law, compte-t-on les schémas d'outils transmis par tour, et sont-ils retransmis intégralement à chaque tour du rollout ? Si oui, quelle fraction du coût d'un rollout est du catalogue re-facturé, et un mécanisme de fetch à la demande est-il envisageable côté serveur d'outils ? 2. Le vérifieur d'entraînement lit-il un état externe (base documentaire, corpus de citations) ou la sortie de l'agent ? Si c'est la sortie, le failure mode de Tau — réponse plausible, travail non fait, aucune erreur levée — est structurellement invisible, et c'est la première chose que RL apprendra à exploiter.
