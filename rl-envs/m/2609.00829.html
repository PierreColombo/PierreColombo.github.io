0. En une phrase

TL;DR — Boucle de self-evolution de harness (prompts, skills, scripts, descriptions d'outils, code d'exécution) sans gradient, à LLM gelé, dont l'ingrédient distinctif est la reference trajectory : le même agent d'exécution rejoue chaque tâche d'entraînement en lui donnant la réponse ground-truth, un juge vérifie que la trajectoire n'est pas un court-circuit, puis les échecs sont diffés contre cette référence pour localiser le premier point de divergence d'action et en faire le root cause [§3.2, §3.4, Alg. 1].

Claim principal — Sur 5 benchmarks × 2 modèles, HarnessEvolve bat GEPA / ACE / SkillOpt partout en accuracy ; le gain le plus fort est +21,6 pt d'accuracy absolue sur CloudCoreNetwork-QA face au meilleur baseline, avec Qwen3.6-27B (86,9 vs GEPA 65,3) [Tab. 1, §4.2]. Les auteurs attribuent l'essentiel à la diagnose guidée par référence : l'ablater fait chuter de 86,9 à 57,8 [Tab. 4].

⚠️ Papier sans RL au sens gradient : aucune mise à jour de poids, aucun advantage, aucun reward scalaire propagé. À lire comme harness engineering / RSI, pas comme RLVR. Sa valeur pour la revue est le protocole de sélection d'une variante de harness, pas l'optimisation.

1. Tâches & data

Origine des tâches — Aucune tâche construite par les auteurs pour les 3 datasets open-source : SearchQA [dunn2017searchqa], OfficeQA (« OfficeQA Pro », benchmark entreprise de grounded reasoning, arXiv 2603.08655 [opsahl2026officeqa]), SpreadsheetBench [ma2024spreadsheetbench]. Deux datasets in-house : CloudCoreNetwork-QA et Wireless-QA, « constructed from cloud core network and wireless network domains », tâches de QA réseau et text-to-SQL (requêtage de KPI, requêtage de configuration d'éléments réseau) ; les requêtes « require selecting and combining multiple skills » [§4.1].

Pipeline de construction des datasets in-house — non précisé. Ni source, ni annotateurs, ni schéma SQL, ni procédure de validation des ground-truth. ⚠️ C'est le dataset qui porte le résultat vedette (+21,6 pt) et il est entièrement opaque.

Volume — non précisé pour les 5 datasets : ni |T_train|, ni |T_val|, ni |T_test|. Seul indice indirect : batch size b = 40 [§4.1], donc T_train ≥ 40. ⚠️ Impossible d'estimer la taille de la validation sur laquelle se fait la sélection de snapshot en fin d'epoch — point critique, voir §7.

Distribution de difficulté — non précisé. Aucune statistique (longueur de trajectoire, nombre d'outils requis, pass@k du modèle de base).

Filtrage — Aucun filtrage des tâches d'entraînement par pass@k ou par difficulté. Le seul filtrage du corpus est indirect : les tâches pour lesquelles les T_att = 5 tentatives de génération de référence échouent (mauvaise réponse ou rejet par A_eval) « fall back to single-trajectory analysis » [§3.2] — elles restent dans T_train mais avec un signal dégradé. ⚠️ La fraction de tâches effectivement dotées d'une référence n'est jamais rapportée : c'est le chiffre manquant le plus important du papier, puisque l'ablation M1 (−29,1 pt) mesure l'effet de supprimer un ingrédient dont on ignore la couverture.

Curriculum — Pas de curriculum par difficulté. Permutation aléatoire à chaque epoch : B ← PermuteAndPartition(T_train, b) en tête de chaque epoch [§3.1, Alg. 2 l. 4]. Rééchantillonnage : seulement via le replay buffer du performance gate, R = 2 batches récents rejoués pour tester la non-régression [§3.5, §4.1].

Contamination / séparation train-test — « All methods use the same training, validation, and test split on each dataset » [§4.1]. Aucune discussion de contamination (SearchQA et SpreadsheetBench sont publics et antérieurs aux modèles ; aucune décontamination mentionnée). ⚠️ Risque structurel supplémentaire spécifique à ce cadre : le harness final est sélectionné en maximisant l'accuracy sur T_val parmi tous les snapshots du pool V accumulés sur jusqu'à 20 epochs [Alg. 2 l. 32] — surapprentissage de la validation non quantifié (aucun écart val/test rapporté).

Données SFT/IFT avant — Qwen3.6-27B est « post-trained with domain-specific fine-tuning » [§4.1] ; source, volume, rôle : non précisé. DeepSeek-V4-Flash est utilisé sans fine-tuning [§4.1]. ⚠️ Asymétrie non contrôlée : le gain vedette (+43,5 pt Base→final sur CloudCoreNetwork-QA) est obtenu sur le modèle déjà fine-tuné sur le domaine, dont le Base part pourtant très bas (43,4).

Coût humain — Aucune annotation nouvelle décrite ; le pipeline consomme les ground-truth existantes. Coût humain d'écriture du harness initial (skills, AGENTS.md, SOUL.md, code projet) : non précisé, mais non nul — HarnessEvolve part d'un « initial harness » commun à toutes les méthodes [§4.1], jamais montré.

2. Environnement / harness

2.1 Ce qui est édité, à quelle granularité — le cœur du papier

Le harness est défini comme « prompts, skills, tools, and execution logic » [§1, §3.1]. Le périmètre éditable dépend du framework [§4.1] :

Framework Datasets Périmètre éditable
LAMAgent (in-house Huawei) CloudCoreNetwork-QA, Wireless-QA « the full project code, skills, prompts, and tools »
OpenClaw SearchQA, OfficeQA, SpreadsheetBench « skills, AGENTS.md, SOUL.md, and tools »

Contraste explicite avec SkillOpt, qui n'édite que skill.md : HarnessEvolve « optimizes the entire skill directory including reference files and scripts » [§4.1].

Granularité réelle — diffs ligne à ligne sur fichiers, six types documentés [App. A, Fig. 2] : - (a) skill.md / OfficeQA : réécriture de la description YAML et de règles numérotées (p. ex. ajout d'une règle « fix the percent-difference denominator : when a question asks for percent difference without naming a baseline, use the symmetric form |A−B|/((A+B)/2) ») ; - (b) skill.md / CloudCoreNetwork-QA : ajout d'un ordre d'exécution (dépendances séquentielles vs parallèles) et d'une checklist pré-réponse ; - (c) création de scripts Python dans le skill / SpreadsheetBench : ajout d'une fonction parse_range(spec, default_sheet) avec regex de parsing de plages 'S'!A1:B2 utilisant openpyxl.utils.column_index_from_string ; - (d) system prompt / CloudCoreNetwork-QA : injection d'une section « 常见错误模式（避免此行为）» — paires ❌/✅ très spécifiques au domaine (p. ex. « SQL COUNT 时必须添加 d.value IS NOT NULL 过滤空值 », distinction OVERTIME vs CLEARTIME) ; - (e) description d'outil (schéma JSON) / CloudCoreNetwork-QA : description de l'outil file-read étendue de « Read the content of a specified file in a sandbox environment. » à « … Use this to read SKILL.md documentation or configuration files. », et le champ file_path.description passe de « The path of the file to be written (absolute path must be used) » à « The absolute path of the file to read. Examples: /app/… » — ⚠️ correction d'un bug de copier-coller humain (« to be written » sur un outil de lecture) trouvée par la boucle ; - (f) code d'exécution Python / CloudCoreNetwork-QA : réécriture de la logique de retry « no tool call » — compteur no_tool_retries, détection <FINISHED> dans le contenu, injection d'un force_prompt (« [系统强制提示] 您的上一次响应没有调用任何工具… 严禁直接生成答案而不调用工具！ ») quand le modèle répond sans appeler d'outil.

Ce qui reste figé — les poids du LLM (« powered by a frozen LLM » [§3.1]) ; le framework hôte lui-même ; le pool d'outils existants (les outils sont réécrits en description/signature, aucune création d'outil nouveau n'est montrée, seulement création de scripts dans les skills [Fig. 2c]) ; les prompts des trois méta-agents A_eval / A_opt / A_gate — non précisé explicitement, mais rien n'indique qu'ils évoluent, et le papier insiste sur leur découplage structurel [§3.1, §3.5].

2.2 Les trajectoires de référence — l'ingrédient distinctif

  • Origine : générées par le modèle, pas par des humains. C'est le même agent d'exécution A_exec, avec son harness courant, à qui l'on donne « both the questions and their ground-truth answers » [§3.2]. Ce ne sont donc ni des démonstrations expertes, ni des traces d'un modèle plus fort.
  • Quand : « prior to the optimization loop », en une passe sur tout T_train [§3.2]. Cache global C, indexé par question [Alg. 1 l. 7]. Elles ne sont pas régénérées quand le harness évolue. ⚠️ Conséquence non discutée par les auteurs : les références deviennent progressivement obsolètes par rapport au harness courant — on diffe une trajectoire d'échec produite par le harness de l'epoch 12 contre une référence produite par le harness initial.
  • Combien : T_att = 5 tentatives max par tâche [§4.1]. Nombre / fraction de références effectivement obtenues : non précisé.
  • Comment elles guident l'évolution : A_opt reçoit (q_i, τ⁻_i, τ⁺_i) et produit un signal d'erreur structuré 𝓕_i = (s_i, m_i, h_i) = (sévérité, cause, hint de correction en langage naturel) ; avec référence, il localise en plus t*_i, le premier point de divergence d'action entre τ⁺ et τ⁻, et l'instruction est de le prioriser comme root cause, « since subsequent divergence points are likely cascading effects » [§3.4, principe « Root-Cause Priority »]. Exemples de causes cités : tool hallucination, argument omission, premature termination [§3.4].
  • Fallback sans référence : A_opt analyse τ⁻_i et q_i seuls, sans localisation de divergence [§3.4, Alg. 1 l. 9-10].
  • Garde-fou anti-court-circuit : A_eval vérifie que la référence est « a genuine execution path rather than a shortcut where the agent directly returns the known answer » — contrôle que l'agent « invokes appropriate tools, processes intermediate observations, and arrives at the answer through valid steps rather than trivially restating the provided answer » [§3.3]. Les non vérifiées sont rejetées, tentative suivante.

Agrégation — clustering des 𝓕_i par cause m_i (pas par sévérité) en groupes C_k = (s̄_k, m̄_k, ē_k, h̄_k) [§3.4]. Clustering fait par le LLM A_opt, pas par distance : les auteurs justifient explicitement d'éviter K-Means pour préserver les clusters à un seul membre (« Long-Tail Protection ») [§3.4]. A_opt est ensuite instruit de prioriser les clusters les plus peuplés et les plus sévères pour synthétiser Δ_harness [§3.4].

2.3 Harness d'exécution proprement dit

  • Observation / espace d'actions : formalisés seulement abstraitement, τ_i = [(o_1,a_1),…,(o_T,a_T)] [§3.2]. Contenu concret de o_t : non précisé.
  • Liste d'outils : non précisé globalement. Une seule signature complète apparaît, dans Fig. 2(e) : file-read(file_path: str, start_line: int|None = None, end_line: int|None = None), schéma JSON avec required: ["file_path"], implémentée par un POST vers {docker_base_url}/file/read avec un container_name issu de context_manager.get_chat_info("container_name"). Autres outils évoqués indirectement : recherche RAG et requête SQL [Fig. 2f, « 调用相应的工具（RAG检索或SQL查询）»], moteur de recherche pour SearchQA [§4.1], manipulation de tableur via openpyxl [Fig. 2c].
  • Multi-turn : oui, boucle perception-planification-action-observation [§1]. Horizon typique et maximal T_i : non précisé. Gestion du contexte long (troncature, résumé, mémoire) : non précisé.
  • Exécution / sandbox : conteneur Docker, attesté seulement par le code de l'outil file-read (« sandbox environment », docker_base_url, container_name) [Fig. 2e]. Déterminisme, reset, timeouts : non précisé. Température de sampling : non précisé — ⚠️ non anodin, puisque tout le performance gate compare des accuracies de batch entre deux harness, différence qui peut être du bruit de sampling (voir §7).
  • Gestion des erreurs et sorties mal formées : pas de mécanisme natif décrit ; c'est précisément ce que la boucle apprend à ajouter — le cas (f) montre l'agent d'optimisation écrivant lui-même un détecteur « réponse sans appel d'outil » + relance forcée [Fig. 2f]. Côté pipeline : si le quality gate reste insatisfait après T_rev = 3 révisions, la mise à jour est abandonnée (Δ_verified = ∅) et le batch est sauté [§3.5, Alg. 2 l. 11-18].
  • Exemple de trajectoire : aucun dans le papier. Ni trajectoire d'exécution, ni trajectoire de référence, ni exemple de diff τ⁺/τ⁻ avec son point de divergence. ⚠️ Pour un papier dont la contribution centrale est la comparaison de trajectoires, ne montrer aucun appariement concret est une lacune sérieuse : le lecteur ne peut pas juger si « premier point de divergence d'action » est bien défini quand les deux trajectoires empruntent des chemins non alignables (outils différents dès le pas 1, longueurs différentes). Aucune définition opérationnelle de l'alignement n'est donnée, ni dans §3.4 ni dans Alg. 1 — c'est laissé au jugement du LLM A_opt.

3. Reward / vérifieur — le critère de sélection d'une variante de harness

Il n'y a pas de reward scalaire différentiable. Le « vérifieur » est un empilement de quatre décisions, trois par LLM-as-judge et une par comparaison d'accuracy :

3.1 A_eval — accuracy assessment (le signal de base)

  • Type : LLM-as-judge. « compares the final output of each trajectory against the corresponding ground-truth answer a*_i » [§3.3]. Pas d'exécution de tests, pas d'exact match annoncé.
  • Granularité : binaire par instance (succès / échec) ; agrégé en accuracy de batch. Aucun crédit partiel, aucun signal de process malgré le cadre multi-turn.
  • Modèle du juge, prompt, rubrique : non précisé — les trois annexes (A : figure de diffs ; B : Alg. 1 ; C : Alg. 2) ne contiennent aucun prompt. ⚠️ Impossible de savoir si A_eval tourne sur Qwen3.6-27B, DeepSeek-V4-Flash, ou un autre modèle.
  • Fiabilité : non mesurée. Aucun accord avec des humains, aucun taux de faux positifs / faux négatifs, sur aucun des 5 datasets. ⚠️ Pour SpreadsheetBench (manipulation de tableur, vérifiable par exécution) et pour le text-to-SQL in-house (vérifiable par exécution de requête), un vérifieur exact était disponible et n'a pas été utilisé — ou alors ce n'est pas précisé.

3.2 A_eval — reference verification (le garde-fou anti-court-circuit)

  • Type : LLM-as-judge binaire, « genuine execution path » vs « shortcut » [§3.3].
  • Critère : l'agent « invokes appropriate tools, processes intermediate observations, and arrives at the answer through valid steps rather than trivially restating the provided answer » [§3.3].
  • Fiabilité : non mesurée. Pas de taux de rejet rapporté, pas d'audit humain d'un échantillon.
  • ⚠️ Vulnérabilité structurelle : rien n'empêche une référence plausible mais fabriquée a posteriori — l'agent connaît la réponse, peut appeler les bons outils, et reconstruire un chemin qui « justifie » la réponse sans l'avoir découverte. Le critère « invoque des outils » ne distingue pas découverte et rationalisation. C'est le failure mode le plus évident du papier, et il n'est ni discuté ni testé.

3.3 A_gate — quality gate (anti-shortcut learning)

Deux tests, par fichier f ∈ Δ_harness ; l'update passe ssi tous les fichiers passent les deux [§3.5] : - Data leakage : LLM-as-judge, score continu 0 à 1, mesurant si les édits « directly embed failed queries and their ground-truth answers into the harness files ». Rejet si score > η_leak = 0,8 [§3.5, §4.1]. - Prompt bloat : comptage du nombre d'exemples in-context nouvellement injectés. Rejet si > η_blo = 5 [§3.5, §4.1]. - Boucle de révision : rejet → renvoi à A_opt avec une raison ρ en langage naturel ; abandon après T_rev = 3 révisions [§3.5, Alg. 2 l. 11-18]. - Anti-gaming architectural : A_gate « operates as an isolated judge, structurally decoupled from the optimization agent, preventing self-serving evaluation » [§3.5]. C'est un argument de conception, pas une mesure. - Fiabilité : non mesurée. Ni la précision du juge de leakage, ni la justification du seuil 0,8, ni celle de 5 exemples. Aucune ablation de η_leak ou η_blo. - ⚠️ Le gate ne couvre pas la forme d'overfitting qu'on observe réellement dans le papier. Fig. 2(a) : le skill.md OfficeQA optimisé contient des règles conditionnées sur la formulation des questions (« when a question asks for percent difference without naming a baseline… », « when the question states… », « when a risk metric is computed on log returns (e.g. historical VaR at the 5th percentile), convert the selected log return via exp(r) − 1 »). Fig. 2(d) : le system prompt CloudCoreNetwork-QA se remplit de règles SQL ultra-spécifiques au schéma. Ce n'est ni du leakage verbatim question/réponse, ni de l'in-context example — donc ça passe les deux tests — mais c'est bien de la mémorisation de la distribution d'entraînement. Le quality gate mesure deux proxys étroits et les auteurs en concluent « prevent shortcut learning » ; l'écart entre le proxy et le concept n'est pas discuté.

3.4 Performance gate (anti-catastrophic forgetting) — le vrai critère de sélection

Acceptation ssi les deux conditions [Éq. 1, §3.5] : 1. Acc(A_cand, B_j) − Acc(A_curr, B_j) ≥ δ, avec δ = 0,0 [§4.1] — donc « ne dégrade pas le batch courant » suffit ; 2. max_{l ∈ [max(1,j−R), j−1]} [Acc(A_curr, B_l) − Acc(A_cand, B_l)] ≤ ε, avec R = 2 et ε = 0,025 [§4.1].

Puis : accepté → snapshot dans le pool V, devient A_current immédiatement. Rejeté → compteur c++ ; si c ≥ P_batch = 10, fin anticipée de l'epoch [§3.5, Alg. 2]. Sélection de fin d'epoch : A_current ← argmax_{A ∈ V} Acc(A, T_val), garantissant que « the final agent is no worse than the best-performing snapshot in the pool » [§3.5]. Arrêt si epoch = E = 20 ou si T_val ne s'améliore pas pendant P_ep = 5 epochs [§4.1].

⚠️ Trois problèmes de fiabilité de ce critère, aucun traité : - Bruit de sampling. Avec b = 40 et δ = 0, un candidat est accepté dès +1 tâche sur 40 (+2,5 pt). La tolérance ε = 0,025 sur le replay vaut exactement 1 tâche sur 40. Aucune répétition, aucune température rapportée : le gate ne distingue pas un vrai gain d'un tirage favorable. C'est un mécanisme de sélection sur du bruit, appliqué des dizaines de fois. - Mémoire courte. R = 2 : la non-régression n'est testée que sur 80 tâches vues juste avant. Rien n'empêche une dérive lente sur les batches plus anciens — or c'est exactement la définition de l'oubli catastrophique que le papier revendique traiter. - Aucune ablation du performance gate. Les trois ablations portent sur la référence (M1), le clustering (M2) et le quality gate (M3) [Tab. 4]. La contribution n°3 revendiquée (« Performance Gate for Stable Evolution ») n'est jamais isolée expérimentalement.

3.5 Robustesse / attaque du vérifieur

Aucun test adversarial. Le seul argument anti-hacking est architectural (découplage A_opt / A_gate [§3.1, §3.5]) et le seul élément quantitatif est indirect : M3, retirer le quality gate, coûte 6,8 pt sur CloudCoreNetwork-QA (86,9 → 80,1) [Tab. 4] — ce qui atteste qu'un shortcut learning existe et est partiellement attrapé, sans dire lequel ni combien reste.

Lecture alternative non exclue par le papier : sur un dataset dont on contrôle la construction et le harness initial, la marge d'amélioration par édition de harness est mécaniquement plus grande (Base à 43,4 %, et Fig. 2(d)/(f) montrent que la boucle corrige des bugs du harness initial — description d'outil erronée, logique de retry cassée). Le gain reproductible et contrôlable est celui à 2 points.

evidence = 2/6 — cases vraies : ablation, coherence. Manquant : [baselines, variance, eval, repro].

Verdict

Plausible mais fragile. Le mécanisme central — générer une trajectoire de référence en donnant la réponse, la faire vérifier comme non-court-circuit, diffé les échecs contre elle pour localiser le premier point de divergence — est une idée nette, bien motivée et soutenue par l'ablation la plus franche du papier (−29,1 pt). Le protocole de gating à deux étages est une contribution d'ingénierie réutilisable. Mais : gains à 2 points sur tout ce qui est public et vérifiable, gains à 20 points sur ce qui est propriétaire et opaque ; zéro variance là où le mécanisme d'acceptation opère au grain d'une tâche sur 40 ; trois juges LLM jamais validés ; pas une ligne de code ; et le transfert présenté comme la preuve de généralisation ne teste pas la dimension qui compte (la distribution de tâches). À répliquer sur un benchmark public, avec seeds et budget d'appels apparié, avant de s'appuyer sur les chiffres.

9. Transférabilité vers le juridique

Contexte du transfert : Gemini Law, post-training juridique, éval Harvey LAB / Vals Legal Research Bench. Contrainte dominante — le vérifieur juridique est lui-même un modèle. C'est précisément la situation de ce papier (A_eval, A_gate sont des LLM), ce qui rend la transposition structurellement naturelle, et ses angles morts directement les nôtres.

Meilleur ingrédient à transposer

La trajectoire de référence générée en conditionnant sur la réponse (answer-conditioned rollout), plus sa vérification anti-court-circuit. Trois raisons : 1. Elle résout le credit assignment sans vérifieur exact — exactement notre contrainte. On n'a pas besoin de savoir si une réponse juridique longue est bonne pour savoir où un chemin de recherche a divergé d'un chemin qui aboutit. 2. C'est le seul ingrédient du papier soutenu par une ablation franche (86,9 → 57,8, soit −29,1 pt, et sous les baselines [Tab. 4]). 3. Elle est indépendante du reste du papier : on peut la brancher sur du RL à gradient (comme source de dense reward ou de shaping par divergence), pas seulement sur de l'édition de harness. Le papier ne l'explore pas — c'est notre angle.

Le deuxième ingrédient, moins original mais immédiatement utile : le performance gate à replay (accepter une modification seulement si elle ne dégrade aucun des R batches précédents). C'est une discipline de non-régression triviale à implémenter et absente de la plupart des pipelines de prompt/harness engineering.

Expérience minimale

Sur Vals Legal Research Bench (ou un sous-ensemble de Harvey LAB), Gemini gelé, harness de recherche juridique existant.

  1. Pour chaque question du train, générer une trajectoire de référence en conditionnant sur la réponse-experte et sa liste de citations, T_att = 5. Vérification « genuine » renforcée par rapport au papier : rejeter toute trajectoire où une source citée dans la réponse finale n'a pas été effectivement récupérée par un appel d'outil antérieur. Mesurer et rapporter le taux de couverture (fraction de questions dotées d'une référence vérifiée) — chiffre que le papier ne donne jamais et qui conditionne tout le reste.
  2. Sur les échecs, deux bras : (A) diagnose sur trajectoire d'échec seule ; (B) diagnose par diff contre la référence, avec localisation du premier point de divergence (première requête / première source consultée qui diverge). Même budget d'appels LLM dans les deux bras.
  3. Édition du harness gatée : leakage + bloat + non-régression sur R = 3 batches stratifiés par domaine. δ et ε calibrés sur la variance du juge, mesurée au préalable par 5 répétitions de l'évaluation du harness initial sur un batch.
  4. Évaluation sur trois ensembles : test in-distribution, held-out domaine jamais vu, held-out juridiction jamais vue.

Résultat attendu — B > A en in-distribution (c'est le résultat du papier, transposé) ; le résultat qui nous intéresse vraiment est l'écart B−A sur les deux held-out. Si B ne conserve son avantage qu'en in-distribution, la référence guide vers des corrections spécifiques aux questions d'entraînement, et l'ingrédient ne vaut pas son coût. Hypothèse de travail : la diagnose par référence produit des corrections plus procédurales (ordre de recherche, quels outils avant quels autres) et donc plus transférables que la diagnose sans référence, qui produit des corrections déclaratives (règles conditionnées sur la question — cf. Fig. 2a). Cette expérience mesure précisément ce que le papier a omis de mesurer. Coût : purement inférence, pas de training. Le poste dominant est la génération des références (|T_train| × jusqu'à 10 appels agentiques).

Question à poser en interne chez GDM

Deux : 1. A-t-on déjà, pour Gemini Law, des rollouts conditionnés sur la réponse (answer-conditioned) et, si oui, servent-ils au-delà du filtrage de données SFT ? La contribution du papier consiste à les utiliser comme référence de diff pour localiser une divergence, pas comme données d'entraînement. Si le pipeline les produit déjà pour du rejection sampling, l'ingrédient est disponible à coût marginal quasi nul. 2. Quelle est la variance mesurée de notre juge juridique sur un même couple (harness, batch) ? Tout ce papier repose sur des décisions d'acceptation prises à un écart de 2,5 pt sans jamais mesurer ce bruit. Avant de transposer le performance gate, il nous faut ce nombre — et il est utile bien au-delà de ce papier.
