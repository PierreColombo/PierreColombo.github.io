0. En une phrase

TL;DR. READY ajoute au-dessus d'un benchmark agentique existant une couche de qualification de déploiement : cible de fiabilité → classe de policies de supervision humaine → sélection de la policy de coût minimal qui satisfait la cible sur un dev set → gel → borne de confiance inférieure sur un held-out ; la sortie n'est pas un score mais un deployment profile (fiabilité, charge de relecture humaine, coût).

Claim principal, formulé précisément. Sur CliniCARE-Bench (audit clinique rétrospectif), 16 systèmes agentiques, 750 cas, 12 000 runs system–case [§5.1] : deux systèmes que le leaderboard autonome sépare de 0,3 point (GPT-5.4 $a_0=72{,}8$ % vs Sonnet 5 $a_0=72{,}5$ %, sur la partition dev $n=375$) exigent respectivement 39,2 % contre 29,6 % de cas routés en relecture humaine pour être qualifiés à la même cible $Y=0{,}76$, sous l'hypothèse de relecture $a_h=0{,}90$ et le prédicat de succès à 4 classes [§5.6, Tab. « Held-Out Qualification »]. Les auteurs affirment que la cause est la qualité de ranking du signal de routage et non l'accuracy (AUROC 0,681 vs 0,601 ; AURC 0,203 vs 0,222 [Tab. « routing summary »]).

⚠️ Le papier ne mesure jamais la relecture humaine : aucun des cas escaladés n'est réellement relu. Toute la branche « humain » du système human–AI est une hypothèse déclarée ($a_h=0{,}90$), pas une mesure [§5.1, §7 « Human-oversight assumptions »].

2. Le testbed et son découplage

(Catégorie AUTRE : pas d'environnement RL. Cette section décrit l'architecture d'évaluation et, surtout, le découplage qui est la vraie contribution d'ingénierie.)

Le découplage, axe par axe

READY sépare trois classes d'artefacts non exécutables de la couche d'exécution [§4.2] :

Artefact Contenu Conséquence
Workflow specification workflow $w$, population $\mathcal{D}_w$, échantillon $S_w$, environnement $E_w$ définit la portée de la claim
Evaluation specification évaluateur $g_w$, prédicat de succès $\phi_w$, signal de routage exposé définit ce qui compte comme succès
Deployment assumptions cible $Y$, modèle de supervision humaine ($a_h$), modèle de coût, tolérance au risque $B_w$ stockées avec le profile, PAS dans le record par instance

Bénéfice concret : « Different organizations may therefore interpret the same measured execution evidence under different deployment requirements » [§4.2]. C'est ce qui rend gratuit le balayage de l'App. B.2 (5 valeurs de $a_h$ × 496 policies) — zéro inférence supplémentaire.

Record de qualification versionné [§4.5] : schema_version ; bloc lineage qui version-stampe workflow, population, système évalué, environnement, $g_w$, $\phi_w$, définition du signal de routage ; measurements par instance ($u_i$, $s_i$, diagnostics $\mathbf{q}_i$, coût) ; identifiants de la task instance et de l'unité d'échantillonnage statistique. Les partitions dev et qual portent un schéma identique — seul le champ partition diffère.

Règles de maintenance / requalification [§4.6] — utile, rarement formalisé ailleurs : - assumptions changent → recompute (preuves inchangées) ; - $g_w$ ou $\phi_w$ changent → re-score sur trajectoires sauvegardées, mais seulement si chaque trajectoire a enregistré tous les inputs que l'évaluateur révisé lit ; sinon ré-exécution ; - agent, harness, environnement, outils ou population changent → ré-exécution complète.

Protocole de validation d'une contribution [§4.6] : un relecteur indépendant du contributeur vérifie quatre points — workflow validity (forme reconnaissable de travail, échantillonnée de la population déclarée), evaluation validity ($g_w$ et $\phi_w$ reproduisent les labels de succès à une tolérance pré-enregistrée), execution validity (dry runs reproductibles, pas d'accès à une référence cachée ni de raccourci), qualification validity (partition gelée, sélection ne touchant jamais le held-out). ⚠️ Aucune instance de ce protocole réellement exécutée n'est rapportée.

Substrat d'exécution

  • READY n'est pas un harness : « READY does not introduce a new general-purpose agent-evaluation harness » [§4]. Implémentation de référence sur Inspect AI [\cite{inspect_ai}] ; peut consommer des tâches packagées Harbor via l'adaptateur inspect-harbor [§6.7].
  • Mapping [Tab. « Minimal logical interface »] : task instance READY = Inspect Sample (pas Task) · population = Dataset · agent = Agent/Solver, agents externes via Agent Bridge · $E_w$ = tools + sandbox config · oversight = approval policies / approver / agent intervention · $Z_i^\pi$ = log par sample (transcript, outputs, metadata, artefacts retenus) · $g_w$ = un ou plusieurs Scorers (ou scores fournis de l'extérieur) · inputs de qualification = scores + metadata + usage + records dérivés READY · lineage = config Task/Sample + logs versionnés.
  • Deux rôles d'acteurs distingués [§4.3] : oversight actor (côté organisation : approuve, clarifie, corrige, rejette, escalade, reprend la main) et user actor (contrepartie externe). L'un ou l'autre peut être humain ou simulé, mais « its identity, configuration, and available actions must be part of the evaluation configuration ».

Ce que voit et fait l'agent (workflow clinique)

  • Observation : une question d'audit clinique concise + accès patient-scoped au dossier longitudinal, structuré et texte libre, via des « clinically meaningful retrieval tools », plus des facilités de calcul explicite et l'accès aux documents de politique applicables [§2.3].
  • Sortie : un verdict parmi quatre — Yes / No / Indeterminate: Lack of Data / Indeterminate: Medically Ambiguous — accompagné de citations d'évidence patient et d'évidence policy, et d'une confiance déclarée $s_i$ (exigée en pourcentage, rescalée dans [0,1]) [§2.3, §5.1].
  • Trajectoire enregistrée $Z_i$ : tool calls, informations retrouvées, calculs, artefacts intermédiaires [§2.3, §4.4].
  • Exemple de scénario donné : un patient en réanimation a-t-il développé une insuffisance rénale aiguë dans les 48 h après un scanner — l'agent doit établir la créatinine de base selon une hiérarchie spécifiée, identifier l'heure d'exécution du CT, inspecter la trajectoire de créatinine post-CT, vérifier le statut dialyse chronique / ESRD, appliquer les critères créatinine KDIGO [\cite{kdigo2012aki}], et citer l'évidence du dossier [§2.3].

Non précisé : signatures des outils (aucune liste, aucune signature), horizon typique et maximal de tours, gestion du contexte long (troncature / résumé / mémoire), déterminisme, politique de reset, timeouts, gestion des erreurs d'outils. Tout est délégué à Inspect sans être spécifié. Seule gestion de sortie malformée documentée : confiance absente → $s_i=0$ [§5.1].

Aucun exemple de trajectoire n'est donné dans le papier (ni corps, ni annexes). ⚠️ Pour un papier de 160 Ko de source dont la thèse est « l'évidence d'exécution observable est ce qui fonde la claim », c'est une absence notable.

Multi-turn, epochs

Agentique et multi-tours par construction (tool calls, artefacts intermédiaires), mais aucune statistique d'horizon. Le framework prévoit plusieurs epochs par task instance en retenant l'identité de l'instance pour que les runs répétés ne soient pas traités comme des cas indépendants [§4.4, §3.5 « Sampling unit »] — non utilisé dans l'étude de cas (1 run par system–case).

Le replay d'évidence sauvegardée — mécanisme et limites

Mécanisme [§3.2, §4.3]. La supervision terminale accept-or-escalate est trajectory-invariant : la décision de routage intervient après que $Z_i$ a été produit, donc changer $\tau$ ne change pas $Z_i$. On exécute donc l'agent une seule fois, on sauvegarde le triplet $(Z_i, s_i, u_i)$ plus les mesures de coût, et on évalue toutes les policies candidates par relecture offline des mêmes runs. C'est ce qui rend calculables, sans une seule inférence supplémentaire : le balayage de 31 cibles × 16 systèmes (496 policies) [§5.4], sa répétition pour 5 valeurs de $a_h$ (2 480 policies) [App. B.2], la re-notation complète sous le prédicat process-aware $u_{\mathrm{df}}$ [App. B.3], et le contrôle négatif $\pi_{\mathrm{IR}}$ [App. B.5].

Limites, énoncées par les auteurs : 1. Ne s'applique qu'à la supervision terminale. Dès que l'intervention se produit pendant l'exécution (approbation, clarification, correction, reprise en main, ou simplement « demander plus d'évidence avant d'adjuger »), $\pi$ change ce que l'agent, le superviseur et l'utilisateur observent ensuite : $Z_i^\pi \sim P(\cdot \mid m, x_i, E_w, \pi)$, et fiabilité/coût/risque doivent être estimés en exécutant ou simulant la policy dans le runtime [§3.7, §5.7]. Ce régime est formalisé mais jamais évalué empiriquement — laissé aux travaux futurs [§7]. 2. La re-notation par un évaluateur révisé n'est valide que si la trajectoire a enregistré tous les inputs que le nouvel évaluateur lit ; sinon il faut ré-exécuter [§4.6]. 3. $a_h(\tau)$ peut dépendre de la policy : « because routing deliberately selects a non-random subset of cases, $a_h(\tau)$ may vary with the policy: cases routed under a more selective policy may be systematically more difficult » [§3.2]. Le replay suppose $a_h$ constant — approximation, pas mesure. 4. ⚠️ Mon ajout : le replay ne rejoue que la branche autonome. La branche relecture n'est jamais jouée du tout. Le replay donne une comparaison exacte entre policies sur la moitié mesurée, et rigoureusement rien sur l'autre moitié.

3. Comment le succès est défini, et comment il est mesuré

(Catégorie AUTRE : pas de reward d'entraînement. On décrit ici la chaîne $g_w \to \phi_w \to u_i$, le signal de routage, et la procédure de qualification statistique.)

3.1 La chaîne de mesure

$$Z_i^\pi \xrightarrow{\;g_w\;} \mathbf{q}_i^\pi \xrightarrow{\;\phi_w\;} u_i^\pi \in {0,1}$$ La séparation est délibérée : « $g_w$ determines what aspects of the work are measured, while $\phi_w$ specifies which combination of those measurements constitutes a successful execution » [§2.1]. $\mathbf{q}_i$ garde l'information diagnostique multidimensionnelle (correction du verdict, abstention appropriée, evidence grounding, policy grounding, respect des exigences d'investigation du scénario [§2.3]) ; $\phi_w$ n'en retient qu'un sous-ensemble.

Contrainte explicite et bien vue : « any process requirement used for qualification must be supported by observable execution evidence, such as retrieved sources, tool calls, or state changes, not unrecorded model reasoning » [§6.2].

3.2 Prédicats de succès instanciés

Prédicat Définition Usage
$u_i$ (primaire) $\mathbf{1}{\hat y_i = y_i^\star}$ — exact match sur le label à 4 classes §5 entier
$u_{i,\mathrm{df}}$ (process-aware) $\mathbf{1}{\hat y_i = y_i^\star \;\wedge\; \text{aucun disqualifying process defect}}$ App. B.3, robustness check

Le defect est enregistré par CliniCARE comme un indicateur binaire unique par run ; il est fréquent : 21,9 % des 12 000 runs, de 12,7 % (GPT-5.5) à 30,0 % (Kimi-K2.7-Code). Comme un defect peut coexister avec un verdict correct, substituer $u_{\mathrm{df}}$ à $u$ abaisse le succès autonome de 4,5 à 13,1 points selon le système [App. B.3].

3.3 Fiabilité du vérifieur — le trou

  • Comment le verdict à 4 classes est-il gradé ? non précisé. Exact match sur une chaîne, parsing structuré, juge LLM, humain ? Le papier ne le dit pas.
  • Comment le « disqualifying process defect » est-il détecté ? non précisé.
  • Aucun prompt de juge, aucune rubrique nulle part dans le papier ni dans les annexes.
  • Aucune mesure de précision du vérifieur, aucun accord avec des humains, aucun taux de faux positifs/négatifs.
  • Le framework prévoit la validation ($g_w$/$\phi_w$ doivent « reproduce success labels within a pre-registered tolerance » lors de la revue d'une contribution, §4.6) mais ne la rapporte pas pour sa propre instanciation.
  • ⚠️ Conséquence directe : tout le profil de déploiement — LCB, seuil qualifié, Review% — est exactement aussi fiable que $u_i$, et $u_i$ n'est validé nulle part dans ce papier. Pour un framework dont l'argument de vente est « statistiquement testable », c'est la faille centrale.

3.5 La procédure de qualification — formalisation exacte

Objectif de sélection [éq. 8, §2.1] : $$\pi^\star_{m,w}(Y,B_w) \in \arg\min_{\pi \in \mathcal{F}{m,w}(Y,B_w)} C(\pi), \quad \mathcal{F}{m,w}(Y,B_w)={\pi \in \Pi_w : R(\pi)\ge Y,\; \rho_w(L_w(Z^\pi))\le B_w}$$ avec $R_{m,w}(\pi)=\mathbb{E}{x\sim\mathcal{D}_w}[u^\pi(x)]$ et $C(\pi)=\mathbb{E}[K_w(Z^\pi)] = C_{\mathrm{agent}} + C_{\mathrm{human}}$. La contrainte de risque $\rho_w$ est optionnelle ($B_w=+\infty$ quand la fiabilité moyenne suffit) ; CVaR est proposé pour les workflows où la concentration des échecs compte [§3.6, App. A.2]. Si $\mathcal{F}=\varnothing$, aucune policy de la classe évaluée ne supporte le point de fonctionnement demandé.

Classe de policies évaluée (unique, terminale, signal-only, agnostique aux classes) [§5.2, éq. clinicare-fourway-global-policy] : $$\pi_\tau(s_i) = \begin{cases}\text{accept} & s_i \ge \tau \ \text{review} & s_i < \tau\end{cases}$$

Identité de fiabilité [§3.2, éq. terminal-reliability-constant-review] : $$R(\tau) = c(\tau)\,a(\tau) + (1-c(\tau))\,a_h, \qquad c(\tau)=\Pr(s\ge\tau),\; e(\tau)=1-c(\tau),\; a(\tau)=\Pr(u=1\mid s\ge\tau)$$

Coût [§3.3, éq. terminal-cost] : $C(\tau) = k_m + k_h\,e(\tau)$. Sous $k_m, k_h>0$ constants, minimiser le coût ≡ minimiser la charge de relecture ≡ maximiser la couverture autonome parmi les policies faisables. Le modèle à coût constant n'est pas exigé par le framework — « when case-level costs are available, READY estimates $C(\pi)$ directly » [§3.3] — mais c'est celui qui est utilisé.

Sélection avec marge [§5.2, éq. threshold-optimization-with-margin] — ingrédient décisif : $$\tau^\star(Y) = \arg\min_\tau C(\tau) \quad\text{s.c.}\quad \widehat R_{\mathrm{dev}}(\tau; a_h) \ge Y + \delta, \qquad \boxed{\delta = 0{,}05}$$ Motivation explicite : « Fitting $\tau$ to hit $Y$ directly on a sampled development set is prone to selection bias and tends to fail the stricter held-out lower-bound test ».

Test statistique — ce n'est pas un test d'hypothèse mais une borne de confiance inférieure unilatérale, et la règle de décision est « LCB ≥ Y » [§3.5, App. B.1] : 1. Router. $d_i = \mathbf{1}{s_i \ge \hat\tau}$ ; $n_{\mathrm{acc}}=\sum_i d_i$, $k_{\mathrm{acc}}=\sum_i d_i u_i$, $\hat p_{\mathrm{acc}} = k_{\mathrm{acc}}/n_{\mathrm{acc}}$. 2. Estimation ponctuelle. $\widehat R = \frac{n_{\mathrm{acc}}}{N_{\mathrm{qual}}}\hat p_{\mathrm{acc}} + \frac{N_{\mathrm{qual}}-n_{\mathrm{acc}}}{N_{\mathrm{qual}}}a_h$. 3. Borne inférieure. Clopper–Pearson exacte unilatérale à 95 % sur $\hat p_{\mathrm{acc}}$ — quantile $\alpha=0{,}05$ de $\mathrm{Beta}(k_{\mathrm{acc}},\,n_{\mathrm{acc}}-k_{\mathrm{acc}}+1)$, avec $\underline p_{\mathrm{acc}}=0$ si $k_{\mathrm{acc}}=0$. Aucune confiance n'est attachée au terme assumé : $$\text{95\% LCB} = \frac{n_{\mathrm{acc}}}{N_{\mathrm{qual}}}\underline p_{\mathrm{acc}} + \frac{N_{\mathrm{qual}}-n_{\mathrm{acc}}}{N_{\mathrm{qual}}}a_h$$ 4. Qualifier ssi $\text{LCB} \ge Y$. « A point estimate above the target is not sufficient. » 5. Break-even : $a_h^{\min}(\hat\pi,Y) = \inf{a_h \in [0,1] : R_{\mathrm{LCB}}^{1-\alpha}(\hat\pi;a_h) \ge Y}$ [éq. break-even-review-assumption] — le LCB étant non décroissant en $a_h$, c'est un solve 1-D. Traduit la claim en exigence auditable sur le processus humain : « la policy qualifie à $Y$ à condition que le circuit de relecture atteigne au moins $a_h^{\min}$ ». C'est, à mon sens, l'objet le plus réutilisable du papier.

Discipline de gel [§3.5] : tous les choix (règle de routage, seuil, procédure d'optimisation, marge) sur $S_{\mathrm{dev}}$ ; la policy est gelée avant examen des résultats de qualification ; une policy qui échoue est déclarée not qualified at target $Y$ ou insufficient evidence — « it is not retuned using the qualification set » ; toute modification après examen du held-out exige une nouvelle qualification. Propagation d'incertitude prévue si $a_h$ est lui-même estimé : remplacer $a_h$ par $a_{h,\mathrm{LCB}}$.

Unité d'échantillonnage [§3.5] : doit correspondre à l'unité sur laquelle la claim généralise. Les exécutions stochastiques répétées d'une même instance ne sont pas traitées comme des cas indépendants ; en cas de clustering naturel (patient, client, compte, site), IC ou rééchantillonnage au niveau du cluster.

3.7 Surface de gaming du critère

⚠️ Le critère est trivialement gamable : un système qui déclare toujours une confiance basse route 100 % des cas en relecture, atteint exactement $a_h$ et « qualifie sans déployer ». Les auteurs le détectent, le signalent par un † dans le tableau (Gemini-3.1-Pro, 100,0 % review, $\widehat R=\text{LCB}=0{,}900$) et corrigent en comparant les systèmes sur Review%, pas sur le statut binaire de qualification [Tab. « Held-Out Qualification », note]. Les cibles $Y>0{,}90$ sont inatteignables non par incapacité de l'agent mais par qualité supposée du circuit de relecture — « a structural point a capability-only benchmark cannot express ». Point important et bien amené.

Le mécanisme derrière 0,3 pt d'accuracy → 9,6 pts de relecture

C'est le point le plus intéressant du papier, et il mérite d'être posé algébriquement. En réécrivant l'identité de fiabilité : $$R(\tau) = a_h - c(\tau)\big(a_h - a(\tau)\big) \;\ge\; Y \iff \underbrace{c(\tau)\big(a_h - a(\tau)\big)}_{\text{déficit laissé en autonome}} \;\le\; a_h - Y$$ À $a_h=0{,}90$ et $Y=0{,}76$, le budget est $0{,}14$. Puisque $a(\tau)=1-r(\tau)$, la quantité contrainte est $c(\tau)\big(r(\tau)-0{,}10\big)$ : c'est la masse absolue d'échecs laissés en autonome, en excès du taux d'échec du circuit humain. La cible ne contraint donc pas l'accuracy moyenne ; elle contraint le nombre absolu de cas ratés qui passent sans relecture.

Il s'ensuit que le déterminant du Review% est la courbe risque–couverture, pas $a_0$. Chiffres reconstruits depuis le tableau :

couverture $c$ cas acceptés succès acceptés $\hat p_{\mathrm{acc}}$ échecs laissés autonomes
Sonnet 5 70,4 % 264 0,837 43 / 375 = 11,5 %
GPT-5.4 60,8 % 228 0,782 50 / 375 = 13,3 %

GPT-5.4 accepte 36 cas de moins et laisse pourtant 7 échecs de plus en autonome. Sa confiance déclarée ordonne mal ses propres erreurs (AUROC 0,601 contre 0,681 ; AURC 0,222 contre 0,203), donc à couverture égale son ensemble accepté est plus contaminé, et il doit couper plus profond pour ramener la masse d'échecs acceptés sous le budget. Formulation des auteurs : « because Sonnet 5's confidence more sharply separates its own successes from its failures, a less aggressive threshold already clears the reliability target and leaves more work safely autonomous » [§5.6]. Le fait générateur global : $a_0$ et AUROC sont décorrélés ($\rho=-0{,}12$) — la capacité et l'auto-connaissance sont deux axes indépendants, et seul le second détermine le coût de supervision.

⚠️ Trois réserves sur ce chiffre phare, que je porterais en réunion : 1. Il dépend de $a_h$. L'écart 9,6 pts ne survit pas à l'hypothèse : 1,6 pt à $a_h=1{,}00$ [Tab. « $a_h$ sensitivity »]. La conclusion qualitative (meilleur routeur → moins de relecture) survit ; l'amplitude, non. 2. C'est une lecture à cible unique, sur une grille de seuils discrète. Les deux systèmes dépassent largement la cible ($\widehat R - Y$ = +0,096 et +0,067) faute de seuil atteignable plus fin. Le papier fournit lui-même le contre-exemple qui l'établit : Qwen-3.7-Plus et MiniMax-M3 ont exactement la même $a_0$ (66,4) et Qwen a le meilleur signal sur AURC et AUROC, mais Qwen exige 61,9 % de relecture contre 33,9 % — overshoot pur (le seuil atteignable le plus proche livre $\widehat R=0{,}874$, soit 11 points de fiabilité que la cible n'exigeait pas) [§5.6]. Les auteurs le rapportent explicitement plutôt que de le taire ✅ et concluent que « single-target review burden is a noisy summary, and the frontier is the fairer cross-system comparison ». Le chiffre de l'abstract est donc exactement le type de lecture que le papier lui-même déconseille. 3. La paire est choisie a posteriori. Les auteurs affirment l'avoir sélectionnée sur $S_{\mathrm{dev}}$ et gelée avant lecture du held-out [§5.6] ; non vérifiable de l'extérieur.

Points durs du droit, traités un par un

  • Pas de vérifieur exact → READY ne le résout pas ; il exige $u_i$ binaire et vous laisse le produire. Il apporte en revanche la bonne discipline : pré-spécifier $\phi_w$, le geler, l'ancrer sur de l'évidence observable, et vérifier la sensibilité au choix (leur $u$ vs $u_{\mathrm{df}}$ change Review% moyen de +16,8 pts — à répliquer en juridique avec « conclusion seule » vs « conclusion + citations vérifiées »).
  • Réponses longues et argumentées → aucun guide. C'est le principal travail à faire en amont.
  • Sources qui évoluent → le versioning de lineage [§4.6] est directement applicable (une nouvelle loi ou un revirement = population change → ré-exécution), mais les déclencheurs de requalification sont hors périmètre [§7].
  • Juridictions multiples → couvertes par la règle d'unité d'échantillonnage : clustering au niveau de la juridiction, IC au niveau du cluster [§3.5]. À ne pas rater, sinon les LCB sont anti-conservateurs.
  • Citations à vérifier → double emploi excellent : composante de $\phi_w$ et signal de routage $s_i$ candidat, bien meilleur que la confiance auto-déclarée.
  • Coût des experts → c'est exactement ce que READY met au centre, et exactement ce qu'il ne mesure pas.

Meilleur ingrédient à transposer

Le deployment profile comme métrique rapportée, avec $a_h^{\min}$ comme artefact contractuel.

Remplacer « Gemini fait X % sur Harvey LAB » par : « à une cible de fiabilité $Y$, Gemini qualifie en routant R % des cas en relecture avocat, LCB 95 % = L, et cette qualification tient tant que la relecture avocat atteint $a_h^{\min}$ ». Trois raisons : 1. C'est le nombre que le client achète. Un cabinet n'achète pas de l'accuracy, il achète des heures d'associé économisées à niveau de risque donné. 2. Il se calcule sur des preuves déjà produites, par replay — coût d'inférence marginal nul. Il suffit que chaque run d'éval logge $(u_i, s_i)$. 3. $a_h^{\min}$ retourne la charge de la preuve : au lieu de supposer que la relecture avocat sauve tout, on publie l'exigence minimale que le processus de relecture doit satisfaire pour que la garantie tienne. C'est auditable, négociable, et c'est le format qu'un service juridique ou un régulateur peut réellement contester.

Corollaire à faire valoir en interne : $a_0$ et AUROC sont décorrélés ($\rho=-0{,}12$). Deux modèles à accuracy identique peuvent différer d'un tiers sur le coût de supervision. Si Gemini Law est optimisé uniquement sur l'accuracy LAB/Vals, on optimise une variable qui n'est même pas corrélée à ce qui détermine le coût de déploiement. Et l'auto-connaissance est entraînable — c'est une cible de post-training légitime, que la frontière de READY rend mesurable.

Expérience minimale

Coût : quasi nul (replay sur des runs déjà payés). Durée : quelques jours.

  1. Reprendre un run d'éval Gemini existant sur un benchmark juridique, ≥ 600 cas.
  2. Ajouter au format de sortie un champ confiance déclarée en pourcentage (un re-run, ou — mieux — l'ajouter dès maintenant au format standard de tous les runs d'éval, ce qui rend l'analyse gratuite ensuite).
  3. Binariser le grader existant en $\phi_w$ pré-spécifié et gelé ; en préparer deux variantes (conclusion seule / conclusion + citations vérifiées) pour répliquer l'ablation $u$ vs $u_{\mathrm{df}}$.
  4. Split 50/50 par cluster de matter/juridiction, seed fixe.
  5. Sélection sur dev à $Y+0{,}05$, gel, LCB Clopper–Pearson sur held-out. Rapporter Review%, $\widehat R$, LCB, $a_h^{\min}$ pour $a_h \in {0{,}80;\,0{,}90;\,0{,}95}$.
  6. Comparer : classement par accuracy vs classement par Review% à $Y$ fixée.

Résultats attendus, extrapolés de ce papier (à vérifier, pas à supposer) : - AUROC de la confiance auto-déclarée autour de 0,60–0,70, faiblement corrélée à l'accuracy → les deux classements divergent, et le meilleur modèle au sens LAB n'est pas le moins cher à déployer. - Une partie des modèles aura une confiance trop grossière (< 6 valeurs distinctes) et aucun point de fonctionnement déployable — échec silencieux qu'aucun leaderboard ne montre. - Sous le $\phi_w$ exigeant les citations vérifiées, la charge de relecture montera fortement (chez eux : +16,8 pts en moyenne, et deux systèmes passent à 100 %). C'est probablement le chiffre à connaître avant de s'engager sur un SLA.

Expérience n°2, la seule qui produise une donnée que personne n'a : mesurer $a_h$. Prendre les brouillons escaladés, les faire relire par N avocats, enregistrer succès et minutes. Cela transforme le terme supposé en terme mesuré, retire le plafond structurel artificiel $R \le a_h$, et donne $k_h$ en unités réelles. Plus coûteux, mais c'est la donnée dont dépend tout le reste — et le papier, honnêtement, en fait sa première recommandation de travaux futurs [§7].

Questions à poser en interne chez GDM

  1. Quelle est notre cible de fiabilité $Y$ sur les workflows Harvey/Vals — existe-t-elle seulement, ou ne pilote-t-on que l'accuracy ? Sans $Y$ déclarée, aucun profil de déploiement n'est calculable.
  2. A-t-on jamais mesuré $a_h$ — le taux de succès de la relecture avocat sur un brouillon Gemini — plutôt que de le supposer ? Et si non, est-on prêt à publier $a_h^{\min}$ comme exigence sur le processus client plutôt que comme hypothèse tacite ?
  3. Exige-t-on déjà un champ de confiance dans le format de sortie des runs d'éval ? Si non, l'ajouter coûte quelques tokens et rend rétroactivement calculable toute l'analyse risque–couverture sur les évals passées. C'est l'action à coût le plus faible et à valeur d'option la plus élevée de ce mémo.
  4. Optimise-t-on quelque part l'auto-connaissance du modèle (calibration / ordination des propres erreurs) comme objectif de post-training, ou seulement l'accuracy ? $\rho(a_0,\text{AUROC})=-0{,}12$ suggère que c'est un axe de gain orthogonal et inexploité.

Ce que ça dit des envs

  1. Un environnement RL et un environnement de qualification demandent la même chose, et presque personne ne la produit. READY n'a besoin que de $(u_i, s_i, \text{coût})$ par instance, plus un lineage versionné. C'est exactement le tuple qu'un env RL produit déjà à chaque rollout. La leçon d'ingénierie : si les logs d'un env sont conçus pour qu'un évaluateur révisé puisse être rejoué dessus (« only when each trajectory records every input the revised evaluator reads », §4.6), on obtient gratuitement le re-scoring sous un nouveau reward, l'analyse de sensibilité, et la qualification de déploiement. C'est un argument fort pour sur-logger les rollouts dès la conception de l'env.

  2. Trajectory-invariant vs trajectory-dependent est la bonne ligne de partage, et elle vaut pour les rewards autant que pour la supervision. Un reward terminal peut être recalculé offline sur des trajectoires sauvegardées ; un reward qui change ce que l'agent fait ensuite (outil qui échoue, feedback injecté, correction en cours de route) exige de réexécuter. READY formalise cette distinction proprement et n'évalue empiriquement que le cas facile — comme, il faut le noter, la quasi-totalité de la littérature RLVR.

  3. Le découplage measurement / success predicate ($g_w$ vs $\phi_w$) est directement transposable au reward design. Garder $\mathbf{q}i$ riche et multidimensionnel, et ne le projeter en scalaire que par un prédicat pré-spécifié et versionné. Bénéfice démontré : leur ablation $u$ vs $u}$ est gratuite (re-scoring offline) et montre que la conclusion sur le signal survit alors que la conclusion sur le coût ne survit pas. Transposé : séparer la mesure du reward permet de tester la sensibilité de l'entraînement à la définition du reward sans relancer un seul rollout.

  4. Une contrainte de déploiement peut plafonner la fiabilité indépendamment de la capacité de l'agent. Comme $R \le a_h$ dès que le succès sélectif reste sous $a_h$, aucune amélioration du modèle ne fait passer $Y>0{,}90$ ici. C'est un type de plafond qu'un env de capacité pure ne peut pas exprimer — et un argument pour que les envs RL rapportent, à côté du score, le point de fonctionnement qu'ils supportent.

  5. Le catalogue de gaming s'enrichit d'un cas propre à la supervision : qualifier sans déployer (tout escalader → atteindre exactement $a_h$). Même structure que le reward hacking classique — le critère est satisfait, l'objectif ne l'est pas. Parade retenue : ne jamais rapporter le statut binaire seul, toujours l'accompagner de la charge de supervision. Généralisation utile : tout critère de succès binaire doit être publié avec sa métrique de coût, sinon il existe une stratégie dégénérée qui le sature.

  6. Le décorrélation $a_0$ ⟂ AUROC ($\rho=-0{,}12$) est le résultat le plus transférable du papier. La capacité et l'auto-connaissance sont deux axes indépendants, et le second détermine le coût de supervision. Aucun env RLVR courant ne récompense le second. C'est une cible de reward inexploitée et, pour un déploiement réel, probablement plus rentable que quelques points d'accuracy.

  7. ⚠️ L'avertissement à retenir : un appareil statistique impeccable posé sur un vérifieur non validé produit de la fausse précision. Ce papier calcule des bornes Clopper–Pearson exactes sur un $u_i$ dont il ne dit ni comment il est produit ni à quel point il est juste. Toute la rigueur est du bon côté de la chaîne ; l'incertitude dominante est de l'autre.
