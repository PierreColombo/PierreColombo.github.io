0. En une phrase

Le taux d'appels d'outils rapporté par une éval d'agent n'est pas une propriété du modèle mais du contrat à trois (ce que le checkpoint a appris à émettre × ce que le chat template lui demande d'émettre × ce que le parser est défini à accepter) ; quand ce contrat casse, le serveur renvoie HTTP 200 avec tool_calls: [] — strictement indiscernable d'un modèle qui refuse d'utiliser l'outil — et la distorsion se propage à l'intérieur de la collecte de rollouts RL, où 45 générations sur 115 portent un appel complet et aucune ne devient une action.

Claim principal, formulé précisément. (i) Sur les données, l'exécuteur et le scorer de BFCL v4, à poids / cas / décodage / seeds fixés et en ne changeant que la configuration de l'adaptateur de serving, le même modèle marque 0.00 ou 0.96 / 0.19 (simple_python / multi_turn_base) [§4.1] ; (ii) un 2×2 template × parser place les deux effets principaux exactement à zéro et la totalité de l'effet dans l'interaction — aucun composant n'est défectueux, réparer un seul côté du contrat ne rapporte exactement rien [Tab. bfcl2x2, §4.1] ; (iii) dans verl à 7B, 45/115 générations portent un appel complet, 0 accepté, 0 exécuté, 0 observation retournée [Tab. rolloutprobe, §4.8] ; (iv) réparer l'interface restaure le mécanisme (parse 0→84, sauvetages 0→9) mais pas un gain d'outcome significatif (53→62, p=0.093) [Tab. repair, §4.7].

2. Environnement / harness — le cœur du papier

2.1 Observation, actions, outils

  • Observation. Deux protocoles comparés, force d'instruction appariée des deux côtés dans chaque comparaison [App. C].
  • ReAct : protocole texte Thought: / Action: run_tests / Action Input: (bloc de code fencé python) / Observation: (rempli par le système) / Final Answer:. Nom d'outil figé dans le template. Deux forces : optional (réponse directe permise) et mandatory (Action obligatoire d'abord). Prompts en chinois, reproduits verbatim en annexe — les auteurs refusent de les traduire car « une traduction est un troisième prompt » [App. C.1].
  • Function calling (FC) : OpenAI-style, tool_choice: auto, un seul outil.
  • Signature de l'outil (schéma terse, recopié) [App. C.3] :

{"type": "function", "function": {"name": "run_tests", "description": "…", "parameters": {"type": "object", "properties": {"code": {"type": "string"}}, "required": ["code"]}}}

Trois variantes : terse (ci-dessus — celle à laquelle on arrive en suivant la doc API, et sous laquelle apparaît le taux de 23 % de mauvais outil de Llama) ; rich (description + contre-exemple + exemple de code, avec l'avertissement explicite « cet outil n'est pas la fonction que tu dois implémenter ») ; strict (strict: true + additionalProperties: false, avec VLLM_ENFORCE_STRICT_TOOL_CALLING=true, le défaut). - Single/multi-turn. Multi-turn des deux côtés. Horizon maximal : non précisé explicitement ; horizons observés : à l'éval, mean turns 1.92 (ReAct) / 0.96 (FC+hermes) / 1.82 (FC+adaptateur) [Tab. repair] ; à l'entraînement, num_turns/mean 2.000 constant (FC) contre 5.883 (ReAct) [Tab. training]. max_tokens = 2048 pour les deux protocoles (⚠️ errata : sept bras ReAct ont tourné à 1024 en enregistrant 2048 — l'asymétrie favorisait FC, et re-tourner à 2048 change le pass final de ≤1 item) [§3, App. A.1]. BFCL : max_model_len = 16384 [App. G.4]. Gestion du contexte long (troncature/résumé/mémoire) : non précisé ; en revanche la sonde tronque le texte brut stocké à 4000 caractères, et 10 des 98 sorties échantillonnées atteignent ce plafond → les comptages d'appels émis sont un minorant [§3.1, App. F]. - Exécution. vLLM 0.27.1 en serving, verl 0.9.0 (backend rollout vLLM) à l'entraînement ; outil run_tests = pytest en sandbox ; matériel = une seule carte A800 80 GB [§3, Tab. trainconfig]. Déterminisme : temperature=0 est greedy mais pas bit-à-bit déterministe sous continuous batching — les auteurs le disent et en tirent la conséquence : le bras BFCL réparé bouge d'un cas entre deux runs (197 vs 196 parsed, 99 vs 98 executed), donc les colonnes intermédiaires du funnel sont rapportées à ±1 et non comme exactes [§3, App. G.4]. Reset / timeouts : un timeout dans le sandbox score 0 [App. G.13] ; politique de reset non précisée. - Gestion des erreurs d'outils et des sorties mal formées. C'est l'objet du papier. Deux dispositifs : 1. Gating de validité des bras, appliqué en code (validate_arms.py, final_table.py, pas par convention) : un bras n'est admissible pour comparaison de pass rate que s'il a exactement 100 items, exit code 0, zéro erreur de requête, et une provenance (modèle / protocole / température / max_tokens / adaptateur) conforme à la configuration visée. Les bras avec erreurs gardent un recensement d'erreurs valide mais sont N/A en pass rate, et aucune p-value n'est calculée pour eux. Un p=0.648 d'une version antérieure, calculé sur un tel bras, est rétracté [§3.3, App. A.3]. 2. Contrôle positif de l'instrument avant d'attribuer un zéro au modèle : même serveur, modèle, outils et prompt, en ne changeant que tool_choice — sous auto le serveur renvoie finish_reason = stop avec tool_calls = 0 pendant que l'assistant écrit la solution en bloc de code ; sous required il renvoie un appel parsé nommant run_tests avec du vrai Python dans arguments. ⚠️ Les auteurs précisent eux-mêmes la limite : cela établit que le pipeline peut accepter un appel conforme, pas que le zéro sous auto vienne du modèle (required passe par du décodage contraint) [§3.2].

2.2 Le mécanisme exact de la censure

Trois parties configurées indépendamment [§1] : 1. ce que le checkpoint a été entraîné à émettre ; 2. ce que le chat template lui dit d'émettre ; 3. ce que le parser est défini à accepter.

Cas canonique : Qwen2.5-Coder émet un appel JSON bien formé mais nu, dans un bloc de code fencé json, et jamais l'enveloppe <tool_call> ; le parser hermes n'accepte que cette enveloppe. Donc hermes ne voit rien — et c'est un comportement correct, pas un bug [§1, §4.3]. L'appel reste dans content, tool_calls est un tableau vide, le code HTTP est 200.

Chaîne de censure : emission → serialization → parse → execution. La censure peut survenir à n'importe quelle frontière, et à chacune l'observable est identique : HTTP 200 + tool_calls: [] [§1].

Deux directions, instanciées proprement toutes les deux [§1] : - masking — un appel valide n'est pas reconnu, l'action n'atteint jamais l'environnement (Qwen2.5-Coder, §4.3) ; - suppression — un appel invalide est retiré du support échantillonnable avant de devenir une action (Llama + strict, §4.5).

D'où la formulation que je retiens : l'interface de serving est simultanément une partie de la fonction de mesure et une partie de l'espace d'actions effectif de l'agent — littéralement sous RL, où ce que la politique émet doit survivre à la sérialisation et au parsing avant de devenir une action qui gagne une récompense [§1].

Ce n'est pas un bug de parser, et c'est démontré, pas affirmé. Rejeu ligne à ligne de l'extracteur hermes de vLLM sur tous les premiers tours stockés de l'archive — 4254 après suppression des doublons byte-identiques — : zéro cas où le serveur a échoué à parser un appel que ses propres règles auraient accepté. « Parser loss » = 0 dans chaque bras [§1, §4.3, Tab. layer, App. G.3].

Taxonomie en quatre couches, quatre familles, quatre remèdes [§4.6, Tab. taxonomy_full] :

Famille Couche Symptôme Détectable à l'avance ? Remède
DeepSeek-Coder template le chat template n'injecte jamais tools ✅ inspection du template aucun
Qwen2.5-Coder parser émet un bloc JSON fencé, pas <tool_call> ❌ le test de template donne un faux positif adaptateur dédié
Llama-3.1-8B schema appelle la fonction de la tâche comme outil (23 %) ❌ exige l'inspection des arguments strict: true
Mistral-7B-v0.3 token répète [TOOL_CALLS] → HTTP 400 ~ erreurs, mais seulement parfois aucun trouvé

Le faux positif est le point le plus vicieux. Le test de dépistage naturel — « est-ce que apply_chat_template(tools=...) rend bien le schéma ? » — rejette correctement DeepSeek-Coder mais accepte Qwen2.5-Coder, qui hérite le scaffolding Hermes de Qwen2.5-Instruct via tokenizer_config.json sans jamais avoir été entraîné dessus. Conclusion des auteurs : le support du protocole est une propriété par-checkpoint et n'est pas inférable du chat template [§4.6, App. B]. Corollaire d'infra : les templates vivent dans tokenizer_config.json et peuvent changer sans changement de modèle → il faut épingler les révisions HF [App. H item 16].

Une seule panne est bruyante. Sur l'omission des flags par famille [Tab. serving, App. D.1] : seul --enable-auto-tool-choice manquant produit un HTTP 400. Toutes les autres omissions renvoient HTTP 200 avec tool_calls vide. Et le cas Qwen2.5-Coder n'a aucune configuration stock fonctionnelle : il faut installer un parser <tools> communautaire plus son chat template.

2.3 La partie RL : pourquoi réparer le serveur ne répare rien

Trois pièges d'infra spécifiques à la boucle d'entraînement, chacun documenté et chacun coûteux [§2, App. D.3–D.5] :

  1. verl AgentLoop parse pour son propre compte. verl/experimental/agent_loop/tool_parser.py, enregistré comme hermes, adapté de vLLM v0.9.1. multi_turn.format=hermes sélectionne ce parser, pas celui du serveur. Donc brancher un plugin de parser sur le serveur vLLM de rollout ne change strictement rien à l'entraînement — « une distinction qui nous a coûté une conception d'expérience » [§2, App. D.5(i)].
  2. Le nom de la métrique est un piège. verl 0.9.0 n'a aucun compteur d'appels d'outils dans ses métriques de step. La métrique nommée timing_s/agent_loop/tool_calls est un temps écoulé en secondes ; la lire comme un compte est une erreur dure, et les auteurs la signalent parce que le nom y invite [App. D.3].
  3. Le compteur ne doit pas être placé dans sandbox.run_tests. La fonction de reward évalue le programme final par la même fonction ; un compteur à cet endroit confond évaluation de la récompense et usage d'outil par l'agent. Les auteurs ont heurté le problème, déplacé le compteur vers les deux sites d'appel côté agent (CodeTool.execute pour FC, ReActAgentLoop._run_tests pour ReAct), et renommé celui du sandbox en sandbox_exec_count pour que les deux ne puissent plus jamais être confondus [App. D.3].

Résultat de l'instrumentation : le fichier de compteur du bras FC a 0 ligne, celui de ReAct en a 788, toutes étiquetées react. Trois signaux mutuellement indépendants concordent : num_turns collé à son minimum de 2, temps d'outil exactement 0.00 s, compteur dédié à 0.000 [App. D.3, Tab. training].

Borne de formulation, posée par les auteurs eux-mêmes : ce qui est mesuré est « appels acceptés par le parser et exécutés = 0 », pas « le modèle n'a jamais tenté d'appeler » — les rollouts FC n'ont pas été sauvegardés [§4.8, App. H item 11].

2.4 Exemple de trajectoire

Le papier ne recopie pas de trajectoire complète. Il recopie en revanche la signature du mauvais appel de Llama/Qwen-1.5B [App. C.5, App. A.2] :

  • faux : {"name": "join_integers", "arguments": {"int_array": [1, 2, 3]}} — le modèle appelle la fonction qu'il est censé écrire ; run_tests ne reçoit aucun code.
  • juste : {"name": "run_tests", "arguments": {"code": "def join_integers(int_array):\n return ','.join(map(str, int_array))"}}.

Noms réellement observés dans le re-run ciblé sur les 23 items : can_form_word, check_password_strength, floyd_warshall [App. A.2].

3. Reward / vérifieur

Deux vérifieurs distincts dans ce papier, à ne pas confondre : le reward d'entraînement et le classifieur d'intention qui sert d'instrument de mesure.

3.1 Le reward d'entraînement (reward_code.py)

  • Type : exécution de tests. Outcome-only : extrait le dernier programme soumis, lance la suite pytest propre à l'item dans le sandbox, renvoie le ratio de passage [App. G.13].
  • Granularité : outcome, crédit partiel (ratio), pas de process reward.
  • Termes additionnels (format, longueur, pénalités) : aucun mentionné.
  • Trois routes de hacking fermées par construction : un run où aucun test ne s'exécute score 0 (et non 1) ; un timeout score 0 ; un item sans chaîne de test score 0 [App. G.13].
  • Deux coutures (« seams ») restantes, auditées plutôt qu'écartées [§6, App. G.13] :
  • (i) le parseur de résumé cherche (\d+) passed sur le buffer stdout/stderr fusionné et prend la première occurrence → un programme qui imprime lui-même une ligne façon pytest pourrait être scoré sur sa propre sortie. N'exige aucune compréhension du harness et pourrait se déclencher par accident ;
  • (ii) skipped / xfail ne sont pas au dénominateur → un rollout qui saute les tests durs est scoré sur le sous-ensemble qu'il n'a pas sauté.
  • Les solutions s'exécutent à l'import sous le layout à deux fichiers, donc les deux coutures sont atteignables en principe.
  • Audit effectif : sur les cinq logs d'entraînement qui conservent du code généré, zéro occurrence d'un "N passed" imprimé, de pytest.skip/allow_module_level, de sys.exit/os._exit ; et critic/rewards/mean oscille dans 0.46–0.73 sans le saut d'échelon que produit un exploit découvert. ⚠️ Limite de l'audit, énoncée par les auteurs : le texte complet des rollouts n'a pas été conservé, l'audit ne couvre donc que les fragments que ces logs portent.
  • Les pass rates rapportés passent par un chemin plus strict (mode="script", exit code seul, all_passed exigeant en plus status=="ok"), donc aucune des deux coutures ne peut les atteindre [App. G.13].
  • Correctifs prévus, non appliqués : ancrer la regex sur la ligne de résumé de pytest elle-même, compter skipped/xfail, séparer le stdout du modèle de la sortie du harness. Non appliqués pour ne pas rendre les futurs runs incomparables à ceux rapportés [App. G.13].

3.2 Le vérifieur de mesure : le critère d'intention

C'est l'instrument qui permet de dire « le modèle a émis un appel que le serveur a jeté ». Une seule fonction (analysis/intent.py), partagée par tout le texte, tous les tableaux et toutes les figures, sans aucun réglage par bras [§3.1, App. C.6]. Recopié verbatim :

TIGHT = re.compile(
    r'"name"\s*:\s*"run_tests".{0,200}?"arguments"\s*:\s*\{'
    r'.{0,80}?"code"\s*:\s*"(.{0,4000}?)"\s*\}', re.S)

REAL  = re.compile(r'\\n|def |class |return |import |lambda ')

def is_tight_call(raw):
    m = TIGHT.search(raw or "")
    return bool(m and REAL.search(m.group(1)))

Trois tiers emboîtés, non exclusifs : tight (nom + objet arguments + clé code dont la valeur est un littéral chaîne contenant du vrai Python — exclut l'écho de schéma, les identifiants passés à la place de chaînes comme "code": test_code, et les placeholders "<your code here>") ; strong ⊇ tight (tag de trajectoire json_named_call ou xml_tool_call, sans exigence sur le payload) ; weak (structure JSON ne nommant pas l'outil, disjoint des deux autres — à 1.5B presque entièrement des faux positifs, rapporté séparément et jamais fusionné) [§3.1, App. C.6].

Fiabilité du vérifieur — mesurée, et c'est rare [App. F] :

Trois points de méthode à voler tels quels : - Les auteurs invalident leur propre première adjudication. Les 13 items ré-examinés au round 1 étaient exactement ceux où l'annotateur divergeait du classifieur (recouvrement 13/13) et les 10 renversements allaient tous vers le classifieur, aucun en sens inverse. « Sous cette règle de sélection l'accord ne peut que monter, donc 0.713 → 0.936 est une propriété du choix des items ré-examinés, pas une preuve de fiabilité. » Ils rapportent le second annotateur à la place [App. F]. - Règle d'adjudication fixée à l'avance pour le second round : revoir toutes les divergences à trois, jamais seulement celles qui s'opposent au classifieur. L'adjudicateur tiers s'est éloigné du classifieur 6 fois sur 15 — « c'est ce chiffre-là qui compte ; la première adjudication s'en était éloignée 0 fois sur 13 » [App. F]. - Le facteur de correction a bougé deux fois et ils publient la trajectoire : 0.950 (adjudication biaisée) → 0.975 (A2 seul) → 0.900 (gold standard adjudiqué). Appliqué uniformément, la tendance est inchangée : 0, 3.6, 18.9, 32.4, 72 contre un zéro côté serveur à chaque taille. Les comptages bruts sont rapportés partout avec le facteur énoncé, plutôt que rescalés silencieusement [App. F].

  • Si juge LLM : aucun juge LLM n'est utilisé pour la récompense. Le seul composant LLM externe est le simulateur d'utilisateur de τ-bench, remplacé par un Llama-3.1-8B servi localement au lieu du gpt-4o du harness original → les scores absolus ne sont pas comparables au leaderboard τ-bench, seule la différence inter-bras est revendiquée [§4.2].
  • Robustesse / attaque du vérifieur : pas d'attaque adversariale menée ; audit passif des deux coutures (ci-dessus). ⚠️ Mon évaluation : l'audit est honnête mais structurellement partiel (texte des rollouts non conservé), et la couture (i) est du type qui se déclenche par accident plutôt que par recherche d'exploit — crédible qu'elle n'ait pas tiré à 1.5B sur 150 steps, non crédible qu'elle reste inoffensive à plus grande échelle ou avec plus de steps.

4. Optimisation

  • Algorithme : GRPO (×2 seeds) et RLOO (×1 seed), les deux en version standard — aucune variante maison revendiquée [Tab. trainconfig, App. D.2].
  • Hyperparamètres rapportés [Tab. trainconfig] : modèle Qwen2.5-Coder-1.5B-Instruct ; framework verl 0.9.0 (backend rollout vLLM 0.27.1) ; trajectoires par step = train_batch_size 16 × rollout.n 8 = 128 ; steps = 150 (runs historiques) et 10 / 3 / 75 pour les bras de §4.8–4.9 ; agent loop tool_agent (FC) ou react_agent (ReAct) ; outil run_tests à un argument code, pytest sandboxé ; prompt système FC_MANDATORY / ReAct mandatory — force appariée ; matériel une A800 80 GB.
  • Non précisé : coefficient et référence du KL, taille de groupe GRPO, calcul et normalisation de l'advantage, clipping, on/off-policy, learning rate, température de sampling à l'entraînement, longueur max de génération côté entraînement. ⚠️ C'est un trou réel pour quiconque veut reproduire la boucle RL elle-même — mais ce n'est pas l'objet du papier, qui porte sur ce que la boucle voit.
  • Dynamique des courbes — et c'est là que le papier a sa valeur [§1, §4.8, Fig. 4] :
  • 150 steps de GRPO : pass@1 sur un split EvalPlus tenu à l'écart monte de 2.6–2.8 points sur trois runs indépendants (p = 0.064 / 0.078 / 0.077 — aucun significatif à α=.05 ; les auteurs disent explicitement que la preuve est la cohérence de direction sur deux algorithmes et deux seeds, pas un test) ;
  • mais 91–94 % des items nouvellement résolus le sont au premier tour, et les items sauvés au tour ≥ 2 restent plats à 6–9 sur 540 du step 0 au step 150 ;
  • lecture naturelle et fausse : « un 1.5B ne peut pas apprendre la réparation multi-turn ». Lecture vraie : l'outil n'a jamais été appelé avec succès. Pas rarement — jamais ;
  • sous FC, critic/rewards/mean monte de 0.233 à 0.281 : la branche sans outil est continûment renforcée pendant que la branche outil a un retour à zéro échantillon dès le step 1.
  • Conséquence théorique, énoncée avec la bonne prudence : « la branche utilisant l'outil ne reçoit aucun gradient on-policy direct sous la distribution de rollouts observée, et est effectivement inaccessible à l'apprentissage par policy gradient dans ce régime de cold start ». Pas « mathématiquement inatteignable » — zéro échantillon observé n'est pas probabilité zéro [§4.8, App. H item 10].
  • Stabilité / compute. GPU-heures et durée : non précisé. Deux pannes d'infra rapportées au lieu d'être tues : la sonde dans verl à 7B s'est terminée par un CUDA OOM pendant l'update de l'acteur suivant la collecte des rollouts, donc aucun pas de gradient n'a été complété (les observations de rollout précèdent toutes ce point) [§4.8] ; et l'évaluation au step 75 du bras ReAct a été perdue parce que l'écriture du checkpoint a saturé le disque après la fin de l'entraînement [§4.9]. Le RL full-parameter à 7B ne rentre pas sur la carte unique de 80 GB — d'où l'absence du bras de contrôle qui compte (§7).

5. Failure modes & reward hacking

Format : comportement → détection → correction. Douze cas, dont une majorité n'est documentée nulle part ailleurs dans le corpus.

  1. Masking d'interface (Qwen2.5-Coder × hermes) → appel JSON nu bien formé, jamais l'enveloppe <tool_call> ; HTTP 200, tool_calls: [] → détecté par le critère d'intention sur les octets émis + re-parse offline des mêmes octets sous 4 règles + rejeu ligne à ligne de l'extracteur → corrigé par un adaptateur dédié (parser <tools> communautaire + chat template + few-shot) : parse 0 → 84/100 à 7B [§4.3, §4.7, Tab. reparse].
  2. Role confusion / suppression (Llama-3.1-8B, 23 %) → l'appel nomme la fonction que la tâche demande d'implémenter, avec les paramètres de cette fonction en arguments ; un re-run restreint à ces 23 items reproduit 23/23 → détecté seulement par inspection des arguments (la sonde ne vérifiait pas le nom de l'outil : erreur de mesure propre aux auteurs, taux d'initiation corrigé de 97/100 à 74/100) → corrigé par strict: true : 23 → 0 (p=0.0001) [§4.5, App. A.2].
  3. Couche template (DeepSeek-Coder) → le chat template n'injecte jamais tools → détecté par inspection du template (le seul cas que le test naturel attrape) → aucun remède trouvé [§4.6].
  4. Couche token (Mistral-7B-v0.3) → répète un marqueur [TOOL_CALLS] → HTTP 400 ; aucun run FC de 100 items admissible, sous aucune des quatre configurations (erreurs : parser seul 2 ; template officiel 42 ; parser+strict 3 ; template officiel+strict 39) → la configuration recommandée par vLLM elle-même fait passer le taux d'erreur de 2 % à 42 %, et strict, qui répare Llama, n'aide pas → aucun remède [§4.6].
  5. Faux positif du test de dépistage naïf → apply_chat_template(tools=...) rend le schéma pour Qwen2.5-Coder (scaffolding Hermes hérité de Instruct via tokenizer_config.json) alors que le checkpoint n'a jamais été entraîné dessus → l'inspection de template ne suffit pas, le support du protocole est une propriété par-checkpoint [§4.6].
  6. La pression sur une interface cassée aggrave tout — trois instances indépendantes [§4.5, App. G.9] : - scaffold Thought ajouté à FC : mauvais outil 23 → 59 (p<0.001, pire) — le modèle fournit exactement les paramètres sur lesquels il vient de raisonner ; - prompt mandatory au lieu d'optional sur Coder-1.5B : appels acceptés toujours 0/100, pass final 31 → 15, sorties non parsables ~0 → 46/100 ; - few-shot de désambiguïsation de rôle à 1.5B : appels récupérables 52 → 64, appels nommant run_tests toujours 0, pass final 15 → 13 — « le modèle est devenu plus fluide à émettre le mauvais appel ». → Règle à retenir : quand un agent semble réticent à utiliser ses outils, renforcer l'instruction est la chose la moins chère à essayer et la plus susceptible d'induire en erreur — ça dégrade la performance tout en laissant le compteur d'appels à zéro, ce qui ressemble à un modèle à la fois récalcitrant et incapable.
  7. Non-monotonie de l'adaptateur → le même adaptateur récupère 84/100 à 7B et 1/100 à 3B (le 3B ignore entièrement le few-shot <tools> : zéro tag <tools> sur 100 items, 99 réponses en code direct) tout en résolvant la tâche à un taux comparable (final 53) → « les adaptateurs ne sont pas un interrupteur universel » [App. G.8].
  8. Contamination par le template tiers → le template communautaire contient des few-shots invoquant get_weather, un outil absent du schéma : laissé tel quel il aurait induit des appels à un outil inexistant, gonflant simultanément le compte d'initiations et la statistique d'arguments vides → corrigé en réécrivant les few-shots vers run_tests, hashes de l'original et du modifié conservés [App. A.6, App. G.8].
  9. L'annotateur humain reproduit l'erreur du parser → 12 des 98 annotations du round 1 ont manqué un appel d'outil parce qu'il se trouvait après un bloc de code fencé : l'annotateur a lu le bloc de code, conclu « réponse directe, pas un appel », et s'est arrêté (positions de match 1209–2585 dans des sorties de longueur médiane ~2000). Onze sont des échecs d'ordre de lecture, un est un échec d'instrument (le pack d'annotation tronquait à 2400 caractères alors que le span commençait au caractère 2585 : la preuve n'était pas dans le pack) → corrigé en portant les sorties en entier → « l'annotateur, comme le parser, a conclu des mêmes octets qu'aucun appel n'avait été fait » [§7, App. F].
  10. Piège de nom de métrique → timing_s/agent_loop/tool_calls dans verl est un temps en secondes, pas un compte [App. D.3].
  11. Piège de placement du compteur → un compteur dans sandbox.run_tests confond évaluation de la récompense et usage d'outil, parce que la fonction de reward passe par la même fonction [App. D.3].
  12. Reward hacking proprement dit → deux coutures du vérifieur d'entraînement (première occurrence de (\d+) passed sur stdout/stderr fusionné ; skipped/xfail hors dénominateur), atteignables en principe, auditées, aucune preuve d'exploitation (zéro "N passed" imprimé, zéro pytest.skip, zéro sys.exit sur les cinq logs qui gardent du code ; critic/rewards/mean oscille 0.46–0.73 sans saut d'échelon) [§6, App. G.13].

Comportements émergents inattendus. Positif : avec strict, la chaîne contrainte → exécution valide (73→97) → performance de tâche (turn-1 33→46, final 44→61) : 23 items qui ne produisaient aucun code exécutable s'exécutent et deviennent réparables [§4.5]. Négatif : la boucle de réparation absorbe la perturbation en amont — pass final ReAct identique (72/72/72) à temperature=0.6 alors que les ensembles résolus ont un Jaccard par paires de 0.71–0.80 (15–24 items diffèrent) ; entre les steps 15 et 30, 85 des 542 complétions de premier tour changent verbatim et 6 items basculent (3 gagnés, 3 perdus) pour un total numériquement identique (340/346 aux deux checkpoints). Conséquence de mesure : un pass rate agrégé est un mauvais instrument pour détecter du changement dans un agent multi-turn — il est stabilisé par le mécanisme même qu'on étudie, et la comparaison d'ensembles au niveau item détecte le mouvement que le total dissimule. « Si nous n'avions rapporté que les totaux, nous aurions conclu — deux fois, sur deux axes différents — qu'il ne se passait rien » [App. G.10].

5.1 ⭐ Le test de dépistage à lancer avant un run

C'est le livrable du papier. Quatre niveaux, du moins cher au plus cher.

Niveau 0 — preflight_toolcall.py, 98 lignes, publié [§5, App. D.1]. Tourne en secondes et « aurait attrapé toutes les pannes silencieuses rapportées ici » : 1. émettre une requête canonique portant tools ; 2. asserter que tool_calls est non vide, avec le nom attendu et des arguments parsables ; 3. répéter sous tool_choice: required comme contrôle positif (cela sépare « le serveur ne peut pas » de « le modèle ne sait pas spontanément »).

Niveau 1 — ne pas se fier à l'inspection du template. Elle donne un faux positif sur Qwen2.5-Coder. Le support du protocole est une propriété par-checkpoint [§4.6].

Niveau 2 — rapporter la composition, pas le modèle. Toute éval d'agent doit rapporter au minimum : (i) appels parsés par le serveur, (ii) appels émis mais non parsés sous un critère énoncé, (iii) erreurs de requête, (iv) la configuration de serving exacte. Ne rapporter que (i) est la pratique que ce papier attaque — et (ii) est là où vit toute la tendance d'échelle [§5].

Niveau 3 — à l'intérieur de la boucle RL, et c'est celui qu'on oublie. « Les praticiens doivent vérifier un compte d'exécutions d'outils non nul au premier step d'entraînement avant d'interpréter le moindre résultat multi-turn » [§5]. Trois précisions non négociables tirées de App. D.3–D.5 : - le preflight doit tourner dans le chemin de rollout du framework RL, pas seulement contre le serveur : verl parse avec son propre registry, un plugin côté vLLM ne l'atteint pas ; - le compteur doit être aux sites d'appel côté agent, jamais dans la fonction de sandbox que la récompense utilise aussi ; - ne pas lire une métrique de timing comme un compte.

Condition générale de danger, énoncée par les auteurs [§5] : dès que (a) les trajectoires outil sont censurées à un taux ≈ 1 et (b) la récompense admet un chemin sans outil, la branche outil n'a aucun retour échantillonné et ne peut pas être renforcée. ⚠️ Mon évaluation : c'est la formulation la plus transférable du papier, et elle est indépendante du stack — elle s'applique mot pour mot à un harness juridique (cf. §9).

6. Infra & coût

  • Matériel : une seule A800 80 GB pour tout l'entraînement [Tab. trainconfig]. Pas de modèle frontier, échelle arrêtée à 32B en inférence [App. H item 7].
  • Débit de rollouts : non précisé en tant que tel. Chiffres dérivables : 128 trajectoires/step ; bras ReAct de 75 steps GRPO = 23 676 appels d'outils exécutés ; temps d'outil moyen par rollout 12.21 s (ReAct) contre 0.00 s (FC) [Tab. training, §4.9].
  • Sync vs async, parallélisme des environnements : non précisé pour l'entraînement. Côté BFCL, le bras réparé fait tourner 8 threads à travers l'exécuteur multi-turn, ce qui est précisément pourquoi le greedy n'est pas bit-à-bit reproductible et pourquoi les colonnes du funnel sont à ±1 [App. G.4].
  • Coût par step / par rollout : non précisé.
  • Goulots d'étranglement documentés : (a) RL full-parameter à 7B ne rentre pas sur 80 GB → le bras de contrôle décisif n'existe pas ; (b) CUDA OOM pendant l'update de l'acteur de la sonde 7B → aucun pas de gradient complété ; (c) saturation disque à l'écriture du checkpoint → évaluation du step 75 perdue ; (d) l'hôte manquait de pytest lors du premier passage sur la ladder Instruct, rendant la couche multi-turn vide — les cinq bras ont été re-tournés avec un exécuteur fonctionnel, sans rien changer d'autre ni toucher au binaire de la sonde, et la colonne parse a reproduit valeur pour valeur [§4.4, §4.8, §4.9].

⚠️ (d) est en soi un mini-enseignement d'infra : une couche entière du funnel peut être à zéro parce qu'un binaire manque sur l'hôte, et seule la re-mesure couche par couche le distingue d'un échec de modèle.

7.2 In-distribution vs OOD, transfert

  • La couche enveloppe est invariante au domaine ; la couche payload ne l'est pas. Sur τ-bench (arguments = scalaires courts, {"order_id": "W123"}, vs un programme entier chez eux), le rejeu de l'extracteur sur les 789 tours émis-non-parsés place 789/789 (100 %) à la couche enveloppe, avec 0 payload malformé, 0 récupérable par décodage indulgent, 0 parser loss. Même signature qu'en code : appel nu dans un fence json, jamais l'enveloppe. À l'inverse, Qwen2.5-Instruct perd 41 % de ses items non parsés en payloads malformés sur la tâche de code — un mode d'échec que des arguments scalaires courts ne peuvent pas produire. Les auteurs énoncent explicitement : « nous attendons que le résultat de couche enveloppe généralise et que les proportions de couche payload non — et nous le posons comme prédiction, pas comme mesure, ayant testé un domaine non-code et non un échantillon de domaines » [§4.2].
  • Transfert vers d'autres envs : mesuré sur deux suites externes (BFCL v4 et τ-bench retail), donc le problème de validité de mesure n'est pas spécifique à leur harness. Restent non testés : les suites à schémas d'outils beaucoup plus grands, celles dont le scoring dépend d'un matching au niveau des arguments, la sélection d'outil parmi plusieurs (tout le papier est à un seul outil — et un schéma mono-outil est le cas le plus facile pour un parser, ce qui ferait de la censure mesurée un minorant : argument, pas mesure) [§6, App. H items 1 et 4].
  • Ce qui reste code-only : la ladder d'échelle et la contamination RL. Les auteurs ne s'attendent pas à fermer la seconde : la récompense est un ratio de passage pytest, donc la porter change environnement, récompense et tâche en même temps [App. H item 1].

  • Dépendance d'échelle de la conséquence RL : à 7B l'absence de trajectoires outil est attribuable à l'interface ; à 1.5B le zéro est sur-déterminé (0 appel bien formé, 54 réponses directes, 46 sorties non parsables, 66 items contenant des fragments JSON mais pas un seul nommant run_tests → échec de capacité, pas de parser). Les auteurs rapportent les deux échelles séparément plutôt que de fusionner [§4.8].
  • Non-monotonie de l'efficacité de l'adaptateur : 84/100 à 7B, 1/100 à 3B [App. G.8].
  • Aucune seconde famille de ladder ; Granite-3.1-8B donne 0 sous hermes et 0 sous son propre parser granite → bras non informatif plutôt que confirmatoire, et les auteurs ne revendiquent rien dessus — « c'est ce bras de secours qui nous dit que le bras est non informatif » [§4.3].

7.5 Solidité

  • ✅ Baselines appariées — les 50 bras longs partagent un seul jeu de 100 items (distinct-set count vérifié = 1) ; les comparaisons BFCL et τ-bench tiennent poids, cas, décodage, seeds, exécuteur et scorer fixes et ne changent que l'adaptateur ; BFCL/τ-bench tournent sur leur propre code à commit épinglé.
  • ✅ Ablations qui isolent la contribution — le 2×2 localise l'effet dans l'interaction, le re-parse offline et le rejeu ligne à ligne ferment les deux objections évidentes, les quatre contrôles Llama sont à variable unique.
  • ❌ Variance / seeds — les bras de tête (Tab. repair, les deux ladders) sont un seul échantillon à temperature=0. La variance n'est estimée que sur Llama-3.1-8B, où 2 des 3 bras FC seulement sont admissibles (seed 3 rejeté : appels d'outils parallèles refusés par vLLM) → intervalle [62, 66] et aucun écart-type. Les auteurs ajoutent le garde-fou correct : les trois finals ReAct identiques (72/72/72) sont une coïncidence de totaux, pas des ensembles d'items identiques, et sd = 0.00 ne doit pas se lire « ReAct est parfaitement stable ».
  • ✅ Fiabilité de l'éval — KodCode décontaminé par containment n-gram contre EvalPlus ; classifieur validé contre un gold standard adjudiqué par un tiers sous règle fixée à l'avance (κ = 0.871) ; inter-annotateurs κ = 0.967 sur octets identiques ; gating de validité appliqué en code ; versions, hashes de parser/template et révisions HF épinglés. ⚠️ Réserve : échantillon de validation stratifié par verdict du classifieur → estime précision/rappel par strate, pas un taux de population ; et plafond de 4000 caractères → minorant.
  • ⚠️ Échelle — s'arrête à 32B en inférence, RL à 1.5B seulement (zéro sur-déterminé), sonde 7B qui OOM ; une seule A800 ; aucun modèle frontier. La question « est-ce que Gemini-classe souffre de ça » n'est pas tranchée par ce papier.
  • ✅ Reproductibilité — dépôt joignable (HTTP 200 vérifié le 2026-10-19), trajectoires des 50 bras, logs d'entraînement, ERRATA.md, index par configuration, préenregistrements, commandes exactes, hashes SHA256 du parser tiers et des templates (original et modifié). ⚠️ Je n'ai pas audité le contenu du dépôt. Trou connu et divulgué : un champ script_sha256 n'a jamais pu être ajouté (patch interrompu deux fois), l'identité du script est garantie extérieurement par hashage avant/après lancement.
  • ✅ Cohérence texte ↔ chiffres — voir 7.0 ; un seul chiffre non tabulé (0.96), et un appareil d'errata qui rétracte et corrige activement.

Verdict. Solide sur le mécanisme (mesure en cinq couches, décomposition 2×2, contrefactuel préenregistré, zéro parser loss sur 4254 tours) ; fragile sur l'effet d'outcome — aucun gain de performance ne survit à Bonferroni, et les auteurs le disent avant qu'on ne le leur reproche ; non prouvé sur la causalité RL — il n'existe aucun bras repaired-FC d'entraînement, la comparaison change protocole et interface ensemble, et les auteurs refusent explicitement de revendiquer « la censure empêche le RL d'apprendre la réparation multi-turn ». Ce qu'ils revendiquent et qui tient : la censure d'interface est observable directement dans la collecte de rollouts et élimine les échantillons médiés par outil.

⚠️ Mon évaluation du cas le plus inconfortable, que les auteurs mettent eux-mêmes en conclusion : trois contrôles à variable unique sur un échec de 23 % ont conclu à un défaut du modèle ; un quatrième, tiré d'une phrase de la documentation de serving, l'a réduit à zéro. Et leur propre validation humaine a reproduit le mécanisme : douze annotations sur 98 ont manqué un appel parce qu'il se trouvait après un bloc de code fencé. Rapporter des taux d'appels d'outils parsés côté serveur comme une capacité du modèle n'est pas un défaut sûr.

9.2 À quoi ça ressemble sur un harness de recherche juridique

Le mécanisme se transpose couche par couche, et chaque couche a une incarnation juridique concrète.

Couche enveloppe (le cas Qwen2.5-Coder, celui qui est invariant au domaine, 789/789 sur τ-bench). Le modèle émet un appel de citator bien formé dans un format que le parser du harness n'accepte pas — par exemple un bloc fencé json nu au lieu de l'enveloppe attendue. Le serveur renvoie 200, tool_calls: [], et l'appel reste dans content. Observable : identique à un modèle qui n'a pas cherché à vérifier sa citation — c'est-à-dire exactement le comportement qu'on veut pénaliser. C'est le résultat du papier que les auteurs attendent voir généraliser hors du code, et leur seul test non-code le confirme à 100 %.

Couche payload (le cas Qwen2.5-Instruct, 41 % de payloads malformés sur la tâche de code). Le papier identifie la cause précise : guillemets de docstring et retours à la ligne bruts non échappés à l'intérieur d'une chaîne d'argument longue. Transposition directe et prévisible : - citations mal formées : une citation Bluebook passée comme chaîne libre ("410 U.S. 113 (1973)") là où l'outil attend {reporter, volume, page, year} ; un pinpoint (at 164) fusionné dans le même champ ; un ECLI (ECLI:EU:C:2019:772) dont les deux-points cassent un parser naïf ; un numéro de pourvoi français (n° 19-21.823) dont le ° et le point intérieur passent mal l'encodage ; - passages cités longs : un extrait de jugement de 800 mots passé en argument passage d'un quote_check — guillemets internes, apostrophes typographiques, retours à la ligne bruts → payload cassé. C'est mot pour mot le mode d'échec de Qwen2.5-Instruct, avec un extrait d'arrêt à la place d'une docstring Python. ⚠️ Et c'est la couche dont les auteurs disent explicitement qu'elle ne généralise pas en proportion : les arguments scalaires courts ({"order_id": "W123"}) ne peuvent pas la produire. Un harness juridique passe des chaînes longues → nous sommes du mauvais côté de cette distinction ; - formats de dates : 2024-01-15 vs 15/01/2024 vs January 15, 2024 vs 15 janvier 2024. Un date_range mal sérialisé ne lève pas d'erreur si le parser est indulgent — il retourne silencieusement le mauvais corpus (droit en vigueur à la mauvaise date). C'est une variante pire que la censure : non pas zéro observation, mais une observation fausse qui passe le vérifieur de format.

Couche schema (le cas Llama, 23 %). Le modèle appelle la tâche elle-même comme un outil : au lieu de search_caselaw(query=...), il émet analyse_clause(contract=..., clause_id=...) ou rediger_memo(question=...) — la fonction qu'on lui demande d'exécuter, avec les paramètres de cette fonction en arguments. Signature identique à can_form_word / check_password_strength. Remède identique et à un flag près : strict: true + additionalProperties: false. Rappel du papier : les trois contrôles « intelligents » (schéma plus explicite, scaffold de raisonnement, template officiel) n'ont rien donné ou ont aggravé — seul le flag a marché.

Couche template. Le chat template de la variante de Gemini utilisée n'injecte pas les outils, ou les injecte dans un format que le checkpoint n'a pas vu. Le test d'inspection du template donne un faux positif quand le template est hérité : c'est précisément le cas Qwen2.5-Coder. Pour nous, cela veut dire qu'un harness juridique validé sur un checkpoint ne l'est pas sur le suivant.

Multi-juridiction = un contrat par juridiction. Le papier établit que le contrat est par-checkpoint. En juridique il est par-checkpoint × par-outil × par-juridiction : un citator Légifrance (identifiants JURITEXT…), un citator US (Bluebook), un citator UE (ECLI) sont trois grammaires d'arguments. Un taux d'appels d'outils agrégé dissout un zéro par juridiction dans une moyenne saine. Le funnel doit être ventilé par juridiction, pas seulement par outil.

⚠️ Le danger maximal, et c'est le point à retenir du papier. La condition générale énoncée en §5 est : (a) trajectoires outil censurées à un taux ≈ 1 et (b) la récompense admet un chemin sans outil → la branche outil n'a aucun retour échantillonné et ne peut pas être renforcée. Un reward juridique à rubriques satisfait (b) par construction : une réponse fluide, bien structurée et non sourcée gagne du crédit partiel sur la plupart des rubriques. Donc si les appels de citator sont censurés, le RL n'apprend pas seulement rien sur la vérification — il apprend activement à répondre sans vérifier, parce que c'est la seule branche qui a un retour positif échantillonné. Le papier le montre numériquement : critic/rewards/mean monte de 0.233 à 0.281 pendant que la branche outil est à zéro échantillon depuis le step 1. Un run de post-training juridique dans cet état produit un modèle mesurablement meilleur et systématiquement plus halluciné sur les citations.

9.3 Meilleur ingrédient à transposer

Le dépistage en cinq couches, et son assertion au step 1. Pas le preflight de 98 lignes seul — la discipline de mesure complète : séparer intent émis / format émis / parse serveur / exécution réelle / sauvetage multi-turn en cinq quantités mesurées indépendamment, et refuser d'interpréter un résultat multi-turn tant que le compte d'exécutions d'outils du premier step est à zéro. Pourquoi celui-là : c'est le seul ingrédient du papier qui soit (i) indépendant du stack et du domaine — la condition (a)+(b) ne mentionne ni vLLM ni pytest —, (ii) à coût quasi nul (secondes vs une semaine de TPU), et (iii) soutenu par l'evidence la plus forte du papier (2×2 à effets principaux nuls, 4254 tours sans parser loss, contrefactuel préenregistré). Les autres ingrédients — l'adaptateur, strict: true — sont des remèdes à des pannes spécifiques à des familles de modèles que nous n'utilisons pas.

Second ingrédient, sous-estimé : un pass rate agrégé est un mauvais instrument pour détecter du changement dans un agent multi-turn [App. G.10]. La boucle de réparation absorbe la perturbation en amont (total identique, Jaccard 0.71–0.80 ; 85 complétions sur 542 changent verbatim pour un total inchangé). Sur Harvey LAB / Vals, rapporter le score agrégé seul nous fera conclure deux fois qu'il ne se passe rien. Il faut la comparaison d'ensembles au niveau item.

9.4 Expérience minimale

Coût : < 1 jour-personne, zéro GPU d'entraînement.

  1. Écrire preflight_legal_toolcall.py sur le modèle du script publié : une requête canonique par (outil × juridiction) portant tools ; asserter tool_calls non vide, avec le bon nom et des arguments parsables ; répéter sous tool_choice: required comme contrôle positif. Trois outils × trois juridictions = 18 requêtes.
  2. Écrire l'analogue du critère d'intention (TIGHT/REAL) par outil : pour citator, un objet JSON nommant l'outil dont l'argument citation est un littéral chaîne matchant la grammaire de citation de la juridiction ; exclure les contaminants que le papier a rencontrés — écho de schéma, identifiant passé au lieu d'une chaîne, placeholder ("<citation ici>"). Une seule fonction, partagée par toutes les tables, aucun réglage par bras.
  3. Instrumenter les sites d'appel côté agent, jamais la fonction de récupération que le juge/vérifieur utilise aussi (le piège sandbox.run_tests). Vérifier que la métrique lue est un compte et non un timing.
  4. Lancer un run de 1 step et asserter en dur : exécutions d'outils > 0, par outil et par juridiction.
  5. Faire tourner le même funnel en cinq couches sur une passe d'éval Harvey LAB / Vals existante, et rapporter les quatre quantités.

Résultat attendu. Deux issues, toutes deux informatives. (i) Tout parse → coût ~0, et on a gagné une assertion permanente en CI. (ii) Au moins un couple (outil, juridiction) à zéro parsé avec des appels émis non nuls — mon pari est sur citator + juridiction non-US, à cause de la grammaire de citation et de l'encodage. Par analogie avec Tab. repair (0→84), le gain n'est pas un gain de score : c'est l'existence de la branche. Et par analogie avec Fig. 4, le signal qui aurait manqué est plat et crédible — des sauvetages multi-turn qui ne bougent pas, qu'on aurait attribués au modèle.

Expérience de second rang, celle que les auteurs désignent comme la plus susceptible de les réfuter : un comparatif broken-FC vs repaired-FC en RL, tout le reste fixé, à une échelle où le modèle émet effectivement des appels bien formés. Les auteurs ne l'ont pas : leur 1.5B n'émet rien à accepter et leur 7B ne tient pas sur une carte. Nous avons le compute qu'ils n'avaient pas, et c'est exactement l'expérience qui dirait si la censure d'interface empêche l'apprentissage multi-turn ou seulement le rend invisible. À 2 bras × 1 run, c'est peu cher pour une question que la littérature ne tranche pas.

9.5 Question à poser en interne chez GDM

Trois, par ordre de coût si la réponse est mauvaise :

  1. Qui possède le contrat à trois ? Le format d'appel d'outils sur lequel le checkpoint Gemini a été post-entraîné, le chat template du harness juridique, et le parser du framework RL : est-ce que ces trois-là sont validés ensemble, par quelqu'un de nommé, à chaque nouveau checkpoint ? Le papier montre que chacun peut être correct séparément et que l'ensemble vaut zéro (effets principaux exactement nuls).
  2. Le chemin de rollout du post-training parse-t-il les appels d'outils avec le même code que le harness d'éval ? C'est la découverte qui a coûté une conception d'expérience aux auteurs : verl parse avec son propre registry, et réparer le serveur ne répare pas l'entraînement. Si les deux chemins diffèrent, un preflight contre le serveur de serving ne prouve rien sur l'entraînement.
  3. Les chiffres Harvey LAB / Vals rapportent-ils les appels émis-mais-non-parsés et les erreurs de requête, ou seulement les appels parsés ? Si c'est seulement le troisième, alors nos scores de référence sont des mesures de la composition Gemini × harness × parser, et une amélioration de harness sera lue comme une amélioration de modèle — ou l'inverse.

Et une assertion à faire adopter, une ligne : aucun run de post-training juridique ne démarre sans un compte d'exécutions d'outils non nul au step 1, ventilé par outil et par juridiction.
