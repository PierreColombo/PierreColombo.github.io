0. En une phrase

Position/system paper (4 pages, aucune section expérimentale) : SMART, une librairie de performance modeling symbolique pour systèmes ML dont la branche master ne contient quasiment pas de code — un DAG de 50 design docs en langage naturel (~9 000 lignes de prose) [Conclusion], régénéré intégralement en code par un orchestrateur + un sous-agent de codage par doc, en ordre topologique [§2, Fig. 1].

Claim principal : traiter les design docs (et non le code) comme l'artefact durable annule « par construction » la dette d'incrémentalité $D_{t+1}=\lVert G(S_{t+1},C_t)-G(S_{t+1})\rVert$ [Éq. 1, §1], et les implémentations régénérées reproduisent des modèles de référence audités à la main — dont DeepSeek-V3 servi sur un pod slice TPU — « à la précision d'arrondi » [Abstract].

⚠️ Aucun RL, aucun environnement, aucun reward, aucun vérifieur appris : hors périmètre de la revue. Le mot « agent » désigne ici des coding sub-agents en inférence, non entraînés.

Le seul point à retenir

  • La seule preuve chiffrée du papier est absente du corps. Le claim « reproduce hand-audited reference models […] to round-off precision » n'apparaît que dans l'Abstract : pas de section résultats, pas de tableau, pas de figure de résultat, pas de protocole de réconciliation chiffré. Verdict 7.0 : introuvable. Les seuls chiffres effectivement tabulés/énoncés dans le corps sont opérationnels : rebuild complet en 1,5–3 h, ~100 USD d'API, ~20 % d'un budget hebdomadaire Claude Max [§2] ; 50 docs / ~9 000 lignes [Conclusion].
  • Ce qui est transposable au juridique (indirect, niveau 2) : le pattern « worked example + reconciliation anchor ». Les auteurs affirment que ce qui rend la régénération fiable n'est pas la « constitution » top-down (tests + règles) mais les worked examples bottom-up — dérouler pas à pas une exécution, valeurs intermédiaires comprises — et que « every number-bearing doc ends with a reconciliation anchor: a small preset whose expected outputs are stated exactly and enforced by generated tests » [§2, An opinionated way of writing design docs]. Transposition possible pour spécifier une rubrique juridique : chaque critère de rubrique accompagné d'un cas travaillé et d'un petit jeu d'ancrage à sortie exacte, servant de test du juge. ⚠️ Aucune mesure ne soutient cette recette ici — idée, pas evidence.
  • Deuxième idée exploitable, non évaluée : le log d'orchestrateur comme signal de difficulté — l'orchestrateur journalise où les sous-agents peinent à interpréter la prose, ce qui indique aux humains quels docs réécrire, et permet un routing dynamique (gros modèle sur les docs fondateurs, petits modèles en aval) [§2, bénéfices 2 et 3]. Analogue possible : router l'effort d'annotation experte vers les items où les rollouts divergent le plus.
  • ⚠️ Écarté en C : pas de RL, pas d'env, pas de baseline, pas d'ablation, pas d'éval. À citer au mieux comme référence rhétorique sur « spec-as-source-of-truth », jamais comme evidence.

Justification des 6 cases d'evidence

  1. baselines ❌ — aucune comparaison : ni workflow incrémental, ni codebase maintenue à la main, ni autre générateur.
  2. ablation ❌ — les deux ingrédients revendiqués (worked examples, IR minimale) ne sont jamais retirés ni testés séparément.
  3. variance ❌ — aucune régénération répétée, aucun seed, aucun intervalle ; pourtant la génération par LLM est stochastique par nature.
  4. coherence ❌ — le claim central de l'abstract (reproduction « to round-off precision », DeepSeek-V3 sur TPU pod slice) n'a aucune source dans le corps ni en annexe (le papier n'a pas d'annexe).
  5. eval ❌ — aucune évaluation : pas de métrique de correction du code régénéré, pas de taux de tests passés, pas de comparaison aux références annoncées.
  6. repro ❌ — ni docs, ni code, ni tests publiés ; aucun lien de dépôt dans le papier ni dans les sources LaTeX.

(Cases toutes jugées applicables : le papier avance un claim empirique explicite dans son abstract, donc aucune case n'est marquée n.a.)
