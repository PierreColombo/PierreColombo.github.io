0. En une phrase

TL;DR — pour évaluer un agent data-science dont la bonne réponse change avec les données, on n'écrit pas la réponse mais la fonction Python qui la recalcule (ground-truth-as-code), exécutée en parallèle de l'agent contre le même état de la base, puis on compare réponse et référence au niveau du factoid (précision / rappel / accuracy) plutôt qu'holistiquement.

Claim principal précis : sur 53 test cases d'un skill ML interne, un juge LLM alimenté par une ground truth exécutable s'accorde mieux avec 3 annotateurs experts (PASS/FAIL) qu'un juge alimenté par la même ground truth en langage naturel — MCC 0.427 vs 0.331, soit +29 % relatif — pour −16 % de tokens par test case ; un juge sans ground truth explicite est anti-corrélé aux humains (MCC = −0.379) [abstract, §1, Tab. 3].

⚠️ Trois précisions qui changent la lecture : 1. « Skill » n'est pas une compétence. Au sens du papier, un skill est l'artefact logiciel au sens Agent Skills — « bundles of markdown, scripts, connectors, and tools that augment the harness while reusing its native engineering features » [§2, citant jiang2026sok]. « Skill-based » veut dire (a) l'unité sous test est un skill déployé, (b) le pipeline d'évaluation est lui-même implémenté comme un harness skill [§1, §3.1]. Il n'y a aucune taxonomie de compétences, aucun rattachement tâche→skill, aucun routage multi-skill dans ce papier. Voir §1 ci-dessous pour ce qui joue réellement ce rôle. 2. Le gain MCC vient quasi entièrement du rappel (1.000 vs 0.920), pas de la précision (0.568 vs 0.561) [Tab. 3]. 3. L'annexe révèle que, dans le benchmark validé, G_i ne recalcule pas depuis les données live : « In this benchmark the function retrieves and formats the reference specification for the case » [App. A]. Le cœur du claim n'est donc pas exercé par l'expérience qui le valide. Détail en 7.0.

1. Tâches & data

Origine des tâches. Écrites par des experts internes. Le papier ne décrit jamais de pipeline de génération de tâches ; il dit seulement que la curation de la ground-truth-as-code « currently rests on expert authoring and review » et qu'« a systematic method for auto-generating the ground-truth code remains to be explored » [Limitations]. Nombre d'auteurs de tâches, temps passé : non précisé.

Volume. 55 test cases single-turn, dont 53 retenus pour l'analyse PASS/FAIL [§5]. La raison de l'exclusion des 2 autres est non précisée. ⚠️ n = 53 pour toutes les conclusions du papier.

Périmètre. Les 55 cas ciblent deux sous-tâches d'un unique skill ML interne : ML-goal identification et dataset discovery à partir d'une requête utilisateur abstraite [§5]. Le skill complet fait plus (construction des input variables et du target feature, exprimée en Python exécutable) [§5] ; App. A montre un cas noté aussi sur target_mapping_function, observation_window_days, outcome_window_days, failure_modes.

Ce qui joue le rôle de « décomposition en compétences ». Trois niveaux imbriqués, aucun n'étant une ontologie de skills : - skill (artefact) → sous-tâches (ML-goal id., dataset discovery) : découpage éditorial du test-bench, chaque cas visant une ou deux sous-tâches. Comment un cas est rattaché à une sous-tâche : non précisé (les cas sont écrits pour, pas classifiés). - sous-tâche → clés de ground truth : G_0 est appelé avec gt_keys=['ml_goal_type','target_variable','expected_datasets','input_variables','target_mapping_function','observation_window_days','outcome_window_days','failure_modes'] [App. A]. C'est le vrai vecteur de compétences du papier : une liste nommée de dimensions attendues, portée par la signature de la fonction de référence. - clés → factoids : granularité finale du score, avec « failure-clustering by fact type » [§6] et des catégories d'issues remontées par le juge (Wrong datasets, Wrong target mechanism, Missing event aggregations, Leakage not flagged, Wrong observation window) [Tab. 5].

⚠️ La conséquence pratique — et c'est elle qui est intéressante — est que le score par compétence n'est pas déclaré dans une taxonomie : il émerge des clés de la fonction de référence. Le schéma de G_i est la grille de compétences.

Pipeline de construction de la base (pas des tâches). [§4] 1. Base synthétique reproduisant schéma, relations d'entités et structure temporelle « continuously advancing » de la production. 2. Moteur Poisson–DAG générant events de comportement, profils clients, catalogue de domaine, sur 3 verticales × fenêtre glissante de 26 semaines, calibré sur les taux d'événements / tailles de cohortes / cardinalités du catalogue de production. 3. Déployée sur un live stage sandbox derrière les mêmes APIs que la production, « so moving to production data requires only a credentials swap » [§4]. 4. Couche de réalisme : seeds fixes, distributions intra-verticale réalistes (credit tiers, income bands, insurance types, chronic-condition flags, loyalty tiers) + injection de column confounds (noms de colonnes plausibles mais sémantiquement trompeurs) « to prevent trivially correct schema matches » [§4]. 5. Decoy datasets — le seul mécanisme de difficulté explicite [§4] : (i) snapshot profils seuls ; (ii) extract events seuls non joignable ; (iii) dataset billing cross-vertical au vocabulaire financier ; (iv) dataset legacy mal étiqueté annonçant 6 mois mais contenant 2 semaines ; (v) export d'audience marketing recouvrant le namespace retail. Plus des bundles à fenêtre 2 semaines sur 5 verticales, même schéma que leurs homologues 6 mois, « trapping agents that ignore data recency ». Satisfaire G_i exige d'identifier les trois datasets d'un bundle (events, profiles, catalog), donc tout decoy coûte en précision.

2. Environnement / harness

⚠️ Avertissement de cadrage : le papier décrit le harness d'évaluation, pas l'environnement de l'agent sous test. L'observation, l'espace d'actions, la boucle d'outils du skill évalué sont en grande partie non précisés.

Structure d'un test case. τ_i = (U_i, G_i, E, C) [§3.1] : - U_i : requête utilisateur. - G_i : fonction Python typée G_i : E → D, D mappant des clés de factoid vers leurs valeurs attendues [§3.2]. - E : environment variables — « business context, co-resident skills ». - C : compute variables — « credentials, timeouts, API endpoints ».

Boucle d'évaluation [§3.1, Fig. 1] : pour chaque τ_i, le harness lance S et exécute G_i « live at evaluation time, in parallel and against the same current state of the data system » → (r_i, g_i), puis extraction de factoids des deux côtés, matching, métriques, scorecard par test case. « the reference ground truth is never precomputed or stored » [§3.1].

Observation / espace d'actions de l'agent : non précisé. Ce qu'on peut inférer d'App. A : le skill reçoit une requête métier en langue naturelle, interroge le catalogue de datasets AEP via API, et rend une spécification (datasets sélectionnés, target variable, input variables, target mapping function). Aucune liste d'outils, aucune signature d'outil n'est donnée. ❌ Lacune sérieuse pour qui veut reproduire.

Single-turn / multi-turn. Les 55 test cases sont explicitement single-turn [§5]. Horizon interne du skill (nb de tool calls, profondeur de la boucle agentique) : non précisé. Gestion du contexte long : déléguée au harness — le papier invoque de façon générique « the harness's native engineering features (sub-agent orchestration, memory and context management) » [§1, §2] sans détailler.

Exécution. Live stage sandbox derrière les APIs de production [§4] ; « secure, sandboxed compute environment » pour l'exécution du code [Ethics] ; C porte credentials, timeouts, endpoints [§3.1]. Valeurs de timeout, politique de reset, garanties de déterminisme : non précisées. ⚠️ Le déterminisme est revendiqué côté référence (« recomputes the reference deterministically against live data » [§5.1]) mais jamais mesuré ; et rien n'est dit sur ce qui se passe si l'état de la base bouge entre le run de S et celui de G_i — le parallélisme est affirmé comme la mitigation, sans verrou ni snapshot décrit.

Ce que « real-time » recouvre exactement. Trois choses distinctes, à ne pas confondre : 1. Propriété du système évalué : la base est non stationnaire (ingestion continue, schéma actif qui change, fenêtre glissante) ; « A frozen reference answer is therefore stale by construction » [§1]. 2. Propriété du protocole : la référence est recalculée à l'instant de l'évaluation, contre le même état que celui vu par l'agent [§3.1]. C'est le sens opératoire. 3. Propriété de robustesse : la signature de G_i sert de schema contract qui « fails explicitly when an upstream API changes » [§1], et G_i est versionnée avec le test-bench en source control, « giving the same per-change auditability as production code » [§3.2].

Contraintes que ça impose à l'environnement (déductibles du papier) : (a) il faut des data APIs accessibles permettant de recalculer la réponse from first principles — les auteurs bornent explicitement leur scope : « extending the approach to settings without such APIs remains outside our current scope » [§1] ; (b) exécution concurrente skill / référence contre le même état ; (c) credentials et endpoints par test case ; (d) un sandbox iso-API de la production, pour que le passage en prod soit un simple changement de credentials [§4] ; (e) la référence doit être du code versionnable et relisible.

Gestion des erreurs d'outils et des sorties mal formées. Aucune politique décrite. Le seul mécanisme d'erreur mentionné est l'échec explicite du schema contract en cas de changement d'API amont [§1]. Sur les sorties mal formées de l'agent : le design les rend en principe non bloquantes, puisque l'extraction de factoids est « format-independent » et que « the scoring layer never observes the raw response format » [§3.3] — prose, liste, table, HTML sont scorées identiquement. ⚠️ Ce qu'il advient d'une réponse dont l'extraction de factoids échoue est non précisé.

Exemple de trajectoire — App. A, test case τ_0, verticale financière, tag financial-modified, benchmark v3 :

U_0 : « Our risk committee requested this after reviewing last quarter's delinquency rates. We need a propensity model to flag credit card accounts showing early signs of default risk—find the relevant AEP datasets, identify the key input variables, the target variable, and define the target mapping function. »

G_0 (stocké comme invocation de fonction, pas comme valeurs littérales) : python get_ground_truth_string(idx=0, gt_keys=['ml_goal_type', 'target_variable', 'expected_datasets', 'input_variables', 'target_mapping_function', 'observation_window_days', 'outcome_window_days', 'failure_modes'])

g_0 (extraits) : ML goal binary_classification ; target default_risk_30d ; datasets = bundle Financial 6M (69bb43ac…, 69bb43ad3…, 69bb43ad7…) ; input variables avec rôles — creditTier (feature), incomeBand (confounder), accountBalance (feature), agrégations count_90d de account.login, creditCard.purchase, billing.paymentReceived, riskBand (confounder), lastPaymentFailedAt (leakage — à exclure) ; target mapping : t_0 = max(timestamp) par user, y=1 si un billing.paymentFailed survient dans (t_0, t_0+30j], features sur (t_0−90j, t_0] ; fenêtres observation 90 j / outcome 30 j.

r_0 (abrégé) : datasets Financial base au lieu du bundle 6M ; target is_default_risk = 1 if utilization_rate > 0.85 OR transactionType == 'missed_payment' ; aucun avertissement de data leakage. Corrects : creditTier, incomeBand, accountBalance, et le goal binary-classification.

Scoring : |F_r| ≈ 14, |F_g| ≈ 12, |F_rg| ≈ 5 → P = 5/14 ≈ 0.36, R = 5/12 ≈ 0.42, A = 5/21 ≈ 0.24 → rescalés ×9 : Precision 3.2, Recall 3.8, Accuracy 2.1, Coverage 6.0, Conciseness 7.5, Tone 8.5, Clarity 8.0, Overall 5.1 [Tab. 4].

⚠️ Noter dans cet exemple le rôle typé des variables (feature / confounder / leakage) : la fonction de référence n'encode pas qu'une réponse, mais une structure de réponse annotée. C'est l'élément le plus réutilisable du papier (voir §9).

3. Reward / vérifieur

Pas de reward au sens RL : vérifieur d'évaluation uniquement. Architecture hybride en deux étages.

Étage 1 — référence exécutable (déterministe). G_i est du code Python exécuté contre le système de données, produisant g_i [§3.2]. Motivation explicite : « the ground truth is encoded as runnable code rather than free-form text, so the reference is computed deterministically rather than generated » [Ethics]. Précédent revendiqué : execution accuracy du text-to-SQL (WikiSQL, Spider, BIRD, Spider 2.0), généralisé « beyond SQL to arbitrary Python computations » [§2].

Étage 2 — juge LLM factoid-level (stochastique). Trois opérations, toutes portées par le LLM / le harness : 1. Décomposition. Φ(·) mappe une chaîne vers son ensemble de claims atomiques. Application asymétrique [§3.3, Eq. 1] : F_r = Φ(r_i) et F_g = Φ(g_i | U_i). L'opérateur réponse est non conditionné — « a well-behaved agent surfaces only facts relevant to U_i, so any extraneous claim in r_i is itself a scoreable signal » ; l'opérateur ground truth est conditionné sur la requête, ne gardant que les factoids de g_i pertinents. Les auteurs présentent ce conditionnement comme leur extension par rapport à jafari2026beyond et fan2025minoseval [§2]. 2. Matching. Effectué par le harness agentique, mapping un-à-un entre F_r et F_g, décision binaire, sans crédit partiel : « a matched factoid is unambiguously correct and an unmatched one unambiguously wrong, preserving the interpretability of the metrics » [§3.4]. 3. Métriques [§3.5, Eq. 2] : A = |F_rg| / (|F_g| + |F_r| − |F_rg|) (Jaccard), P = |F_rg| / |F_r|, R = |F_rg| / |F_g|. Lecture : P bas = hallucination, R bas = omission. Le scorecard journalise verbatim F_r \ F_rg (claims hallucinés) et F_g \ F_rg (faits omis) [§3.5].

Granularité. Outcome, pas process — rien n'est noté sur la trajectoire, seulement sur la réponse finale. Binaire au niveau du factoid, donc crédit partiel au niveau de la réponse par agrégation. C'est le point de design important : la binarité est poussée au plus petit grain vérifiable, et le crédit partiel émerge du comptage.

Termes additionnels — dimensions qualitatives. Un juge LLM guidé par rubrique note trois dimensions supplémentaires [§3.5] : Question Coverage (complétude vis-à-vis des sous-questions / action items explicites de U_i), Tone (politesse, professionnalisme), Conciseness (verbosité relative à l'information transmise). « Each rubric anchors its scale to reduce intra-judge variance across test cases and agent versions » [§3.5]. Toutes les métriques, factoid-level et qualitatives, sont rapportées sur une échelle commune 0–9 par rescaling linéaire du [0,1] sous-jacent (×9).

❌ Le prompt du juge et les rubriques ne sont PAS donnés — ni dans le corps, ni en annexe. L'annexe A ne contient que le worked example. C'est la lacune la plus handicapante du papier pour qui veut le reproduire ou le transposer : le papier revendique que les rubriques sont « anchored » sans montrer un seul ancrage.

⚠️ Incohérences dans la rubrique : Tab. 4 rapporte une dimension Clarity (8.0) qui n'est définie nulle part — §3.5 ne liste que Coverage, Tone, Conciseness. Et un score Overall (5.1) dont la règle d'agrégation est introuvable dans le papier.

Fiabilité du vérifieur — mesurée, et c'est le cœur du papier. - Qualité des annotations humaines : Gwet's AC_2 (prevalence-adjusted) = 0.931 au niveau factoid et 0.883 toutes dimensions, au-dessus du seuil d'acceptabilité 0.667 [Tab. 2, §5]. Protocole : 3 annotateurs experts, round de calibration préalable, notation indépendante, accès aux données live, Likert 5 points (a) par factoid atomique et (b) sur les 3 dimensions qualitatives ; rescaling humain vers 0–9 via (x−1)×9/4 [§5]. - Accord juge ↔ humains : MCC 0.427 sur PASS/FAIL, précision 0.568, rappel 1.000, F1 0.724, n = 53 [Tab. 3]. ⚠️ Mon évaluation : 0.427 est un accord faible dans l'absolu. Précision 0.568 signifie que ~43 % des PASS prononcés par le juge sont des faux positifs au regard des experts. Le papier ne commente jamais ce niveau absolu et ne discute que les écarts relatifs entre configurations. Un vérifieur à P = 0.57 serait inutilisable comme signal de reward dense en RL sans correction. - Taux de faux négatifs : rappel = 1.000 → zéro faux négatif sur ces 53 cas [Tab. 3]. Les faux positifs sont donc l'intégralité de l'erreur.

Robustesse / attaque du vérifieur. ❌ Aucun test adversarial, aucune tentative de hacking du juge. Le papier ne teste pas si un agent peut gonfler son score en multipliant les factoids triviaux vrais (ce que P pénalise en théorie, A étant un Jaccard) ni en reformulant pour forcer des matchs. Les auteurs identifient en revanche deux risques structurels [Limitations] : - Self-judging bias : même LLM (Sonnet 4.6) pour le skill sous test et pour les opérateurs d'évaluation. Les auteurs affirment que le risque est « substantially mitigated » parce que le juge ne note pas holistiquement mais via une rubrique ancrée sur une ground truth externe et exécutable au niveau des factoids, « leaving little room for stylistic self-preference ». Ils concèdent qu'« a systematic study that varies the judge model independently of the skill model remains valuable future work ». ⚠️ L'argument est raisonnable pour les dimensions de style, mais ne couvre pas la décomposition en factoids elle-même, qui est faite par le même modèle des deux côtés et peut converger sur un découpage auto-favorable. - Complétude de G_i : « If G_i omits a relevant sub-query or computes it incorrectly, the resulting factoid-level metrics will misjudge the agent accordingly » ; garantir complétude et correction de G_i « currently rests on expert authoring and review » [Limitations]. ⚠️ C'est le vrai point de fragilité : le déterminisme est déplacé, pas créé — il repose sur la qualité d'un artefact écrit à la main.

Diagnostic qualitatif des baselines [§5.1] : - Baseline-1 (No GT) — réutilise le skill natif skill-creator du harness, avec un prompt le poussant à étudier le skill sous test et à inventer ses propres critères. Comportement observé : il a systématiquement évalué chaque réponse contre les seuls final checks déclarés dans le skill sous test, « it never formulated an alternate pathway to compute the ground truth and thus never accessed the real-time data ». Noter le skill contre son propre comportement auto-déclaré → anti-corrélation. ⚠️ C'est le résultat le plus instructif du papier et il passe presque inaperçu : un juge agentique laissé libre se replie sur les assertions du système qu'il évalue. C'est un mode de défaillance de vérifieur générique, pas propre à la data science. - Baseline-2 (NL GT) — même réponse attendue mais en instructions en langue naturelle. A bien invoqué la bonne fonction d'API, mais a sur-spécifié certains paramètres d'entrée, produisant une référence porteuse de factoids surnuméraires.

In-distribution vs OOD, transfert

❌ Rien. Aucune mesure OOD, aucun transfert vers un autre skill, un autre domaine, un autre harness ou un autre modèle. Les auteurs affirment que « The framework is nonetheless model- and harness-agnostic: any sufficiently capable LLM and any agentic harness can be substituted without changes to the test-bench or metrics » [§5] — affirmation non testée, et les Limitations le concèdent implicitement (« efficacy of natural-language ground truth should be re-examined with higher-capacity models such as Claude Opus or OpenAI GPT-5.5 » ; « robustness of the token-efficiency claim needs to be tested by running similar experiments on agentic harnesses with different memory and tool-call caching mechanisms »).

Ablations

Les deux baselines sont l'ablation, et elles isolent proprement deux facteurs orthogonaux : Baseline-1 ablate l'existence même d'une ground truth ; Baseline-2 ablate la forme exécutable en gardant le contenu. Dispositif minimal mais correctement conçu. ✅

Ce qui n'est pas ablaté : le conditionnement Φ(g_i | U_i) vs non conditionné (présenté comme la contribution propre vs la littérature [§2], jamais isolé) ; le matching un-à-un binaire vs crédit partiel ; l'apport des 3 dimensions qualitatives ; l'effet du modèle juge.

Scaling

❌ Aucun. Un seul modèle, un seul harness, un seul skill, 53 cas, une seule taille.

Solidité

  • ✅ Baselines appariées : deux baselines, même harness, même modèle, mêmes 53 TC, même référence humaine — la comparaison est honnête. ⚠️ Mais aucune comparaison à un framework publié (RAGAS, ARES, FActScore, MINOSEval sont cités en §2 et jamais évalués).
  • ✅ Ablations : Baseline-1 / Baseline-2 isolent « une GT » et « une GT exécutable ». Suffisant pour le claim tel que formulé.
  • ❌ Variance / seeds : aucun IC, aucun bootstrap, aucune répétition du juge (pourtant stochastique) sur les mêmes cas. Avec n = 53, l'écart MCC 0.427 vs 0.331 est très probablement dans le bruit d'échantillonnage — un bootstrap aurait coûté quelques lignes de code et n'a pas été fait. Le claim « +29 % » est non qualifié statistiquement.
  • ⚠️ Fiabilité de l'éval : le juge est validé contre des humains, avec un protocole sérieux (3 annotateurs, calibration, Gwet AC_2 prevalence-adjusted, accès données live) et une base synthétique excluant la contamination. Mais le niveau d'accord atteint est faible en absolu (MCC 0.427, précision 0.568), et le self-judging bias reste non résolu par l'expérience — seulement par un argument.
  • ❌ Échelle : 53 test cases, 2 sous-tâches, 1 skill, 1 modèle. Trop petit pour généraliser.
  • ❌ Reproductibilité : aucun code, aucun jeu de données, aucun test-bench, aucun prompt de juge, aucune rubrique publiés (vérifié par recherche d'URL dans le source LaTeX et de dépôt GitHub → néant). Même le générateur de données synthétiques Poisson–DAG, qui pourrait être publié sans risque de confidentialité, ne l'est pas.
  • ❌ Cohérence texte ↔ chiffres : voir 7.0 — sur-généralisation du claim central, explication contredite par Tab. 3, dimensions non définies dans Tab. 4.

Verdict : plausible mais fragile. L'idée de design est bonne et l'architecture en deux étages (référence déterministe + comparaison factoid-level) est le bon découpage conceptuel. Mais l'appareil probatoire ne la soutient pas : n = 53, pas de variance, un seul modèle juge identique au modèle testé, aucun code, et — surtout — la propriété qui donne son titre au papier (recomputation live) n'est pas exercée par l'expérience qui le valide [App. A]. À traiter comme un design document argumenté, pas comme un résultat empirique.

Sur la question posée : une évaluation par compétence plutôt que par tâche

⚠️ Attention, le papier ne fait pas ce qu'on pourrait croire. Il n'y a aucune décomposition en compétences : « skill » y désigne un artefact logiciel (bundle markdown + scripts + connectors + tools) au sens Agent Skills [§2], et le papier évalue un seul skill sur deux sous-tâches. Aucun mécanisme de rattachement tâche→compétence, aucune matrice de couverture, aucun score agrégé par compétence n'est proposé.

Mais le papier fournit, sans le nommer, le mécanisme qui rendrait une telle évaluation possible, et c'est là qu'est la valeur pour Gemini Law. Trois lignes :

  1. La grille de compétences doit être la signature de la fonction de référence, pas une taxonomie à part. gt_keys [App. A] fait office de contrat : ce qui est attendu est énuméré, nommé, et mécaniquement aligné avec ce qui sera scoré. Transposé : un cas juridique déclare gt_keys=[regime_applicable, juridiction, sources_faisant_autorite, faits_qualifiants, exceptions, contre-arguments, date_de_validite], et le score par compétence se lit en groupant les factoids par clé — recherche, qualification, rédaction, vérification de citations deviennent des agrégats de factoids, sans ontologie séparée à maintenir.
  2. Séparer factualité et présentation est directement applicable et important en droit. Le juge ne voit jamais le format brut [§3.3] ; P mesure l'hallucination, R l'omission, et le scorecard journalise verbatim les claims hallucinés et les faits omis [§3.5]. Pour un mémo juridique — long, argumenté, sans forme canonique — c'est exactement le découpage qu'il faut : une réponse élégante qui cite un arrêt infirmé doit s'effondrer en précision sans être sauvée par le style. Les dimensions Tone/Conciseness restent séparées et non sommées au factuel.
  3. Le seul sous-domaine juridique où le GT-as-code transfère tel quel est la vérification de citations, parce que c'est la seule compétence juridique dont la vérité est interrogeable de façon exécutable : G_i = fonction qui interroge l'API de jurisprudence et renvoie {existence, statut (bon droit / infirmé / distingué), juridiction, pinpoint valide, date de validité}. Pour recherche / qualification / rédaction, il n'existe pas de fonction de référence — il faut retomber sur une référence experte figée, et le papier n'aide plus. ⚠️ Un agent juridique aurait donc un vérifieur hybride à deux régimes, exécutable sur les citations, expert-référencé ailleurs — ce que ce papier ne traite pas.

Meilleur ingrédient à transposer

La référence-comme-contrat typé : gt_keys + rôles annotés (feature / confounder / leakage). Pas le GT-as-code lui-même — le droit n'a pas d'API de vérité pour l'essentiel. Ce qui se transpose, c'est que la référence énumère explicitement (a) les dimensions attendues, et (b) le rôle de chaque élément, y compris les pièges à ne pas mordre. En droit c'est direct : sources contraignantes vs persuasives vs abrogées — le pendant exact du lastPaymentFailedAt marqué leakage que l'agent devait exclure et n'a pas exclu [App. A]. Ça donne un signal négatif explicite, nommé et auditable, là où un juge holistique ne dit que « réponse moyenne ». C'est aussi ce qui rend le scorecard actionnable pour du RL : chaque échec est attribuable à une clé.

Second ingrédient, presque aussi utile : le conditionnement asymétrique Φ(g｜U) conditionné sur la requête, Φ(r) non conditionné [Eq. 1]. En juridique, le rappel doit se mesurer sur les seuls moyens pertinents à la question posée (sinon tout mémo est incomplet), alors que la précision doit pénaliser tout claim surnuméraire (une source hors sujet dans un mémo est une faute). L'asymétrie est le bon défaut. ⚠️ Non ablatée dans le papier.

Expérience minimale

Setup. 60–80 requêtes de recherche juridique (une juridiction, un domaine), chacune avec une référence experte structurée en gt_keys à 6–7 clés, rôles de sources typés (contraignante / persuasive / abrogée-piège). Corpus figé par snapshot daté, avec decoys injectés à la manière de §4 : arrêts infirmés, versions antérieures d'articles, décisions de juridiction voisine. Deux vérifieurs en parallèle sur les mêmes sorties d'agent : (A) juge LLM holistique avec référence en prose ; (B) juge factoid-level avec référence structurée en gt_keys, Φ(g｜U) conditionné, matching binaire, P/R/A par clé. Référence : 3 juristes, round de calibration, Gwet AC_2 comme le papier [§5]. Ajouter ce que le papier n'a pas fait : bootstrap sur MCC, et un modèle juge différent du modèle testé (le self-judging bias reste non résolu [Limitations]).

Résultat attendu. (i) Le juge factoid-level améliore l'accord avec les juristes surtout en rappel — c'est là qu'est le gain dans Tab. 3 (0.920 → 1.000), pas en précision (+0.007) ; parier sur un gain de précision serait parier sur un chiffre que le papier lui-même ne soutient pas. (ii) Le gain devrait être plus grand qu'en data science, parce que les réponses juridiques sont longues et hétérogènes de format, ce qui est précisément la pathologie que le factoid-level corrige. (iii) La précision absolue du juge restera probablement < 0.7, donc le résultat utile de l'expérience est le diagnostic par clé (quelles compétences le juge sait fiabiliser, lesquelles non), pas un vérifieur prêt pour du reward. (iv) Prédiction reprise de Baseline-1 : un juge agentique laissé libre de définir ses critères se repliera sur les assertions de l'agent évalué [§5.1] — si ça se reproduit en juridique, c'est un argument fort contre tout juge auto-dirigé dans la pipeline.

Question à poser en interne chez GDM

Deux, liées : (1) A-t-on, pour la vérification de citations, une API interrogeable donnant statut et validité d'une décision à une date donnée ? Si oui, c'est le seul endroit du pipeline juridique où l'on peut avoir un vérifieur exécutable et déterministe, donc le premier candidat pour un reward RLVR propre — tout le reste du droit devra vivre avec un juge à P ≈ 0.6, avec les conséquences que ça a sur le reward hacking. (2) Quel est le plancher de précision juge qu'on s'autorise avant de brancher un vérifieur sur du RL ? Le papier publie P = 0.568 sans le commenter [Tab. 3] ; il vaut mieux fixer ce seuil à l'avance que le découvrir après une run.
