0. En une phrase

TL;DR. Pointer un coding agent off-the-shelf (Claude Code) sur un répertoire de rollouts figés, avec une instruction d'un paragraphe, produit un system prompt meilleur que celui trouvé par la recherche réflexive SOTA (GEPA) — sans accès à l'environnement, sans validation set, sans boucle d'optimisation.

Claim principal. À accès données apparié (même pool statique de tâches : retail 35, telecom 50, SSB 50, ALFWorld 50), une passe unique de CASD bat GEPA sur 3 benchmarks sur 4 et SkillOpt sur 4 sur 4, avec un gain moyen de +16.6 pts sur la baseline non optimisée contre +10.9 (GEPA) et +5.3 (SkillOpt) [Abstract ; Tab. 1]. Coût de production du prompt ≈ 1.60 $, soit >22× moins cher que la recherche à validation-gate [Tab. 3]. Mécanisme revendiqué : la reflection scope — l'agent écrit et exécute du code d'analyse pour calculer des statistiques sur tout le corpus (pass rate par catégorie, histogrammes d'appels d'outils, doublons, hallucinations d'arguments) au lieu de réfléchir sur un minibatch de trajectoires [§Inside the distillation process].

⚠️ Ce n'est pas un papier d'environnement RL ni de RL sur poids : aucun gradient, aucune mise à jour de θ. L'optimisation se fait dans l'espace du prompt, en offline, sur un corpus de trajectoires. Les auteurs le positionnent explicitement comme l'analogue textuel du one-step offline RL [§Related Work, « Offline improvement and conservatism », citant brandfonbrener2021onestep].

1. Tâches & data

  • Origine des tâches : aucune tâche créée. Quatre benchmarks publics réutilisés tels quels [§Experimental Setup] :
  • ALFWorld [shridhar2021alfworld], scaffold ReAct, win rate sur 50 parties held-out ;
  • tau^2-bench retail et telecom [barres2025tau2], successeur dual-control de tau-bench, agents outillés face à un user simulator LM, pass@1 sur 40 tâches held-out chacun ;
  • SpreadsheetBench-Verified (SSB), dérivé de SpreadsheetBench [ma2024spreadsheetbench], « modified accuracy » sur 50 items held-out.

  • ⚠️ « Verified » : comment SSB-Verified est dérivé de SpreadsheetBench — non précisé (ni critère, ni taille d'origine, ni qui a vérifié).

  • La vraie « data » du papier = le corpus de rollouts. D = {tau_i}, chaque trajectoire enregistrant « messages, tool calls, tool outputs, rewards, and execution metadata » [§Problem Setup]. Produit en exécutant le prompt initial p0 sur le pool d'entraînement. Note : les rewards font partie du corpus — le corpus n'est donc pas gratuit en environnement sans vérifieur.

  • Pipeline de construction : (1) exécuter p0 sur le pool de tâches → corpus figé ; (2) donner corpus + p0 au coding agent avec une instruction unique ; (3) l'agent écrit le skill file ; (4) ce fichier est le prompt optimisé p*. Aucune étape de filtrage, de génération synthétique ou de vérification n'est appliquée au corpus [§The Distillation Pass].

  • Volume : pools d'optimisation de 35 à 50 tâches selon le benchmark [§Data regimes]. N (nombre de rollouts par pool) : le papier dit « 50-rollout pool » pour telecom [Fig. 4 caption] ; pour les autres, non précisé explicitement (implicitement 1 rollout par tâche du pool). ⚠️ C'est très petit. Le papier revendique la « corpus-scale reflection » mais le corpus fait 35 à 50 trajectoires.

  • Distribution de difficulté : non précisé. Aucune stratification, aucun histogramme de difficulté.

  • Filtrage par pass@k du modèle de base : aucun. Le corpus est brut, riche en échecs ; les auteurs affirment que « failure-rich no-think rollouts alone carry enough signal » [§sec:think].

  • Curriculum : sans objet — une seule passe offline, pas d'entraînement itératif.

  • Contamination / séparation train-test : le pool d'optimisation et le test set sont disjoints (test « held-out ») [§Experimental Setup]. En revanche, aucune analyse de contamination des quatre benchmarks publics dans les données de pré-entraînement de GPT-5.4-mini ou de Claude Sonnet 5 : non précisé.

  • Données SFT/IFT avant RL : sans objet (pas d'entraînement).

  • Coût humain : une seule intervention humaine rapportée — la classification manuelle des 816 tool calls des 24 runs de distillation en 4 catégories sémantiques (exploring 94, corpus statistics 184, inspecting episodes 510, writing 28 ; somme = 816 ✓) [§Inside the distillation process]. ⚠️ Un seul annotateur apparent, aucun accord inter-annotateur mesuré. ⚠️ Incohérence non expliquée : 24 runs de distillation loggés [§Inside] mais 12 skills CASD analysés (3 par benchmark × 4) [§Methods, §Inside]. Le facteur 2 correspond peut-être aux deux compositions de corpus (think / no-think) de §sec:think, mais ce n'est pas dit.

2. Environnement / harness

Deux harnesses distincts à ne pas confondre : (a) celui de l'agent cible (fourni par les benchmarks, non modifié) ; (b) celui du distiller, qui est la contribution.

(b) Harness du distiller — le cœur du papier

  • Observation : le coding agent voit un répertoire contenant le fichier de résultats (les N trajectoires) et le prompt initial p0. Rien d'autre : « no other inputs, no precomputed summaries » [§The Distillation Pass].
  • Espace d'actions / outils : ceux d'un coding agent off-the-shelf non modifié (Claude Sonnet 5 / Claude Code) — navigation filesystem, exécution de code, lecture de fichiers, écriture de fichiers [§Related Work « Coding agents » ; §The Distillation Pass]. ⚠️ La liste et la signature exactes des outils ne sont pas données — le papier s'appuie sur le fait que le harness est celui, public, de Claude Code.
  • Instruction unique (recopiée intégralement, §The Distillation Pass) :

    « There is a results file here containing N agent rollout trajectories for [task family]. Analyze it directly---no other inputs, no precomputed summaries---and distill a skill markdown file capturing the behavioral rules that would make a future agent instance more accurate and more token/step-efficient on this task family. Use your own judgment fully on methodology. Write the skill file into this directory. »

  • Ce qui est délibérément NON prescrit : pipeline d'analyse, procédure d'optimisation, métrique d'évaluation, représentation intermédiaire [§The Distillation Pass].
  • Multi-turn, horizon : 16 à 51 tool calls par run, moyenne 34.0 [§Inside]. Terminaison = écriture du skill file. Pas de limite d'horizon rapportée.
  • Gestion du contexte long : c'est l'argument central. Le corpus entre « through the interpreter rather than through the context window » [§Related Work] — l'agent exécute du code d'agrégation (type pandas) et ne lit ensuite que les épisodes que les statistiques désignent. Pas de troncature ni de résumé explicite.
  • Workflow émergent (mesuré sur 24 runs) [§Inside] : 1. exploration front-loaded (première occurrence médiane en position 0.0 ; 34 % des tool calls dans le premier cinquième du run, 5 % ensuite) ; 2. alternance statistiques ↔ inspection ciblée, médiane 5 bascules (jusqu'à 16) ; 3. écriture du skill terminale (position médiane 1.0), fichier de 5-8 KB.
  • Statistiques calculées [§Inside, Fig. 2b] : 100 % des runs mesurent rewards/pass rates et longueurs d'épisodes ; 96 % quantifient terminaison et failure modes ; 92 % analysent l'usage d'outils ; 79 % ventilent par catégorie de tâche ; ~33 % cherchent explicitement les appels d'outils dupliqués.
  • Exécution / sandbox / déterminisme : non précisé (dépend de Claude Code). Aucun timeout, reset ou politique de déterminisme rapporté.
  • Gestion des erreurs d'outils / sorties mal formées : non précisé. Aucun cas d'échec de distillation rapporté.
  • Exemple de trajectoire : le papier n'en recopie aucune. Il cite deux règles produites : « 16/50 episodes fabricated an identity-lookup argument » et « get_details_by_id was called 284 times, 123 of them exact duplicates » [§Inside ; §Why does corpus-scope reflection win?].

(a) Harness de l'agent cible

Non modifié, fourni par chaque benchmark : ReAct pour ALFWorld, agent outillé + user simulator LM pour tau^2, harness SSB [§Experimental Setup]. ⚠️ Exception importante : SkillOpt sur ALFWorld tourne sur son scaffold natif, avec sa propre baseline à 58.7 % — les auteurs déclarent eux-mêmes cette cellule « not directly comparable » [Tab. 1, note ‡].

3. Reward / vérifieur

Il faut distinguer trois objets. Le point le plus intéressant pour nous : CASD n'a aucun vérifieur dans sa boucle d'optimisation.

  1. Vérifieur des benchmarks (métrique de test) : programmatique dans les trois cas — win rate ALFWorld, pass@1 tau^2, « modified accuracy » SSB [§Experimental Setup]. Binaire par épisode. Pas de LLM-as-judge pour scorer les réponses. ⚠️ Mais tau^2 embarque un user simulator LM (GPT-5.4-mini) dans la boucle d'évaluation : c'est un composant stochastique non validé ici contre des humains.

  2. Vérifieur dans la boucle d'optimisation : - GEPA : gate de sélection sur front de Pareto, budget de 120 metric calls ; en limited-data, le Pareto set = le train [§Optimizer settings]. - SkillOpt : 3-5 epochs, minibatch dimensionné sur le split train (8-40), budget d'édition de 4 par step (décroissance cosinus jusqu'à 2), validation gate activée, split interne 25/10 sur retail et 35/15 ailleurs [§Optimizer settings]. - CASD : aucun. Pas de gate d'acceptation, pas de validation set, pas de rollout supplémentaire [§The Distillation Pass]. C'est le point différenciant revendiqué.

  3. Critère de rétention d'un prompt candidat — le point critique demandé : - CASD n'en a pas : le skill file écrit est retenu tel quel, sans test. - Conséquence positive sur la méthodologie de report : les auteurs synthétisent 3 skills indépendants par benchmark et reportent leur moyenne [§Methods]. Il n'y a donc pas de cherry-picking du meilleur skill — la SD rapportée pour CASD est une variance skill-à-skill, pas une variance de seed (les auteurs le signalent explicitement en Limitations). - ✅ C'est propre : le gain annoncé n'est pas un gain de sélection sur le set d'optimisation. C'est l'argument le plus solide du papier. - ⚠️ Conséquence négative : rien ne garantit qu'un skill donné ne dégrade pas la performance. Aucune distribution des 3 skills n'est publiée, seulement moyenne et SD. - Argument des auteurs sur les baselines : « No gate, no gate-overfitting » — GEPA-telecom en limited-data descend sous la baseline (17.5 vs 19.2) parce que ses éditions sont sélectionnées sur le pool même sur lequel il réfléchit, et il sur-apprend ; SkillOpt retail a une SD de 10.1 [§Why does corpus-scope reflection win? (3), citant smith2006optimizerscurse, dwork2015reusable].

  4. Granularité / termes additionnels : l'instruction demande des règles « more accurate and more token/step-efficient » — un objectif implicitement bi-critère (qualité + efficience), sans pondération explicite. Aucune pénalité de format ou de longueur. ⚠️ Effet mesuré en creux : le prompt de SkillOpt induit 20.1 M prompt tokens sur l'éval 3 seeds de telecom contre 11.9 M pour GEPA — « verbose optimized prompts are not free to deploy » [§Cost]. Le chiffre correspondant pour CASD n'est pas donné.

  5. Fiabilité du vérifieur : mesurée nulle part. Aucun taux de faux positifs/négatifs, aucun accord humain. Le seul « contrôle qualité » du papier est la taille des ensembles de test, dont les auteurs reconnaissent eux-mêmes que l'erreur standard binomiale seule vaut ≈ 7 points par seed [§Experimental Setup, citant miller2024errorbars].

  6. Robustesse / attaque du vérifieur : aucun test. Mais ⚠️ il y a un risque structurel non discuté : le coding agent distille des règles à partir d'un corpus qui contient les rewards. Rien n'empêche qu'il écrive une règle exploitant une régularité du scorer plutôt que de la tâche. Le papier ne mentionne aucun garde-fou, et l'absence de gate signifie qu'une telle règle serait retenue sans contrôle.

In-distribution vs OOD, transfert

  • Généralisation hors pool d'optimisation : mesurée ✅ — le test est held-out et disjoint du pool dans les quatre cas [§Experimental Setup]. Le gain n'est donc pas un gain de sélection sur le set d'optimisation. C'est le point méthodologique correct du papier.
  • ⚠️ Mais la taille des sets (40-50 items) est telle que les auteurs annoncent eux-mêmes une SE binomiale ≈ 7 pts par seed [§Experimental Setup]. Deux des quatre « victoires » tombent sous ce plancher.
  • Transfert d'un environnement à un autre : non mesuré. Chaque skill est distillé et évalué sur sa propre famille de tâches. Aucune expérience croisée (skill telecom → retail, p. ex.), alors que ce serait le test le plus informatif sur la nature « policy-like » des règles.
  • Transfert de composition de corpus : partiellement mesuré — distiller depuis des rollouts think puis déployer sur la policy no-think donne des résultats « within a few points » sans gagnant consistant [§sec:think]. Les auteurs concluent que les traces de raisonnement coûteuses sont un enrichissement optionnel.

Ablations

⚠️ Aucune ablation n'isole la contribution revendiquée. Le claim est que c'est la reflection scope (statistiques corpus-wide) qui fait la différence. Ce qui manquerait pour l'établir : - le même coding agent contraint à un minibatch (scope réduit, scaffold identique) ; - GEPA/SkillOpt dotés d'un outil d'exécution de code pour leur étape de réflexion (scope réduit, scaffold identique) ; - variation de la taille du corpus N ; - variation du distiller (les auteurs le reconnaissent en Limitations : « the recipe's sensitivity to distiller capability is untested »).

Confond majeur non traité : CASD compare un coding agent outillé (exécution de code + filesystem) à des LM de réflexion nus. L'écart peut venir du scaffold autant que de la reflection scope. Les preuves fournies à l'appui de l'explication « reflection scope » [§Why does corpus-scope reflection win?] sont observationnelles (les règles citent des statistiques ; Fig. 4 montre un cas d'absence corpus-level), pas interventionnelles.

La seule section étiquetée « Ablation » [§sec:think] compare le skill au mode think du même modèle : c'est une comparaison de référence utile (le skill récupère 55-100 %+ du gap de raisonnement en émettant 0.6-0.8k tokens de sortie contre 2.9-4.5× plus en think, Tab. 5), mais elle n'ablate rien de CASD.

Budget d'évaluation des baselines — question posée explicitement

Les budgets ne sont PAS appariés, et le déséquilibre joue en faveur des baselines, ce qui est le bon sens de l'écart : - CASD : 0 rollout d'environnement, 0 metric call, 0 validation set. - GEPA : 120 metric calls (Pareto set = train en limited-data). Les auteurs signalent qu'une reprise du run telecom jusqu'à 240 calls a rendu un prompt byte-identique, d'où le report au point 120 [§Optimizer settings] — argument honnête de saturation. - SkillOpt : 3-5 epochs, gate de validation active, split interne 25/10 ou 35/15 [§Optimizer settings]. - En régime head-to-head, GEPA et SkillOpt reçoivent en plus un validation set séparé et un accès environnement illimité [§Data regimes].

Ce qui est apparié, c'est le pool de tâches, pas le budget d'évaluation. ✅ Le déséquilibre ne gonfle donc pas le résultat de CASD. ⚠️ En revanche le scaffold de l'optimiseur n'est apparié dans aucun régime (cf. confond ci-dessus), et le coût de génération du corpus de CASD est exclu de la comptabilité [§Cost].

Scaling

Non étudié. Un seul modèle cible (GPT-5.4-mini no-think), un seul distiller (Claude Sonnet 5), une seule taille de corpus par benchmark. Les auteurs listent ces trois points en Limitations. Aucune courbe de scaling.

Solidité

  • ⚠️ Baselines : GEPA est la bonne cible (SOTA réflexif) et reçoit plus de budget que CASD, ce qui est conservateur ; mais la cellule ALFWorld/SkillOpt est déclarée non comparable par les auteurs et alimente pourtant l'agrégat +5.3.
  • ❌ Ablations : aucune n'isole la reflection scope ; le confond coding-agent-scaffold vs réflexion LM nue reste entier.
  • ⚠️ Variance / seeds : 3 seeds et SD partout, SE binomiale explicitée — bon réflexe ; mais la SD de CASD mesure une variance skill-à-skill et celle des baselines une variance de seed (les auteurs le disent en Limitations), et §sec:think révèle une dispersion run-à-run inter-round allant jusqu'à ~6 pts, non commentée.
  • ⚠️ Fiabilité de l'éval : métriques programmatiques (pas de LLM-judge à valider), mais 40-50 items par test set pour des écarts de 1 à 9 pts ; aucune analyse de contamination ; user simulator LM dans tau^2 non contrôlé ; taxonomie des 816 tool calls annotée à la main sans accord inter-annotateur.
  • ⚠️ Échelle : 4 benchmarks, 1 modèle cible, 1 distiller, pools de 35-50 tâches.
  • ❌ Reproductibilité : aucun code, aucun corpus, aucun skill file publié. Pas d'annexe. Même les prompts produits — l'artefact central — ne sont pas reproduits, seulement cités par fragments. Le modèle cible « GPT-5.4-mini » et le distiller « Claude Sonnet 5 » sont des API propriétaires versionnées.
  • ❌ Cohérence texte/chiffres : le « 2 of 4 » du head-to-head est contredit par Tab. 2 (1 of 4) ; l'agrégat +5.3 mélange deux baselines ; le « 22× » ne vaut que contre SkillOpt.

Verdict : plausible mais fragile. L'hypothèse est séduisante, bien motivée théoriquement (analyse biais-variance §Bias-Variance, analogie one-step offline RL), et deux résultats sortent franchement du bruit (ALFWorld +9.3 vs GEPA ; telecom, où GEPA dégrade sous la baseline). Mais : la contribution revendiquée n'est isolée par aucune ablation, le claim head-to-head de l'abstract est contredit par sa propre table, les sets de test sont trop petits pour la moitié des écarts, et rien n'est publié. À répliquer avant d'y adosser une décision.

Cases evidence : 1. baselines ✅ — même modèle cible et même LM optimiseur pour toutes les méthodes, GEPA à jour, hyperparamètres donnés, et le budget déséquilibré l'est en défaveur de CASD [§Experimental Setup, §Optimizer settings]. 2. ablation ❌ — aucune expérience ne sépare « reflection scope » de « scaffold de coding agent » ; la seule section « Ablation » compare au mode think, pas à CASD amputé. 3. variance ✅ — 3 seeds, SD rapportées dans toutes les tables, SE binomiale explicitée [§Experimental Setup, Tab. 1-2-5]. 4. coherence ❌ — « ahead on two of four » en head-to-head contredit par Tab. 2 (1/4) ; +5.3 calculé sur une baseline différente des deux autres chiffres du même triplet. 5. eval ❌ — 40-50 items par test set pour un bruit binomial admis de ~7 pts, aucune analyse de contamination sur 4 benchmarks publics, user simulator LM et taxonomie manuelle non validés. 6. repro ❌ — ni code, ni corpus, ni skill files, ni annexe ; modèles propriétaires.

evidence = 2/6, manquant : [ablation, coherence, eval, repro].

Meilleur ingrédient à transposer. Pas CASD comme optimiseur de prompt, mais CASD comme instrument de diagnostic pré-RL. Le résultat réellement robuste du papier est que des statistiques corpus-wide exécutées en code font apparaître des failure modes que la lecture de trajectoires ne fait pas apparaître — en particulier les absences : Fig. 4 montre que make_payment n'est jamais appelé dans le pool de 50 rollouts telecom, fait invisible dans toute trajectoire individuelle, et que seul CASD écrit la règle correspondante [§Why does corpus-scope reflection win?]. Transposé : « aucune trajectoire n'a jamais consulté la jurisprudence postérieure à telle date », « l'outil de vérification de citation n'est jamais invoqué sur les affaires de catégorie X », « 123 recherches sur 284 sont des doublons exacts ». Ce sont exactement les failure modes qu'on veut cartographier avant de dessiner un reward juridique, et ils se calculent sans vérité terrain.

Corollaire opérationnel, indépendant du claim principal : à 1.60 $ la passe, CASD est la baseline que tout gain de RL post-training devra battre. Le papier montre qu'un prompt distillé récupère 55 % à >100 % du gap no-think→think en émettant zéro token de raisonnement [Tab. 5]. Si un run RL sur Gemini Law ne bat pas un skill file à 1.60 $, ce n'est pas un résultat.

Expérience minimale. (1) Logger N ≈ 200-500 trajectoires de l'agent juridique courant sur un pool de tâches type Harvey LAB, incluant tool calls et outputs — sans reward. (2) Pointer un coding agent dessus avec l'instruction du §The Distillation Pass adaptée, en 3 exemplaires indépendants. (3) Évaluer les 3 skills sur un test held-out suffisamment grand — pas 40 items : à 40 items l'incertitude binomiale du papier (~7 pts) rendrait l'expérience ininterprétable ; viser plusieurs centaines. (4) Reporter la moyenne des 3, jamais le meilleur, exactement comme le papier. Résultat attendu, en extrapolant depuis telecom et ALFWorld : un gain net sur les erreurs procédurales (outil non appelé, citation non vérifiée, recherche dupliquée) et un gain faible ou nul sur la qualité substantielle du raisonnement juridique — le papier montre lui-même que la part « instance-specific deduction » du raisonnement n'est pas récupérable par un prompt statique [§sec:think, « the residual gaps on telecom and SSB suggest a portion of thinking [...] that no static prompt recovers »].

Question à poser en interne chez GDM. Deux. (1) Avant tout run RL : dispose-t-on déjà d'un corpus de trajectoires loggées de Gemini sur des tâches juridiques, avec tool calls et outputs ? Si oui, la passe de diagnostic coûte quelques heures et cadre le design du reward. (2) Gouvernance : peut-on faire analyser des trajectoires contenant des données client par un agent d'analyse, et sous quel périmètre ? Le papier ignore complètement cette contrainte, qui est bloquante côté juridique.
