0. En une phrase

TL;DR — pipeline qui transforme des agent skills écrites par des humains (registry en ligne, type ClawHub/Anthropic Skills) en environnements Docker exécutables avec vérifieur code, puis en trajectoires longues pour SFT ; 2 756 envs + 8 364 trajectoires publiées ; le modèle SFT (35B) dépasse sa base de +199 Elo / +19,10 pts / +28,13 pts sur trois benchmarks agentiques.

Claim principal précis : SFT sur trajectoires vérifiées dérivées de skills humaines améliore Qwen3.5-35B-A3B sous harness Claude Code de 974→1173 Elo (GDPval-AA v2), 39,33→58,43 % (Terminal-Bench 2.1), 23,34→51,47 % (SkillsBench v1.1 avec skills) et 12,13→26,81 % (sans skills) [Tab. 3, Tab. A5] ; et le modèle entraîné sans skills à l'inférence dépasse sa base avec skills (26,81 > 23,34 sous Claude Code ; 21,08 > 5,33 sous Codex), ce que les auteurs interprètent comme une « procedural competence réutilisable » [§5.2].

⚠️ Point capital : aucun RL n'est conduit dans ce papier. Le RL outcome-based est annoncé comme supporté par la ressource et explicitement renvoyé aux travaux futurs [§6 : « Future work will explore reinforcement learning in our task environments »]. Le papier est donc un papier d'environnement + SFT distillé, pas un papier RL. L'intérêt pour nous est en amont : le pipeline skill → tâche → checker, pas l'optimisation.

1. Tâches & data

Origine des tâches

Trois niveaux à bien distinguer, car c'est exactement l'analogue « playbook → env vérifiable » :

  1. Skills humaines (matière première). Registry en ligne de skills écrites par des humains [§3.1, cite openclaw2026clawhub]. Les auteurs organisent la registry en 12 major categories et 63 sub-categories, et à l'intérieur de chaque sub-category sélectionnent les skills « high-star » [§3.1]. Seuil de stars, nombre de skills retenues, date du snapshot, licences : « non précisé ».
  2. Skill cards (structuration humaine de la skill). Pour chaque skill s_i, une carte K_i consolide : descriptions, usage examples, pseudocode ou scripts, execution constraints [§3.1]. La carte « préserve la distinction entre une skill réutilisable et une instance de problème concrète » [§3.1]. ⚠️ Le papier ne recopie aucun skill card, ni en corps ni en annexe — la seule trace concrète est le fichier SKILL.md bundlé dans l'exemple d'env [App. C.2].
  3. Templates de sub-category (le cœur, et c'est manuel). Pour chaque sub-category c, construction manuelle d'un template réutilisable T_c spécifiant : task blueprint, input assets, file structure, runtime requirements, checker specifications, execution constraints [§3.1, « we manually construct »]. Le template « capture le workflow commun à la sub-category tout en laissant varier inputs, instructions, outputs attendus et conditions de succès d'une skill à l'autre » [§3.1]. Les auteurs positionnent explicitement ce choix contre « unconstrained automatic generation ».

Comment un template spécifie les exigences de vérification [§3.1, « Outcome-oriented task specifications »] — recopié : - tâches de content generation → exigences sur sections, length, formatting, keyword coverage, file naming ; - tâches software / data-processing / automation → vérifiables par executable tests, file inspection, structured-output comparison, schema validation, final-state checks. - Principe affiché : ces specs définissent des critères de complétion, pas la reproduction verbatim d'une réponse de référence ; leur portée est « les exigences encodées dans la tâche et le checker, pas des jugements de qualité de sortie ».

⚠️ Le texte du template n'est pas recopié dans le papier. La seule chose donnée en annexe est la structure de fichiers du seed task (App. C.1), recopiée ici intégralement :

seed_task/
|-- instruction.md
|-- task.toml
|-- PLAN.json
|-- README.md
|-- environment/
|   |-- Dockerfile
|   `-- skills/
|-- tests/
`-- solution/

Chaque sub-category part d'un seed task réutilisable fournissant « the basic task-facing scaffold, runtime environment, verification logic, and reference solution » [App. C.1]. Nommage observé : famille de template business__payment__template_new, appariée à la skill electric-deployment → tâche payment_electric-deployment__task1 [App. C.1].

Pipeline de construction, étape par étape

E_i = Instantiate(K_i, T_c(i)) = (x_i, A_i, ρ_i, V_i) [Éq. 1, §3.2] : x_i instruction, A_i input assets, ρ_i file structure + runtime + dependencies + access interface + execution constraints, V_i vérifieur code outcome-based. Chaque tâche est packagée en Docker [§3.2].

Étapes déclarées : planning → materialization → validation → failure-driven refinement [App. C.1].

Acceptation à deux niveaux [§3.2, Éq. 2] : - F_i = 1 ⟺ la tâche passe les checks design, structure, end-to-end execution, avec un vérifieur qui tourne et une solution de référence qui passe le vérifieur. (C'est le seul contrôle de correction du checker documenté : le checker doit accepter la reference solution.) - Exécutions contrastives : on compare les exécutions d'un reference agent avec et sans la skill cible, verdicts r_i^+, r_i^- ∈ {0,1}. - Labels : Skill-Dep. si F_i=1 ∧ (r_i^+, r_i^-) = (1,0) ; Verifier-Passed (fallback) si F_i=1 mais pas la condition contrastive ; Discarded si F_i=0. - Les auteurs sont prudents : ceci donne « evidence of dependency under the reference configuration, not proof that the skill is necessary for every agent » [§3.2].

Protocole contrastif exact — les manques : identité du reference agent (modèle + harness) « non précisé » ; nombre de runs par condition « non précisé » (le formalisme r ∈ {0,1} suggère un seul run par condition, donc un test binaire à 1 échantillon, très bruité — ⚠️) ; température / budget « non précisé ». Seuil retenu : strictement (1,0), pas de pass@k ni de delta de taux de succès.

Combien de tâches écartées par le test contrastif : aucune. C'est un point important et souvent mal lu : les tâches qui échouent au critère contrastif ne sont pas jetées, elles sont reclassées en fallback [§3.2, §4.1]. Résultat : 1 081 / 2 756 (39,2 %) Skill-Dep., 1 675 (60,8 %) Verifier-Passed fallback [Tab. 1, §4.1]. ⚠️ Donc 60,8 % des envs « dérivés de skills » n'ont aucune preuve empirique de dépendance à la skill. Le nombre de tâches réellement Discarded (F_i = 0) et le nombre de candidats tentés au départ sont « non précisés » — impossible de calculer un taux de rendement du pipeline.

Refinement piloté par les échecs [§3.2] : les échecs de validation sont typés en 4 familles — environment errors, checker errors, difficulty mismatch, weak skill dependency. Les construction traces, execution logs, verifier outputs et reflection notes guident les révisions du runtime, des exigences de la tâche et de la logique du vérifieur. Chaque tâche reçoit un construction budget (valeur « non précisée ») ; les tentatives ratées peuvent redémarrer avec les reflection records. ⚠️ Taux d'échec par famille : non précisé. Aucun chiffre sur la fréquence des checker errors, alors que c'est la quantité la plus informative pour nous.

Qui écrit les checkers

  • Templates et checker specifications : humains [§3.1, §3.2, Fig. 1A « manually designed sub-category templates specify reusable task structures and verification requirements »].
  • Instanciation du checker pour chaque tâche : un agent, en pratique GPT-5.4 — « The average construction time is 4.5 hours per accepted task with GPT-5.4 » [§4.1].
  • Contrôle de correction : (a) le checker doit tourner de bout en bout ; (b) la solution de référence doit le passer ; (c) le vérifieur embarque des anti-shortcut checks contre input tampering, answer copying, bypassed requirements, fabricated outputs [§3.2] ; (d) boucle de refinement sur checker errors. Aucune relecture humaine des checkers générés n'est mentionnée, ni de mesure de leur précision → voir §3 du mémo.

Volume et distribution

  • 2 756 environnements, 12 major / 63 sub-categories [Tab. 1, Tab. A2]. Top 3 : development 552, business 542, tools 358 [Tab. 1].
  • Proportion Skill-Dep. très hétérogène : 15,6 % en blockchain (7/45) → 58,3 % en business (316/542) [Tab. 1, §4.1].
  • 8 364 trajectoires réussies, dont 3 722 sur tâches Skill-Dep. et 4 642 sur fallback [Tab. 2, §4.2].
  • Difficulté : 48 152 rollouts tentés → 8 364 succès = 17,4 % de taux de succès global sous les 4 configs teacher [§4.2]. Par catégorie : de 9,0 % (documentation) à 22,4 % (devops) [Tab. 1].
  • Couverture après dédup : 2 302 tâches uniques, 12/12 major, 62/63 sub-categories (culinary-arts : 1 tâche acceptée, 0 trajectoire réussie) [Tab. 2, App. A].
  • Sub-category d'intérêt direct pour nous : business / real-estate-legal : 45 tâches, 22 Skill-Dep., 23 fallback, 3,9 h de construction, 153 trajectoires (18,5 %), 41,4 tool calls moy., 53,5k tokens moy. [Tab. A2]. Aucun détail sur leur contenu.

Filtrage

  • Pas de filtrage par pass@k du modèle de base. Le seul filtre est binaire par vérifieur : au niveau tâche (F_i, + label contrastif), au niveau trajectoire (r_i^{h,m} = V_i(z(τ)) ∈ {0,1}, Éq. 3).
  • Le SFT est fait sur les trajectoires réussies ; les échouées sont conservées pour analyse de failure modes [§3.3], pas utilisées pour l'entraînement (pas de DPO/rejection-sampling négatif rapporté).
  • ⚠️ Aucun filtrage qualité des trajectoires retenues (longueur, détours, actions inutiles) n'est décrit. Les trajectoires « All Teachers » sont poolées telles quelles.

Curriculum

Aucun. Pas d'ordonnancement, pas de rééchantillonnage, pas de mélange par difficulté : SFT offline sur le pool. Les seules « ablations de mélange » portent sur quels teachers / quels harnesses sont poolés [Tab. 4], pas sur un curriculum.

Contamination et séparation train/test

« Non précisé » — et c'est un trou sérieux. ⚠️ SkillsBench v1.1 est un benchmark dont les tâches sont livrées avec des skill packages curés [§5.1] ; SkillGym est construit à partir d'une registry publique de skills. Le papier ne fournit aucune analyse de chevauchement entre les skills d'entraînement et celles de SkillsBench, ni de déduplication. Les gains les plus spectaculaires sont justement sur SkillsBench (+28,13). Idem pour Terminal-Bench 2.1 vs les catégories devops/development de SkillGym. À vérifier soi-même sur les artefacts publiés avant de citer ces chiffres.

Données SFT/IFT avant RL

Sans objet ici : le SFT est le training (pas de cold-start pour un RL ultérieur). SFT long-context sur les 8 364 trajectoires, tous les paramètres LM mis à jour, backend Megatron de ms-swift, 16 GPU NVIDIA H200 [§5.1]. LR, epochs, longueur de séquence, masquage (tokens d'observation masqués ou non) : « non précisé » — ⚠️ pour un SFT sur trajectoires de 63k tokens moyens, le masquage des observations d'outils est un choix décisif, non documenté.

Coût humain

  • Travail humain revendiqué : taxonomie 12/63, sélection des skills, 63 templates de sub-category + seed tasks construits manuellement (verification logic + reference solution incluses).
  • Heures humaines : « non précisé ». Le seul coût chiffré est machine/agent : 4,5 h par tâche acceptée avec GPT-5.4 [§4.1], de 2,6 h (research) à 6,3 h (documentation) [Tab. 1]. ⚠️ 2 756 × 4,5 h ≈ 12 400 h d'agent de construction (hors tâches rejetées, non comptées) — c'est le vrai prix du pipeline, et il n'est pas converti en $ ni en tokens.

2. Environnement / harness

Observation

Le harness n'est pas maison : ce sont Codex et Claude Code, non modifiés, qui fournissent « the interaction interface through which the model issues actions and receives environment feedback » [§3.3]. L'observation est donc celle de ces CLI agents : sortie de commandes shell, contenus de fichiers, résultats d'outils. L'agent « interacts with the Docker environment, inspects inputs, executes actions, observes results, and submits a final answer or artifact » [§3.3].

Contenu du package vu par l'agent [App. C.2, recopié] :

task1/
|-- plan.json
|-- instruction.md
|-- task.toml
|-- environment/
|   |-- skills/
|   |   `-- electric-deployment/
|   |       `-- SKILL.md
|   `-- task/
|       |-- docker-compose.yml
|       |-- k8s/
|       |-- configs/
|       |-- data/
|       `-- scripts/
|-- tests/
|   `-- trusted_runtime/
`-- solution/
    `-- solve.sh

La skill cible est montée dans l'environnement (environment/skills/<skill>/SKILL.md) : l'agent peut la lire ou l'ignorer — c'est ce qui rend mesurable le taux d'invocation (§ ci-dessous) et le test contrastif.

Espace d'actions et outils

Non spécifié par le papier : aucune liste d'outils, aucune signature. L'espace d'actions est celui de Codex / Claude Code (shell, édition de fichiers, exécution). ⚠️ Conséquence notable pour nous : SkillGym ne définit pas d'action space ; il définit des tâches et des vérifieurs, et délègue le harness à des CLI existants. C'est un choix de design assumé (multi-harness) mais qui rend l'env dépendant d'outils propriétaires côté collecte.

Composition mesurée du texte loggé, à défaut de spécification d'outils [App. B.2] : 35,9 % reasoning_content, 34,0 % sorties de tool-messages, 19,6 % noms + arguments de tool calls, reste = résidu. Fortes disparités : 55,59 % de sorties d'outils dans le groupe GPT-5.4, alors que le reasoning domine dans les deux groupes Claude Code.

Exécution

  • Docker par tâche, « packaged for reproducible execution » [§3.2].
  • Environnement auto-suffisant : dans l'exemple, des services Python locaux reproduisent backend/pooler/couche de synchro/dashboard, « sans nécessiter un cluster Electric/PostgreSQL/Kubernetes de production » [App. C.2]. → design pattern intéressant : simuler localement l'infra externe plutôt que d'appeler des API réelles (déterminisme, coût, reset).
  • Infra d'exécution à l'évaluation : sandbox auto-hébergée sur OpenSandbox, benchmarks via Harbor, GDPval-AA v2 via NVIDIA NeMo Gym [§5.1].
  • Déterminisme, reset, timeouts : « non précisés » (le vérifieur repart d'un « fresh stack », ce qui implique un reset, mais rien n'est spécifié).

Gestion des erreurs d'outils / sorties mal formées

« Non précisé » — déléguée aux harnesses. Aucune pénalité de format, aucun parsing maison.

Exemple de trajectoire

Le papier donne un env complet + 4 trajectoires pour payment_electric-deployment__task1 [App. C.2–C.3]. Tâche : réparer un déploiement de synchronisation de paiements. Défauts initiaux injectés [Tab. La supervision est donc surtout du workflow long-horizon vérifié, pas de l'usage de skill.

3. Reward / vérifieur

Type

Vérifieur code, outcome-based, binaire, spécifique à chaque tâche : r = V_i(z(τ)) ∈ {0,1}, où z(τ) sont les outputs et l'état d'exécution final, pas le texte de la trajectoire [Éq. 3, §3.3]. Explicitement : « checks these outcomes rather than the wording of the trajectory ». Aucun LLM-as-judge, aucun reward model, aucune rubrique dans l'environnement SkillGym (le seul juge LLM du papier est côté évaluation, sur GDPval-AA v2, hors du contrôle des auteurs).

Familles de checks fournies par les templates [§3.1] : executable tests · file inspection · structured-output comparison · schema validation · final-state checks ; et pour la génération de contenu : sections, longueur, formatting, keyword coverage, file naming.

Granularité

Outcome, binaire, pas de crédit partiel. r ∈ {0,1} au niveau trajectoire. Agrégation interne des critères : « non précisée » (implicitement conjonctive dans l'exemple — la moindre assertion qui casse fait échouer). Aucun reward de process, aucun reward de format, aucune pénalité de longueur : aucun terme additionnel, cohérent avec l'absence de RL.

Deux niveaux à ne pas confondre, les auteurs insistent [§3.3] : ℓ_i (label d'acceptation à la construction) vs r_i^{h,m} (récompense d'une exécution). Un label Skill-Dep. ne garantit pas qu'un agent donné résoudra la tâche.

Anti-hacking (conception)

Le vérifieur embarque des anti-shortcut checks contre : input tampering, answer copying, bypassed requirements, fabricated outputs [§3.2]. Le mécanisme structurel le plus intéressant, vu dans l'exemple [App. C.2] :

« Final evaluation uses an independent runtime under tests/trusted_runtime/, separate from the task-local helper scripts that the agent may modify. »

C'est-à-dire : séparation du runtime de vérification et des scripts que l'agent peut éditer — la défense la plus élémentaire et la plus efficace contre la réécriture des tests. Le trusted runtime de l'exemple : démarre un stack neuf, vérifie la synchro des paiements seedés, injecte une nouvelle mise à jour, vérifie la propagation live, redémarre le service, attend un HTTP-200, injecte une seconde mise à jour, vérifie la synchro post-restart et la réutilisation du cache persisté [App. C.2]. Les auteurs notent aussi une limite propre : le check statique du manifeste Kubernetes vérifie que la probe est exec mais n'exécute pas la commande shell qu'elle contient ; c'est le trusted runtime qui teste réellement la readiness [App. C.2]. ⚠️ Aveu implicite qu'un check statique seul est contournable.

Fiabilité du vérifieur

⚠️ Le point faible du papier, et il est majeur pour nous. - Aucune précision mesurée, aucun taux de faux positifs / faux négatifs, aucun accord inter-annotateurs humain, aucun audit manuel d'un échantillon de checkers : « non précisé » partout. - Le seul contrôle de correction est indirect : le checker doit tourner et la reference solution doit le passer [§3.2]. Cela borne les faux négatifs sur une seule solution et ne dit rien des faux positifs (solutions incorrectes acceptées) — pourtant c'est exactement ce que le RL exploiterait. - Les checker errors sont listées comme une famille d'échecs de validation [§3.2] mais leur fréquence n'est jamais chiffrée. - Aucun test d'attaque / red-teaming du vérifieur n'est rapporté, aucun reward hacking observé n'est décrit. C'est crédible ici uniquement parce qu'il n'y a pas de RL : en SFT on n'entraîne que sur des trajectoires déjà acceptées, et la pression d'optimisation sur le vérifieur est nulle. ⚠️ Rien dans ce papier ne permet de dire que ces 2 756 vérifieurs tiendraient sous RL. Les auteurs eux-mêmes projettent le RL en future work sans discuter ce risque.

Si juge LLM

Aucun juge LLM dans l'environnement. Côté évaluation, GDPval-AA v2 est un Elo issu de « blind pairwise comparisons » [§5.1] via le pipeline NeMo Gym ; le modèle juge, le prompt, les rubriques et toute validation humaine sont « non précisés » (hérités du benchmark). Aucun prompt ni aucune rubrique n'est recopié dans le papier — il n'y a aucun prompt en annexe, ce qui limite fortement la reproductibilité du pipeline de construction.

Verdict

Plausible mais fragile — et à re-cadrer. La ressource (2 756 envs Docker + vérifieurs + 8 364 trajectoires longues, publiée) a une valeur propre, indépendante des claims. Les gains SFT sous Claude Code sont gros et probablement réels — mais (a) contre une base non entraînée à l'agentique, donc un plancher très bas ; (b) sans aucune ablation montrant que l'origine « skills humaines » compte ; (c) sans contrôle de contamination sur le benchmark où le gain est le plus spectaculaire. Ce qui mérite d'être repris, c'est le pipeline de construction, pas les chiffres.

Meilleur ingrédient à transposer

Le couple « template de sous-catégorie qui pré-spécifie le checker » + « test contrastif de dépendance au playbook ». - Le premier inverse l'ordre habituel : on ne génère pas une tâche puis on cherche comment la noter ; le juriste écrit d'abord ce qui sera vérifiable, et l'instanciation par LLM n'a plus le droit de produire une tâche invérifiable. C'est la seule manière que je voie de scaler des envs juridiques sans que le vérifieur devienne un juge LLM non contrôlé. - Le second donne une mesure objective de la valeur d'un playbook : si un modèle réussit aussi bien sans lui, la tâche n'enseigne rien sur ce playbook. Directement utile pour prioriser quels playbooks Harvey valent l'effort d'être transformés en env.

À ne pas importer : les chiffres, l'absence d'ablation, et surtout l'idée implicite que des checkers générés par LLM non audités sont prêts pour du RL.

Expérience minimale

Sur une seule famille (p. ex. « memo de recherche jurisprudentielle », l'analogue de la sub-category business/real-estate-legal qui pèse 45 tâches chez eux [Tab. A2]) : 1. 1 template écrit par un juriste senior, spécifiant les checks : sections obligatoires, juridiction cible, toutes les citations résolvables dans la base d'autorités, exactitude des dates/parties, format de sortie (JSON + memo Markdown). 2. Instancier ~100 tâches par LLM à partir de 20 playbooks ; exiger pour chacune une solution de référence qui passe le checker et 3 contre-exemples négatifs qui doivent échouer → mesurer directement le taux de faux positifs du checker, chiffre que SkillGym ne donne jamais. 3. Test contrastif k=5 runs avec / sans playbook ; garder comme playbook-dependent les tâches avec un delta de taux de succès ≥ 0,4 (au lieu du (1,0) à 1 run du papier). 4. Collecter des trajectoires multi-teacher, SFT, évaluer sur Vals Legal Research Bench et Harvey LAB, avec et sans playbook à l'inférence.

Résultat attendu, par analogie avec [Tab. 3] : gain net sur le réglage avec playbook, gain plus faible mais non nul sans playbook — c'est ce second chiffre qui dirait si la compétence procédurale est réellement internalisée. Signal négatif à surveiller : un taux de faux positifs du checker > ~10 % rendrait toute étape RL ultérieure dangereuse.

Question à poser en interne chez GDM

Deux : 1. Avons-nous le droit d'utiliser les playbooks et notes de pratique de Harvey comme matière première de construction d'environnements (et pas seulement comme contexte d'inférence) — et si oui, sous quel régime de confidentialité pour les trajectoires publiées/loggées ? 2.
