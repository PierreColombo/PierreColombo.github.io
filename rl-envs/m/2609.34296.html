0. En une phrase

TL;DR : les rubriques qui servent déjà à noter le rapport final servent aussi de référence pour noter chaque tour d'outil — un juge LLM évalue le support marginal qu'une page apporte à chaque rubrique relativement à l'historique des points de support déjà acceptés pour cette rubrique dans le même rollout ; la somme donne un crédit par tour, normalisé en groupe et additionné à l'avantage GRPO d'outcome.

Claim principal : sur 4 benchmarks deep research, à initialisation SFT / données / reward d'outcome / budget d'entraînement / harness d'éval identiques, l'ajout du crédit de process fait passer la moyenne de 58,2 → 61,7 (+3,5 pts) vs GRPO [§4.2, Tab. 1] ; l'ablation de l'historique par rubrique coûte −3,0 pts de moyenne sur 3 benchmarks [Tab. 3(b)] ; le coût de scoring est absorbé par l'asynchrone et par le raccourcissement des trajectoires (63,96 h vs 75,14 h sur 200 steps) [Tab. 6].

Contribution revendiquée explicitement comme générale : « a general approach to process reward design for agent RL on open-ended tasks with rubric-based evaluation… without requiring a canonical answer » [§1, contribution (1)] — testée sur un seul domaine (deep research), un seul backbone, un seul juge.

1. Tâches & data

Origine des tâches. Aucune tâche n'est créée par ce papier. Les paires (question, rubric set) viennent de DeepRubric [§4.1, App. A.1] — rubriques « evidence-grounded », produites par un travail antérieur. Les benchmarks OOD : ResearchQA (QA scientifique), DeepResearchBench (rapports, métrique RACE), ResearchRubrics (rubriques écrites par des experts) [§4.1]. ⚠️ Qui écrit les rubriques et à quel coût n'est pas dans ce papier : non précisé. C'est un intrant externe, et c'est le point aveugle pour un transfert juridique.

Pipeline de données [App. A.1] : 1. 9 062 paires question–rubriques DeepRubric ; 2. exclusion des 1 785 questions présentes dans la collection SFT intermédiaire → 7 277 ; 3. 128 tirées au hasard = DeepRubric-Val ; 7 149 = set RL ; 4. vérification de disjonction par matching exact du texte de question entre SFT / RL / Val (⚠️ exact-match seulement : aucun contrôle de near-duplicate / paraphrase).

Données SFT avant RL [App. A.1] : GLM-5.2 génère des trajectoires de recherche sans accès aux rubriques (prompt Fig. 12). Filtres cumulatifs : structure du rapport, citations, arguments d'outils valides, score rubrique normalisé ≥ 0,65, et 4–18 tours de recherche suivis d'un rapport. 1 505 trajectoires retenues, pas de split de validation ; les instructions système sont remplacées par le prompt agent partagé (Fig. 11) à l'export. Rôle : cold start de format (balises <cite>, bloc <answer> unique, un seul appel d'outil par tour) + comportement de recherche.

Volume RL : 7 149 paires, 200 steps, 32 questions/batch, G = 8 → ≈ 6 400 questions vues en une passe (≈ 0,9 époque) [§4.1 Impl., Tab. 4].

Distribution de difficulté / curriculum / rééchantillonnage : non précisé — aucun filtrage par pass@k du modèle de base, aucun curriculum, aucun rééchantillonnage, aucune sélection par difficulté. ⚠️ Pour un papier ENV c'est une absence notable : tout l'effort est sur le crédit, rien sur la sélection des tâches.

Contamination : traitée uniquement comme disjonction train/val sur DeepRubric ; rien sur le chevauchement entre DeepRubric et ResearchQA / DRB / ResearchRubrics. Non précisé.

Coût humain : aucune annotation humaine dans ce travail (⚠️ y compris pour valider les juges). Les rubriques expertes de ResearchRubrics ne servent qu'à l'éval.

2. Environnement / harness

Observation [App. A.2, Fig. 11] : - Search → jusqu'à 2 requêtes, 3 résultats par requête, chaque résultat = titre + URL + snippet + source ID (S*), plafond combiné 4 096 tokens ; - Visit → jusqu'à 2 URLs ; Qwen3.6-35B-A3B extrait, conditionné au goal fourni par l'agent, un couple evidence + summary dans 2 048 tokens par page (prompt Fig. 13) ; format retourné : <webpage ...><evidence>…</evidence><summary>…</summary></webpage> avec ID W*.

Espace d'actions / outils (signatures recopiées, Fig. 12) : - web_search : {"queries": ["..."]}, 1 ou 2 requêtes non vides ; - web_visit : {"urls": ["..."], "goal": "..."}, 1 ou 2 URLs + un goal non vide ; - contrainte : exactement un appel d'outil par tour ; « Visit only exact URLs returned by a successful search in an earlier assistant turn » ; seuls les W* de visites réussies sont citables, jamais les S*.

Multi-turn / horizon [App. A.3] : ReAct [think] → [tool call] → [tool response], puis [think] → [answer]. ≤ 20 tours assistant (réponse finale comprise), 8 192 tokens générés par tour, contexte politique 32 768 tokens pour SFT, RL et le tableau principal. Les observations consomment le contexte et le rapport final doit tenir dans ce qui reste. Gestion du contexte long : aucune (ni troncature, ni résumé, ni mémoire externe) — seulement la compression implicite via l'extraction à 2 048 tokens/page.

Exécution [App. A.2] : Serper (interface Google Search) pour Search, Firecrawl pour Visit — APIs externes réelles, donc non déterministe, non resettable, non rejouable ; aucun timeout, aucune politique de retry, aucune mise en cache rapportés. Non précisé. ⚠️ Conséquence directe : les baselines « + Our Tools » ne sont pas évaluées sur un web figé ; aucune garantie de comparabilité temporelle entre runs.

Gestion des erreurs : « failed retrieval or extraction produces a tool error » [App. A.2] ; le prompt SFT demande de corriger une fois une requête malformée puis de ne pas répéter un chemin qui échoue [Fig. 12]. Le juge de crédit traite explicitement CAPTCHA / erreurs d'accès / pages vides / texte de navigation / titre seul comme aucun support [Fig. 16]. Si la limite de tours ou de contexte est atteinte sans rapport valide, « the evaluated model completes the report from the original question and collected trajectory » [App. A.3] — ⚠️ ce fallback est appliqué à tous les modèles évalués, et il est à la fois un pansement de robustesse et un facteur de confusion (un modèle qui sature le contexte est rattrapé par une génération hors harness).

Exemple de trajectoire : le papier n'en donne aucune verbatim ; seulement le schéma en bas de la Fig. 2 ([think] [tool call] [tool response] … [think] [report], les [tool response] en pointillés étant masqués de la loss) et l'exemple illustratif « Which exercise types best reduce inflammation in older adults? » avec 3 rubriques et 4 visites.

3. Reward / vérifieur

3.1 Outcome

Somme pondérée [App. A.5, Eq. 9] : r^O = 0,70 r_rubric + 0,05 r_format + 0,05 r_search + 0,15 r_cite + 0,05 r_length

  • r_rubric : juge LLM, une rubrique à la fois, score entier 0–4 divisé par 4, puis moyenne pondérée par w_k (Eq. 1) [Fig. 14]. Prompt recopié : barème 4 = « Fully satisfies… All essential components explicitly, correctly, sufficiently addressed » ; 3 = « Mostly… minor omissions » ; 2 = « Partially… one or more essential parts missing » ; 1 = « Minimally… mostly generic » ; 0 = « Does not satisfy ». Garde-fous explicites : « Do not reward an answer merely for mentioning related topics or keywords », « Generic, high-level, or background-only discussion should score low ». Sortie : {"score": x} uniquement. Les rubriques sont typées factual ou logical, avec des consignes distinctes.
  • r_cite = 0,4 r_ID + 0,6 r_semantic : r_ID = fraction des références bien formées qui résolvent vers une evidence de la trajectoire ; r_semantic = pour chaque claim, moyenne harmonique du support joint des sources et de la fraction de sources qui la soutiennent individuellement. Les citations structurellement non notables reçoivent zéro ; les échecs techniques du juge sont exclus [App. A.5]. Prompt de vérification de citation recopié [Fig. 15] : score 2 = toute proposition matérielle (qualificatifs compris) directement soutenue ; 1 = partiel ; 0 = aucun ; « An equivalent paraphrase counts; mere topic overlap or a plausible inference does not » ; 3 exemples few-shot.
  • r_format : bloc réponse, balisage de citation, appels porteurs de requêtes, blocs de raisonnement. r_search (nombre d'appels) et r_length : croissance linéaire jusqu'à un plafond [App. A.5]. ⚠️ Un reward de longueur croissant-jusqu'au-plafond est un incitatif à l'allongement : la Fig. 10(c) montre effectivement les rapports passer de ~1 000 à ~4 576 tokens (Dr.Credit) et ~4 900 (GRPO) pendant l'entraînement.
  • Rapport final vide/non extractible → outcome reward = 0.

3.2 Crédit de process — la mécanique rubrique → crédit par tour (exigence (a))

Chaîne exacte, telle qu'instanciée pour Visit [§3.1, §3.3, Fig. 16, Fig. 17] :

  1. Un appel de juge par couple (tour Visit, rubrique k) — donc K appels par visite. Le juge reçoit en JSON : question ; rubric = {id, type: factual|logical, description, weight, trusted_evidence[]} ; prior_confirmed_support_points_for_this_rubric[] (= l'historique H_{t,k}) ; current_visit_turn = {visit_index, research_turn_index, reasoning (le think pré-visite), tool_calls, pages[{page_id, url, evidence, summary}]}.
  2. Le juge renvoie {level: 0|1|2, page_ids[], support_points[1-3], rationale}. Définitions recopiées [Fig. 16] : - 0 = « failed or irrelevant retrieval; topical overlap without a concrete usable fact; scope mismatch; or information already present in prior confirmed support with no material strengthening » ; - 1 = « a new concrete fact, premise, relation, constraint, or materially stronger verification… but indirect, incomplete, narrow, or covers only a secondary part of its core requirement » ; - 2 = « new, direct, specific, well-supported evidence that substantially satisfies a core factual requirement or supplies a key relation/premise for a logical rubric ». Règles de nouveauté : « Judge semantic novelty, not wording novelty. Exact paraphrases and repeated values are level 0. A materially stronger source, important qualification, more precise value, or missing part of an earlier clue may be level 1 or 2 ». Règles de calibration anti-sur-notation : pas de niveau 2 pour une evidence détaillée qui ne couvre qu'une partie secondaire ; interdiction de combiner le raisonnement pré-visite avec les pages pour « fabriquer » une relation absente ; une page en échec n'invalide pas une autre page substantielle du même tour. Politique evidence > summary : « If Summary conflicts with Evidence, follow Evidence ». Et : « Do not calculate the visit score » — le juge ne produit qu'un ordinal, l'arithmétique est externe.
  3. Mapping ordinal → numérique (hors juge) : niveau 0/1/2 → g_{t,k} = 0 / 0,2 / 0,5 [§4.1 Impl.].
  4. Agrégation : c_t^v = Σ_k g_{t,k} (Eq. 3), plafonnée à 1 [§4.1 Impl.]. ⚠️ La somme est non pondérée : weight est passé au juge mais n'entre pas dans l'arithmétique du crédit, alors que l'outcome est pondéré par w_k (Eq. 1). Incohérence de design non discutée par les auteurs. ⚠️ Le plafond à 1 sature dès 2 rubriques au niveau 2 : une page excellente sur 4 rubriques vaut autant qu'une page excellente sur 2.
  5. Mise à jour de l'historique : H_{t+1,k} = H_{t,k} ∪ ΔH_{t,k} (Eq. 4), où ΔH = les support_points extraits des pages courantes (vide si niveau 0). L'évaluation lit l'historique avant la mise à jour [§3.1]. Les historiques partent vides et évoluent indépendamment à l'intérieur de chaque rollout (pas de partage entre rollouts du groupe).
  6. Tours Search [§3.3, Fig. 3] — crédit composite : - navigation c_t^nav : matching des URLs de résultats normalisées vers les visites ultérieures du même rollout, puis somme des crédits Visit appariés, plafonnée à 1. ⚠️ C'est un double comptage assumé : la même evidence crédite le tour de recherche et le tour de visite. - snippet c_t^snp : pour les résultats jamais visités dans la trajectoire complète, un juge indépendant (sans lecture ni écriture d'historique) renvoie une liste sparse de matches rubrique↔snippet, chaque match acceptée valant η = 0,1. Prompt recopié [Fig. 18] : « Snippets are noisy and unverified; default to no match » ; seule la lettre du snippet compte (titres, URLs, formulation de requête, evidence de référence de la rubrique et connaissance externe exclues) ; une rubrique au plus une fois ; un fait atomique affecté à une seule rubrique ; citation exacte (evidence_quote) obligatoire ; sinon {"matches": []}. - c_t^s = c^nav + c^snp, plafonné à 1. Note d'implémentation révélatrice : les jugements de snippet sont sautés quand le crédit de navigation est saturé [App. B.3].

Qui écrit la rubrique, à quel coût (exigence (a), deuxième moitié) : personne, dans ce papier — les rubriques sont importées de DeepRubric (train/val) et de ResearchRubrics (experts, éval seule). Coût d'écriture non précisé. Ce qui est chiffré, c'est le coût de notation : 29,09 tâches de juge de process par trajectoire, latence de scoring complète 23,03 s/trajectoire contre 2,40 s pour GRPO [Tab. 7] ; 10 043,93 tâches de process par step aux steps 1–40, retombant à 6 231,20 aux steps 161–200 (−38,0 %) [App. C.2]. Le juge est Qwen3.6-35B-A3B, qui fait aussi l'extraction de pages, la notation rubrique du rapport et la vérification de citations [§4.1 Impl., App. A.1].

3.3 Fiabilité du vérifieur

  • Précision mesurée : non. Aucun accord juge↔humain, ni pour le juge d'outcome, ni pour le juge de crédit, ni pour le vérifieur de citations. Aucun taux de faux positifs / faux négatifs. ❌ C'est le trou central du papier.
  • Le seul diagnostic de fiabilité est interne et relatif [App. B.2] : re-notation de trajectoires figées avec/sans historique, température 0, sans thinking, mêmes rubriques/prompts/filtres, jugements à historique vide réutilisés à l'identique ; CI à 95 % par bootstrap apparié sur 10 000 rééchantillonnages de questions [Fig. 6]. Résultat clé : parmi les paires notées niveau 2 sans historique, 12,0 % tombent à 0 avec historique pour Dr.Credit et 20,9 % pour GRPO [App. B.2, Fig. 8]. Cela mesure l'effet de l'historique, pas la justesse du juge.
  • Sensibilité aux paramètres [App. B.3, Tab. 5] : replay offline sur 519 groupes de 8 rollouts (4 152 rollouts, 32 966 tours non finaux), trajectoires / jugements ordinaux / historiques / avantages GRPO figés. Variations testées : niveaux Visit (0, 0.25, 0.5) et (0, 0.2, 1.0), plafond 0,75 et 1,25, η = 0,025 et 0,30, plus un changement joint (partiel 0,1 + plafond 0,5). Résultat : W₁ ≤ 0,077, RMSE ≤ 0,192, accord de signe fusionné ≥ 96,6 %. ⚠️ Deux réserves fortes : (i) le tableau présente des réglages « selected for signal stability from a 53-configuration sweep » — c'est une sélection du sous-ensemble le plus stable, pas la distribution du sweep ; (ii) la stabilité est mesurée sur le signal, jamais sur la performance : aucun réentraînement sous un autre réglage de crédit.
  • Robustesse / attaque : le vérifieur n'a pas été attaqué ni testé contre le hacking. Les seules défenses sont a priori, dans les prompts (default to no match, un fait → une rubrique, citation exacte, nouveauté sémantique).

4. Optimisation

Algorithme : GRPO (DeepSeekMath) avec une seule modification, l'avantage fusionné par tour [§3.2] :

  • normalisations séparées (Eq. 5) : A^rg_{i,t} = (c_{i,t} − μ^rg)/σ^rg avec μ/σ calculés sur tous les tours de politique non finaux du groupe de rollouts, tours à crédit nul inclus, poids égal par tour quelle que soit la longueur du rollout, écart-type de population ; A^O_i = (r_i − μ^O)/σ^O avec la moyenne et l'écart-type d'échantillon GRPO sur les G rewards ;
  • fusion (Eq. 6) : Ã_{i,t} = A^O_i + A^rg_{i,t} pour 0 ≤ t < T_i, et Ã_{i,T_i} = A^O_i sur le tour du rapport — donc le rapport final ne reçoit que de l'outcome, et chaque tour intermédiaire reçoit la totalité de l'avantage d'outcome plus son crédit ;
  • objectif (Eq. 7) : surrogate GRPO clippé, tous les tokens d'un tour partagent Ã_{i,t(i,j)}, moyenne sur tous les tokens de politique du groupe (agrégation token-level), observations d'environnement masquées de la loss mais conservées dans le conditionnement.

Hyperparamètres [Tab. 4, §4.1] : LR RL 5e-7 ; 32 questions/batch ; G = 8 ; 200 steps ; température de rollout 1,0, top-p 1,0 ; PPO epochs 1, clipping ε = 0,2 ; coefficient KL = 0 (le terme KL figure pourtant dans Eq. 7 — ⚠️ incohérence formelle : la référence π_ref est inopérante) ; poids de l'avantage de process = 1 ; max 20 tours, 8 192 tokens/tour, contexte 32 768. SFT : AdamW, LR 1e-5, cosine 30 % warmup, batch 1 × accum 4, BF16, 3 époques, checkpoint époque 2 retenu — et le papier précise que le schedule couvrant 3 époques « fixe la durée SFT à deux époques sans sélection de checkpoint par validation » [App. A.1].

Variante testée puis abandonnée : propagation temporelle escomptée (Eq. 8, App. B.4) — D^(γ)_{i,t} = Σ_{u≥t} γ^{u−t} A^rg_{i,u}, γ = 0,95, accumulée en arrière après normalisation, sans renormalisation ni clipping d'avantage additionnel, rapport exclu. Dégrade les 4 benchmarks, avec ou sans snippets (59,0 et 59,9 vs 60,4 et 61,7) [Tab. 2 ablation]. Conclusion utile : le crédit immédiat (γ = 0) bat le crédit propagé — cohérent avec le fait que l'attribution spatiale est déjà faite par le matching d'URL.

Stabilité : aucune instabilité rapportée, aucune astuce de stabilisation (pas de clip-higher, pas de dynamic sampling, pas de filtrage des groupes à reward constant). Non précisé.

Compute [App. A.1, Tab. 6] : 16 accélérateurs PPU-ZW810E, 96 GB chacun (modèles auxiliaires sur nœuds séparés ou via API) ; 63,96 h pour 200 steps (Dr.Credit) contre 75,14 h (GRPO), décomposées en rollout collection 42,89 vs 49,41 et policy update 13,91 vs 17,12.

Dynamique [Fig. 5, Fig. 10] : - validation DeepRubric : Dr.Credit dépasse le score final de GRPO dès le step 120 et finit avec +3,2 pts [§4.5] ; - rubric score d'entraînement : les deux courbes sont quasi superposées (~69 vs ~67,5 en fin) [Fig. 10(a)] — ⚠️ l'écart se voit surtout en validation/OOD, pas sur le reward optimisé ; - nombre de tours de recherche : 16 → ~6,5 pour Dr.Credit contre ~11 pour GRPO [Fig. 10(b)] ; chiffré par ailleurs 13,2 → 7,8 tours d'interaction par trajectoire entre les steps 1–40 et 161–200 [App. C.2] ; - longueur de rapport croissante pour les deux (~1 000 → 4 576 / 4 900 tokens) [Fig. 10(c)] ; - entropie : non rapportée.

5. Failure modes & reward hacking

Le papier ne contient aucune section de failure modes et ne rapporte aucun cas de reward hacking. Les auteurs n'affirment pas qu'il n'y en a pas : le sujet n'est simplement jamais abordé. ⚠️ Peu crédible vu la conception : reward de longueur croissant jusqu'à un plafond, reward de nombre d'appels, juge LLM unique pour l'extraction et la notation et le crédit, crédit de snippet attribuable sans visite.

Ce que les données du papier laissent néanmoins voir, en étant honnête sur le statut de chaque lecture :

6. Infra & coût

  • Asynchronisme explicite [App. C.2] : « Completed trajectories enter scoring while others continue generating, and independent rubric histories are assessed concurrently through external services. Through this overlap, scoring shares the rollout collection interval » — la latence de scoring est déjà incluse dans le temps total et ne doit pas être ajoutée. C'est la clé du résultat de coût.
  • Parallélisme : les historiques par rubrique étant indépendants, les K appels de juge d'une visite sont parallélisables ; en revanche l'historique crée une dépendance séquentielle au sein d'une rubrique (le tour t+1 ne peut être noté avant que ΔH_t soit accepté) — le papier ne discute pas ce goulot.
  • Chiffres : 23,03 s/trajectoire de latence de scoring complète (vs 2,40 s), 29,09 tâches de juge de process par trajectoire [Tab. 7] ; ~10 044 → 6 231 tâches de process par step [App. C.2]. Coût monétaire par step / par rollout : non précisé (le juge est self-hosted ou API, non tranché). Débit de rollouts : non précisé.
  • Comparaison de temps à nombre de steps fixé, pas à qualité égale — les auteurs le disent eux-mêmes : « This comparison fixes training steps without measuring time to a matched quality threshold » [App. C.2]. Honnête.

Le contrôle manquant : attribution vs densité (exigence (b))

Question : les +3,5 pts viennent-ils de ce que le crédit arrive au bon tour, ou simplement de ce que le reward est devenu dense et que la variance du gradient a baissé ?

Ce que le papier apporte, partiellement : - Ablation « sans historique » [Tab. 3(b), −3,0] : c'est le contrôle le plus proche d'un contrôle de densité. Sans historique, le crédit reste dense, par tour, sur la même échelle ordinale (0/0,2/0,5), produit par le même juge, avec la même normalisation ; seule disparaît la discrimination du support nouveau. Que 3,0 des 3,5 points s'évaporent est un argument réel : la densité seule n'explique pas l'essentiel du gain. - Ablation du discounting [Tab. 2] : montre que déplacer le crédit dans le temps (propagation γ) dégrade — autre indice que la position temporelle du crédit importe.

Ce qui manque, et c'est exactement le défaut récurrent de cette famille de travaux : 1. Aucun contrôle de permutation : rejouer les mêmes crédits en les mélangeant aléatoirement entre les tours du même rollout (même moyenne, même variance, même densité, attribution détruite). C'est le seul contrôle qui sépare proprement « bon tour » de « reward dense ». 2. Aucun contrôle à crédit constant : A^rg constant non nul par tour, ou crédit tiré d'un bruit calibré — contrôle du pur effet de réduction de variance / de shaping. 3. Aucun contrôle de crédit non ancré sur la rubrique : par ex. un crédit purement « nouveauté de l'information » sans rubrique, ou longueur d'evidence extraite. On ne sait donc pas ce que la rubrique apporte au-delà d'un signal de nouveauté générique. 4. Aucun contrôle d'attribution directe : aucune mesure du type « le tour crédité est-il bien le tour cité dans le rapport final / le tour dont le retrait dégraderait le rapport ». Le papier n'évalue jamais la justesse d'attribution, seulement l'effet de bout en bout. 5. ⚠️ L'ablation « sans historique » n'est pas non plus parfaitement appariée en densité : retirer l'historique augmente mécaniquement les crédits (plus de niveaux 2, davantage de saturation du plafond — cf. App. B.2), donc change la distribution du signal, pas seulement son information. Elle est suggestive, pas concluante.

Conclusion sur (b) : le contrôle existe à moitié (historique + discounting), le contrôle décisif (permutation / crédit constant) est absent. À dire tel quel : le papier établit solidement qu'un crédit dense informatif par rubrique bat un crédit dense non informatif, et pas du tout qu'il bat un crédit dense arbitraire.

Scaling

Non mesuré. Un seul backbone (Qwen3-8B), un seul juge (Qwen3.6-35B-A3B), un seul volume de tâches, un seul budget (200 steps). Pas d'étude d'échelle. Les auteurs ne revendiquent rien sur ce point.

Solidité

  • ✅ Baselines fortes et appariées : GRPO partage initialisation SFT, données, reward d'outcome, budget et harness d'éval [§4.1] ; DeepRubric-8B et DR Tulu-8B réévalués avec les mêmes outils, sur le même Qwen3-8B [App. A.3]. C'est au-dessus du standard du domaine.
  • ⚠️ Ablations : nombreuses et bien construites (composants, fusion, historique, discounting, sensibilité offline), mais le contrôle densité/permutation manque (ci-dessus), et les effets de composants (0,7–1,3 pt) sont du même ordre que la non-monotonie observée.
  • ❌ Variance / seeds : un seul run par configuration, aucune seed, aucun intervalle de confiance sur les scores de benchmark. Les seuls CI (bootstrap, 10 000 rééchantillonnages) portent sur une re-notation offline, pas sur l'entraînement [App. B.2]. Avec DeepRubric-Val à n = 128, DRB à n = 100 et RR à n = 101, un écart de 2–3 pts n'est pas distinguable du bruit sans réplicats.
  • ❌ Fiabilité de l'éval : (i) aucun juge validé contre des humains, nulle part ; (ii) le juge d'éval de DeepRubric-Val est non précisé — s'il s'agit du même Qwen3.6-35B-A3B qui calcule le reward d'entraînement, l'éval in-domain est juge-contaminée (les 3 autres benchmarks échappent à ce reproche et c'est ce qui sauve l'article) ; (iii) contamination inter-benchmarks non vérifiée ; (iv) web vivant non figé.
  • ⚠️ Échelle : 8B, 200 steps, 16 accélérateurs — modeste mais honnêtement rapportée ; un seul point d'échelle.
  • ❌ Reproductibilité : ni code, ni données, ni poids, ni environnement publiés ; aucun lien dans le papier. Les prompts complets (9 figures) et les hyperparamètres sont donnés, ce qui rend une réimplémentation possible — mais les services payants (Serper, Firecrawl), le web vivant et un accélérateur non standard (PPU-ZW810E) empêchent toute réplication exacte.
  • ✅ Cohérence texte ↔ chiffres : excellente (cf. 7.0), aucune contradiction trouvée.

Verdict : plausible mais fragile. Le mécanisme est bien spécifié, l'appariement de la baseline est sérieux, et le gain survit à trois juges externes — c'est beaucoup. Mais un seul run par config, aucun juge validé, aucun code, et surtout l'absence du contrôle d'attribution font que l'affirmation « le crédit va au bon tour » reste non établie ; seule l'affirmation « ce crédit-ci aide » l'est, sur un backbone et un domaine. À répliquer avant de fonder un design dessus — mais à répliquer en priorité.

Meilleur ingrédient à transposer : l'historique de support par rubrique comme référence de nouveauté. Raisons : (i) c'est le seul mécanisme du papier qui supprime le besoin de vérité exacte sans la remplacer par un reward model opaque — la référence est la rubrique plus ce que la trajectoire a déjà établi, donc une référence locale, auditable, en langage naturel ; (ii) c'est l'ingrédient qui porte l'essentiel du gain (−3,0 sur −3,5 à l'ablation) ; (iii) c'est exactement la structure du travail juridique, où la valeur d'une recherche est marginale par rapport au dossier déjà constitué ; (iv) l'appariement de la baseline et les 3 juges externes OOD rendent le résultat crédible malgré l'absence de seeds. Second choix, moins cher : le prompt de vérification de citation [Fig. 15] — réutilisable presque tel quel comme composante de reward sur Harvey LAB / Vals, indépendamment du reste.

Expérience minimale. Sur un set de questions juridiques à rubriques (par ex. 300–500 questions, 4–8 issues chacune, rubriques écrites par 2 juristes avec trusted_evidence = autorité de contrôle), agent à 2 outils (recherche base + ouverture de document), 20 tours, backbone déjà SFT : 1. baseline GRPO outcome-only (rubriques + vérif. citations), même init / données / budget ; 2. + crédit de process avec historique par issue (réplication Dr.Credit) ; 3. + les deux contrôles que le papier n'a pas : (3a) crédits permutés aléatoirement entre tours du même rollout, (3b) crédit constant par tour — tous deux à densité et échelle identiques ; 4. 3 seeds, CI bootstrap sur les scores. Résultat attendu, si le mécanisme est réel : (2) > (3a) ≈ (3b) ≳ (1), avec l'écart (2)−(3a) ≈ l'écart (2)−(1) ; gain surtout sur la couverture d'issues sous budget de tours contraint (l'analogue de la Fig. 4(c)), pas sur le score à budget illimité. Si au contraire (3a) ≈ (2), le gain est de la densité et il faut arrêter les frais sur le crédit ancré-rubrique. Coût : une boucle GRPO existante + ~K appels de juge par visite (≈ 29 appels/trajectoire chez eux, à provisionner), plus le coût expert des rubriques — qui est le vrai poste.

Question à poser en interne chez GDM : a-t-on, sur Gemini Law, les moyens d'écrire des rubriques evidence-grounded (issue + autorité de contrôle attendue) à l'échelle de plusieurs milliers de questions — c'est-à-dire exactement l'intrant que ce papier importe sans le payer ? Et subsidiairement : qui, en interne, a déjà fait tourner le contrôle de permutation sur un reward de process, sur n'importe quel domaine ? La réponse conditionne l'ensemble de cette famille de méthodes, pas seulement son application juridique.
