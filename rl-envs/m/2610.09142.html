C'est la seule pièce du lot qui donne une méthode directement applicable à un vérifieur juridique. Profondeur = grille complète 0–9 ; §4 (optimisation) et §6 (infra) adaptées faute d'entraînement.

0. En une phrase

Audit par mutation d'effets (et non du code du checker) des vérifieurs livrés d'AppWorld et WorkArena : en dupliquant une écriture non-idempotente ou en écrivant un champ hors périmètre, on produit un effet faux que les checkers acceptent — 6/15 effets construits AppWorld (2/5 générateurs éligibles) et 21 effets faux confirmés par lecture Table API sur 23 cellules WorkArena qui reçoivent toutes PASS [§3.5, Tab. 2].

Claim principal, formulé précisément : (i) AppWorld est aveugle au cardinal des enregistrements — ses unit tests vérifient les valeurs de champs, pas len(added_*) — donc une écriture dupliquée crée une ligne supplémentaire sans changer aucune valeur vérifiée, et le checker renvoie PASS sur les 3 variantes quotidiennes de 2 des 5 générateurs éligibles [§3.5] ; un patch d'une ligne len(added_*)==N, déjà documenté par AppWorld, appliqué à des copies des tests, fait basculer les 6 cellules en FAIL en préservant les 6 contrôles [§3.6]. (ii) WorkArena détecte les écritures hors périmètre via un flag page-local (WORKARENA_BAD_FIELD_CHANGED) qui ne survit pas à la navigation du submit ; sur 23 cellules re-jouées prospectivement, la Table API confirme une valeur non-défaut persistée dans 21, et le checker renvoie PASS dans les 23 [§3.5, App. E, App. F]. (iii) Claim négatif explicite : aucun taux de population n'est revendiqué — les cellules sont des census fixes et dépendants, pas un échantillon [§5, §8].

1. Tâches & data

Pas de dataset d'entraînement : les « tâches » sont les tâches livrées des deux benchmarks, et les « données » sont des mutations mécaniques de solutions de référence correctes.

  • Origine des tâches : benchmarks existants, non modifiés. AppWorld : les 48 tâches DEV state-changing = 16 scenario generators × 3 variantes quotidiennes [§3.2, §5]. Le split HOLDOUT reste scellé et n'est pas ouvert pour ce papier [§5]. WorkArena : les 13 templates L1 state-changing autorisés sur l'instance pool (4 form + 9 catalog) aux index de configuration 0–2 → 39 cellules [§3.2].
  • Pipeline de construction (c'est le cœur du papier) : 1. Obtenir une trajectoire de référence correcte délivrée depuis l'état de départ frais (AppWorld : programme d'appels API enregistré ; WorkArena : driver cheat() livré, via BrowserGym + Playwright) [§2, App. H]. 2. Appliquer une édition mécanique issue d'une grammaire de fautes fixée [App. A, Tab. 4] — l'édition est conçue pour rendre l'effet faux d'une manière nommée. 3. Délivrer la trajectoire mutée par l'interface normale de l'environnement (pas d'injection JS, pas d'écriture directe en base, pas de modification du validateur) [App. H]. 4. Lire l'effet réellement persisté via un canal indépendant du checker (replay write counters côté AppWorld ; lecture de l'enregistrement exact par la Table API côté WorkArena, avant l'appel du checker et avant le cleanup) [Tab. 2, App. F]. 5. Appeler le checker livré, non modifié. 6. Ne compter un faux accept que si PASS et évidence retenue prouvant l'effet faux [§2 « Confirmed false accepts »].
  • Volume : 2 762 cellules pour le bras intent-swap (70 contrôles diagonaux + 2 692 hors-diagonale, 3 en erreur, 2 689 verdicts valides) [§1, Tab. 1] ; bras fautes = 10 familles distinctes, 48–76 cellules planifiées par famille [Tab. 5].
  • Distribution de difficulté : remplacée par une échelle de sévérité sémantique sur le bras swap — Diag (contrôle), Rung-0 (intention jumelle à un paramètre près), Rung-1 (tâche sœur, même scénario), Rung-2 (cross-scénario, modèles d'effet partagés), Rung-3 (cross-scénario, modèles disjoints) [§2].
  • Filtrage : par census engagé avant scoring, pas par pass@k : census d'idempotence (pour Extra-NI), census des valeurs par défaut on-form (pour Omit-Divergent), candidats dont la valeur de template diffère du défaut (pour Extra-Field) [App. A]. Exclusion après coup des dégénérescences : 42 éditions écartées car l'effet restait correct (33 PASS AppWorld Extra sur endpoints idempotents + 9 PASS WorkArena Omit-Field préservant le défaut du formulaire) [§2, Tab. 5].
  • Curriculum : sans objet. Les incréments sont ordonnés par discipline de commit freeze (protocole + code d'énumération + census requis committés avant la première cellule gouvernée scorée ; freeze privé, « not public preregistration ») [§3.1, App. B].
  • Contamination / séparation train-test : pas d'entraînement, donc pas de contamination de modèle (zéro appel de modèle [§3.1]). Séparation préservée : HOLDOUT AppWorld scellé [§5] ; ⚠️ mais la population WorkArena re-jouée est sélectionnée sur l'outcome (ce sont les 23 cellules qui avaient déjà PASS) — l'auteur le dit explicitement et refuse d'en tirer un taux [§8 « WorkArena selection »].
  • Données SFT/IFT : sans objet.
  • Coût humain : non précisé (pas d'annotation ; travail auto-financé, crédits AWS Activate [§ Competing interests]).

2. Environnement / harness

Le harness audité n'est pas un harness d'entraînement mais le harness d'évaluation livré de chaque benchmark ; le papier ajoute un runner d'audit autour.

  • Observation : côté AppWorld, l'évaluateur reçoit l'état terminal de la base applicative (unit tests d'état sur un diff changed_records : added_*, updated_*, removed_*) [§3.6]. Côté WorkArena, le validateur lit l'état de la page courante + un ID d'enregistrement stocké côté navigateur [§3.4, App. D].
  • Espace d'actions / outils : AppWorld = appels aux API applicatives du benchmark (programmes d'API enregistrés rejoués) [§2]. WorkArena = interactions navigateur via les drivers de tâche livrés et Playwright ; pour Extra-Field, l'audit ajoute un champ source-informed au task_fields du driver, et la routine amont _fill_fields saisit la valeur via les label locators Playwright, puis le driver clique le bouton insert [App. H]. Aucune signature d'outil n'est recopiée dans le papier (ce ne sont pas des outils LLM).
  • Single/multi-turn, horizon : non applicable (pas d'agent LLM). Les cellules WorkArena sont une passe scriptée : un cheat() (fill + insert) puis un validate() sur la page post-submit [App. E]. ⚠️ Conséquence reconnue : l'audit ne teste pas le protocole BrowserGym de validation par pas, où l'écriture hors périmètre et le submit tomberaient dans deux pas distincts [§3.5, App. E].
  • Exécution, déterminisme, reset, timeouts : AppWorld réinitialise la base d'exécution à chaque cellule [App. H]. WorkArena tourne sur une instance ServiceNow pool hébergée partagée (build Washington DC), crée un utilisateur par épisode, invoque le teardown et vérifie le résidu actor-scoped — ce n'est pas un reset global de base, d'autres utilisateurs pouvant écrire [App. H]. Paramètres : viewport 1280×720, slow_mo = 1 000 ms, task timeout 10 s, limite par cellule 420 s, seed 7001 à chaque reset avec index de configuration fixe, nom d'utilisateur Faker par épisode délibérément non seedé [App. H]. Exécution strictement séquentielle.
  • Gestion des erreurs : reprises cellule par cellule depuis des ledgers enregistrés après kills de processus et une perte de session, « so no graded cell was scored twice » [§3.1, App. B]. 3 cellules WorkArena en erreur (références déplacées dont le champ a un autocomplete dépendant) exclues du dénominateur et conservées au ledger [§3.3]. Les refus sont enregistrés avec leur motif [App. B]. 2 cellules diagonales de shakedown antérieures au premier freeze sont divulguées et re-exécutées [§3.1].
  • Exemple de « trajectoire » : le papier recopie le test livré du générateur 22cc237 (Venmo payment request), qui est exactement le point aveugle [§3.5] :
test.case(
    dict_of(added_payment_requests, "receiver_id", "amount"),
    "==",
    private_data.pending_user_id_to_share,
)

Le générateur 396c5a2 compare queue_song_ids par union d'ensembles et n'asserte ni l'unicité ni |Δ| : un enqueue dupliqué est invisible [§3.5, §3.6]. 22cc237 asserte bien |updated| = 0 et |removed| = 0, mais jamais |added| = N [§3.6].

3. Reward / vérifieur — le protocole d'audit en détail

3.a Ce qui est audité

Deux designs de checker d'exécution volontairement distincts [§3.2] : (i) assertions d'état API-native (AppWorld : unit tests Python sur le diff de base) ; (ii) validation web live (WorkArena : validateur qui lit la page + un canal d'évidence navigateur). Verdict = binaire PASS/FAIL, avec possibilité de refus de scorer [§2]. Aucun LLM-as-judge, aucun reward model, aucun crédit partiel.

3.b Modèle de menace

Checker c = programme fixe attaché à la tâche t, recevant l'évidence d'une trajectoire terminée (état terminal + pour certaines familles les appels API émis) [§2]. Adversaire : connaît la tâche, contrôle la trajectoire exécutée, ne peut pas modifier le checker, son canal d'évidence, ni l'environnement après le début de tâche [§2]. L'auteur relie explicitement ce modèle au risque d'entraînement : « an agent (or a policy being trained on checker rewards) produces plausible-but-wrong work, and the question is whether the checker's acceptance boundary separates it from correct work » [§2].

3.c Comment les mutants sont générés

Unité de mutation = l'effet de la tâche, pas le code du checker — c'est la différence revendiquée avec la mutation testing classique [§6]. Chaque édition s'applique à une solution de référence correcte avant délivrance fraîche [App. A, Tab. 4] :

Famille Construction Suite
claim-only ne délivrer que l'étape de claim/completion ; aucune écriture AppWorld + WorkArena (GUI)
omit supprimer le dernier appel d'écriture AppWorld
partial ne garder que la première d'une séquence d'écritures répétées AppWorld
wrong-value déplacer une valeur écrite vers une autre valeur légale AppWorld
extra dupliquer le dernier appel d'écriture AppWorld
extra-ni idem, restreint aux endpoints marqués non-idempotents par un census d'idempotence committé (POST dupliqué → payment request + notification en trop ; action dupliquée → player record doublé) AppWorld
omit-field soumettre le formulaire sans un champ WorkArena
omit-divergent omettre un champ dont la valeur attendue diffère de son défaut on-form (census de défauts committé), pour que l'omission change bien l'effet WorkArena
no-submit laisser le formulaire non soumis ; ne pas invoquer le driver WorkArena
extra-field écrire un champ supplémentaire que la tâche ne mentionne jamais, choisi parmi des candidats dont la valeur de template diffère du défaut (p. ex. category sur le formulaire incident, acquisition_method sur l'actif matériel) WorkArena

Second bras, intent-swap : la trajectoire de référence de la tâche j est délivrée fraîche puis notée par le checker de la tâche i ≠ j, à distances sémantiques graduées (Rungs 0–3) [§2]. Grille AppWorld = 74 lignes d'évaluateurs (31 évaluateurs DEV + 43 évaluateurs à intention déplacée admissibles selon un manifeste de gate committé) × 31 trajectoires exécutées = 2 294 cellules ; grille WorkArena = 13 templates × 3 configs = 468 cellules sur 7 passes de reprise [App. C].

3.d Comment un faux accept est confirmé (la règle décisive)

« A fault-cell PASS counts as a confirmed false accept only if retained environment evidence proves that the delivered effect differs from the correct effect. The verdict alone is insufficient. » [§2]

Deux types d'évidence seulement sont acceptés [Tab. 2, colonne Evidence] : 1. No-write garanti par construction — le runner prouve qu'aucune écriture n'a eu lieu (familles claim-only, no-submit). 2. Readback d'effet — replay write counters (AppWorld extra) ou lecture de l'enregistrement exact par la Table API, effectuée après submit mais avant l'évaluation par le checker et avant le cleanup (WorkArena extra-field) [§3.5, App. F].

Conséquences appliquées : - 42 éditions dégénérées exclues du compte de faux accepts : 33 PASS AppWorld extra sur endpoints idempotents + 9 PASS WorkArena omit-field laissant l'effet par défaut correct [§2, Tab. 5]. L'auteur les assimile aux equivalent mutants de la mutation testing [§6]. - Les 15 cellules extra-ni ne sont comptées qu'une fois car l'incrément re-score des transformations déjà présentes dans extra [§2, Tab. 5 caption]. - L'incrément WorkArena extra-field d'origine (23 PASS) reste hors du Tab. 2 faute de readback post-submit : il est étiqueté candidate_only_no_post_submit_extra_field_readback [§2, App. F]. - Un PASS hors-diagonale du bras swap n'est pas un faux accept : les artefacts retenus ne prouvent pas, cellule par cellule, que l'intention cible était insatisfaite avant et après [§2, §5, §8].

3.e Taux de faux positifs de l'audit lui-même

Le seul chiffre direct : sur les 23 cellules WorkArena re-jouées, l'oracle gelé de l'audit s'est trompé 2 fois — il comparait le display label demandé, or un audit de représentation retenue a trouvé 2 lignes dont la valeur brute persistée égalait le défaut stocké ; ces lignes ont été reclassées en dégénérescences après scoring, conservativement, sans ajout ni retrait de cellule [App. F]. Soit 2/23 ≈ 8,7 % de faux « effets faux » dans l'incrément, détectés par une vérification de la valeur canonique et non de l'étiquette affichée. Autres garde-fous mesurés : contrôles diagonaux 31/31 (AppWorld) et 39/39 (WorkArena) [Tab. 1, App. H] ; 48/48 contrôles de référence passants sur le bras fautes AppWorld [App. H] ; les 6 contrôles du patch restent PASS [§3.6] ; zéro erreur ou timeout d'évaluateur sur la grille AppWorld [App. C] ; cleanup propre sur les 23 cellules, aucune reprise, aucun remplacement [§3.5]. ⚠️ Aucun taux de faux rejet de l'audit n'est estimé hors contrôles, et aucune mesure d'accord humain (il n'y a pas de juge humain dans la boucle).

3.f Granularité, termes additionnels

Verdict binaire, aucun crédit partiel, aucun terme de format/longueur. L'audit ajoute en revanche une partition de dénominateur rendue explicite avant toute lecture d'outcome [Tab. 5] : Scheduled → Refused/ineligible → Incomplete → Degenerate → Candidate (effet non confirmé) → Classified, les colonnes Pass et FA restant hors de la partition. C'est, pour un env RL, le bon gabarit de comptabilité d'un vérifieur.

3.g Robustesse / attaques

Le papier est l'attaque, mais une attaque non adaptative : fautes mécaniques issues d'une grammaire fixe, « no live model-generated adversary, checker-aware search, or natural-failure corpus » [§8]. L'auteur place l'adversaire adaptatif (candidats générés par modèle, sous pression d'optimisation) en future work [§7]. ⚠️ C'est la limite la plus importante pour un usage RL : une policy entraînée explore un espace de fautes bien plus large qu'une grammaire de 11 familles.

3.h Réparations proposées

  • AppWorld : ajouter test.case(len(added_*), "==", N) sur le diff changed_records — l'assertion que le guide des générateurs d'AppWorld documente déjà et que les deux générateurs fautifs n'écrivent pas [§3.6]. Appliquée à des copies spécifiées après le census : 6/6 PASS → FAIL, 6/6 contrôles inchangés. Le Tab. 2 reste celui des tests livrés non modifiés.
  • WorkArena : persister le flag WORKARENA_BAD_FIELD_CHANGED dans le localStorage ou sur l'enregistrement créé, ou relire la ligne par la Table API après submit (ce que l'audit fait déjà) [§3.6, App. E]. ⚠️ Non testé : « We did not re-run WorkArena » avec ce patch [§3.6].

4. Optimisation

Sans objet : aucun entraînement, aucun algorithme RL, aucun appel de modèle [§3.1, §8]. Ce qui tient lieu de « méthode » est la discipline de protocole [§3.1, App. B] : (i) protocole, code d'énumération et census requis committés avant la première cellule gouvernée ; (ii) chaque incrément spécifié avant que ses propres cellules soient scorées ; (iii) reprise par ledger interdisant le double scoring ; (iv) freeze privé — l'auteur refuse explicitement le terme de préenregistrement public.

Le lien avec l'optimisation est argumentatif, en §4 du papier (Rank orders under an assumed Extra-NI budget) : la métrique officielle Task Goal Completion est « insulated » car les deux générateurs fautifs sont DEV-only, mais « any training or selection loop that rewards DEV Task Goal Completion is not. Duplicate-write successes would look like valid reward. » [§4]. C'est le point à retenir pour un env RL : une faille connue d'un checker peut être neutre pour un leaderboard et toxique pour une boucle d'entraînement qui échantillonne le même split.

5. Failure modes & reward hacking

Ce papier est un catalogue de failure modes de vérifieurs ; aucun comportement émergent de policy (pas de policy).

  1. Aveuglement au cardinal (AppWorld) — comportement : dupliquer une écriture non-idempotente crée un enregistrement en trop (payment request + notification supplémentaires, player record doublé) tout en préservant toutes les valeurs de champ vérifiées → détection : construction extra-ni ciblée par un census d'idempotence + replay write counters → correction : len(added_*)==N sur copies, 6/6 FAIL, contrôles préservés [§3.5, §3.6, Tab. 2]. ⚠️ Lecture RL : c'est la forme canonique du reward hacking par sur-production — l'agent peut toujours ajouter, jamais être pénalisé.
  2. Canal d'évidence volatile (WorkArena, écriture hors périmètre) — comportement : le setup injecte un script qui pose un listener change sur tout input/select/textarea hors de la liste protégée et lève un flag page-local ; le validateur lit ce flag en premier et renverrait reward 0 avec « Some fields outside of the task scope have been changed » — mais le submit charge une nouvelle page et le flag disparaît → détection : 23 cellules re-jouées prospectivement + lecture Table API de l'enregistrement exact avant le checker → 21 valeurs non-défaut persistées, 23 PASS → correction proposée, non testée : persister le flag (localStorage / sur l'enregistrement) ou relire la ligne après submit [§3.5, App. E, App. F]. Nuance honnête de l'auteur : les listeners ne sont liés qu'à l'injection, donc des champs créés ensuite échapperaient aussi — mais ce n'est pas la cause des cellules confirmées, category et acquisition_method étant présents à l'injection [App. E].
  3. Scoping de session (WorkArena, faux rejet potentiel) — comportement : le validateur de formulaire stocke l'ID de l'enregistrement créé sous une clé localStorage contenant l'identité Python de l'objet tâche validant ; le validateur catalog lie l'évidence par un request ID dans l'URL courante. Hors du canal d'origine, le validateur renvoie FAIL (« The form has not been submitted ») alors que l'enregistrement existe en base → détection : cellules de probe divulguées ; ces routes expliquent la totalité des 57 rejets Rung-3 WorkArena → correction : aucune ; l'auteur refuse de classer cela en faux rejet, car hors du contrat « same-session » supporté, et retire ces 57 cellules de l'évidence sémantique [§3.4, App. D].
  4. Dégénérescences qui ressemblent à des faux accepts — 33 PASS extra sur endpoints idempotents et 9 PASS omit-field préservant le défaut : PASS corrects, écartés [§2, Tab. 5]. Leçon : sans readback, on surestime massivement le taux de faux accepts.
  5. Faute de l'oracle d'audit lui-même — l'oracle gelé comparait des display labels ; 2 des 23 valeurs demandées étaient des alias de la valeur stockée par défaut → reclassées en dégénérescences après scoring [§3.5, App. F]. ⚠️ À retenir : le piège « étiquette affichée ≠ valeur canonique » est exactement le piège des citations juridiques (références parallèles, ECLI vs référence nationale).
  6. Absence de faux accept ailleurs : omit, partial, wrong-value, claim-only (AppWorld) et claim-only, no-submit, omit-divergent (WorkArena) renvoient FAIL sur toutes les cellules scorées enregistrées [§3.5, Tab. 5]. L'auteur avertit : « A zero in FA means that no false accept was independently confirmed, not that none exists » [Tab. 5 caption]. Crédible : ces familles détruisent ou omettent un effet que les assertions de valeur regardent directement.

6. Infra & coût

  • Parallélisme : aucun. Exécution strictement séquentielle, contrainte par une instance ServiceNow hébergée partagée ; l'auteur en fait une limite explicite au volume de réplication (« how much replication fits a weekend slice ») [§8, App. H].
  • Débit mesuré : grille AppWorld 2 294 cellules, 531 s de wall clock de scoring, zéro erreur/timeout, reprise après un kill sans re-scoring [§8, App. C]. Grille WorkArena 468 cellules sur 7 passes, dernière passe 3 123 s, ≈ 11 h cumulées ; ≈ 71 s par cellule live (mesuré sur un pilote de 12 cellules) [App. C]. Rerun prospectif des 23 cellules : 1 963,7 s [App. F]. Pilote 6 tâches / 30 cellules hors-diagonale : 88,4 s [App. C].
  • Goulot : le live web (71 s/cellule) domine de ~300× le coût d'une cellule AppWorld (531 s / 2 294 ≈ 0,23 s). Ordre de grandeur utile : un vérifieur d'état API s'audite à grande échelle, un vérifieur piloté par navigateur non.
  • Coût monétaire : non précisé. Auto-financé, crédits AWS Activate, zéro coût d'API modèle (aucun appel) [§ Competing interests, §3.1].
  • Dates : grille WorkArena 23–24 août 2026, readback 28 août 2026 [App. H].
  • Lacune de réplication reconnue : OS hôte et version patch de Python non retenus dans les artefacts de grille [App. H].

Ablations

Deux ablations propres, au sens strict : 1. Isolation du mécanisme AppWorld : extra (toutes écritures, 39 PASS, 33 dégénérés) vs extra-ni (restreint par census d'idempotence, 15 effets réels, 6 PASS) → la duplication n'est fautive que sur endpoints non-idempotents, et c'est bien le cardinal, pas la valeur, qui est en cause [§2, Tab. 5]. 2. Isolation de la cause par réparation : ajout de len(added_*)==N sur copies → 6/6 bascules, contrôles préservés → l'assertion manquante est la cause [§3.6]. S'y ajoutent deux contrôles négatifs forts : le bras intent-swap (0/2 689) montre que les checkers ne sont pas globalement permissifs, et l'exclusion des 42 dégénérescences montre que le PASS brut surestime le défaut de 39→6 et 23→21.

Solidité

  • Baselines fortes et à jour : n.a. — pas de méthode concurrente à battre ; ce qui en tient lieu, les contrôles diagonaux et de référence, est présent et passe à 100 % ✅.
  • Ablations qui isolent la contribution ✅ — le patch d'une ligne et la coupure idempotent/non-idempotent isolent exactement le mécanisme revendiqué.
  • Variance / seeds ❌ — une seule exécution par cellule, seed unique 7001, aucun intervalle (refusé par argument : census fixe et dépendant, 107/109 groupes générateur×famille homogènes [§5]). Seule stabilité test-retest observable : les 23 cellules WorkArena redonnent 23 PASS au rerun.
  • Fiabilité de l'éval ✅ — zéro appel de modèle donc zéro contamination ; évidence d'effet indépendante du checker audité (Table API, write counters) ; l'audit détecte et corrige ses propres 2 faux positifs ; refus explicite de compter un PASS sans readback.
  • Échelle ⚠️ — 2 suites, 2 générateurs AppWorld et 3 templates WorkArena fautifs ; une seule instance ServiceNow partagée ; le bras WorkArena confirmé est sélectionné sur l'outcome.
  • Reproductibilité ✅ (avec réserve) — pins exacts (versions, commits, SHA-256 des wheels, Playwright/Chromium), supplément checksummé sur OpenReview, reproducer en bibliothèque standard ; ⚠️ mais aucun dépôt public nommé, identifiants ServiceNow exclus, OS/Python non retenus [App. H, App. I].

Verdict : solide dans son périmètre, et explicitement borné. Le papier revendique exactement ce qu'il prouve — deux mécanismes confirmés par évidence indépendante — et refuse par trois fois d'en tirer un taux de population [§5, §7, §8]. C'est un papier dont la méthode vaut plus que les chiffres : les faux accepts confirmés sont peu nombreux (6 et 21, que l'auteur interdit d'agréger [Tab. 2 caption]) et issus de census sélectionnés, mais le protocole qui les isole est réutilisable et contraignant. Ce qu'il ne montre pas : qu'un agent réel ou une policy entraînée déclenche ces points aveugles (adversaire non adaptatif, aucun appel de modèle), ni l'effet réel sur un entraînement RL — la §4 reste une analyse de sensibilité sous budget assumé. ⚠️ Conflit d'intérêts déclaré : l'auteur commercialise une approche de vérification apparentée.

Meilleur ingrédient à transposer

La règle « PASS ≠ faux accept sans readback indépendant », couplée à la mutation de réponses correctes. Elle résout précisément le point dur du droit — pas de vérifieur exact — en le contournant : on n'a pas besoin d'un oracle de vérité pour auditer un vérifieur, il suffit de savoir par construction qu'une sortie est fausse, parce qu'on l'a soi-même corrompue à partir d'une sortie correcte. Le coût expert tombe à la validation initiale des réponses gold et à l'arbitrage des dégénérescences. Second ingrédient, plus immédiat : le mode de faute extra. Le mécanisme AppWorld (union d'ensembles sur queue_song_ids, aucune assertion de cardinal) a un analogue direct et très probable dans toute rubrique juridique qui vérifie « chaque autorité citée existe et est pertinente » par appartenance — elle acceptera le citation padding, qui est exactement le reward hacking qu'une policy RL trouvera en premier sur un reward de couverture.

Expérience minimale

Prendre ~50 items de recherche juridique à réponse gold validée. Définir 6 familles de corruption (citation surnuméraire réelle ; pinpoint faux ; autorité abrogée ; mauvaise juridiction ; proposition inversée à citations inchangées ; omission de l'autorité dispositive), figer la grammaire et la grille avant tout scoring. Générer 3 variantes par item et par famille (~900 cellules), les faire passer par le vérifieur/juge candidat de Gemini Law non modifié, et n'enregistrer un faux accept que si (a) le juge renvoie PASS et (b) une résolution d'identifiants canoniques hors du juge confirme la corruption (pour les familles vérifiables mécaniquement) ou (c) la corruption est vraie par construction et validée comme non-dégénérée. Tenir la partition de dénominateurs du Tab. 5. Puis, sur des copies de la rubrique, ajouter un terme de précision citationnelle et re-noter les seules cellules acceptées. Résultat attendu : taux de faux accept proche de 0 sur les familles destructives (omission, pinpoint faux détectable), et élevé sur citation surnuméraire et proposition inversée — les deux familles où toutes les valeurs que la rubrique regarde restent correctes. Coût estimé par analogie avec le papier : dominé par les appels au juge, pas par la construction ; l'audit lui-même ne nécessite aucun entraînement.

Question à poser en interne chez GDM

Deux, liées par le §4 du papier : 1. Le reward utilisé pour le RL de Gemini Law a-t-il un taux de faux accept mesuré, et sur quelle population ? — et si la mesure vient d'un split DEV, la boucle d'entraînement échantillonne-t-elle ce même split ? Le papier montre le cas exact où un leaderboard est « insulated » alors que toute boucle qui récompense la métrique DEV ne l'est pas : « Duplicate-write successes would look like valid reward » [§4]. 2. Existe-t-il un holdout scellé d'items juridiques, jamais utilisé pour calibrer le juge ? Le papier préserve délibérément le HOLDOUT AppWorld et énumère les conditions d'une vraie estimation de population (cadre d'échantillonnage fixé, mélange de fautes fixé, unité d'analyse, oracle d'effet, séparation sélection/évaluation) [§5] — c'est la spécification à reprendre telle quelle avant de publier un taux de faux accept interne.
