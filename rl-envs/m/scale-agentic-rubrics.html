0. En une phrase

TL;DR — Un agent expert explore le dépôt avant de voir la moindre réponse, et en tire une checklist pondérée, spécifique à l'instance ; un juge LLM séparé note ensuite chaque patch candidat contre cette checklist, sans exécuter aucun test [TL;DR ; § How It Works].

Claim principal, formulé précisément — Sur SWE-Bench Verified (500 problèmes, K=16 rollouts parallèles par problème), utilisé comme sélecteur de patch (Best@16), Agentic Rubrics atteint 54,2 % sur les trajectoires Qwen3-Coder-30B-A3B et 40,6 % sur Qwen3-32B, soit ≥ +3,5 pts sur la meilleure baseline du set de comparaison ; les scores de rubrique corrèlent avec les tests ground-truth à ROC-AUC = 0,886 tout en signalant des défauts que les tests ne couvrent pas ; l'interaction avec le dépôt au moment de la génération de la rubrique est l'ingrédient causal (ablation : −4,0 pts Qwen3-32B, −1,4 pt Qwen3-Coder) [TL;DR ; § What We Found ; § What We Learned].

Le point qui compte pour notre revue : c'est une méthode de vérification sans vérité exécutable — exactement le régime du droit — et elle est validée contre un oracle exécutable (les tests), ce qui est le seul moyen honnête de valider ce type de vérifieur. Le droit n'a pas cet oracle ; c'est là que le transfert coince (§ 9).

1. Tâches & data — la construction des rubriques

Origine des tâches

  • Les tâches ne sont pas construites par les auteurs : SWE-Bench Verified, 500 problèmes [§ What We Found]. Pas de génération, pas de minage, pas de filtrage de tâches décrit.
  • Ce qui est construit, c'est l'artefact de vérification : une rubrique par instance.

Pipeline de construction des rubriques, étape par étape [§ How It Works]

  1. Entrée : l'énoncé du problème (problem statement / issue) + accès complet au dépôt.
  2. Exploration : un rubric agent tourne dans un scaffold de coding standard — « like SWE-Agent or OpenHands » (formulation du billet, sans préciser lequel est utilisé en pratique → non précisé). Il peut « search files, read code, inspect directory structures, anything a developer would do ».
  3. Production : un fichier de rubriques structuré (le schéma de la Fig. 1 le nomme rubric.yaml), organisé sur quatre axes : - File Change : les éditions sont-elles minimales, correctement scopées, suffisantes ? le patch évite-t-il les modifications inutiles ? - Spec Alignment : le patch satisfait-il les exigences énoncées dans l'issue ? - Integrity : évite-t-il les raccourcis — hardcoder les valeurs attendues, désactiver des tests, contourner une validation ? - Runtime : le patch s'exécutera-t-il correctement — problèmes d'import, incompatibilités de types, cas limites non traités ?
  4. Format d'un item : « each item is a natural-language criterion with an importance weight » [§ How It Works]. Format exact du poids (échelle, discret/continu), non précisé.

⚠️ Qui écrit les rubriques : ni humain, ni miné depuis des revues de code. Elles sont générées par un agent LLM frontier. Le billet ne mentionne aucune écriture humaine, aucun minage de code review / commentaires de PR, aucune validation humaine des rubriques produites. Réponse directe à la question posée : générées, pas écrites ni minées.

Volume

  • Nombre de rubriques : une par instance ; > 20 items/instance pour Sonnet-4.5, ~10 pour Qwen3-32B, 5–10 pour Meta-CWM et Gemini 3 Pro (d'après la description de la figure du § « Better Models… »). Total agrégé non précisé.
  • Distribution de difficulté : non précisée (héritée de SWE-Bench Verified).

Coût — l'argument économique explicite [§ How It Works]

  • Génération : nécessite un modèle frontier (« deep reasoning and repository exploration »), mais c'est un investissement one-shot amorti à chaque réutilisation de la tâche.
  • Grading : « comparatively straightforward », « even a lightweight model performs nearly as well as a frontier one ». Aucun chiffre de coût ($ , tokens, latence) n'est donné → non précisé. ⚠️ « nearly as well » n'est chiffré nulle part dans le billet.
  • Coût humain : aucun rapporté — ni annotation, ni heures d'expert, ni revue. C'est le point de vente implicite ; c'est aussi la faiblesse (§ 3).

Filtrage / curriculum / contamination / SFT

  • Filtrage des rubriques (pass@k, seuil, dédup, revue) : non précisé.
  • Curriculum : sans objet (pas d'entraînement RL).
  • Contamination : non discutée. ⚠️ SWE-Bench Verified est massivement présent dans les corpus d'entraînement des modèles 2026 ; ni les générateurs de patchs, ni les générateurs de rubriques ne sont dédouanés.
  • SFT : une seule mention, en future work — 2 000 trajectoires de génération de rubriques distillées de Sonnet-4.5, utilisées pour fine-tuner Qwen3-32B comme « open-weight agentic rubric generator that works well » [§ What's Next]. Aucun chiffre de résultat pour ce modèle distillé. ⚠️ « works well » sans métrique.

2. Environnement / harness — l'espace d'actions du vérifieur

Le point le plus important du mémo, et il est contre-intuitif. L'« agentique » est dans la génération de la rubrique, pas dans le grading. Deux boucles distinctes :

Phase Qui agit Accès au dépôt Outils Exécution de code
Rubric Generation (one-shot / instance) rubric agent (modèle frontier) oui, complet scaffold de coding agent : search files, read code, inspect directory structures [§ How It Works] non explicité ; le billet ne liste que des actions de lecture
Rubric Grading (à chaque candidat) juge LLM séparé, léger non mentionné aucun outil listé non — « without executing any tests » [TL;DR]

Réponses aux questions posées

  • Le juge peut-il exécuter des outils ? Le billet ne lui en attribue aucun. Le grading est décrit comme : « a separate LLM judge scores each candidate patch against the rubric, assigning a binary pass/fail per criterion » [§ How It Works]. Rien n'indique que le juge lise le dépôt ou lance quoi que ce soit.
  • Lire le dépôt ? Le rubric agent oui, complètement. Le juge, non précisé — et par défaut à lire le billet : non.
  • Lancer des tests ? Non, ni l'un ni l'autre. C'est le claim central (« execution-free » dans la description de la figure comparative). ⚠️ Nuance : une des baselines, Agentic Tests, génère et exécute des tests ; Agentic Rubrics ne l'inclut pas.
  • Espace d'actions du rubric agent : décrit en langage naturel uniquement (« search files, read code, inspect directory structures, anything a developer would do »). Aucune liste d'outils, aucune signature, aucun budget de tours, aucun horizon max, aucune gestion de contexte long dans le billet → non précisé sur toute la ligne.

Rubrique agentique vs rubrique statique — la définition opérationnelle

L'ablation donne la définition la plus nette [§ What We Learned] : même modèle, même format de rubrique, dépôt retiré. Ce qui change est la spécificité référentielle des critères. Exemple recopié du billet :

  • Agentique (Django) : « The patch must modify django/db/models/query.py and preserve the existing QuerySet.filter() interface while correctly handling the edge case where related_name is None. »
  • Non agentique, même issue : « The patch should touch the right code path and fix the filtering behavior. »

Commentaire des auteurs : la première « makes grading easy, and unambiguous », la seconde « needs the judge to be capable enough to understand and interpret correctness from it ». Le gain de l'agentique = déplacer la charge d'interprétation du juge vers le générateur de rubrique, une fois pour toutes. C'est exactement ce qui rend le juge léger suffisant — et c'est l'idée transposable (§ 9).

Exécution, déterminisme, erreurs, trajectoire

  • Sandbox/conteneur pour le rubric agent : non précisé (le billet oppose justement son approche au coût de « sandboxed environment, dependency installation, test execution » de l'approche exécution).
  • Déterminisme, reset, timeouts, gestion des erreurs d'outils, sorties mal formées (rubrique non parsable, juge hors format) : non précisés.
  • Exemple de trajectoire : aucun dans le billet. Seul l'extrait de rubrique ci-dessus est fourni.

3. Reward / vérifieur

Type et granularité

  • Rubrique + LLM-as-judge, sans exécution. Hybride au sens où la rubrique est produite agentiquement puis appliquée statiquement.
  • Par critère : binaire pass/fail [§ How It Works].
  • Agrégation : somme pondérée par les poids d'importance → score dans [0, 1], utilisé pour ranker les candidats [§ How It Works]. Formule exacte non précisée.
  • Granularité effective : c'est l'argument du § « Better Models… » — « Rubrics can distinguish a patch that gets 18 of 22 things right from one that gets 15. With only 5 items, both patches might look identical. » Le crédit partiel est donc le mécanisme, contre la sparsité binaire des tests (« a test either passes or fails, telling you nothing about how close a failing patch came » [§ The Verification Bottleneck]).
  • Termes additionnels (format, longueur, pénalités) : aucun mentionné.

Fiabilité du vérifieur — le point central de la revue

Ce que le billet donne : 1. ROC-AUC = 0,886 contre les tests ground-truth [TL;DR]. ⚠️ Ce chiffre n'apparaît que dans le TL;DR (voir 7.0). 2. Séparation des distributions [§ Rubric Scores are Meaningful] : patchs qui passent les tests → scores concentrés 0,85–1,0 ; patchs qui échouent → étalés sur 0,4–0,5. Décomposition par axe : les patchs incorrects scorent bas sur File Change et Spec Alignment, mais haut sur Integrity — « they're not cheating; they're genuinely trying and falling short ». Les patchs corrects saturent Spec Alignment et Integrity mais perdent parfois des points sur File Change (édits sur-scopés). 3. Analyse des désaccords [§ Rubrics Catch What Tests Miss] : sur les cas où le test accepte (reward = 1) mais la rubrique score < 0,7, 54 % High Utility / 46 % Low Utility. Les causes High Utility dominantes : Root Cause Missed 17,5 %, Missing Edges 15,1 %. Sur les cas d'accord (High Alignment) : 78 % High Utility / 22 % Low Utility, dont Core Semantics 45,0 % ; la cause Low Utility principale est Low-Signal 12,1 %. 4. Modes de faible utilité identifiés [§ What's Next] : over-specification (exiger des détails d'implémentation au-delà de ce que la correction requiert), redundancy, et mismatches occasionnels avec l'intention ground-truth. Les autres catégories Low Utility nommées dans la figure : Over-Specified Fix, Redundant Signal, Test Rules Mismatch.

Ce que le billet ne donne pas — et c'est décisif : - Aucun accord avec des développeurs humains. Le mot « human » n'apparaît qu'une fois, en future work (« human-in-the-loop refinements like lightweight review »). Le vérifieur n'est validé contre aucun humain. - Qui étiquette « High/Low Utility » ? Non précisé — humains, LLM, auteurs ? Taille de l'échantillon des désaccords analysés : non précisée. ⚠️ Sans ce protocole, le chiffre le plus intéressant du billet (« en désaccord, la rubrique a raison 54 % du temps ») n'est pas auditable : si l'étiqueteur est un LLM, on mesure potentiellement l'accord d'un juge avec lui-même. - Taux de faux positifs / faux négatifs : non rapportés comme tels. Le ROC-AUC agrège ; le seuil d'acceptation (« our acceptance threshold », implicitement 0,7 d'après la figure) n'est ni justifié ni ablaté. - Prompt du rubric agent, prompt du juge, template de rubrique, rubrique complète d'exemple : aucun n'est fourni dans le billet (le preprint de 31 p. en contient peut-être en annexe). - Modèle du juge de grading : non précisé.

Robustesse / anti-hacking

  • L'axe Integrity est un anti-hacking explicite, intégré dans le vérifieur : « avoid shortcuts like hardcoding expected values, disabling tests, or bypassing validation » [§ How It Works]. C'est un détecteur de reward hacking classique pour les vérifieurs à base de tests, transplanté dans la rubrique. Conception intéressante : le vérifieur porte en lui le critère qui interdit de le contourner.
  • ⚠️ Le vérifieur lui-même n'a jamais été attaqué. Aucune red-team, aucun test d'adversarialité de la rubrique, aucune mesure de ce qui se passe si le générateur de patchs est optimisé contre la rubrique. Le setup est purement best-of-K sur des rollouts non optimisés contre le juge : c'est le régime le plus favorable possible. Un juge LLM statique notant du texte, sans exécution et sans accès à la source au moment du grading, est a priori très hackable sous pression RL (patch verbeux qui récite les critères, commentaires qui affirment satisfaire la rubrique). Le billet ne dit rien là-dessus, et c'est la principale réserve pour un usage en reward.

Usage : évaluation ou reward d'entraînement ?

Évaluation / test-time scaling uniquement dans ce travail. Le vérifieur sert à ranker K=16 candidats (Best@K). L'usage comme reward RL est explicitement du future work : « Integrating rubric signals into training loops as reward signals for reinforcement learning is extremely exciting » [§ What's Next]. Le billet motive néanmoins le tout par le RL dès l'intro : « verification… provides the reward signal for reinforcement learning » [§ The Verification Bottleneck]. ⚠️ Donc : aucune évidence d'entraînement RL sur ce reward dans ce travail. À ne pas citer comme une preuve que les rubriques agentiques marchent comme reward.

Pourquoi ça bat la génération de tests agentique — argument des auteurs [§ What We Found]

Les tests générés doivent être syntaxiquement valides, s'exécuter proprement, et discriminer correctement ; les patchs de référence pénalisent une correction sémantiquement juste mais d'approche différente. Les rubriques contournent les deux en énonçant à quoi ressemble la correction plutôt qu'en l'encodant dans un artefact exécutable ou de référence. ⚠️ Argument convaincant et générique — c'est précisément pourquoi il devrait se transférer à un domaine sans artefact exécutable (§ 9).

Ablations

  • Accès au dépôt (la seule ablation propre : même modèle, même format) : −4,0 / −1,4 pt. Les auteurs en tirent « repository grounding is not optional ». ⚠️ Le support quantitatif est faible sur un des deux générateurs.
  • Modèle générateur de rubriques (sweep, quasi-ablation de capacité) : frontier ~54 % > open-weight ~45 % > non-coding ~43 %. Mécanisme proposé : granularité (nombre d'items). ⚠️ Corrélationnel : granularité et capacité varient ensemble, aucun contrôle qui fixe le nombre d'items pour isoler la granularité. Contre-exemple dans leurs propres données : Gemini 3 Pro scale fort tout en produisant 5–10 items, ce qui contredit l'explication par la granularité seule.
  • Non ablatés : poids d'importance (vs non pondéré), les 4 axes (contribution de chacun), seuil 0,7, modèle du juge, taille du scaffold.

Scaling

  • En K : la courbe Best@K montre Agentic Rubrics « consistently scaling better than other verifiers as K increases, sitting just below the Oracle pass@k baseline » [fig. § What We Found]. Aucun point chiffré au-delà de K=16.
  • En capacité du générateur de rubriques : ~54 / ~45 / ~43 (cf. supra).
  • En taille du modèle générateur de patchs : non testé au-delà de 2 modèles ~30 B. ⚠️ Rien au-delà de l'échelle 30 B côté policy. On ne sait pas si un vérifieur par rubrique garde un signal utile quand le générateur est frontier.

In-distribution vs OOD / transfert

  • Aucun transfert mesuré. Un seul benchmark (SWE-Bench Verified), un seul langage (Python), un seul type de tâche (bug fix depuis une issue). Pas de SWE-Bench Multilingual, pas de repos hors distribution, pas d'autre domaine.

Solidité

  • Baselines fortes et à jour ✅ — comparaison appariée (mêmes rollouts, même K, même jeu de problèmes) contre 4 familles de vérifieurs + oracle + random, dont deux baselines agentiques (tests générés, patch de référence), ce qui est le bon adversaire.
  • Ablations qui isolent la contribution ✅ — l'ablation « même modèle, même format, sans dépôt » isole exactement le claim central. Réserve sur la magnitude (−1,4 pt).
  • Variance / seeds ❌ — aucun seed, aucun intervalle de confiance, aucun test statistique dans le billet. Les légendes de figures reconstruites mentionnent des « confidence bands omitted », ce qui suggère que les figures originales en portaient (⚠️ inférence de ma part, pas une affirmation du billet).
  • Fiabilité de l'éval ❌ — juge jamais validé contre des humains ; protocole d'étiquetage High/Low Utility non précisé ; contamination SWE-Bench Verified non discutée ; seuil d'acceptation 0,7 non justifié.
  • Échelle ⚠️ — 500 problèmes × 16 rollouts × 2 générateurs, c'est correct pour du test-time scaling ; mais un seul benchmark et des policies ≤ 30 B.
  • Reproductibilité ❌ — aucun code, aucune rubrique publiée, aucun prompt, aucun modèle de juge nommé. Seul artefact vérifié : le preprint arXiv 2601.04171 (HTTP 200).
  • Cohérence texte ↔ chiffres ❌ — cf. 7.0 (78 % ; « significantly » à −1,4 pt ; deux chiffres-clés absents du corps).

Cases evidence : baselines ✅ · ablation ✅ · variance ❌ · coherence ❌ · eval ❌ · repro ❌ → evidence = 2/6.

Verdict : plausible mais à répliquer. L'idée est bien posée et l'ablation clé est la bonne ; mais telle que lue dans le billet, la méthode n'est validée que contre un oracle automatique sur un seul benchmark, sans variance, sans validation humaine, sans artefact public, et jamais sous pression d'optimisation. Pour un usage en reward RL — le seul qui nous intéresse — il n'existe aucune preuve ici.

Le parallèle citations — à corriger avant de s'en servir

L'intuition (« un juge qui peut aller vérifier la source citée plutôt que juger sur le seul texte ») est la bonne intuition, mais ce n'est pas ce que fait ce travail. Distinction à tenir :

  • Ce que fait le papier : ancrage ex ante, au moment de la génération de la rubrique. L'agent explore le dépôt avant d'avoir vu la moindre réponse, et fige la vérité dans des critères nommant des cibles précises (django/db/models/query.py, QuerySet.filter(), related_name is None). Le juge, lui, ne vérifie rien : il compare du texte à une checklist.
  • Ce que la vérification de citations demande : ancrage ex post, au moment du grading — aller chercher l'arrêt cité et vérifier qu'il existe, qu'il est en vigueur, et qu'il dit ce que la réponse lui fait dire. Ce cas d'usage est ouvert dans ce papier.

Pourquoi la version ex ante du papier est quand même le bon point de départ pour le droit : 1. Elle marche quand il n'y a rien à exécuter. C'est exactement notre régime : pas de test suite juridique, pas de match exact sur une réponse argumentée de 3 pages. 2. Elle déplace le coût au bon endroit : un modèle cher une fois par question, un juge bon marché à chaque rollout. Sous RL, on note des dizaines de milliers de rollouts par question — l'amortissement est encore plus favorable qu'en test-time scaling. C'est l'argument économique qui rend un reward par rubrique tenable à l'échelle d'un run RL. 3. Elle rend le grading vérifiable. Un critère qui nomme sa source (« doit citer l'art. L.1234-9 C. trav. et énoncer la condition d'ancienneté ») est auditable par un juriste en quelques secondes, sans relire tout le dossier. C'est la propriété que les auteurs appellent auditability [§ What's Next] et c'est décisif face à un client / un régulateur / une équipe d'annotation. 4. Elle produit du crédit partiel interprétable par axe (18/22 vs 15/22). En droit, l'analogue est immédiat : sources citées · règle correctement énoncée · application aux faits · limites et exceptions · intégrité (pas de citation fabriquée). Sur des réponses longues, ce signal dense vaut infiniment mieux qu'un binaire.

Ce qui ne se transfère pas, et qu'il faut regarder en face : - La validation disparaît. Toute la crédibilité du papier vient du ROC-AUC 0,886 contre un oracle exécutable. Le droit n'a pas cet oracle. Sans lui, il ne reste que l'accord humain — que le papier, précisément, ne mesure jamais. Nous devrons construire ce que les auteurs se sont dispensés de construire. - Les sources évoluent (revirements, abrogations) : une rubrique figée le jour J devient fausse. Le dépôt, lui, est immuable au commit près. Il faut horodater/versionner chaque rubrique sur l'état du corpus. - Over-specification, que les auteurs reconnaissent comme mode d'échec [§ What's Next], est bien plus grave en droit : exiger une formulation ou un chemin d'argumentation pénalise une réponse juste qui raisonne autrement — c'est exactement le défaut qu'ils reprochent à la baseline Patch Similarity. Le risque est de réintroduire par la rubrique ce qu'ils évitent par la rubrique. - Multi-juridictions : sans objet ici (un dépôt = un contexte). Il faudra probablement une rubrique par juridiction, ou un axe explicite « juridiction correcte ».

Meilleur ingrédient à transposer

La séparation générateur frontier ancré / juge léger non ancré, et l'exigence que chaque critère nomme sa source. C'est ce que l'ablation isole (−4,0 pts sans dépôt), c'est ce qui rend le juge bon marché suffisant, et c'est ce qui rend le reward auditable par un juriste. Second ingrédient, sous-estimé : l'axe Integrity comme composant du vérifieur — en droit, « aucune citation fabriquée, aucune source non consultée » devient un critère de reward de première classe plutôt qu'un filtre post-hoc.

Expérience minimale

Sur ~200 questions Vals / Harvey LAB : 1. Agent frontier avec accès au corpus (recherche + lecture) → rubrique pondérée de 10–20 items, chaque item nommant sa source et son axe (sources · règle · application · limites · integrity). Figer l'état du corpus. 2. K=8 à 16 rollouts par question depuis la policy candidate ; grader avec un juge léger contre la rubrique. 3. Trois mesures, dans cet ordre d'importance : - accord avec des juristes sur un sous-échantillon (~100 questions × 2 annotateurs) — la mesure que le papier ne fait jamais, et notre seul substitut d'oracle ; - ablation de l'ancrage : même modèle, même format, sans accès au corpus. Résultat attendu, par analogie : écart plus grand qu'en code, parce qu'un critère juridique non ancré (« doit citer la jurisprudence pertinente ») est presque vide, alors qu'un critère code non ancré garde du contenu ; - gain Best@K vs juge LLM direct sans rubrique. 4. Extension que le papier ne couvre pas : un second juge avec outil de lookup qui vérifie l'existence et le contenu réel de chaque source citée. Comparer juge-sans-outil vs juge-avec-lookup sur des réponses contenant des citations volontairement fabriquées → mesure directe du taux de faux positifs sur l'hallucination de citations. C'est là que se trouve la contribution originale possible, et le billet la laisse entièrement ouverte.

Résultat attendu : rubriques ancrées > rubriques non ancrées > juge direct sur l'accord humain ; et un juge sans outil incapable de détecter les citations fabriquées plausibles — ce qui justifierait d'ajouter le lookup au grading, à l'inverse du design du papier.

Question à poser en interne chez GDM

Deux, liées : 1. Existe-t-il un corpus juridique versionné, interrogeable par un agent de manière déterministe et reproductible d'un rollout à l'autre ? Sans ça, ni la génération de rubriques ancrées ni un juge avec lookup n'est stable — et ce papier ne rencontre jamais le problème parce qu'un dépôt git est trivialement reproductible. 2. Quelqu'un a-t-il déjà mesuré, chez nous, ce que devient un juge à rubrique sous pression RL (des dizaines de milliers de rollouts optimisés contre lui) plutôt qu'en best-of-K ? Le papier travaille exclusivement dans le régime facile ; notre risque est exclusivement dans le régime dur.
