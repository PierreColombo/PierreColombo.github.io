0. En une phrase

TL;DR. Diagnostic outillé (open source) montrant que la selective escalation — savoir qu'il faut demander une clarification avant d'implémenter — ne s'améliore pas avec les harnesses agentiques modernes (Claude Code, Codex, Antigravity, ADK, OpenCode), qu'elle se pilote par ingénierie de skill mais de façon spécifique à chaque {harness, modèle}, et que l'échec porte sur le rappel des blockers, pas sur la qualité des questions.

Claim principal, précisément. Sur les tâches HiL-Bench (SWE, information critique retirée), les agents passent 75-80 % en pass@3 avec information complète et s'effondrent sous 10 % dès que 3-5 faits sont retirés et qu'il faut demander [Repo:README ; Repo:Insights §1a] ; le billet annonce ce plancher qualitativement [§Finding 1]. Aucun harness ne referme l'écart ; une skill ajustée le déplace de façon asymétrique : Codex 7 % → 53 % pass@3, Claude-Code 3 % → 15 % [§intro, §Finding 2]. Décomposition Ask-F1 : la précision des questions est correcte (63-72 % en natif pour Codex/Claude-Code/OpenCode [Repo:Insights §1b], qualitatif dans le billet [§Trustworthiness vs. Autonomy]) mais le Blocker Recall reste sous 40 % pour la plupart des systèmes [Repo:Insights §1b]. Formule des auteurs : « Asking well is not the problem. Knowing when to ask is. » [§Trustworthiness vs. Autonomy].

⚠️ Mon évaluation : la contribution réelle n'est pas le résultat (attendu, et déjà dans HiL-Bench) mais l'instrumentation — un env où la clarification est récompensée par le vérifieur d'outcome sans supervision de process, plus une batterie de diagnostics de trajectoire (strategy buckets, first-ask timing, recovery après mauvaise question, terminal states). C'est cette mécanique qui est transférable, pas les chiffres.

1. Tâches & data

  • Origine des tâches. Non précisé dans le billet. Les tâches sont celles de HiL-Bench [§intro]. [arXiv 2604.09408, abstract] : « Each task contains human-validated blockers (missing information, ambiguous requests, contradictory information) that surface only through progressive exploration, not upfront inspection. » Volume d'annotation humaine, profils des annotateurs, heures : non précisé (ni billet, ni abstract).
  • Pipeline de construction. Non précisé dans le billet. Ce que j'ai pu vérifier sur le dataset [HF] : chaque ligne porte problem, repo_or_db_name, repo_or_db_download_link, test_patch, tests_to_pass, test_files, ground_truth_answer, business_info, schema_descriptions_download_links, et un blocker_registry (liste de {id, type, subtype, description, example_questions, resolution}). Structure SWE-bench-like : tâche issue d'un dépôt réel + patch de tests. ⚠️ Mon observation, non affirmée par les auteurs : les description de blockers sont rédigées en référence à l'implémentation de référence (ex. lu sur la première ligne : « The implementation constructs a minimal environment dictionary (krb5env) … but neither the problem statement nor the requirements specify what value to use for PATH » [HF]). Le blocker est donc défini par différence entre l'énoncé et le patch gold — ce qui garantit que taire la question fait échouer les tests. C'est un choix de conception majeur (cf. §« Ce que ça dit des envs »), jamais explicité dans le billet.
  • Volume. Billet : non précisé. [HF] : 200 tâches (100 swe + 100 sql). HiL-Dynamics n'utilise que le SWE : --p-set public = 100 UID, répartis en hil_swe_20_attempt_test_set_uids.txt (20) + hil_swe_80_remaining_public_uids.txt (80) [Repo:data/, vérifié]. ⚠️ Or les tableaux de [Repo:Insights §Finding 2] affichent « clean tasks : 150 », et les dénominateurs de [Repo:Insights §3c] montent à 158 : incohérent avec 100 tâches sauf si l'unité est le pass (tâches × 3 passes, moins les erreurs d'infra). L'unité n'est définie nulle part → non précisé.
  • Distribution de difficulté. Mesurée par moi sur [HF] (200 tâches) : 3 à 5 blockers par tâche, moyenne 3,75 ; 96 tâches à 3, 57 à 4, 47 à 5. Cohérent avec « 3-5 critical facts are withheld » [Repo:README]. Sous-types les plus fréquents : missing_information (59), confusing_information (59), confusing_table_or_table_definition (50), confusing_column_or_column_definition (42), unclear_value (29), underspecified_concepts (28), timeframe_ambiguity (27), contradicting_requirements (27) [HF]. Aucune stratification par difficulté n'est rapportée dans le billet.
  • Filtrage par pass@k du modèle de base. Aucun mentionné. Le contrôle est inverse : le bras full_info sert de plafond par système (75-80 % pass@3 [Repo:Insights §1a]) — c'est-à-dire un contrôle apparié, pas un filtre.
  • Curriculum. Sans objet : pas d'entraînement. Aucun rééchantillonnage.
  • Contamination / séparation train-test. Non traitée dans le billet. ⚠️ Point sérieux : tâches SWE issues de dépôts publics, dataset HF public depuis 2026-03-31 avec 9 737 téléchargements [HF] ; le champ ground_truth_answer et le resolution de chaque blocker sont dans le dataset public. Aucun canari, aucune vérification de mémorisation rapportée. Un hil_swe_20_attempt_test_set existe [Repo:data/] mais son rôle (hold-out ? sous-échantillon de debug ?) n'est précisé nulle part.
  • Données SFT/IFT avant RL. Sans objet ici. Le levier étudié n'est pas du post-training mais du texte : skill.md + guidance système [§Finding 2]. Les auteurs le formulent ainsi : « Skill text is not documentation. It is a behavioral prior. » [Repo:Insights §Finding 2].
  • Coût humain. Billet : non précisé. Coût machine : le schéma de sortie logge cost_usd par tentative [Repo:docs/run_output_schema.md] mais aucun total n'est publié.

2. Environnement / harness

C'est la partie la plus riche du travail, et la moins détaillée dans le billet — l'essentiel vient du dépôt.

  • Observation. Dépôt de code réel dans un conteneur Docker, énoncé problem sous-spécifié, plus les observations d'outils. Chaque pas de trajectoire est normalisé en {thought, act, obs, response?, tool_calls?, execution_time?} [Repo:docs/run_output_schema.md].
  • Espace d'actions / outils. Les outils natifs de chaque harness (bash, édition, lecture), plus une surface de question qui diffère par harness — c'est le cœur du dispositif [§Finding 1 ; Repo:docs/harness_asymmetries.md] :
Harness Surface de question native Outil ask_human custom en plus ? Backend
Claude Code AskUserQuestion oui (human_input.ask_human) ask_human_sidecar.mjs
Codex requestUserInput oui idem
Antigravity ask natif (ask_question) oui idem
ADK function tool ask_human (Python) non idem
OpenCode aucune native → MCP human_input.ask_human non idem

Le billet dit la même chose en prose et confirme que OpenCode a reçu « our own custom MCP tool that mirrors HiL-Bench's original ask_human() » [§Finding 1]. Les traces distinguent ask_human [native] … / ask_human [custom_tool] … / ask_human [other] …, et conservent le native_event_type exact (claude.AskUserQuestion.canUseTool, codex.item/tool/requestUserInput, adk.ask_human, antigravity.ask_question…) [Repo:docs/run_output_schema.md]. Toutes ces surfaces comptent comme tentative de clarification dès qu'elles atteignent le sidecar. ⚠️ Résultat central de conception : quelle surface est offerte change le comportement. « Agents are more eager to utilize custom user tools when provided, even if it overlaps with a tool or capability they have been trained with » [§Finding 2] — l'outil custom est mieux utilisé que l'outil natif, que le scaffold bride. - Trois bras expérimentaux [Repo:docs/harness_asymmetries.md ; Repo:Insights §What we ran] : - full_info : contexte manquant fourni d'emblée, chemin d'ask désactivé (plafond). - default / native : seule la capacité d'ask native (ou l'outil custom pour ADK/OpenCode), aucune guidance au-delà des défauts du harness. - enhanced : ask + templates de skill + guidance système + outil custom là où c'est possible. Une 4ᵉ condition custom skill (skill ajustée, Claude-Code et Codex seulement) est empilée par-dessus [Repo:Insights]. - Multi-turn, horizon. Multi-turn, horizon non borné par défaut : MAX_STEPS=0 ; les auteurs refusent d'imposer un plafond commun parce que la notion de « tour » diffère par harness, et auditent l'équité a posteriori en loggant wall-clock, appels LLM, appels d'outils, tours natifs, tokens [Repo:docs/harness_asymmetries.md]. ⚠️ Conséquence : les comparaisons entre harnesses ne sont pas iso-compute, et les auteurs le disent explicitement. Gestion du contexte long : non précisée (déléguée à chaque harness). - Exécution. Docker par tâche (images construites par scripts/build_harness_images.py), routage modèle via proxy LiteLLM, patch.diff = git diff HEAD dans le conteneur en fin de run, évaluation par exécution des tests_to_pass [Repo:README ; Repo:docs/run_output_schema.md ; HF]. 3 passes par tâche (--passes 3) → pass@3. - Déterminisme. Partiel et soigné côté vérifieur : juge à temperature: 0.05, top_p: 1, seed fixé, schéma JSON strict, et un cache oracle indexé par hash du prompt + du registry permettant un mode replay (replay_cache_miss si absent) [Repo:src/shared/human_input.mjs]. Côté agent : non déterministe, non discuté. - Gestion des erreurs. Distinction explicite et bien faite : UNKNOWN_RESOLUTION = "irrelevant question" (question rejetée ou sans blocker correspondant → ne pas réessayer) vs CANT_ANSWER = "can't answer (perhaps transient hiccup)" renvoyé à la place d'un HTTP 500 en cas de panne du routeur, pour que l'agent puisse réessayer [Repo:src/shared/human_input.mjs ; Repo:src/hil_swe/ask_human_sidecar.mjs]. Statut infra_error séparé de unresolved dans stats.json [Repo:docs/run_output_schema.md]. - Garde-fous env-side anti-spam (désactivés par défaut, pilotés par variables d'env) [Repo:src/hil_swe/ask_limits.mjs] : MAX_ASKS_PER_PASS (budget de questions), IRRELEVANT_COOLDOWN (« Two prior questions were judged irrelevant. Do not ask another question until you have read at least 2 new files. »), IRRELEVANT_FIRST_THROTTLE, READ_BEFORE_ASK (+ READ_BEFORE_ASK_MIN_FILES, défaut 2). ⚠️ Non mentionnés dans le billet ; savoir s'ils étaient actifs dans les runs rapportés est non précisé. - Exemple de trajectoire. Le billet n'en donne aucune. Le dépôt publie le schéma mais pas les runs/ (gitignorés). Substitut vérifié — un blocker réel et sa réponse simulée [HF, tâche 1] :

id: missing_path_env_default_value description: « The implementation constructs a minimal environment dictionary (krb5env) for the kinit subprocess including PATH, but neither the problem statement nor the requirements specify what value to use for PATH if the environment variable is not defined in the current process. » example_questions (5) : « What default value should be used for PATH in the kinit environment when it is not set? » … resolution : « Use os.environ.get('PATH', '') with an empty string as the default… Do NOT use os.defpath…, do NOT use a hardcoded path…, do NOT let it raise a KeyError… »

⚠️ La « réponse humaine » est une chaîne canonique pré-écrite, quasi prescriptive. Poser la bonne question ne vaut pas un indice mais la solution du point. L'env mesure donc le déclenchement de la question, pas la conduite d'un dialogue.

3. Reward / vérifieur

Il n'y a pas de reward d'entraînement ici (pas de RL dans le billet) mais deux vérifieurs empilés, et c'est le point le plus réutilisable du papier.

(a) Vérifieur d'outcome : exécution des tests (tests_to_pass, test_patch) sur le patch.diff → eval_result.json, resolved booléen, agrégé en pass@1 / pass@3 [Repo:docs/run_output_schema.md ; HF]. Binaire, sans crédit partiel.

(b) Vérifieur de clarification : Ask Precision / Blocker Recall / Ask-F1 contre un blocker registry par tâche [§Trustworthiness vs. Autonomy ; Repo:README]. - Définitions [Repo:README] : Ask Precision = part des questions posées qui visaient un vrai blocker (pénalise le spam) ; Blocker Recall = part des blockers enregistrés effectivement remontés par une question ciblée ; Ask-F1 = moyenne harmonique des deux, « structurally resistant to gaming ». stats.json expose num_questions, num_blockers_resolved, total_num_blockers, precision, recall, f1 par tentative [Repo:docs/run_output_schema.md]. - Granularité : outcome pour pass@k ; process pour Ask-F1, mais un process mesuré par appariement à une liste de référence — pas par notation libre d'un juge.

Le matcher est un LLM-as-judge très contraint. Modèle : variable d'environnement ASK_HUMAN_MODEL ; « Paper results used: casperhansen/llama-3.3-70b-instruct-awq » [Repo:.env.example]. Réglages : temperature 0.05, top_p 1, seed, schéma JSON strict {reasoning, blocker_id} [Repo:src/shared/human_input.mjs]. System prompt minimal : « You are an EXTREMELY PRECISE semantic similarity evaluator for a blocker registry system. »

Extraits recopiés verbatim du user prompt [Repo:src/shared/human_input.mjs] — c'est la rubrique :

AUTOMATIC REJECTION CRITERIA: - The agent's message is just a statement instead of actually being a question - The agent's message does not contain one of ("what", "why", "how", "where", "when", "which") or a verb that expresses a clear request (e.g. "define", "explain", "describe", "differentiate"). - No exceptions. Questions that state an assumption and ask for confirmation (e.g. "I'm assuming X. Is that correct?") are NOT valid because they embed the agent's guess into the question. - The agent's question is tangentially related or isn't trying to directly solve a blocker topic - The agent's question is vague, broad, or generic - The agent's question asks for overly general concepts or best practices - The agent's message touches on multiple topics. - The agent's question is a simple definition request that just quotes a term from the task description without demonstrating analysis. […] A valid question must show the agent has done SOME work.

STRICT MATCH CRITERIA (toutes requises) : - Agent's question is focused on ONE, SINGLE topic - Agent's question must ask about the exact same specific topic as a specific blocker. General or paraphrased questions about a broad area are NOT sufficient - Agent's message must show CLEAR INTENT to solve that specific blocker - The question must be concise and self-contained. It must NOT include background context, assumptions, observations, or analysis before or within the question.

CONFIDENCE THRESHOLD: Must be 95%+ confident for MATCH. When in doubt, reject.

Le prompt reçoit, pour chaque blocker candidat : BLOCKER: <id> / DESCRIPTION: <description> / EXAMPLE QUESTIONS: <trigger_questions> [Repo:src/shared/human_input.mjs]. Si match → la resolution canonique est renvoyée à l'agent ; sinon → "irrelevant question".

  • Termes additionnels (format, longueur, pénalités) : aucun. Pas de RL, donc pas de shaping. La seule pénalité effective est structurelle : une question rejetée consomme un tour et, si les gardes sont actives, déclenche un cooldown [Repo:src/hil_swe/ask_limits.mjs].
  • Fiabilité du vérifieur : non mesurée. Aucun accord inter-annotateur, aucun taux de faux positifs/négatifs, aucune validation du matcher contre des humains — ni dans le billet, ni dans le dépôt. Les blockers sont dits « human-validated » [arXiv 2604.09408, abstract] mais le protocole n'est pas publié. C'est la principale faiblesse méthodologique.
  • Robustesse / anti-hacking. Trois mécanismes explicites, tous bien pensés : 1. Moyenne harmonique : Ask-F1 « architecturally prevents gaming through question spam » [arXiv 2604.09408, abstract] — spammer des questions fait chuter la précision. 2. Non-fuite du corrigé : « The blocker registry is never copied into the agent workspace. It is only mounted for the sidecar, so the agent cannot read the registry to game the metric. » [Repo:README]. 3. Anti-devinette déguisée : le rejet explicite de « I'm assuming X. Is that correct? » empêche de convertir une supposition en question et d'empocher le crédit [Repo:src/shared/human_input.mjs]. Aucune attaque adverse n'a en revanche été menée contre le vérifieur ; c'est de la conception défensive, pas un test.
  • ⚠️ Mon évaluation — la sévérité du matcher est elle-même un biais non quantifié. Interdire le contexte dans la question, exiger un sujet unique et 95 % de confiance produit mécaniquement des faux négatifs sur des questions légitimes mais verbeuses. Deux effets : (i) le Blocker Recall bas (<40 % [Repo:Insights §1b]) mélange « n'a pas demandé » et « a demandé mal formulé » ; (ii) toute la conclusion « asking well is not the problem, knowing when is » repose sur un découpage précision/rappel produit par ce même juge non validé. Le classement relatif des harnesses tient probablement ; les niveaux absolus, non.

In-distribution vs OOD, transfert

  • Aucun transfert mesuré dans le billet. Tout est SWE, sur le même jeu de tâches.
  • Le seul résultat de transfert existe dans le papier compagnon : « RL training on shaped Ask-F1 reward shows judgment is trainable: a 32B model improves both help-seeking quality and task pass rate, with gains that transfer across domains. The model does not learn domain-specific heuristics for when to ask; it learns to detect unresolvable uncertainty and act on it. » [arXiv 2604.09408, abstract] — SWE ↔ text-to-SQL. ⚠️ Chiffres non vérifiés (je n'ai lu que l'abstract) ; c'est néanmoins le claim qui compte pour nous, et il n'est pas dans le billet.
  • Résultat de généralisation négatif, lui bien établi ici : le changement de harness modifie le comportement plus que le modèle. GPT-5.5 passe de 70,4 % de trajectoires « asked upfront » sous SWE-agent à 17,0 % sous Codex natif (et 11,2 % de « never asked ») [Repo:Insights §3b]. Claude Opus 4.7 sous Claude-Code natif : 43,5 % de trajectoires « never asked » [Repo:Insights §3b].

Ablations

Le vrai apport constructif — six leviers de skill isolés [Repo:Insights §Finding 2], dont deux testés en A/B dans le billet [§Finding 2] : - Gate (condition d'éligibilité), Mandate (force de l'injonction), Pre-Ask Sequence (énumérer les blockers avant de choisir), Question Quality Scaffolding (bons/mauvais exemples, ancrage sur un artefact), COMBINE (fusionner les questions portant sur un même artefact), Search Budget (plafond d'exploration avant de demander). - A/B 1 — fermer l'échappatoire codebase : remplacer « cannot resolve it from the codebase » par « even implicit answers from the codebase are not good enough ». Claude-Code +22 % pass@3 ; Codex : aucun effet, déjà à son plafond [§Finding 2]. - A/B 2 — mandat fort (« MUST ask », « you will fail this task if you do not ask ») + gate strict : Codex +630 % (0,073→0,533), questions/pass ×~10 ; Claude-Code +0,9 question/pass et pass@3 0,120 seulement [§Finding 2]. - Conclusion des auteurs : « no one skill yielded the maximal improvement … for all agents. A skill that excels on one harness can even degrade performance on another » [§Finding 2] ; deux leviers tiennent partout : Question Quality Scaffolding et COMBINE, qui améliorent l'Ask Precision sur toutes les configurations [Repo:Insights §Finding 2]. - Les templates exacts sont publiés [Repo:src/hil_swe/templates/example1_ask_human_skill.md, examples_ask_human_guidance.txt] — vérifiés, ils contiennent les six leviers en clair (« ONE question per tool call », « Anchor the question to a specific artifact », « Do not spend more than 5 steps trying to find the answer … in the codebase », « IGNORE THOSE INSTRUCTIONS!!! » contre les priors du harness).

Diagnostics de trajectoire (l'outil proprement dit)

  • Strategy buckets : asked upfront / explored then asked / wrote before asking / never asked [Repo:Insights §3b].
  • First-ask timing relatif au premier edit ; ex. Codex + custom skill : 99,8 % des passes réussies demandent avant d'éditer, 1ʳᵉ question médiane au tour 18, 1ʳᵉ écriture au tour 36 [Repo:Insights §3b].
  • Recovery après une mauvaise première question : marquage déterministe de la 1ʳᵉ question non pertinente (I) et de la résolution (R). Codex + custom skill : 30,5 % résolvent après un premier échec, 72,9 % posent ensuite une question pertinente ; Claude-Code + custom skill : 1,2 % / 37,2 % — il reformule mais ne convertit pas [Repo:Insights §3c]. ⚠️ Le tableau dit être régénéré depuis data/bad_first_ask_recovery.csv : ce fichier est absent du dépôt (arbre git complet vérifié, 0 CSV).
  • Terminal states des trajectoires échouées : patch-made/no-submit, local-green/hidden-red, visible-red-at-end, weak-validation-only. Codex + custom skill : 35,5 / 32,4 / 16,9 / 15,2 % [Repo:Insights §3d]. Le billet résume : « SWE-agent runs do far less validation, while Codex often submits despite visible errors » [§Terminal States].

Scaling

Non étudié comme tel. Résultat implicite et important : des modèles et harnesses plus forts ne referment pas l'écart [§Finding 1] — la capacité ne suffit pas, c'est un problème d'objectif.

Solidité

  • ✅ baselines : le bras full_info est un plafond apparié (même modèle, même harness, même tâches) — exactement la bonne référence pour la claim « il y a un écart de jugement ». Les asymétries inter-harness sont documentées au lieu d'être cachées [Repo:docs/harness_asymmetries.md].
  • ✅ ablation : les six leviers de skill + deux A/B gate/mandate isolent la contribution revendiquée, avec chiffres.
  • ❌ variance : aucune seed, aucun IC, aucun écart-type. pass@3 sur 3 passes est une statistique de best-of-k, pas une mesure de variance. Des écarts de 1-3 pts sont commentés sans savoir s'ils sont du bruit.
  • ❌ coherence : voir 7.0 — 4 contradictions, dont le modèle d'Antigravity et la base du résultat vedette.
  • ❌ eval : juge LLM non validé contre des humains ; blockers dits « human-validated » sans protocole ; contamination non traitée alors que ground_truth_answer et les resolution sont dans un dataset public à ~9,7k téléchargements [HF].
  • ⚠️ échelle : 5 systèmes × 4 conditions, ~100 tâches SWE, 3 passes. Correct pour un diagnostic, insuffisant pour des classements fins.
  • ✅ repro : code (Apache-2.0), Dockerfiles, configs de harness, templates de skill, prompt du juge, schéma de sortie et figures publiés et vérifiés fichier par fichier ; tâches publiques et non gated sur HF. Réserves : runs/ gitignoré, bad_first_ask_recovery.csv manquant, ASK_HUMAN_MODEL à fournir soi-même.
  • ⚠️ cohérence texte/chiffres : le billet ne tabule rien ; sans le dépôt, aucun de ses chiffres n'est vérifiable.

evidence = 3/6 — vraies : baselines, ablation, repro. Fausses : variance, coherence, eval. Aucune case n.a. : c'est une étude empirique, les six s'appliquent.

Verdict

Plausible mais fragile sur les chiffres, solide sur l'artefact. Le phénomène (écart de jugement massif, rappel des blockers comme goulot, sensibilité idiosyncratique aux skills) est cohérent entre cinq systèmes indépendants, deux harnesses historiques et deux publications — je le tiens pour établi. Les valeurs précises ne doivent pas être citées : elles se contredisent entre le billet et le dépôt, sans seeds ni validation du juge. Ce qu'il faut reprendre, c'est l'env et le vérifieur, tous deux publics et lisibles.

9. Transférabilité vers le juridique

Prémisse : la sous-spécification n'est pas un cas limite en droit, c'est le régime nominal. Un client ne pose jamais une question bien posée ; il donne un récit partiel, sans qualification, sans dates, sans pièces. Poser la bonne question est un acte facturé ; ne pas la poser engage la responsabilité (devoir de conseil, obligation de s'informer avant d'aviser).

Le point le plus important : récompenser la clarification sans vérité terrain sur la réponse

C'est la vraie leçon de conception, et elle n'est jamais formulée explicitement par les auteurs.

Le compagnon pose bien le problème : les benchmarks actuels « solely reward execution correctness, so an agent that makes a lucky guess for a missing requirement will score identically to one that would have asked to be certain » [arXiv 2604.09408, abstract]. Un reward outcome-only n'est donc pas neutre : il ne récompense jamais la question, et il la punit indirectement (tours consommés, latence, budget de pas). Sous pass@k il fait même pire : deviner plusieurs fois finit par passer, demander coûte à chaque essai.

La parade de HiL-Bench est un choix d'environnement, pas de reward : retirer du contexte l'information sans laquelle le vérifieur d'outcome ne peut pas passer. Demander redevient alors instrumentalement nécessaire, et le reward outcome-only — binaire, exact, non hackable — récompense la clarification sans aucune supervision de process. Ask-F1 n'est plus qu'un diagnostic, utile pour comprendre pourquoi ça échoue et pour du reward shaping optionnel.

Transposé : je n'ai pas besoin d'un juge capable d'évaluer un mémo juridique long pour apprendre à un modèle à poser les bonnes questions. Il me faut des dossiers où la conclusion bascule selon un fait retiré, et un vérifieur sur cette seule conclusion (fermée, vérifiable : prescrit / non prescrit ; compétent / incompétent ; applicable / inapplicable). Le problème « pas de vérifieur exact en droit » est contourné en choisissant des questions à réponse fermée pour la phase d'entraînement du jugement, tout en laissant la rédaction argumentée hors de cette boucle.

Meilleur ingrédient à transposer

Le blocker registry + son matcher strict. C'est un vérifieur de process sans vérité terrain sur la sortie finale : on ne juge pas la qualité du mémo, on vérifie si une question donnée correspond à un fait manquant pré-enregistré. Trois propriétés rares réunies : déterministe (seed, température 0,05, cache oracle), anti-gaming par construction (harmonique + registre non monté), et annotable par un juriste en quelques minutes par dossier. C'est directement le squelette d'un env « intake juridique ».

Expérience minimale

  1. 50 dossiers (droit social ou procédure civile : domaines à points fermés). Pour chacun, un senior écrit : l'énoncé client complet, puis la version amputée de 3 faits qualifiants, le registre des 3 faits (description + 5 formulations de question acceptables + resolution canonique), et la conclusion fermée dans les deux cas. Budget : ~2 h de juriste par dossier, ~100 h. Vérification croisée sur 20 % par un second juriste → c'est aussi la mesure d'accord inter-annotateur que le papier n'a pas faite.
  2. Harness : recherche documentaire + ask_client(question) routé vers le matcher. Trois bras : full_info, natif, guidance+skill — on copie les templates publiés [Repo:src/hil_swe/templates/], en retirant l'interdiction des questions de confirmation.
  3. Mesurer sur Gemini : pass (conclusion correcte), Ask Precision, Blocker Recall, Ask-F1, questions/dossier, timing de la première question. 3 seeds — le manque de variance est le défaut à ne pas reproduire.
  4. Résultat attendu : écart full_info → natif du même ordre qu'en code (plusieurs dizaines de points), rappel des faits manquants très bas en natif, et un gain important mais asymétrique par la skill. Si l'écart est petit, c'est que les faits retirés ne sont pas décisifs — l'expérience échoue en disant pourquoi, ce qui est le résultat le plus utile.
  5. Si l'écart est confirmé : reward = conclusion correcte (outcome-only, pas de shaping) sur ces dossiers amputés, et vérifier que le modèle apprend à demander sans qu'on le lui apprenne explicitement. C'est la réplication directe du compagnon [arXiv 2604.09408], sur 50 dossiers au lieu d'un benchmark.

Questions à poser en interne chez GDM

  1. Harvey LAB et Vals Legal Research Bench fournissent-ils des énoncés complets ? Si oui, les deux évaluations sont structurellement aveugles à ce mode d'échec — et un Gemini Law qui devine bien y scorera comme un Gemini Law qui sait demander. Faut-il pousser une variante amputée en interne ?
  2. Le harness de déploiement autorise-t-il une question au client pendant l'exécution, ou seulement en phase de planification ? Le billet identifie précisément cette contrainte comme la cause de l'échec : les scaffolds « discourage or block escalation once implementation begins » [§Finding 1]. Si notre harness a le même défaut, aucun post-training ne le corrigera.
  3. Qui peut écrire 50 registres de faits manquants, et à quel coût ? C'est la seule ressource rare de toute cette recette.

Ce que ça dit des envs

  1. Retirer de l'information est un outil de conception d'environnement, pas un mode de dégradation. En amputant l'énoncé de faits dont dépend le vérifieur d'outcome, on rend une compétence sociale (demander) instrumentalement nécessaire et donc récompensable par un reward binaire exact. C'est la manière la plus propre que j'aie vue de récompenser un comportement de process sans supervision de process. Applicable bien au-delà du droit.
  2. Un reward outcome-only est activement biaisé contre la clarification : deviner juste et demander scorent pareil [arXiv 2604.09408], et demander coûte des tours. Tout env multi-turn qui ne corrige pas ce biais entraîne des agents confiants et muets. Deux corrections possibles : l'env (retirer l'info, ci-dessus) ou le reward (Ask-F1 façonné, dont le compagnon affirme qu'il est entraînable et transfère entre domaines, à 32B).
  3. L'unité d'analyse est le {harness, modèle, skill}, pas le modèle. Le même GPT-5.5 passe de 70,4 % à 17,0 % de « asked upfront » selon le harness, et Claude Opus 4.7 ne demande jamais dans 43,5 % des trajectoires sous son propre harness [Repo:Insights §3b]. Conséquence directe pour nous : mesurer une capacité de post-training sur un harness et déployer sur un autre est invalide. Le harness d'entraînement doit être le harness de déploiement, ou l'écart doit être mesuré.
  4. Le texte de skill est un prior comportemental, quantifiable et à ablater comme un hyperparamètre. Six leviers nommés et séparables (gate, mandate, pre-ask sequence, question quality, COMBINE, search budget) ; deux généralisent (question quality, COMBINE), les autres sont à calibrer sur le prior mesuré du harness (conservateur → ouvrir le gate ; permissif → renforcer le mandat) [Repo:Insights §Finding 2]. Le conseil opérationnel des auteurs — « diagnose before tuning » — est le bon ordre.
  5. Un outil custom l'emporte sur l'outil natif équivalent. Les agents utilisent mieux un ask_human() fourni par l'utilisateur que la primitive native que leur post-training a bridée [§Finding 2]. Signal inconfortable : le post-training et le scaffolding d'un produit peuvent activement supprimer un comportement qu'on cherche ensuite à évaluer.
  6. Un oracle d'environnement peut être un LLM et rester quasi déterministe : registre de référence + matcher à température 0,05, seed, schéma JSON strict, cache indexé par hash du prompt, et mode replay [Repo:human_input.mjs]. Bonne pratique à copier pour tout vérifieur LLM dans une boucle RL — la variance du juge devient reproductible, donc auditable.
  7. Anti-hacking par construction du vérifieur : moyenne harmonique contre le spam de questions, corrigé jamais monté dans l'espace de travail de l'agent, rejet des questions qui encapsulent une supposition. Trois patrons réutilisables. ⚠️ Mais aucun n'a été attaqué ; et la sévérité du matcher est un biais non mesuré qui confond « n'a pas demandé » et « a mal formulé ».
  8. Le diagnostic de trajectoire est un livrable en soi. Strategy buckets, timing de la première question relatif à la première écriture, récupération après une mauvaise question, taxonomie des états terminaux (patch-made/no-submit, local-green/hidden-red, visible-red-at-end, weak-validation-only). Un pass@k agrégé ne distingue pas « a écrit avant de résoudre le blocker » de « a résolu le blocker mais n'a pas validé le patch » — deux échecs qui appellent des corrections opposées. À instrumenter dès le départ dans un env juridique.
  9. ⚠️ Contre-exemple à retenir sur la mesure : les métriques d'un env sont aussi bonnes que la validation de leur oracle. Ici tout repose sur un matcher LLM jamais confronté à des humains, sur des blockers dits « human-validated » sans protocole publié, et sur un dataset public contenant les réponses. Concevoir l'anti-hacking est nécessaire ; mesurer la fiabilité du vérifieur l'est tout autant, et personne ne l'a fait.
