0. En une phrase

TL;DR : à tool surface strictement identique (le CLI est auto-généré depuis les schémas MCP), l'interface MCP vs CLI change les performances d'un agent de manière conditionnelle — elle aide les modèles faibles sur les tâches data-heavy, nuit sur les tâches ciblées, et l'effet s'effondre sur les modèles frontier, où il ne reste qu'un écart de coût et de latence.

Claim principal, formulé : sur 50 tâches agentiques long-horizon réparties sur 2 environnements d'entreprise, avec ≥4 runs par tâche et par condition, (a) Opus 4.6 passe de ~8,5 % à ~17,7 % de task success en passant de MCP à CLI sur l'environnement data-heavy, mais l'écart s'inverse sur l'environnement léger (~7,3 % CLI → ~11,8 % MCP) ; (b) Opus 4.8 et GPT-5.5 « perform similarly » sur les 4 conditions d'interface ; (c) le mécanisme est la réduction des erreurs de process (tool selection, query construction), que les modèles forts ne commettent plus ; (d) exposer les deux interfaces ne produit pas de routing intelligent — le modèle retombe sur MCP [TL;DR + § Less Capable Models… + § More Capable Models… + § Why the Interface Gap Shrinks + § What This Means in Practice].

⚠️ Aucun RL, aucun entraînement : c'est une étude d'évaluation du harness, pas d'un environnement d'entraînement. Son intérêt pour la revue est l'axe « harness comme variable de design », pas « env RL ».

1. Tâches & data

  • Origine des tâches : construites par les auteurs — « We built a total of 50 long-horizon agentic tasks across two realistic, enterprise-style environments » [§ Experimental Setup]. Humaines ou générées par modèle : non précisé. Qui les a écrites, avec quel profil : non précisé.
  • Pipeline de construction : non précisé (aucune description sources → génération → filtrage → vérification). Seules les propriétés cibles sont données : réussir une tâche demande typiquement 50 à 100 tool calls, du multi-source retrieval, du suivi d'état intermédiaire, du raisonnement long-horizon et de la synthèse, et il faut produire le bon état final de l'environnement, pas seulement un texte plausible [§ Experimental Setup]. ⚠️ Ce dernier point est le choix de design le plus important du billet et il n'est pas détaillé.
  • Volume : 50 tâches au total. Répartition entre Env. 1 et Env. 2 : non précisée (⚠️ gênant, puisque tous les résultats clés sont par environnement).
  • Env. 1 — « lighter » : 8 serveurs, 113 outils, ~2 000 artefacts. Tâches = lookups précis et updates ciblés à travers plusieurs applications.
  • Env. 2 — « high-cardinality and data-heavy » : 8 serveurs, 140 outils, > 30 000 artefacts. Tâches = retrieval large, inspection répétée, collecte de preuves sur de nombreux enregistrements. [§ Experimental Setup]
  • Distribution de difficulté : « intentionally hard for current frontier agents » [§ Experimental Setup]. Pas de stratification, pas d'histogramme. Confirmé indirectement par les taux de réussite : 7–18 % chez Opus 4.6, ≈ 0 % chez GPT-5.4 reasoning-off.
  • Filtrage (pass@k du modèle de base, seuils) : non précisé. Rien n'indique que les tâches aient été filtrées sur la difficulté mesurée.
  • Curriculum : sans objet (pas d'entraînement).
  • Contamination / séparation train-test : non précisé et non discuté. ⚠️ Environnements propriétaires non publiés — le risque de contamination est faible par construction mais n'est ni argumenté ni testé.
  • Données SFT/IFT : sans objet (pas d'entraînement).
  • Coût humain : chaque tâche est livrée avec 11 à 49 critères de rubrique créés par des humains, médiane 24 [§ Experimental Setup] → ordre de grandeur ~1 200 critères humains pour 50 tâches (⚠️ dérivé par moi : 50 × 24). Heures d'annotation, profil et nombre des annotateurs, protocole de double annotation : non précisés.

2. Environnement / harness

C'est le cœur du billet, et le seul endroit où il est vraiment informatif pour nous.

  • Le contrôle central : « the CLI command is generated from the MCP tool schemas. Every MCP tool has a corresponding CLI command with the same underlying backend capability from the server. Therefore, the agent is not getting a better tool in one form factor than another » [§ Experimental Setup]. C'est le point qui distingue ce billet des comparaisons antérieures, où le terminal agent opérait sur une surface d'outils différente (couverture API, doc, composition programmatique différentes) [§ Motivation].
  • Observation :
  • en MCP, l'agent voit « a structured MCP tool with a tool name, description, and parameter schema » ;
  • en CLI, il voit « a command-line interface », exposée de façon réaliste : « a lightweight skill pointing to the binary and its --help for discovery, rather than a full embedded command schema » [§ Experimental Setup]. ⚠️ Asymétrie assumée et non ablatée : côté MCP, le schéma complet est dans le contexte ; côté CLI, il faut le découvrir via --help. Les auteurs le reconnaissent explicitement — « Part of that extra length is command discovery, which is a direct consequence of how we expose CLI to the model… Follow-up experiments with pre-documented CLI commands, even though less realistic, would help isolate the interface effect » [§ CLI Runs Longer…]. Donc l'« effet d'interface » mesuré = effet de protocole + effet de mode de découverte. C'est le principal confondant du billet.
  • Espace d'actions / outils : 113 outils (Env. 1) et 140 outils (Env. 2), répartis sur 8 serveurs chacun, « to inspect or modify the environment » [§ Experimental Setup]. La liste et les signatures des outils ne sont pas fournies — aucun nom d'outil, aucun schéma, aucun exemple de commande. ⚠️ Pour un billet dont toute la thèse porte sur la forme de la tool surface, c'est l'omission la plus coûteuse.
  • Les 4 conditions d'interface [§ Experimental Setup] : | Condition | Définition | |---|---| | MCP-only | l'agent ne voit que les outils MCP | | CLI-only | l'agent ne voit que les commandes CLI | | Both | les deux interfaces exposent les mêmes opérations backend ; l'agent choisit | | Hybrid | routage imposé par le concepteur : search/list larges → CLI ; reads, writes et opérations état-modifiantes ciblées → MCP |
  • Single vs multi-turn : multi-turn long-horizon. Horizon typique observé (Tab. coûts) : 16,0 turns/run (Opus 4.8 MCP) à 45,2 (GPT-5.5 CLI). Horizon maximal autorisé, budget de turns, budget de tokens : non précisés. Le billet donne aussi l'ordre de grandeur cible en tool calls (50–100) [§ Experimental Setup], qui ne coïncide pas avec les turns rapportés (plusieurs tool calls par turn, vraisemblablement — ⚠️ non explicité).
  • Gestion du contexte long : pas de description directe, mais un élément essentiel sort de l'analyse de coût — le harness, pas l'interface, décide du sort des gros outputs : « We ran Opus with the Claude Code harness, which spills large MCP outputs to files » vs « We ran GPT-5.5 with the OpenAI Agents SDK, which re-sends large MCP outputs inline across calls » [§ CLI Runs Longer…]. Conséquence directe : l'ordre des coûts MCP vs CLI s'inverse selon le harness, à interface identique.
  • Exécution : serveurs backend d'entreprise simulés (« thousands of artifacts and server entities designed to mimic a different type of real-world business ») [§ Experimental Setup]. Sandbox, conteneurisation, déterminisme, procédure de reset entre runs, timeouts : tous non précisés. ⚠️ Or les tâches sont state-changing (« producing the correct final state ») et il y a ≥4 runs par tâche : un reset propre est indispensable, et rien ne dit comment il est fait.
  • Gestion des erreurs d'outils / sorties mal formées : pas de mécanique décrite, mais une observation forte — « Many CLI errors were recoverable: GPT-5.5 made more raw command errors than Opus and still finished stronger in pure CLI » et « Raw tool-error counts are not a good proxy for agent quality in long-horizon tasks » [§ What This Means in Practice]. Aucun chiffre associé.
  • Exemple de trajectoire : aucun dans le billet. Aucun prompt, aucun transcript, aucun extrait.

3. Reward / vérifieur

Pas de reward (pas de RL) : c'est un vérifieur d'évaluation. Structure, néanmoins directement pertinente pour un env juridique.

  • Type : rubrique humaine notée par un LLM judge. « Each of the 50 tasks comes with 11 to 49 (median 24) human-created rubric criteria. The final trajectory is evaluated against those criteria using an LLM judge » [§ Experimental Setup].
  • Granularité : hybride, à deux niveaux exploités séparément —
  • binaire au niveau tâche (« task success », « task pass rate », « solved task ») ;
  • crédit partiel : « percentage of rubric criteria that were passed », utilisé explicitement comme métrique de secours quand le pass binaire sature à 0 : « With reasoning off, task success is close to 0, so the binary task-level pass metric is no longer a reliable differentiator, therefore we look at the percentage of rubric criteria that were passed for each task instead » [§ Less Capable Models…]. ⚠️ Le meilleur enseignement méthodologique du billet pour nous : sur des tâches long-horizon difficiles, le succès binaire est un différenciateur mort ; la rubrique à crédit partiel reste informative. Exactement la situation d'un env juridique.
  • Règle d'agrégation critères → succès de tâche (tous les critères ? un seuil ? pondération ?) : non précisée. ⚠️ Omission sérieuse : tous les chiffres de « task success » en dépendent.
  • Le juge évalue la trajectoire finale (« the final trajectory »), pas seulement la réponse — donc process autant qu'outcome, mais le découpage exact n'est pas donné.
  • Taxonomie d'erreurs superposée : chaque critère de rubrique échoué est étiqueté en outcome / tool-selection / query-construction (tool parameter) / hallucination [§ Why the Interface Gap Shrinks]. Par qui ou par quoi l'étiquetage est fait (humain ? LLM ?) : non précisé. ⚠️ C'est pourtant la brique qui porte toute l'explication causale du billet.
  • Termes additionnels (format, longueur, pénalités, bonus) : aucun — sans objet hors RL.
  • Fiabilité du vérifieur : non mesurée. Aucun accord juge-humain, aucun taux de faux positifs/négatifs, aucune double annotation, pas même l'identité du modèle juge. ⚠️ C'est la faiblesse décisive du billet : tous les écarts revendiqués (y compris le « 8,5 % → 17,7 % ») transitent par un juge non validé.
  • Si juge LLM : modèle non précisé, prompt non fourni, rubriques non fournies (ni exemple, ni catégorie, ni extrait) — aucune annexe, format billet de blog.
  • Robustesse / anti-hacking : non testée, non discutée. Aucune mention de gaming de la rubrique. ⚠️ Risque réel et non traité : une rubrique à 24 critères notée par LLM sur la trajectoire est exactement le type de vérifieur sur lequel un modèle apprend à « cocher les cases » — ici sans conséquence (pas d'entraînement), mais rédhibitoire si on réutilisait ce vérifieur comme reward.

Chiffres clés

Tableau des erreurs par critère de rubrique échoué (GPT-5.4) [§ Why the Interface Gap Shrinks] :

Outcome 40 % 30 % 20 % 22 %

Query Construction / Tool Parameter 36 % 23 % 16 % 10 %
Hallucination 1 % 1 % 1 % 1 %

Lecture : le CLI n'aide que là où le modèle faisait des erreurs de process. Une fois le reasoning activé, tool-selection et query-construction s'effondrent côté MCP (20→7, 36→16) et l'avantage CLI se réduit à la query construction (16 → 10). Le résidu outcome (20–22 %) est insensible à l'interface : c'est de la couverture et de la planification. Hallucination invariante à 1 % partout — ⚠️ suspicieusement plat et stable sur 4 conditions ; méthode d'étiquetage non précisée.

Le confondant modèle × harness n'est jamais cassé : Opus n'est jamais testé sous OpenAI Agents SDK, ni GPT sous Claude Code.

Par domaine / par type de tâche — le point qui nous intéresse

C'est le résultat le plus solide du billet, et il ne porte pas sur des domaines métier mais sur un profil d'accès à l'information :

  • Env. 2 (data-heavy, retrieval large, > 30 000 artefacts) → CLI gagne nettement chez le modèle faible (8,5 → 17,7 %). Explication avancée par les auteurs : « CLI encourages the model to work more iteratively by trying scoped commands, inspecting outputs, and refining the search over multiple steps » [§ Less Capable Models…].
  • Env. 1 (léger, lookups précis et updates ciblés, ~2 000 artefacts) → MCP gagne (l'écart s'inverse, 7,3 vs 11,8 %). « MCP remained the better starting point for precise reads and writes » [§ What This Means in Practice].
  • Confirmation sur un second modèle faible : GPT-5.4 reasoning-off, l'avantage CLI est plus fort sur Env. 2 (+14 %) que global (+9 %) [§ Less Capable Models…].

La variable discriminante est donc « exploration/retrieval large » vs « read/write ciblé », pas le sujet des tâches. ⚠️ Aucun des deux environnements n'est du code ni du juridique ; l'extrapolation vers un domaine est à ma charge, pas à celle des auteurs. Avec 2 environnements, 1 modèle faible par famille et aucune dispersion rapportée, la généralité de cette inversion reste à établir.

In-distribution vs OOD / transfert

Aucun transfert mesuré au sens RL (pas d'entraînement). Le seul axe de généralisation testé est entre les deux environnements, et il montre une inversion de signe — soit le contraire d'un effet robuste. Généralisation à d'autres harness : explicitement non testée [§ CLI Runs Longer…].

Ablations

  • Condition Both vs Hybrid : la plus informative. Donner les deux interfaces ne produit pas de routing ; le modèle « almost always fell back to MCP and barely touched the CLI ». Le routing imposé (Hybrid) « was the most reliable configuration for a handful of models in our runs » [§ What This Means in Practice], et pour GPT-5.4 reasoning-on, Both est « significantly worse than deliberate hybrid routing » [§ More Capable Models…]. ⚠️ « significantly » sans test statistique ni chiffre.
  • Reasoning off/on (GPT-5.4) : isole proprement l'axe capability à modèle et interface constants, et c'est ce qui porte l'explication mécaniste (tableau d'erreurs). ✅ La meilleure ablation du billet.
  • Ablation manquante et reconnue par les auteurs : CLI pré-documenté vs CLI découvert par --help. Tant qu'elle n'est pas faite, « effet d'interface » et « effet de découverte » restent confondus [§ CLI Runs Longer…].
  • Ablation manquante non reconnue : harness × modèle (voir ci-dessus).

Scaling

Pas de scaling au sens taille de modèle/compute/nb de tâches. L'axe « capability » est opérationnalisé de deux façons : génération de modèle (4.6→4.8, 5.4→5.5) et reasoning effort (off/on) [§ Experimental Setup]. ⚠️ Confondre « génération suivante » et « reasoning effort » sur un seul axe « less/more capable » est commode mais discutable : ce sont deux interventions de nature différente.

Solidité

  • Baselines fortes et à jour ✅ — 4 modèles frontier récents, 4 conditions d'interface, 2 environnements ; comparaison appariée par construction (mêmes tâches, mêmes opérations backend, CLI généré depuis les schémas MCP).
  • Ablations qui isolent la contribution ⚠️ — l'ablation reasoning off/on est propre, mais le confondant CLI-discovery (reconnu) et le confondant harness×modèle (non reconnu) empêchent d'isoler l'effet d'interface pur.
  • Variance / seeds ❌ — ≥4 runs par tâche et par condition, mais aucun intervalle de confiance, aucun écart-type, aucun test ; les écarts clés sont donnés en « roughly », sur des sous-ensembles de 50 tâches, à des taux de 7–18 %. Un écart 8,5 → 17,7 % sur une fraction de 50 tâches est de l'ordre de quelques tâches.
  • Fiabilité de l'éval ❌ — LLM judge non identifié, non validé contre des humains, prompt et rubriques non publiés, règle d'agrégation critères → tâche non précisée, étiqueteur de la taxonomie d'erreurs non précisé.
  • Échelle ⚠️ — 50 tâches, 2 environnements, 4 modèles, 4 conditions : correct pour un billet, insuffisant pour trancher une inversion de signe par environnement.
  • Reproductibilité ❌ — ni environnements, ni tâches, ni rubriques, ni prompts, ni code, ni traces. Vérifié : aucun lien GitHub/HuggingFace sur la page ; aucun preprint arXiv correspondant.
  • Cohérence texte ↔ chiffres ⚠️ — les deux tableaux sont cohérents avec le texte, mais le claim central sur les modèles frontier n'est jamais chiffré, et les taux de réussite implicites du tableau de coûts (14–16,5 %) sont en tension avec le récit « les modèles plus capables aplatissent l'écart » (voir 7.0).

Décompte evidence (3/6) : 1. baselines ✅ — comparaison appariée sur mêmes tâches / mêmes opérations backend / mêmes modèles ; c'est exactement l'apport du design. 2. ablation ✅ — reasoning off/on à modèle et interface constants + condition Hybrid vs Both isolent respectivement l'axe capability et l'axe routing. (Caveat CLI-discovery noté.) 3. variance ❌ — ≥4 runs/tâche mais aucune dispersion, aucun IC, aucun test. 4. coherence ✅ — de justesse : tout ce qui est tabulé concorde avec le texte ; les problèmes relevés sont des absences (claim frontier non chiffré) et une sur-généralisation du TL;DR sur la condition Both, pas des contradictions numériques. 5. eval ❌ — juge non identifié et non validé, rubriques et prompt non publiés. 6. repro ❌ — rien de publié ; vérifié par HTTP (page source sans lien code ; API arXiv sans preprint correspondant).

Verdict

Plausible mais fragile. Le design expérimental est le bon — c'est la première comparaison MCP/CLI qui neutralise vraiment la tool surface, et cela seul justifie la lecture. Mais les conclusions reposent sur un juge non validé, sans variance, sur 50 tâches, avec le claim principal (frontier ⇒ insensibilité à l'interface) jamais chiffré et mis en tension par les taux de réussite implicites que j'ai reconstruits. À traiter comme une hypothèse de design bien posée, pas comme un résultat acquis. Le seul résultat que je tiendrais pour robuste est directionnel : le CLI aide quand le goulot est l'exploration d'un grand espace de données et que le modèle commet des erreurs de process ; il n'aide pas quand le goulot est le raisonnement. Le tableau d'erreurs est cohérent avec cela sur les 4 colonnes.

Quelle interface pour un agent juridique ? Sur la seule base de ce billet, et en assumant l'extrapolation : la recherche juridique est structurellement une tâche Env. 2 (corpus à très haute cardinalité, retrieval large, inspection répétée, collecte de preuves sur de nombreux documents) → cela plaide pour le CLI sur les opérations de recherche et de listing. Mais le livrable, la vérification de citation et toute écriture sont des opérations ciblées, typées, auditables et permissionnées → MCP. Donc : configuration Hybrid, avec le split encodé par nous, jamais laissé au modèle. Et sur Gemini (modèle frontier), le billet prédit que l'accuracy dépendra peu de ce choix, et que le vrai critère sera le coût par tâche résolue sur notre propre stack — qui dépend surtout de la façon dont notre harness traite les gros outputs (spill-to-file vs re-send inline), un point où un corpus juridique produit des retours documentaires très volumineux.

Ce que ce billet ne permet PAS de conclure : (a) rien sur le juridique — aucune tâche juridique testée ; (b) rien sur le code non plus ; (c) rien sur l'interaction interface × RL — si on entraîne Gemini par RL dans un harness donné, la sensibilité à l'interface mesurée en zero-shot disparaît probablement, et le billet ne l'aborde pas ; (d) rien de fiable sur l'ampleur de l'effet chez les modèles frontier, puisqu'elle n'est jamais chiffrée ; (e) rien sur l'effet du nombre d'outils en contexte (113 vs 140) — les deux environnements diffèrent sur trop de dimensions à la fois pour l'isoler.

Meilleur ingrédient à transposer : la métrique de secours à crédit partiel. « Task success ≈ 0 ⇒ on bascule sur le % de critères de rubrique passés » [§ Less Capable Models…]. Sur des tâches juridiques réalistes et longues, le succès binaire saturera à zéro et ne fournira aucun gradient ; une rubrique dense (médiane 24 critères) donne un signal continu, et — c'est l'argument décisif pour nous — un signal décomposable par type d'erreur, donc directement utilisable comme reward à crédit partiel et comme diagnostic.

Expérience minimale : prendre ~30 tâches de recherche juridique long-horizon, rubrique de ~20 critères rédigée par des juristes, et évaluer Gemini en 3 conditions à backend d'outils strictement identique (outils CLI générés depuis les schémas MCP, comme ici) : MCP-only / CLI-only / Hybrid (search→CLI, read+cite-check+write→MCP), ≥4 runs par tâche. Mesurer task success et % de critères passés et $/solved task et taux d'hallucination de citation. Résultat attendu si le billet se transporte : écarts de task success faibles (Gemini est frontier), Hybrid en tête ou à égalité, écart de coût par tâche résolue significatif, et — prédiction propre au droit, non couverte par le billet — le taux d'hallucination de citation devrait être plus bas en MCP (paramètres typés, citation résolue par un outil dédié) qu'en CLI (texte libre). Si cette dernière prédiction se confirme, elle tranche en faveur du MCP pour tout ce qui touche aux citations, indépendamment de l'accuracy.

Question à poser en interne chez GDM : comment notre harness d'entraînement traite-t-il les gros retours d'outils — spill-to-file ou re-envoi inline dans le contexte ? Le billet montre que ce seul choix inverse l'ordre des coûts MCP vs CLI à interface identique [§ CLI Runs Longer…]. Si on entraîne par RL sur des rollouts contenant des retours documentaires volumineux, ce choix détermine à la fois le coût des rollouts et ce que la policy apprend à faire de ses observations — et il doit être figé avant de comparer quoi que ce soit.

Ce que ça dit des envs

  1. Le harness est une variable de design de l'environnement, pas un détail d'implémentation. À tâches, modèle et opérations backend strictement identiques, la forme d'exposition des outils change le taux de réussite d'un facteur ~2 sur un modèle faible [§ Less Capable Models…]. Corollaire pour la revue : toute comparaison d'environnements RL qui ne contrôle pas le harness compare deux choses à la fois. Ce billet est, à ma connaissance de ce dossier, le seul à faire ce contrôle explicitement (CLI généré depuis les schémas MCP).
  2. L'effet d'interface est un effet de béquille, pas de capability. Le tableau d'erreurs [§ Why the Gap Shrinks] est net : le CLI ne répare que les erreurs de process (tool selection 20→11, query construction 36→23) et ne touche pas au résidu outcome, qui relève de la planification et de la couverture. Transposé au RL : un bon harness substitue en partie à ce que le RL apprendrait de toute façon. Plus la policy est entraînée, moins le choix d'interface devrait compter — donc les gains de harness mesurés en zero-shot ne se cumulent probablement pas aux gains de RL. ⚠️ Ceci est mon extrapolation, le billet ne teste aucun entraînement.
  3. Le profil d'accès à l'information détermine l'interface, pas le domaine. Data-heavy/exploratoire ⇒ CLI ; ciblé/transactionnel ⇒ MCP. Un env RL qui mélange les deux profils devrait exposer les deux surfaces avec un split imposé, puisqu'on sait maintenant que le modèle ne route pas de lui-même : exposer Both revient en pratique à exposer MCP seul [§ What This Means…]. C'est directement actionnable pour la conception d'un env.
  4. Le succès binaire est une métrique morte sur les tâches long-horizon difficiles. Les auteurs sont contraints de basculer sur le % de critères de rubrique quand le pass rate tombe à ~0. C'est le même problème que le reward sparse en RL, et la même solution : rubrique dense à crédit partiel. Converge avec la pratique des rubriques process-level.
  5. Le coût d'un env ne se lit pas dans le nombre de turns. CLI = ×2 à ×2,6 turns mais peut être moins cher ou plus cher selon que le harness spill les gros outputs vers des fichiers ou les re-renvoie inline [§ CLI Runs Longer…]. Pour un budget de rollouts RL, la politique de gestion des gros observations domine le nombre de pas.
  6. Ce que ce billet ne fournit pas, et qu'un vrai papier d'env fournirait : aucune signature d'outil, aucune trajectoire d'exemple, aucun prompt de juge, aucune rubrique, aucune procédure de reset pour des tâches pourtant state-changing, aucune variance. ⚠️ À traiter comme une hypothèse de design bien posée et un protocole à reprendre, pas comme une source de chiffres.
