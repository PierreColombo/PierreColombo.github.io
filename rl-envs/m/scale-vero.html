0. En une phrase

TL;DR — VeRO est un outer harness qui transforme l'optimisation d'un agent (prompts, tools, control flow) en tâche de code-gen budgétée pour un coding agent : git auto-commit à chaque édition, ExperimentRunner gaté par un budget dur de B = 8 appels d'évaluation, base de traces consultable, test set bloqué au niveau outil ; 105 runs sur 5 benchmarks servent d'étude empirique [lede, §Harness, §Méthodo].

Claim principal — sur les trois benchmarks tool-use (GAIA, TAU-Bench Retail, SimpleQA), les meilleures configurations d'optimizer obtiennent « roughly 8–9% average lift over baseline », contre « almost no improvement » sur les benchmarks reasoning (GPQA, MATH) ; et l'infrastructure compte plus que le modèle : Claude Code sans les outils VeRO ne gagne que 3 % contre 8 % avec [§Findings].

⚠️ Claim secondaire, le plus intéressant pour nous : les gains ne survivent pas au changement de modèle cible — « sometimes improved … yet sometimes degraded it substantially » — et ce sont les modifications de tools/workflow, pas de prompt, qui généralisent [§Truth 2]. Or les modifications de prompt représentent > 50 % de tous les changements [§Truth 1]. Autrement dit : le mécanisme de proposition produit majoritairement le type de changement qui ne généralise pas, et le gate de rétention (in-distribution) ne le détecte pas.

1. Tâches & data

  • Origine des tâches : aucune tâche créée. Réemploi de 5 benchmarks publics — GAIA, GPQA, MATH, TAU-Bench Retail, SimpleQA [figure-tableau §Findings, §Findings]. L'« instance » d'optimisation = un couple (agent cible, benchmark).
  • Agents cibles écrits à la main (2, case study §Truth 3) :
  • Pawn : 4 tools, prompt de 25 lignes — « minimal ».
  • Knight : 6 tools, prompt de 140 lignes avec best-practice patterns — « sophisticated ». Auteur des agents : non précisé (implicitement les auteurs). Signatures des tools : non précisé.
  • Templates d'instruction au builder, écrits à la main, 4 nommés : Cookbook+Reasoning (librairie de patterns d'optimisation + workflow structuré en 4 phases), Minimal, Tool-Centric, Evidence-Based (décourage explicitement les nouveaux tools complexes, impose une expérimentation à variable unique) [§Findings, §Truth 3 figure]. Contenu intégral des templates : non précisé.
  • Pipeline de construction : sans objet — pas de génération ni de filtrage de tâches. Le seul « pipeline » est la boucle edit-execute-evaluate [§Méthodo].
  • Volume : « 105 optimization runs spanning five benchmarks » [lede]. ⚠️ Incohérent avec « five optimizer configurations … N = 3 times per task … total of 105 » (5 × 3 × 5 = 75) — voir §7.0. Nombre de samples par split, et par appel d'évaluation : non précisé — pire, le nombre de samples est choisi par le coding agent lui-même (« hand it a commit hash and a number of samples ») [§Harness], donc la granularité du signal de reward est une variable libre non contrôlée.
  • Distribution de difficulté : non précisé. Implicitement bimodale au niveau benchmark (tool-use optimisable vs reasoning non optimisable) [§Findings].
  • Filtrage par pass@k du modèle de base : aucun. Non applicable.
  • Curriculum : aucun au sens RL. Ordre implicite = trajectoire du builder sur 7 phases [figure « Code Change Type by Optimization Phase »]. Pas de rééchantillonnage.
  • Contamination et séparation train/test : split train (ou validation — voir §3) / held-out test. Deux garde-fous [§Harness, §Méthodo] : 1. DatasetViewer bloque l'accès au test set au niveau outil — « so the agent can't game its evaluation » ; 2. le test n'est évalué qu'au début (baseline) et à la fin (best commit) ; la sélection se fait sur la validation. Les auteurs qualifient explicitement l'alternative de « a subtle but important form of reward hacking to guard against ». ⚠️ Contamination des LLM sous-jacents sur GAIA/GPQA/MATH/SimpleQA : jamais discutée → non précisé. Sur des benchmarks de 2023-2024 avec des modèles de 2025-2026, c'est une lacune qui touche directement le niveau des baselines (cf. le 4.3× sur GAIA).
  • Données SFT/IFT avant RL : aucune — pas d'entraînement. Le billet propose seulement en travaux futurs d'utiliser les trajectoires VeRO comme données de fine-tuning (« RL for Trajectory Tuning ») [§Next].
  • Coût humain : écriture des 2 agents cibles, des 4 templates d'instruction, et du harness. Heures / annotateurs / experts : non précisé.

2. Environnement / harness

Architecture en trois espaces [§Harness, Fig. 1] :

Espace Contenu
Optimizer Space (Builder) le coding agent : propose des édits, inspecte les traces, navigue l'historique de versions
VeRO Harness (Infrastructure) Git Worktrees (snapshots auto-commités), Experiment Database (traces + scores granulaires), Evaluation Engine
Target Space (Subject) le code de l'agent cible sous forme de package Python ; renvoie rewards + traces
  • Observation du builder : code courant de l'agent cible ; via ExperimentViewer — « all prior evaluation results, per-sample scores, full execution traces, error logs » ; via DatasetViewer — les inputs de l'agent cible (test bloqué) ; historique git des commits [§Harness]. ⚠️ Point de design notable : les traces d'exécution sont des observations, pas du reward — le signal scalaire reste outcome-level, mais le builder a accès au process. C'est exactement la séparation qui manque dans un RLVR classique.
  • Espace d'actions / outils — outils natifs du coding agent « hooked or restricted », plus 4 outils harness [§Harness] :
  • Auto-Commit : hook, pas un appel — chaque édition du code cible auto-commite dans git. Trace complète et non contournable de ce que fait l'agent.
  • ExperimentRunner(commit_hash, n_samples) : outil d'évaluation gaté. Checkout de la version, exécution de l'agent cible, stockage des résultats, décrément du budget. « The agent cannot evaluate more times than its budget allows, the tool enforces this hard. »
  • ExperimentViewer : lecture des résultats antérieurs, scores par sample, traces, logs d'erreur.
  • DatasetViewer : inspection des inputs ; accès au test bloqué au niveau outil. (Signatures exactes au-delà de commit_hash + number of samples : non précisé dans le billet.)
  • Single/multi-turn, horizon : multi-turn, long. Unité = phase (« a cycle of modification and evaluations ») [§Truth 1] ; la figure des types de changement couvre les phases 1 à 7. Horizon dur = budget B = 8 appels d'évaluation complets [§Méthodo]. Nombre de tours LLM, longueur de contexte, troncature/résumé/mémoire : non précisé — la base d'expériences joue de facto le rôle de mémoire externe (l'état survit hors contexte).
  • Exécution : environnement isolé, checkout git de la version évaluée [§Méthodo]. Sandbox/conteneur explicite : non précisé. Déterminisme : explicitement non — c'est la prémisse du papier (« agents are stochastic programs; they mix deterministic logic with probabilistic LLM completions ») [§Problem]. Reset : rollback vers un commit antérieur (« If the new version underperforms, the optimizer can roll back ») [§Méthodo]. Timeouts : non précisé.
  • Gestion des erreurs d'outils / sorties mal formées : les « error logs » sont exposés au builder via ExperimentViewer [§Harness] ; aucune politique de retry, de pénalité ou de parsing décrite → non précisé.
  • Exemple de trajectoire : la Fig. 1 (bande orange, haut) annonce « example optimization trajectory », mais aucune trajectoire n'est transcrite en texte dans le billet → non précisé. La section « Aside: The Tricks Coding Agents Discovered » promet des exemples d'optimisations trouvées mais la figure associée est vide dans la version texte récupérée — contenu non récupérable.
  • Objectif formel [§Problem] : maximiser le score d'évaluation espéré sur un espace de programmes restreint A_r (checkpoint du modèle fixé, contraintes d'API, pas d'accès au test), l'espérance marginalisant sur la distribution de test, la stochasticité de l'évaluateur et la stochasticité de l'agent, sous contrainte n_E ≤ B. Formule exacte : figure non transcriptible.

3. Reward / vérifieur

  • Type : score d'évaluation du benchmark cible, produit par l'Evaluation Engine et stocké en base [§Harness]. Le billet ne dit jamais quel vérifieur est utilisé par benchmark → non précisé. (L'abstract arXiv:2602.22480 parle de « reference evaluation procedures » pour VeRO-Bench ; aucun détail.) ⚠️ GAIA et SimpleQA impliquent en pratique un grader modèle ou un match sur référence courte, mais le billet ne le dit pas : je ne l'affirme pas.
  • Granularité : outcome-level, mais doublement exposé — score agrégé rendu au builder par ExperimentRunner, et scores par sample + traces complètes consultables via ExperimentViewer [§Harness, §Méthodo]. Pas de process reward. Crédit partiel : dépend du benchmark, non précisé.
  • Reward de l'agent cible vs reward du builder : à distinguer. Le builder n'est pas entraîné — le « reward » n'est qu'un signal de recherche consommé dans le contexte. Aucune fonction de reward RL n'est définie.
  • Le gate de rétention (point central) [§Méthodo] :
  • chaque édit → auto-commit ;
  • le builder choisit quels commits évaluer, et sur combien de samples, dans la limite de B = 8 ;
  • « The best-performing commit across all evaluations is selected as the final output » — soit un argmax sur ≤ 8 estimations bruitées, sans test de significativité, sans ré-évaluation des top-k à plus grand n, sans hold-one-out ;
  • test évalué uniquement au début et à la fin. ⚠️ Ambiguïté de split : l'étape « Evaluate » dit que ExperimentRunner « runs the target agent on the training split », tandis que le paragraphe suivant dit « we select the best commit based on validation performance ». Les deux termes désignent apparemment le même signal. Ce n'est pas cosmétique : c'est exactement la variable qui définit le gate de rétention. Non tranché par le billet. ⚠️ Winner's curse : l'argmax sur 8 mesures bruitées surestime mécaniquement le commit retenu. Le read-out final sur le test set corrige ce biais de sélection (c'est un vrai bon choix de design), mais le test est in-distribution — même benchmark, même distribution de tâches. Il est donc aveugle au sur-apprentissage adaptatif au benchmark lui-même, et le billet le confirme indirectement : c'est le changement de modèle cible (§Truth 2), pas le test in-distribution, qui révèle la fragilité.
  • Termes additionnels (format, longueur, pénalités, bonus) : aucun. Le coût en tokens et la latence sont explicitement hors objectif aujourd'hui — « Future work should incorporate "Agentic ROI" as an explicit objective » [§Next]. Le seul terme régularisant est le budget dur B.
  • Fiabilité du vérifieur : précision, accord humain, taux de faux positifs/négatifs — non mesurés, non discutés. La « evaluator stochasticity » est reconnue dans la formalisation [§Problem] mais jamais quantifiée.
  • Si juge LLM : modèle, prompt, rubriques — non précisé, rien à recopier.
  • Robustesse / anti-hacking : une seule mesure, mais explicite et bien pensée — blocage du test set au niveau outil + évaluation du test aux seules bornes, désignée par les auteurs comme protection contre « a subtle but important form of reward hacking » [§Méthodo]. ⚠️ Le signal de validation, lui, est librement hill-climbable dans la limite du budget ; aucune attaque n'a été tentée contre le vérifieur ; aucun audit des commits retenus pour détecter des raccourcis (ex. mémorisation de réponses de la validation dans le prompt) n'est rapporté.

Le gain est-il distinguable du bruit ?

⚠️ Non démontré par le billet. - N = 3 runs par configuration et par tâche [§Findings] — seeds multiples, donc, mais aucun intervalle de confiance, aucun écart-type, aucun test de significativité n'accompagne le 8–9 %. - Le billet décrit lui-même une variance du même ordre que l'effet : templates prescriptifs → « higher peak performance but also more variance and occasional catastrophic regressions » ; Pawn → « much higher variance … a single bad modification could regress performance across multiple benchmarks simultaneously » [§Findings, §Truth 3]. - Les candle plots (§Truth 3) montrent la dispersion mais uniquement pour le case study Pawn/Knight, pas pour le résultat principal. - Le 8–9 % est une moyenne sur 3 benchmarks et sur « the best optimizer configurations » — sélection a posteriori des meilleures configs, ce qui rebiaise l'estimation vers le haut. - ⚠️ Écart d'ordres de grandeur non expliqué : +8–9 % en moyenne vs 4.3× en pic sur GAIA. Cela ne se réconcilie que si la distribution est très étalée — c'est-à-dire si le bruit domine. - Ce qui manque et qui trancherait : score baseline et final par benchmark avec écart-type sur les 3 seeds, et la distribution complète des 105 runs (combien de runs finissent sous la baseline ?). Le billet mentionne l'existence de régressions mais n'en donne jamais le taux.

In-distribution vs OOD

  • Held-out in-distribution : mesuré. Test du même benchmark, bloqué au niveau outil, évalué au début et à la fin [§Méthodo]. C'est le seul read-out non biaisé par la sélection — mais aveugle au sur-apprentissage adaptatif au benchmark, puisque train/val/test partagent la distribution de tâches.
  • OOD par changement de modèle cible : mesuré, et c'est le résultat le plus informatif [§Truth 2]. Les meilleurs commits trouvés avec GPT-4.1 mini comme modèle de l'agent cible sont rejoués sur GPT-4.1, Gemini 2.5 Flash, variantes Qwen3, sur 4 tâches (GAIA, GPQA, SimpleQA, TAU-Bench Retail), avec Codex ou Sonnet comme optimizer. Résultat : « sometimes improved … yet sometimes degraded it substantially ». Chiffres : tableau-figure, non lisibles. Structure : les améliorations par ajout de tools et changement de workflow généralisent mieux que les modifications lourdes de prompt, « sensitive to the specific model's instruction-following tendencies ».
  • OOD par transfert entre benchmarks : non mesuré systématiquement. Aucune expérience « optimiser sur A, tester sur B ». Seule trace indirecte : dans le case study, une mauvaise modification de Pawn « could regress performance across multiple benchmarks simultaneously » [§Truth 3] — donc les agents cibles sont bien évalués multi-benchmarks, mais aucun tableau de transfert n'est donné.
  • ⚠️ Conclusion pour notre revue : le billet fournit un cas concret où un held-out in-distribution valide un gain que le changement de modèle détruit. Le gate de rétention (argmax sur la validation) sélectionne préférentiellement du prompt-tuning — le type de changement qui, par le constat même des auteurs, généralise le moins. Le gate et le mécanisme de proposition sont donc corrélés dans le mauvais sens.

evidence = 4/6, evidence_manquant: [coherence, eval]. Aucune case n.a. : c'est une étude empirique complète, les 6 s'appliquent.

Verdict : plausible mais fragile. Le design du harness est le vrai apport (budget dur imposé par l'outil, auto-commit non contournable, test bloqué au niveau outil, traces comme observations) et il est publié et exécutable. Les résultats numériques, eux, sont invérifiables dans le billet, entachés d'une incohérence arithmétique, et le gain principal n'est jamais distingué du bruit. ⚠️ Les trois « uncomfortable truths » sont qualitativement plus solides que le chiffre de tête, parce qu'elles sont des constats de structure (dominance du prompt-tuning, fragilité cross-modèle, couplage headroom/risque) robustes à l'imprécision des valeurs. À répliquer sur le preprint arXiv:2602.22480 pour les chiffres.

9. Transférabilité vers le juridique

Contexte de transfert : contrairement à VeRO, notre vérifieur juridique est lui-même un modèle. Chez VeRO le grader est supposé fiable (benchmarks publics à référence) et la stochasticité de l'évaluateur n'est qu'un terme de bruit dans l'espérance [§Problem]. Dans notre cas le grader est biaisé ET bruité, et le builder peut l'optimiser directement. Toutes les conclusions doivent être relues sous cette contrainte.

Meilleur ingrédient à transposer

Le gate de rétention à deux niveaux + budget d'évaluation imposé par l'outil, et non le builder.

Justification par les preuves du billet : l'ablation la plus nette est « infrastructure > modèle » (+3 % sans outils VeRO, +8 % avec) [§Findings] — à modèle constant, c'est le contrôle de l'évaluation qui produit le gain. C'est exactement la thèse que la revue porte : le mécanisme de proposition est secondaire, le gate décide. Et VeRO fournit la version minimale correcte de ce gate : (i) budget dur non contournable, imposé par l'outil et non par le prompt ; (ii) sélection sur validation ; (iii) test touché deux fois seulement.

⚠️ Mais le billet fournit aussi la limite de ce gate, et c'est son apport le plus utile pour nous : le held-out in-distribution valide un gain qui disparaît ou s'inverse au changement de modèle cible [§Truth 2], et le type de modification qui survit (tools, workflow) est minoritaire (< 50 %) face au type qui ne survit pas (prompt, > 50 %) [§Truth 1]. Pour un env juridique dont le vérifieur est un modèle, la leçon se durcit : un held-out qui partage la distribution des tâches ET la famille du juge ne prouve rien. Il faut faire varier l'axe du juge comme VeRO a fait varier l'axe du modèle cible.

Expérience minimale

Brancher VeRO (repo MIT, tel quel) sur le harness Gemini Law avec ~200-300 tâches juridiques en split train/val/test, budget B = 8, deux templates d'instruction (Evidence-Based contraint vs Cookbook+Reasoning libre), N = 5 seeds. Trois read-outs au lieu d'un : 1. test in-distribution, juge principal — reproduit le protocole VeRO ; 2. même test, juge secondaire d'une autre famille de modèles, jamais exposé à la boucle ; 3. tâches Harvey LAB / Vals, jamais vues.

Résultat attendu, si le constat de VeRO tient en juridique : gain net sur (1), gain fortement rogné sur (2), et gain proche de zéro voire négatif sur (3) — avec un écart (1) − (2) qui mesure directement la part de reward hacking du juge. Cette quantité n'existe nulle part dans la littérature que je connais, et c'est un livrable en soi. Attendu secondaire, par analogie avec §Truth 1 : la majorité des modifications retenues seront des réécritures de prompt, et ce seront celles qui s'effondreront le plus entre (1) et (2). Coût : faible — aucun entraînement, uniquement de l'inférence budgétée.

Question à poser en interne chez GDM

Deux, liées : 1. Le harness de Gemini Law est-il versionné et scorable automatiquement (package isolable, runner d'éval appelable sur un commit) ? Sans cela, rien de VeRO n'est branchable, et c'est un prérequis d'infra qui se décide tôt. 2. Réserve-t-on un juge held-out — une famille de modèles, ou un budget d'annotation expert — qui ne soit jamais exposé à aucune boucle d'optimisation, ni harness-search ni RLVR ? C'est la seule mesure qui distinguera un vrai gain d'un gain contre le grader, et elle coûte cher : il faut la budgéter avant de lancer, pas après.
